# 週報／階段總結

## 為什麼這個 skill 存在

2026-09-19 寫第一份週報時踩了五個坑，每一個都讓報告失真：

1. **把自己接手的日子當成專案開始**。專案 09-14 起，我從 09-17 寫起，
   漏掉了整個第一階段（整條簽核流程從零做出來）
2. **拿 git log 當工作量依據**。使用者前幾天累積到一個階段才提交，
   git 在 09-15～09-17 之間是空白的，但那幾天做的是地基
3. **只寫自己做的**。專案是兩台機器平行開發，另一台的工作一開始
   只用一段帶過
4. **只寫報告編號不給連結**。表格裡寫「測試報告 07」，讀的人要自己
   去猜檔名。而檔名其實是 `07_登入與選單導覽測試報告.md`——
   報告本身就成了一道查詢題（見〈硬規則〉的連結規定）
5. **測試合計沒加過**。表格裡各列加起來是 1118，合計欄寫 1061，
   §0 也跟著寫 1061。沒有人會去驗算，錯的數字就這樣留在文件裡

這個 skill 把「先查證再寫」的順序固定下來。

---

## 硬規則

### 不可以做的

| 禁止 | 理由 |
|---|---|
| 憑對話記憶寫工作內容 | 對話只涵蓋自己這台、自己這段。會漏掉另一台與更早的階段 |
| 把 git log 當唯一時間軸 | 使用者可能累積後才提交。空白不等於沒做事 |
| 抄舊報告的測試數字 | 必須當場跑出來 |
| 寫沒驗證過的檔案路徑 | 列出的每個檔案都要 `ls` 確認存在 |
| **只寫文件編號不給連結** | 「測試報告 07」逼讀的人自己猜檔名。見下方連結規定 |
| **合計欄沒加過各列** | 這次就寫錯了（1061 vs 1118），而且錯了兩處 |

### 必須做的

- 問清楚**專案／這個階段從哪天開始**，不要假設
- 用**測試報告的日期**重建時間軸（它們是真實的完成紀錄）
- 兩台開發時，**兩條線都要寫成對等的章節**，不是一段帶過
- **每一個步驟都要列出它的文件產出，並且是可點的相對連結**
- **每一個合計數字都要手動加過各列**

## 連結規定（這次新增的重點）

### 為什麼

總結文件的讀者有兩種：想快速知道發生什麼事的、想深入某一段細節的。
第二種人需要能一路點進去，而不是拿著編號去 `ls` 找檔名。

### 三條規則

**1. 提到任何文件，一律用相對連結，不用裸編號**

不好：

```markdown
| 登入與選單導覽 | 07 | 路由守衛、四個設計器的入口 |
```

好：

```markdown
| 登入與選單導覽 | [07_登入與選單導覽測試報告](../../../測試報告/202609/07_登入與選單導覽測試報告.md) | 路由守衛、四個設計器的入口 |
```

**2. 每個開發步驟都要有「文件產出」小表**

一個步驟通常會產生四類文件，寫成一張表放在那一節的末尾：

| 類別 | 位置 | 角色 |
|---|---|---|
| 需求 | `docs/需求規劃/YYYYMM/` | 為什麼要做 |
| 實踐規劃 | `docs/實踐規劃/規劃/YYYYMM/` | 動手前怎麼打算 |
| 測試報告 | `docs/測試報告/YYYYMM/` | 做完怎麼驗證的 |
| 階段總結 | `docs/實踐規劃/總結/YYYYMM/` | 這一段的收尾 |

四類不一定都有，有哪些寫哪些。缺哪一類本身就是資訊
（例如「這一段尚未寫測試報告，紀錄在 commit `xxx` 的訊息裡」）。

**3. 文件末尾放一張「文件地圖」**

讓讀者用「我想找什麼」而非「文件叫什麼」來查：

```markdown
| 要找什麼 | 去哪 |
|---|---|
| 某個步驟怎麼驗證的 | §2、§4 各節的「測試報告」欄 |
| 怎麼操作某個功能 | §11 的「操作手冊」表 |
| 測試數字怎麼來的 | §10 的重跑指令 |
```

### 相對路徑的層數

從 `docs/實踐規劃/總結/YYYYMM/` 出發：

| 目標 | 前綴 |
|---|---|
| 同目錄的其他總結 | `./` |
| `docs/實踐規劃/規劃/YYYYMM/` | `../../規劃/YYYYMM/` |
| `docs/` 底下其他目錄 | `../../../` |
| repo 根目錄（例如 `server/`） | `../../../../` |

寫完一定要跑驗證（見〈完成前的檢查〉）。

## 執行順序

### 步驟 1：確認範圍

問使用者：這次總結涵蓋哪段時間？從哪天開始？

不要自己推斷。git 的第一個 commit、自己接手的日子、
自己記得的第一件事——三者都可能不是真正的起點。

### 步驟 2：蒐集素材（三個來源，缺一不可）

```bash
# a) commit（知道做了什麼，但不等於全部）
git log --since="<起日>" --pretty=format:"%h|%ad|%s" --date=format:'%m/%d %H:%M' --reverse

# b) 測試報告的日期（真實的完成紀錄，涵蓋 git 空白的期間）
for f in docs/測試報告/202609/*.md; do
  echo "$(grep -m1 -oE '2026-[0-9]{2}-[0-9]{2}' "$f")  $(basename "$f" .md)"
done | sort

# c) 規劃文件（知道原本要做什麼，才說得出哪些沒做）
ls docs/系統規劃/ docs/需求規劃/202609/ docs/實踐規劃/規劃/202609/

# d) 全部文件清單（連結要用的，一次撈齊）
ls docs/ && ls docs/*/ docs/*/202609/ 2>/dev/null
ls docs/操作手冊/ docs/交接手冊/
```

git 與測試報告的日期對不上時，**以測試報告為準**並在文件裡註明原因。

### 素材蒐集的兩個陷阱

**別假設檔名是連號的。** 這個專案的 `12`、`13` 實際檔名是
`B12_`、`B13_`（分叉後寫的），而 README 卻說「01～13 是共同歷史」。
一定要 `ls` 看真實檔名，不要從編號推。

**別漏掉當天稍晚的 commit。** 寫報告的當下可能還有新的提交。
寫完之後再 `git log -1` 看一次，有新的就補一節。

### 步驟 3：跑出當下的測試數字

```bash
cd server && cargo test --workspace 2>&1 | tail -2
cd web && npm test -- --run 2>&1 | grep -E "Tests "
cd web && npx playwright test --reporter=line 2>&1 | tail -3
cd python-ai && .venv/bin/python -m pytest -q 2>&1 | tail -2
cd pdfme && npx vitest run 2>&1 | tail -3
```

起點的數字從最早那份測試報告抓，不要抄中間的。

E2E 只要題數的話用 `--list`，不必真的跑完：

```bash
cd web && npx playwright test --list 2>&1 | tail -1
```

**跑完之後把各列加起來對合計。** 這一步不能省——
2026-09-19 那份就是各列 1118、合計寫 1061。

把重跑指令寫進報告的 §10，讓讀的人能自己驗。

### 步驟 4：核對規劃完成度

對每個規劃項目給出**可重跑的核對指令**，不是憑印象打勾：

```bash
# 例：某功能是否實作
grep -rln "<關鍵字>" --include="*.rs" --include="*.py" server/crates/ python-ai/
psql -d workflow -c "\d <表名>" | grep <欄位>
ls <預期存在的檔案>
```

無輸出就是未實作。把指令寫進報告，讓人能自己驗。

### 步驟 5：寫文件

放 `docs/實踐規劃/總結/YYYYMM/`，檔名 `NN_YYYYMMDD<主題>.md`。

**檔名一定要帶日期。** 這是每週都會產出的文件——
`08_下週工作備註.md` 這種寫法，下週再寫一份時就不知道該叫什麼，
而且兩份的內容差異從檔名完全看不出來。
（2026-09-19 就是這樣，事後由使用者手動改名補日期。）

## 文件結構

按這個順序，每一節都有明確的職責：

| 節 | 內容 | 注意 |
|---|---|---|
| 0 | 一句話 | 分階段講。「做得出來嗎」與「上線前驗證得了嗎」是不同的問題 |
| 1 | 兩台怎麼分工 | 只在平行開發時需要。寫清楚為什麼這樣分 |
| 2 | 第一階段（或更早的階段） | **最容易漏掉的一節**。git 看不到就去翻測試報告 |
| 3 | 這個階段的起點：要解什麼問題 | 用「上線前發現不了」這類具體後果，不要寫「為了提升品質」 |
| 4 | 做了什麼（依時間順序） | 兩條線各一個子節，對等 |
| 5、6 | 各線值得記住的設計決定 | 寫**為什麼這樣選**，不是寫做了什麼 |
| 7 | 抓到的真 bug | 加一欄「怎麼發現的」——測試抓到還是實機驗證抓到，差別很大 |
| 8 | 踩過的坑 | 同一類問題犯幾次要寫出來 |
| 9 | 平行開發的代價 | 編號衝突、測試污染這類 |
| 10 | 測試數字 | 起點、中間、現在三欄，**加上重跑指令**，合計要加過 |
| 11 | 產出的文件與檔案 | **每個路徑都要 `ls` 驗證，而且要寫成可點的連結** |
| 12 | 還沒解決的 | 分「需要人決定」與「可以自己做」 |
| 13 | 一句話收尾 | 回到 §0 的問題 |
| 附錄 | 文件地圖 | 用「我想找什麼」查，不是用「文件叫什麼」 |

§11 至少要有這幾張表，每張都是連結：需求與決議、系統規劃、
實踐規劃、階段總結、測試報告、新增的主要檔案、操作手冊、交接手冊。

§0 末尾加一句話告訴讀者「每一節都附了文件連結，完整地圖在 §11」，
不然沒有人會知道可以點。

## 寫作要求

### 解釋為什麼，不只列做了什麼

不好：

> 加了完整性閘。

好：

> 來源 1000 人只回 823 人時，若照寫，消失的 177 人會被當成離職。
> 其中只要有一個是主管，全公司相關流程立刻卡死。

### 分清「觀察到」與「推論」

報告裡若有沒直接驗證的事，明說。例：

> 標題前綴沒有直接驗證。它與收件人改寫是同一個條件，
> 所以收件人改寫生效就代表前綴也加了——**這是推論，不是觀察**。

### 修正別人的回報時要說清楚

另一台回報的問題可能描述得不準。修好之後要寫出**實際的根因**，
而不是照他們的描述寫。

例：回報說「種子沒有 readable_roles」，實際上一直都有——
沒生效是因為 seed 只用 POST 建表單，已存在就跳過。

### 舊文件被新進度推翻時要標出來

總結是最後寫的，常會發現某些文件的狀態已經過時。
不要默默用新狀態蓋過去——**指名哪份文件的哪一節過時了**，
讓還在讀那份文件的人知道。

例：

> N1、N3 已於 09-19 晚間定案並實作。
> [08_下週工作備註] 與 [A18 測試報告] §7 都還寫著「待決」，
> 那是 09-19 下午的狀態，已被當晚的實作取代。

順手把「補上那兩份文件」列進 §12 的待辦。

### 兩台的工作對等

另一台的章節要有：他們的核心設計決定、實機走查紀錄、
他們修掉的錯誤、以及他們自己記下的「沒驗證到」的部分。

素材從他們的測試報告讀，不要憑印象。

## 完成前的檢查

- [ ] 起始日期跟使用者確認過
- [ ] 測試數字是當場跑的
- [ ] **各列加起來等於合計欄，§0 的數字跟 §10 一致**
- [ ] 列出的檔案路徑都 `ls` 驗證過存在
- [ ] **每個開發步驟都有「文件產出」小表**
- [ ] **所有文件引用都是可點的相對連結，沒有裸編號**
- [ ] **所有連結都驗證過能解析**（指令在下方）
- [ ] 規劃完成度有可重跑的核對指令
- [ ] 兩台的工作都有獨立章節
- [ ] 章節編號連續（插入新節後容易亂）
- [ ] **寫完後再看一次 `git log -1`，有新 commit 就補**

### 驗證連結（一定要跑）

```bash
cd docs/實踐規劃/總結/202609 && \
grep -oE '\]\(\.\./[^)]*\)|\]\(\./[^)]*\)' <報告檔名>.md \
  | sed 's/^](//;s/)$//' | sort -u \
  | while read p; do
      [ -e "$p" ] && echo "OK   $p" || echo "BROKEN $p"
    done
```

出現任何 `BROKEN` 就修到零為止。

### 驗證章節編號

```bash
grep -n "^## \|^### " <報告路徑>
```

## 順帶產出：下週工作備註

寫完總結後，通常接著要寫「哪些沒做完」。放
`docs/需求規劃/YYYYMM/NN_YYYYMMDD_下週工作備註.md`。

**同樣要帶日期**，理由見步驟 5。每週都有一份，
沒有日期的話第二份就沒有名字可用。

內容：

1. 逐項核對規劃的完成度（附核對指令）
2. 本期額外做的（不在原規劃內的，說明為什麼被換掉）
3. 沒進實作的需求文件
4. **需要人決定才能動的**——標明誰決定、擋住什麼
5. 幾個排序選項與各自的風險

第 4 項最重要：開發不該自己決定營運政策、法遵語意這類事。
