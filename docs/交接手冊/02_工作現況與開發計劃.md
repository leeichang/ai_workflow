## 5. 已知缺陷

記錄真實存在、尚未修的問題。

### 5.1 條件式路徑打錯會靜默跳過簽核

**這是目前最危險的一個。**

流程定義的條件式：

```jsonc
"expression": "quotation.discount_rate > 0.15"
```

如果業務資料的路徑對不上（例如寫成 `discount_rate` 或打錯字），
表達式求值取不到值，**當成 false**，流程照跑，只是少走一段簽核。

實際後果：高折扣的報價單不經財務核准就發給客戶，而且沒有任何錯誤訊息。

對比之下 resolver 取不到值會讓流程 FAILED——那是明確的失敗，
反而安全。

建議：在 DSL 驗證（`WF-Exxx` 那組規則）加一條，
檢查條件式引用的路徑是否存在於業務物件的結構定義中。

### 5.2 pdfme 的 `keepLastRowsTogether` 從未執行

寫了「合計列不要單獨換頁」的保護邏輯，但渲染時根本沒呼叫到。

根因：pdfme 的 `Plugin` 型別沒有 `getDynamicHeights`，
generator 硬寫 `case 'table': getDynamicHeightsForTable(...)`。
當初用 `as unknown as` 壓掉型別錯誤，那段程式就再也沒執行過，
而測試依然全綠（測的是純函數本身，不是渲染路徑）。

目前「合計不分離」的需求由 `pdfme/src/plugins/rowStyleRender.ts`
以另一種方式達成（攔截 `schema.__bodyRange` 把一頁的表格拆成
明細段與合計段兩次繪製）。該檔的註解有完整說明。

### 5.3 測試不回收資料

整合測試每個案例建立一個隨機 UUID 的租戶，跑完不刪。
E2E 每次執行留下約 10 筆流程實例。

清點時的實況：

| 類別 | 數量 |
|------|------|
| 測試租戶 | 574 |
| 連帶的稽核事件 | 634 |
| 使用者 | 992 |
| 表單定義 | 432 |

不影響功能，但資料庫只增不減，待辦徽章的數字也會被測試殘留灌水。

`audit_event` 的外鍵是 `RESTRICT` 不是 `CASCADE`——刪租戶會被稽核事件擋住。
這是刻意設計（稽核軌跡不該因上層刪除而消失），清理時要顯式決定稽核留不留。

### 5.4 Temporal 重複 workflow_id 靜默失敗

用已存在的 `business_key` 啟動流程，API 回 201 並建立資料庫記錄，
但 Temporal 不會有新的執行——它以 workflow_id 去重。

呼叫端拿到 201 會以為成功。應該明確報 409。

### 5.5 登出無法立即失效 token

JWT 無狀態，後端沒有 session 可作廢。登出只清前端，
token 會一直有效到 `exp`（預設值見 `.env`）。

要立即失效需要黑名單或改用 refresh token。

## 9. 給接手的 AI agent

幾件這個專案特別在意的事：

**不要用 `as unknown as` 壓型別錯誤。** 5.2 就是這樣來的——
型別系統當初正確地警告「這個切點不存在」，被壓掉之後，
整段保護邏輯從未執行而測試依然全綠。

**測試通過不等於功能正確。** 已經發生過：

- 測純函數但渲染路徑沒呼叫到（5.2）
- 斷言用 `toHaveURL` 會重試，截圖卻立即執行，於是截到上一頁
- fixture 寫 `participants or [DEFAULT]`，空列表是 falsy，
  「沒有參與者」的測試實際上測了「一個參與者」

**改動後要實機驗證。** 這個專案有六個服務，
單元測試的 mock 與真實行為差距很大。`./start_service.sh` 起來實際點一遍。

**報告要誠實。** 測試報告裡記錄的缺陷包含「我先前報告這個功能可用，
那是錯的」這類內容。發現自己之前搞錯了就直說，不要默默改掉。
