## 4. 建議的工作順序

### 階段 A：熟悉（半天）

1. 依 [開發環境建立](../01_開發環境建立.md) 把六個服務跑起來
2. `./start_service.sh` 確認七個都是綠的
3. 用 `leeichang@gmail.com` / `demo1234` 登入 http://localhost:3040
   （這個帳號有 admin、designer、requester、approver 四種角色）
4. 手動走一次：建報價單 → 簽核 → 看 PDF
5. 跑一次全部測試

### 階段 B：暖身（一天）

從已知缺陷挑一個範圍清楚的。推薦這兩個：

**B-1　Temporal 重複 workflow_id 靜默失敗**

用已存在的 `business_key` 啟動流程，API 回 201 並寫入資料庫，
但 Temporal 不會有新執行——它以 workflow_id 去重。
呼叫端拿到 201 會以為成功。

- 改動位置：`server/crates/http-public/src/instances.rs`
- 做法：啟動前先 `describe` 檢查，已存在就回 409
- 難度：低。有明確的錯誤條件與預期回應

**B-2　測試資料回收**

574 個測試租戶、634 筆稽核事件、992 個使用者。資料庫只增不減。

- 難點：`audit_event` 的外鍵是 `RESTRICT` 不是 `CASCADE`，
  刪租戶會被擋。這是刻意設計（稽核軌跡不該因上層刪除而消失），
  清理時要顯式決定稽核留不留
- 做法：整合測試加 teardown，或寫一支以租戶名稱白名單為界的腳本

### 階段 C：主線（一～二週）

**外部客戶 Portal**——這是目前唯一擋住報價單流程真正端到端完成的缺口。

現況：流程定義的 `customer_review` 節點 `participant: external`，
resolver 從 `quotation.customer_contact_ids` 取聯絡人，待辦會建立，
但**客戶沒有任何管道登入來處理它**。

先前的 E2E 是用 `temporal workflow signal` 直接送 Signal 繞過 API，
資料庫因此沒有記錄那筆決策，流程結束時被當成殘留的 PENDING 取消。

需要做的：

| 項目 | 注意事項 |
|------|----------|
| 免登入的簽核連結 | 一次性 token，有效期限。**不要用 JWT**——客戶沒有帳號 |
| 欄位可見性 | 必須吃 `external_visible: false`。內部備註、毛利率絕不能讓客戶看到 |
| 核准／退回介面 | 比內部的簡化，但要能填意見 |
| 決策走正式 API | 不可直接送 Signal，否則沒有稽核記錄 |

可以先讀 `web/src/designer/usePermissionPreview.ts`，
權限預覽已經實作過「外部客戶看得到什麼」的判定邏輯。

### 階段 D：後續

依價值排序，非強制：

| 項目 | 說明 | 參考 |

| DSL 驗證檢查路徑存在 | 條件式路徑打錯會**靜默跳過簽核**。見第 6.1 節 | — |

## 6. 接手前必讀的五個陷阱

這些都是實際發生過、且不看說明會重蹈的。

### 6.1 條件式路徑打錯會靜默跳過簽核

**目前最危險的一個。**

```jsonc
"expression": "quotation.discount_rate > 0.15"
```

路徑對不上時（寫成 `discount_rate` 或打錯字），表達式求值取不到值，
**當成 false**，流程照跑，只是少走一段簽核。

實際後果：高折扣的報價單不經財務核准就發給客戶，沒有任何錯誤訊息。

對比之下 resolver 取不到值會讓流程 FAILED——那是明確的失敗，反而安全。

**建議**：在 DSL 驗證加一條，檢查條件式引用的路徑是否存在於
業務物件的結構定義中。這也是「AI 產生流程」的前置條件——
使用者不會去檢查 JSON。

### 6.2 不要用 `as unknown as` 壓型別錯誤

`pdfme/` 的 `keepLastRowsTogether` 就是這樣來的：
型別系統正確地警告「這個切點不存在」，被壓掉之後，
整段保護邏輯**從未執行**而測試依然全綠（測的是純函數本身，
不是渲染路徑）。

### 6.3 測試通過不等於功能正確

已經發生過的：

| 情況 | 後果 |
|------|------|
| 測純函數但渲染路徑沒呼叫到 | 保護邏輯從未執行 |
| `toHaveURL` 會重試，`screenshot()` 立即執行 | 截到上一頁的畫面 |
| fixture 寫 `participants or [DEFAULT]` | 空列表是 falsy，「沒有參與者」的測試實際測了「一個參與者」 |
| Activity 漏傳欄位 | 信寄出了但標題是通用的「流程通知」 |

最後一項是 SMTP 實測才發現的——單元測試只驗到有呼叫 `send_notification`，
沒驗欄位內容。

### 6.4 改動後要實機驗證

六個服務，單元測試的 mock 與真實行為差距很大。
`./start_service.sh` 起來實際點一遍。

**Rust API 與 Python Worker 跑的是啟動當下的程式碼**——
改完要重啟才會生效。改 Rust 還要先 `cargo build --bin api`。

### 6.5 macOS 的 bash 3.2 與 shell 陷阱

```bash
# 同一個 local 敘述引用前面剛宣告的變數 → unbound variable
local name=$1 file="$DIR/$name.pid"        # 壞
local name=$1; local file="$DIR/$name.pid" # 好

# 變數緊貼全形字元 → 位元組被併進變數名
echo "$port）"    # 壞
echo "${port}）"  # 好

# .env 的值含空格沒加引號 → shell 把第二段當指令執行
SMTP_PASSWORD=abcd efgh ijkl   # 壞，密碼變成空字串
SMTP_PASSWORD="abcd efgh ijkl" # 好
```

最後一項是接 SMTP 時踩到的：API 日誌顯示「缺少帳號或密碼」
但 `.env` 明明有值。

## 7. 開發約定

### 7.1 測試

TDD，目標覆蓋率 80%。實際做法：

1. 先寫測試，**確認 RED**
2. 實作到 GREEN
3. 每個功能都要有 client→server API 單元測試與 E2E 測試
4. 測試報告寫到 `docs/測試報告/YYYYMM/`，**E2E 要附截圖**

五層：

| 層 | 內容 | 位置 |
|----|------|------|
| L1 | 單元 | 各語言的測試目錄 |
| L2 | 契約 | `server/crates/*/tests/` |
| L3 | client API（MSW） | `web/tests/api/` |
| L4 | 整合 | `server/crates/http-public/tests/` |
| L5 | E2E（Playwright） | `web/e2e/` |

### 7.2 語言與註解

- 程式碼註解、文件、commit message 一律**繁體中文**
- 註解寫「**為什麼**」不寫「做什麼」
- 技術名詞保持原文（`RLS`、`Temporal`、`resolver`、`join`）

### 7.3 Git

- Conventional commits：`feat:` `fix:` `refactor:` `docs:` `test:` `chore:`
- **未經指示不要自行 commit 或建立分支**

## 8. 環境的注意事項

### 8.1 密鑰管理

`.env` 已在 `.gitignore`，不進版控。但**對話紀錄會留存**——
不要把密碼貼給 AI agent，直接寫進 `.env`。

目前 `.env` 含 Gmail 應用程式密碼（SMTP 通知用）。
另一台機器要自己產生一組，不要共用。

### 8.2 服務啟停

```bash
./start_service.sh            # 啟動全部（依相依順序）
./start_service.sh --status   # 只看狀態
./stop_service.sh             # 停止（保留 PostgreSQL 與 Docker）
./stop_service.sh --keep-temporal  # 保留 Temporal，重啟較快
```

**啟動順序有相依性**：Temporal 要早於 Rust API（否則 API 以
`temporal=None` 執行且不會自己重連），Rust API 要早於 Worker。

日誌在 `.logs/`。

## 10. 給接手的 AI agent

除了第 6 節的五個陷阱，幾件這個專案特別在意的：

**報告要誠實。** 測試報告裡記錄過「我先前報告這個功能可用，那是錯的」
這類內容。發現自己搞錯了就直說，不要默默改掉。

**不確定就問，但先做完不依賴那個答案的部分。** 這個專案的決議
（`docs/需求規劃/202609/02`）都是先問清楚再動手的結果。

**實機驗證的價值高於加測試。** 已經有 754 個測試，
但 SMTP 的欄位漏傳、N_OF_M 的預設值、截圖搶跑，
全都是實機操作才發現的。

**看到「尚未實作」的註解要查證。** 有過註解指向一個不存在的
`test_timeout.py`，而四種逾時策略中有兩種行為與設定相反，
沒有任何測試會發現。
