# AI 產生表單與流程 — 工作交接

- 日期：2026-09-17
- 對象：負責 AI 串接的開發機器
- 範圍：使用者用自然語言描述需求，系統產生 Form DSL 與 Flow DSL
- 先讀：[工作規劃交接](01_工作規劃交接.md) → [表單流程異動治理需求](../../需求規劃/202609/03_表單流程異動治理需求.md) 第 3.1 節

## 1. 核心決策：AI 是 Compiler，不是 Frontend Developer

這是整份文件唯一不可妥協的原則。

```
❌  Prompt → AI → Vue template / JavaScript
✅  Prompt → AI → DSL (JSON) → Validator → 既有 Renderer
```

AI 負責**理解需求並產生結構**。畫面怎麼畫、流程怎麼跑，由系統既有的
Renderer 與 Workflow Engine 決定。

理由不只是「比較穩定」：

| 讓 AI 產生 Vue code | 讓 AI 產生 DSL |
|---|---|
| 每次輸出都要人審程式碼 | 輸出可被 JSON Schema 機器驗證 |
| 改一個欄位要重產整個檔案 | 可以下 patch（`add_field`、`update_node`）|
| 產出無法存進資料庫做版本控制 | 直接進 `form_definition_version` |
| 綁死 Vue，換平台要重做 | 同一份 DSL 可餵 Vue / Mobile / API |
| 權限、RLS、稽核全部繞過 | 走既有的 API 與治理流程 |

**AI 的創造力用在理解需求，不是發明系統規格。**

## 2. 好消息：DSL 已經做好了

參考資料假設要從零設計 DSL。這個專案不用——**兩份 Schema 都已存在且被
生產程式碼使用中**。

### 2.1 Form DSL

`schemas/form.schema.json`（216 行）

```
form_key / version / business_object / name / layout / sections / fields
$defs: expression, field, uiSpec, tableColumn, dataSpec, workflowSpec
```

已支援的欄位類型：

```
input  textarea  number  integer  decimal  date  datetime
select  radio  checkbox  multi_select  file
department_picker  computed  table（明細，即 one2many）
```

已支援的進階能力（**比參考文章講的第一版完整很多**）：

| 能力 | DSL 欄位 |
|------|---------|
| 明細表格（Header/Lines） | `component: table` + `ui.columns` |
| 計算欄位 | `computed` + `formula` |
| 條件顯示 | `expression` |
| 欄位級權限 | `readable_roles` / `editable_roles` |
| 外部客戶可見性 | `ui.external_visible` |
| 巢狀資料對應 | `data.path`（如 `customer.delivery_site`）|
| 驗證 | `required` / `min` / `max` / `pattern` / `max_length` / `precision` |

**不要新增欄位類型，除非確定既有的做不到。** 受限生成正是讓 AI 輸出可
預測的關鍵。

### 2.2 Flow DSL

`schemas/workflow-dsl.schema.json`（722 行）

九種節點：

```
trigger  condition  human_approval  human_task
parallel  join  action  notification  end
```

七種 resolver（誰來簽）：

```
user  role  department_manager  manager_of
initiator  external_contacts  expression  composite
```

已支援：`joinPolicy`（ALL/ANY/N_OF_M）、`timeoutPolicy`
（WAIT/ESCALATE/AUTO_APPROVE/AUTO_REJECT）、`rejectPolicy`、
`retryPolicy`、`remind_at`（到期前多點提醒）。

### 2.3 Validator

`server/crates/domain/src/workflow_validator.rs`（1188 行，11 條規則）

| 碼 | 檢查 |
|----|------|
| WF-E001～E008 | 起訖節點、孤兒節點、循環、邊的有效性、resolver 完整性等 |
| WF-E009 | parallel 分支、N_OF_M 設定、join ESCALATE |
| WF-E010 | 分支收斂 |
| WF-E011 | ESCALATE 必須有 `to` |

表單端：`server/crates/domain/src/form_schema.rs`

**這套 validator 就是 AI 輸出的守門員。** 不要另外寫一套。

## 3. 所以要做的是什麼

不是建 DSL。是**在既有 DSL 上補一層 AI 產生器**：

```
使用者 Prompt
     │
     ▼
┌─────────────────┐
│ Requirement     │  ← 要做（可能需要回問使用者）
│ Analyzer        │
└────────┬────────┘
         ▼
┌─────────────────┐
│ DSL Compiler    │  ← 要做（structured output）
│ (LLM)           │
└────────┬────────┘
         ▼
┌─────────────────┐
│ Validator       │  ← 已有，直接呼叫
│ + Repair loop   │  ← 要做（把錯誤餵回 LLM 修正）
└────────┬────────┘
         ▼
┌─────────────────┐
│ 差異顯示        │  ← 需求 03 §3.2
│ 沙箱模擬        │  ← 需求 03 §3.3
│ 審核上線        │  ← 需求 03 §3.4
└─────────────────┘
```

後三段已在需求 03 規劃，**不是這次交接的範圍**，但 AI 產生器的輸出格式
必須配合它們。

## 4. 前置條件（擋路的，必須先解決）

### 4.1 DSL 驗證要檢查路徑存在性 ⚠️ 阻斷性

**這是整個 AI 功能的前置條件，不是附帶項目。**

目前的行為：

```jsonc
"expression": "quotation.discount_rate > 0.15"
```

路徑打錯（寫成 `discount_rat`）時，表達式求值取不到值，**當成 false**，
流程照跑，只是少走一段簽核。沒有任何錯誤訊息。

人工編輯時這已經很危險。**AI 生成時更危險**——使用者不會去看 JSON，
不會發現高折扣報價單沒經過財務就發給客戶了。

要做的：在 validator 加一條規則（WF-E012），檢查條件式與
`data.path` 引用的路徑是否存在於 `business_object` 的結構定義中。

不做這個就不要開始接 LLM。

### 4.2 Prompt 注入防範

使用者輸入會進到 prompt。使用者輸入內容不受信任。

最低要求：

- 使用者輸入以資料而非指令的形式傳入（分隔標記、明確界線）
- 輸出一律過 JSON Schema 驗證，不接受 schema 外的欄位
- 產生的 DSL 只能引用該租戶已存在的 `business_object`、`role`、`form_key`
- **AI 產生的內容永不直接上線**，一律進需求 03 的審核流程

### 4.3 決定用什麼模型

尚未決定。要考慮的：

| 選項 | 考量 |
|------|------|
| 雲端 LLM（Claude / OpenAI）| structured output 支援成熟，但表單定義含業務資訊，中小企業客戶可能在意 |
| 地端模型 | 資料不出門，但 JSON 輸出穩定度差，硬體成本轉嫁客戶 |
| 混合 | 敏感租戶走地端，其餘走雲端。複雜度高 |

建議先用雲端把流程跑通，把 LLM 呼叫抽成介面（參考
`server/crates/http-public/src/mailer.rs` 的 `Transport` trait 做法），
之後要換不會動到上層。

## 5. 建議做法

### 5.1 放在 Python 端

`python-ai/` 已有 Temporal Worker，加一個 `ai/` 模組：

```
python-ai/
├── ai/
│   ├── __init__.py
│   ├── client.py        # LLM 呼叫，抽成 Protocol 方便測試
│   ├── form_compiler.py # Prompt → Form DSL
│   ├── flow_compiler.py # Prompt → Flow DSL
│   ├── patcher.py       # 既有 DSL + Prompt → patch operations
│   └── prompts/         # system prompt 版本化管理
├── dsl/                 # 既有
└── workflows/           # 既有
```

放 Python 的理由：LLM SDK 的 Python 生態最成熟，且 `python-ai` 已經是
既有的第二語言邊界，不需要為此在 Rust 引入新相依。

Rust 端只負責：接 HTTP 請求、驗證、寫資料庫、稽核。與現有的
`internal API` 模式一致。

### 5.2 Structured Output，不要自己 parse

用模型供應商的 structured output / JSON mode，把
`schemas/form.schema.json` 直接當成輸出 schema。

不要讓模型輸出 markdown 再用正規表示式挖 JSON——那是失敗模式的溫床。

### 5.3 Patch 而非全量重產

第二次以後的修改必須是 patch：

```jsonc
{ "operation": "add_field",
  "section": "customer",
  "field": { "key": "delivery_site", "component": "input",
             "label": "交貨地點", "data": { "path": "customer.delivery_site" } } }

{ "operation": "update_node",
  "node_id": "manager_approval",
  "changes": { "timeout": { "after": "P2D", "policy": "ESCALATE" } } }

{ "operation": "insert_node", "after": "department_director",
  "node": { "id": "finance_approval", "type": "human_approval", ... } }
```

理由：

- 全量重產會讓使用者沒改的部分也被動到，diff 無法閱讀
- 需求 03 §3.2 要求「用業務語言顯示改了什麼」，patch 天然對應這個
- 版本歷史（需求 03 §3.5）要能還原到任一版，patch 讓歷史有意義

### 5.4 Validator Repair Loop

```
LLM 產生 DSL
    ↓
呼叫既有 validator
    ↓
  valid? ──否──→ 把 GraphError 清單餵回 LLM 要求修正（最多 N 次）
    │                    ↓
    是              仍失敗 → 降級成手動編輯，告訴使用者哪裡不合法
    ↓
進入差異顯示
```

`GraphError` 結構已定義在 `workflow_validator.rs:22`，直接序列化給 LLM。

**重試次數要有上限**，否則成本失控。建議 2 次。

### 5.5 位置交給程式算

Vue Flow 需要 `position: {x, y}`。**不要讓 LLM 產生座標**——它算不準，
會重疊。

DSL 只描述邏輯（node + edge），前端用 dagre 之類的自動佈局算位置。
這也符合既有設計：`workflow-dsl.schema.json` 本來就不含 position。

## 6. 關於 form-create-assistant

使用者指定參考 `xaboy/form-create-assistant`。

**值得參考的**：

- 它用 JSON Patch 做增量修改（呼應 §5.3）
- 支援多模型（DeepSeek、智譜、通義、OpenAI 相容介面）的抽象方式
- system prompt 的寫法（強制 JSON、給範例、限制類型）

**不要照抄的**：

- 它的 rule JSON 是 FormCreate 專用格式。**本專案有自己的
  `form.schema.json`，不要換成 FormCreate 的格式。** 我們的 DSL 已經包含
  權限、外部可見性、明細表格、巢狀路徑——那些是 ERP 場景必需，
  FormCreate 沒有。
- 它假設 AI 輸出直接渲染。本專案的輸出必須進治理流程（需求 03）。

定位：**參考它的 AI 互動設計，不參考它的資料格式。**

## 7. 分階段

### 階段 1：前置（必做，約 2 天）

1. WF-E012 路徑存在性驗證（§4.1）
2. LLM client 介面 + 一個假實作（測試用）
3. 決定模型與供應商

**驗收**：條件式引用不存在的路徑時，validator 回報錯誤。

### 階段 2：Form 產生（約 1 週）

1. system prompt（限制在既有的欄位類型內）
2. structured output 接 `form.schema.json`
3. validator repair loop
4. 全新產生（不含 patch）

**驗收**：輸入「建立員工基本資料表單，必填員工編號、姓名、部門、
職稱、到職日，部門用下拉選單」→ 產生合法 Form DSL → 既有 renderer
畫得出來。

### 階段 3：Flow 產生（約 1 週）

同上，接 `workflow-dsl.schema.json`。

**驗收**：輸入「請假流程，員工申請後部門主管審核，核准再由 HR 審核，
任一關拒絕就結束，全部通過通知員工」→ 產生合法 Flow DSL → 既有
designer 畫得出來 → Temporal 跑得起來。

### 階段 4：Patch 修改（約 1 週）

1. 既有 DSL + Prompt → patch operations
2. patch 套用與驗證

**驗收**：對階段 2 的表單說「再增加生日和手機號碼」→ 產生
`add_field` patch，其餘欄位不變。

### 階段 5：接治理流程

交回主線，與需求 03 的差異顯示、沙箱、審核整合。

## 8. 測試要求

沿用專案既有標準（見 [工作規劃交接](01_工作規劃交接.md) §7.1）：

| 層 | 這個功能要測什麼 |
|----|-----------------|
| 單元 | prompt 組裝、patch 套用、validator repair loop 的分支 |
| 契約 | LLM 回傳各種畸形輸出時的處理（截斷的 JSON、多餘欄位、schema 外的類型）|
| 整合 | 產生的 DSL 存進 `form_definition_version` 後能被既有 API 讀回 |
| E2E | Prompt → 產生 → 預覽 → 存檔，**要附截圖** |

**LLM 呼叫一律 mock。** 測試不該依賴外部服務，也不該花錢。真實模型的
驗證另外做實機測試並寫報告。

特別要測的失敗情境：

- LLM 回傳不合法 JSON
- LLM 產生了 schema 外的欄位類型（如 `magic_dropdown`）
- LLM 產生引用不存在 role 的 resolver
- LLM 產生引用不存在路徑的條件式 ← §4.1 的核心
- repair loop 重試耗盡

## 9. 已知陷阱（來自本專案實戰）

除了 [工作規劃交接](01_工作規劃交接.md) §6 的五個，這個功能特別要注意：

**測試通過不等於功能正確。** 已經發生過：mock 驗到「有呼叫
send_notification」就算過，但實際欄位漏傳，信寄出去標題是錯的。
LLM 功能的 mock 更容易造成這種假象——mock 回傳的永遠是你寫的那個
完美 JSON。**一定要有實機驗證。**

**fixture 的 falsy 陷阱。** 寫過 `participants or [DEFAULT]`，空列表
是 falsy，導致「沒有參與者」的測試實際測了「一個參與者」。LLM 回傳
空 fields 陣列是很可能的失敗模式，測試要能真的測到它。

**不要用 `as unknown as` 壓型別錯誤。** `pdfme/` 有前例：型別系統正確
警告「這個切點不存在」，被壓掉後整段保護邏輯從未執行，而測試全綠。

## 10. 要避免的方向

記錄下來，避免重新討論：

| 不要做 | 理由 |
|--------|------|
| 讓 AI 直接產生 Vue 程式碼 | §1 |
| 為 AI 新設一套 DSL | 既有的已被生產程式碼使用，兩份會漂移 |
| 換成 FormCreate 的 rule 格式 | §6，會丟失權限與明細表格能力 |
| 讓 AI 決定資料庫 schema | AI 可提案，但要過命名規則、安全規則、migration engine |
| 讓 AI 產生 Vue Flow 的 position | §5.5，程式算 |
| AI 產出直接上線 | 一律進需求 03 的審核流程 |
| 新增欄位類型 | 受限生成是輸出可預測的關鍵。要新增先證明既有的做不到 |

## 11. 這件事的意義

專案定位是「不換 ERP，把 Excel／Email／LINE 上的簽核變成有 ERP 寫回、
可稽核的正式流程」，服務對象是**沒有資訊單位的台灣製造業中小企業**。

市面上的流程系統都預設有資訊人員維護表單與流程。本專案要讓**使用者
自己是 Owner**。

AI 產生 DSL 是這個定位的關鍵一塊——沒有它，使用者面對的還是一個要懂
JSON 才能改的系統。

但也正因如此，**治理比生成更重要**。AI 產得出來只是開始，能讓使用者
看懂改了什麼、能先試跑、能送審、能還原，才是產品。
