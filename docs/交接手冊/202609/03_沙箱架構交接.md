# 流程監控與編輯開發模式（沙箱）— 工作交接

- 日期：2026-09-17
- 對象：負責 AI 串接的開發機器（與 [02_AI產生表單與流程交接](02_AI產生表單與流程交接.md) 同一批工作）
- 範圍：正式流程的唯讀監控 + 進入編輯開發模式（沙箱）設計與模擬簽核
- 相關需求：[表單流程異動治理需求](../../需求規劃/202609/03_表單流程異動治理需求.md) §3.3

---

## 1. 使用者的決策（2026-09-17 定案）

原話：

> 選單有一個目前執行的所有流程的清單與詳細內容顯示！但是都是唯讀！
> 如果要編輯！就要進入編輯開發模式！編輯開發模式就是一個沙箱！
> 可以設計與測試執行！執行時可以直接由系統依據目前的系統角色設定
> 解析出實際簽核的人員，測試的人可以直接點選模擬這個人簽核，
> 系統依據權限設定顯示每個簽核人員的畫面，讓使用者模擬簽核！
> 一一完成後最後整個流程完成！

拆成三個功能：

| # | 功能 | 性質 |
|---|------|------|
| A | **流程監控**：所有執行中流程的清單與詳情 | 唯讀，正式環境 |
| B | **編輯開發模式**：從監控進入，設計表單與流程 | 沙箱 |
| C | **模擬簽核**：一個人扮演所有簽核人走完流程 | 沙箱 |

### 1.1 這修正了先前的沙箱設計

先前規劃的沙箱是「影子租戶 + 使用者換身分登入進去操作」。
使用者的描述改了關鍵一點：

| 先前設計 | 使用者要的 |
|---------|-----------|
| 複製使用者帳號到沙箱，測試者要換身分登入 | **不換身分**。測試者一個人，點選要扮演誰 |
| 操作體驗與正式一致 = 用一樣的登入流程 | 操作體驗一致 = **看到的畫面與那個人會看到的一樣** |
| 沙箱是隔離的執行環境 | 沙箱是**開發模式**，設計與測試在同一個地方 |

後者務實得多：

- 不必複製使用者主檔（先前列為「最容易出錯的一步」）
- 測試者一個人就能走完五關簽核，不必請五個同事配合
- 「解析出實際簽核人員」這件事本身就是在驗證 resolver 設定對不對

**核心轉變：沙箱不是另一個環境，是一個附身模式。**

## 2. 功能 A：流程監控（唯讀）

### 2.1 現況

選單目前有：首頁、我的待辦、報價單、採購申請、報表、設定、設計器。

`/quotations` 是**單據**列表，不是流程實例列表。沒有跨業務物件看
「現在有哪些流程在跑、跑到哪一關」的地方。

API 已有基礎：

```
GET  /instances        （list）
GET  /instances/{id}   （get_one）
POST /instances/{id}/cancel
```

要確認回傳內容是否足夠支撐詳情頁（目前節點、已完成節點、待辦對象、
耗時）。不足就補，不要另開一套 API。

### 2.2 要做的

選單新增「流程監控」。

**清單**：

| 欄位 | 說明 |
|------|------|
| 業務物件 / 單號 | 報價單 QT-2026-001 |
| 流程定義 + 版本 | quotation_flow v3 |
| 目前節點 | 財務簽核 |
| 待簽核人 | 李淑芬（解析後的實際人員）|
| 狀態 | RUNNING / COMPLETED / FAILED / CANCELLED |
| 已耗時 | 3 天 2 小時 |
| 發起人 / 發起時間 | |

篩選：狀態、流程定義、日期區間、是否逾時。

**詳情**：

- 流程圖，標出已走過的路徑、目前位置、未走的分支
- 每個節點的簽核記錄（誰、何時、核准或退回、意見）
- 目前待辦的對象與到期時間
- 平行分支的各branch狀態（哪些完成、join 還在等誰）
- 表單資料（唯讀，依當前使用者的權限顯示）

**唯讀是硬性要求。** 這個畫面不提供任何修改流程定義的入口，
只有一個「進入編輯開發模式」的按鈕，走的是完全不同的路徑。

### 2.3 權限

流程監控看得到的範圍要受權限控制。至少三級：

| 角色 | 看得到 |
|------|--------|
| 一般使用者 | 自己發起的、自己簽過的 |
| 主管 | 部門內的 |
| admin | 全部 |

表單資料的欄位顯示要吃既有的 `readable_roles`。
**監控畫面不是權限的後門**——不能因為是「管理功能」就顯示
所有欄位，薪資、成本這類欄位在監控畫面一樣要遮蔽。

## 3. 功能 B：編輯開發模式

### 3.1 進入點

從流程監控的詳情頁，或從設計器列表，按「編輯開發模式」。

進入後：

- 全畫面明顯標示處於開發模式（顏色、橫幅，不可關閉）
- 載入該流程定義的當前版本為草稿
- 可用表單設計器與流程設計器修改
- 可用 AI 產生／修改（見 [02_AI產生表單與流程交接](02_AI產生表單與流程交接.md)）
- 可隨時「測試執行」（功能 C）

### 3.2 資料隔離

沿用影子租戶（需求 03 選項 A），但**簡化**：

```
demo（正式租戶）
  └── demo__dev_a1b2c3（開發模式租戶）
        ├── 複製：role、department、業務物件定義、主檔（部門、客戶等）
        ├── 不複製：user 帳號（測試者不換身分，見 §4）
        └── 掛上草稿版本的表單與流程
```

現有系統已經提供的隔離（**不需要改**）：

| 機制 | 現況 |
|------|------|
| RLS（`workflow_app` 非超級使用者）| 已啟用，九項隔離測試通過 |
| `tenant_tx()` 單一進入點 | 所有 DB 存取都經過它 |
| Temporal `workflow_id::build` | 已含 tenant 前綴 |
| `workflow_id::belongs_to` | 已實作歸屬檢查 |

建一個開發租戶，資料隔離就自動成立。不需要在任何查詢加
`where is_sandbox = false`。

**為什麼不用「同租戶加 `is_sandbox` 標記」**：每處查詢都要記得過濾，
漏一個就洩漏，而且是靜默失敗——與
[工作規劃交接](01_工作規劃交接.md) §6.1 那個「條件式路徑打錯靜默跳過
簽核」是同一類問題。靜默的錯誤比會爆炸的錯誤危險。

### 3.3 要新增的資料表

```sql
alter table tenant
  add column parent_tenant_id uuid references tenant(id),
  add column is_sandbox boolean not null default false,
  add column expires_at timestamptz;

comment on column tenant.parent_tenant_id is
  '開發模式租戶的來源租戶。正式租戶為 NULL';
comment on column tenant.is_sandbox is
  '開發模式租戶。前端據此顯示警示標示，清理程序據此回收';
comment on column tenant.expires_at is
  '開發模式租戶的到期時間。正式租戶為 NULL，永不過期';
```

```sql
create table sandbox_session (
    id                uuid primary key default uuid_generate_v4(),
    tenant_id         uuid not null references tenant(id),  -- 來源租戶
    sandbox_tenant_id uuid not null references tenant(id),  -- 開發租戶
    change_request_id uuid,                                  -- 對應的變更提案，可為 NULL
    created_by        uuid not null,                          -- 測試者（唯一的真實使用者）
    status            text not null default 'ACTIVE'
                      check (status in ('ACTIVE', 'RESET', 'EXPIRED', 'DISCARDED')),
    created_at        timestamptz not null default now(),
    expires_at        timestamptz not null
);
```

## 4. 功能 C：模擬簽核（本次的核心）

這是使用者描述最具體、也最有產品價值的部分。

### 4.1 流程

```
測試執行
   ↓
系統依「目前的角色設定」解析簽核人員
   ↓
┌────────────────────────────────────┐
│ 目前節點：主管簽核                  │
│ 解析結果：張文華（cfo）             │
│                                    │
│         [ 以張文華的身分簽核 ]      │
└────────────────────────────────────┘
   ↓
切換到張文華會看到的畫面
（欄位依 readable_roles / editable_roles 過濾）
   ↓
測試者按核准／退回
   ↓
流程前進到下一節點，重複
   ↓
所有節點完成 → 流程結束
```

### 4.2 「解析出實際簽核人員」要真的解析

**不能用假資料。** 要呼叫既有的 resolver
（`resolve_participants` activity），用開發租戶裡真實的角色與組織設定。

這正是這個功能最大的價值：**它在驗證 resolver 設定對不對**。

已經踩過的坑（見 [工作規劃交接](01_工作規劃交接.md) §6）：

- `resolver.user_id` 需要 UUID 不是 email，寫錯會讓流程 FAILED
- 主檔複製不完整會讓 resolver 找不到人

模擬簽核會讓這兩類錯誤在**上線前**就浮現，而不是上線後第一張單卡住。

resolver 解析失敗時要**明確顯示錯誤**，不要跳過或用預設人員頂替：

```
❌ 無法解析簽核人員
   節點：財務簽核
   resolver：role = finance_manager
   原因：此角色沒有指派任何使用者
```

### 4.3 「依權限設定顯示每個簽核人員的畫面」

切換扮演對象時，表單欄位要依**那個人的角色**重新計算可見性與可編輯性：

| DSL 欄位 | 效果 |
|---------|------|
| `readable_roles` | 不在清單內 → 不顯示該欄位 |
| `editable_roles` | 不在清單內 → 唯讀 |
| `external_visible` | 外部客戶節點 → false 的欄位不顯示 |

**三態語意要正確**（既有規則，不可改）：

```
key 不存在 → 不限制（所有人可見／可編輯）
[]         → 全部拒絕
["a"]      → 只有角色 a
```

#### 判定邏輯在後端，不在前端

```
web/src/designer/usePermissionPreview.ts   ← 只有 97 行，不算權限
        │  它只負責呼叫 API 與處理請求競態
        ▼
GET /forms/{form_key}/permissions/preview
        │  server/crates/http-public/src/permissions.rs:163
        ▼
domain::permission::resolve_form()          ← 真正的判定在這裡
        server/crates/domain/src/permission.rs:68
```

**要複用的是 `domain::permission::resolve_form()`。**

前端那支的檔頭註解已經說明了為什麼：

> 用後端而非前端重算的理由：判定邏輯只該有一份。
> 前端複製一份必然會與後端漂移，而漂移的症狀是
> 「畫面說可編輯、實際送出被擋」，極難追查。

模擬簽核同理——不要在模擬畫面重算一份。

#### ⚠️ 現有的預覽 API 不能直接用於模擬

`permissions.rs:187` 把 `data` 寫死成空物件：

```rust
let empty = Value::Object(Default::default());
let ctx = Context { data: &empty, ... };
```

設計器預覽時沒有實際單據，空的合理。
但**模擬簽核有真實單據**，而 `permission.rs:193` 的 `eval_bool`
會用 `data` 求值條件式。

後果：凡是 `visibility.when` 依賴欄位值的欄位，模擬時全部判錯。
使用者看到的畫面與真實簽核不同——
**而沙箱的整個價值就是「看到的畫面與那個人會看到的一樣」**。

要做的（二選一，建議前者）：

| 選項 | 做法 |
|------|------|
| **A. 擴充預覽 API** | 加一個可選的 `instance_id`，有值時帶入該實例的真實 `business_object` |
| B. 模擬走另一條路徑 | 另開端點。缺點是兩條路徑要維持一致 |

選 A 的話，設計器的行為不變（不傳 `instance_id` 就照舊用空物件），
模擬簽核傳實例 id 拿到正確結果。改動小且沒有兩份邏輯。

**這是階段 2 的前置條件**，不是實作細節。

### 4.4 模擬簽核的身分處理

這是最容易做錯的地方。

**測試者始終是同一個真實使用者。** 「扮演張文華」不是登入成張文華，
是在該次簽核操作上標註 `acting_as = 張文華的 uuid`。

稽核記錄必須兩者都留：

```jsonc
{
  "actor_id": "測試者的 uuid",        // 真正按下按鈕的人
  "acting_as": "張文華的 uuid",       // 扮演的對象
  "is_simulation": true,
  "sandbox_tenant_id": "..."
}
```

**理由**：如果只記 `acting_as`，稽核會顯示張文華核准了某張單，
而他根本不知道有這回事。這在正式環境會是嚴重問題，在沙箱雖然無害，
但**兩套稽核語意會讓程式碼分岔**——寧可從一開始就一致。

`acting_as` 目前**不存在**，要新建。
`grep acting_as|impersonat|on_behalf` 在整個 `server/crates/` 零命中。
`AuditEvent::actor()` 現在收 `(id, name)` 兩個參數，
要加第三個或新增 `.acting_as()`。這是跨所有稽核呼叫點的改動，
工作量比「加個欄位」大。

### 4.5 簽核 API 的授權檢查要開洞 ⚠️ 安全邊界

**這是整份文件最需要謹慎的地方。**

`server/crates/http-public/src/tasks.rs:134`：

```rust
let is_assignee = task.assignee_user_id == Some(actor.user_id);
```

模擬簽核時測試者**不是** assignee，會被這條擋下來。
所以這條規則必須開洞——而開洞的地方正是安全邊界。

**開洞的條件要寫死，不可設計成可配置的權限：**

```rust
// 模擬簽核允許非 assignee 操作，但條件嚴格且寫死：
//   1. 必須是沙箱租戶
//   2. 操作者必須是該沙箱的建立者本人
//
// 不做成「有某個角色就能扮演」——那會變成正式環境的提權路徑。
// 沙箱身分不是一種權限，是一種環境狀態。
let is_simulation = tenant.is_sandbox
    && sandbox_session.created_by == actor.user_id;
```

**為什麼不能做成權限**：若寫成「擁有 `simulator` 角色的人可以扮演他人簽核」，
那麼在正式租戶誤給這個角色，等同開放冒名簽核。
綁在 `is_sandbox` 上則不可能——正式租戶的 `is_sandbox` 永遠是 false。

要測的：

- 正式租戶的非 assignee **必定**被擋（即使有任何角色組合）
- 沙箱租戶的非建立者被擋
- 沙箱租戶的建立者可以扮演任何解析出的簽核人

第一條是回歸測試，防止日後有人為了方便把條件放寬。

### 4.6 平行分支的模擬

平行節點會同時產生多個待辦。模擬畫面要能：

- 列出所有分支目前各自等誰
- 讓測試者逐一扮演，也能只簽部分
- 顯示 join 的完成條件（ALL / ANY / N_OF_M）與目前進度

```
並行簽核（join: N_OF_M, n=2）
  ├── 財務  李淑芬   ✅ 已核准
  ├── 法務  王大明   ⏳ 待簽      [ 以王大明簽核 ]
  └── 採購  陳小華   ⏳ 待簽      [ 以陳小華簽核 ]

  進度：1 / 2（再一人核准即通過）
```

這個畫面本身就是 join policy 設定是否正確的驗證工具。

### 4.7 逾時與提醒的模擬

流程含 `timeout` 與 `remind_at` 時，等真實時間不可行（P3D 要等三天）。

要提供**時間快轉**：

```
[ 快轉到下一個時間點 ]   → 觸發最近的提醒或逾時
```

Temporal 的 time-skipping 測試環境（`start_time_skipping()`）已在
Python 測試中使用過，可以評估複用。但要注意它與 `start_local()` 的
行為差異——測試曾因此卡住。

**這項可以排到第二階段**，不阻擋第一版。

## 5. 通知照常寄出，標題加「【沙箱模擬】」前綴（2026-09-17 定案）

**使用者的決策**：沙箱的通知**要真的寄出**，只是標題加前綴標示。

```
正式：【待辦提醒】報價單 QT-2026-001 待簽核
沙箱：【沙箱模擬】【待辦提醒】報價單 QT-2026-001 待簽核
```

### 5.1 為什麼寄比不寄好

先前的規劃是「開發租戶強制 `Mailer::disabled()`，畫面顯示本來會寄給誰」。
使用者的做法更好：

| 攔截不寄 | 照常寄出加前綴 |
|---------|--------------|
| 只驗證到「系統決定要寄給誰」 | 驗證到**信真的送達**了 |
| 收件人 email 打錯不會發現 | 退信就發現 |
| SMTP 設定問題上線才爆 | 沙箱就爆 |
| 信件內容要另外預覽 | 收件人直接看到實際內容 |

這與 §4.2「解析出實際簽核人員要真的解析」是同一個原則：
**沙箱的價值在於它真的跑，不是模擬它跑。**

已經有前例支持這個判斷——SMTP 那次，單元測試驗到「有呼叫
`send_notification`」就算過，但 Activity 漏傳 `kind` 欄位，
信寄出去標題是通用的「【流程通知】」而不是「【待辦提醒】」。
**那個錯誤只有真的寄一封信才會發現。**

### 5.2 實作

標題前綴由**寄送端**加，不是由呼叫端傳。

`server/crates/http-public/src/internal.rs` 的 `subject_of` 組出標題後，
若當前租戶 `is_sandbox = true` 就加上前綴：

```rust
// 沙箱的信一定要能一眼認出來。
// 前綴在寄送端加，不靠呼叫端記得傳——漏一處就會有人
// 把測試信當成真的待辦去簽核。
const SANDBOX_SUBJECT_PREFIX: &str = "【沙箱模擬】";
```

**為什麼在寄送端**：呼叫 `send_notification` 的地方有多處
（human_task 建立、提醒、逾時、ESCALATE、流程結束）。
靠每一處記得傳前綴，遲早漏一個。

信件內文也要加一段說明，因為手機通知可能只顯示部分標題：

```
──────────────────────────────
這是沙箱模擬的通知，不是真實待辦。
由 李一昌 於 2026-09-17 14:30 發起的流程測試產生。
──────────────────────────────
```

### 5.3 收件人一律改寄測試者，內文標明原收件人（2026-09-17 定案）

沙箱模擬解析出來的簽核人是**真實的同事**。若照常寄給他們，
除了打擾沒有額外價值——而且中小企業的主管收到
「【沙箱模擬】待簽核」很可能還是會點進去簽。

**決議**：收件人一律改成**發起模擬的測試者**，
原收件人寫在內文。

```
收件人：李一昌 <leeichang@gmail.com>       ← 測試者
標題：【沙箱模擬】【待辦提醒】報價單 QT-2026-001 待簽核

──────────────────────────────
這是沙箱模擬的通知，不是真實待辦。

原收件人：張文華 <cfo@demo.local>
解析依據：resolver role = cfo
發起人：李一昌
發起時間：2026-09-17 14:30
──────────────────────────────
```

這樣三件事都驗證得到：

| 驗證項 | 怎麼驗 |
|--------|--------|
| 收件人解析對不對 | 內文的「原收件人」 |
| resolver 設定對不對 | 內文的「解析依據」 |
| 信真的寄得出去 | 測試者收到了 |

而唯一寄不到的情況——**原收件人的 email 打錯**——
在內文一眼看得出來（`cfo@demo.locall`），不需要真的寄過去試。

### 5.4 改寫收件人要在哪一層做

與前綴同一層：**寄送端**，不是呼叫端。

具體插入點是 `server/crates/http-public/src/internal.rs:408`：

```rust
let recipients = resolve_recipients(&mut tx, &body.to).await?;
// ↑ 沙箱改寫插在這裡，subject_of / text_of 之前
//   若 is_sandbox：recipients 換成測試者，原清單留給內文
```

測試者的 email 從 `sandbox_session.created_by` 取。

**不要在 Python 端的 Activity 改。** 那裡有多個呼叫路徑，
而且 Activity 不該知道沙箱這個概念——它只負責「請寄這封信」。

#### 稽核要記兩份收件人

現有稽核已經同時記 `to`（原始參與者 id）與 `recipients`（解析後 email），
理由是「解析本身可能出錯，只記一個查不出是解析錯還是寄錯」。

沙箱改寫後同理，要記三層：

```jsonc
{
  "to": ["<uuid>"],                      // 原始參與者 id
  "recipients": ["cfo@demo.local"],      // 解析後的真實收件人
  "actual_recipients": ["tester@..."],   // 沙箱改寫後實際寄達的
  "is_sandbox": true
}
```

只記最後一層的話，查不出「這封信原本要寄給誰」——
而那正是沙箱要驗證的東西。

#### `is_sandbox` 怎麼取得

`send_notification` 手上只有 `tenant_id`。要判斷是否沙箱就得查 `tenant` 表，
每封信一次查詢。

三個選項：

| 選項 | 代價 |
|------|------|
| **A. `tenant_tx()` 回傳時帶上** | 改動集中在一處，所有呼叫端自動拿得到 |
| B. `AppState` 快取 | 要處理失效；沙箱租戶會頻繁建立與銷毀 |
| C. 每次查詢 | 簡單但每封信多一次往返 |

**建議 A**。`tenant_tx()` 已經是所有 DB 存取的單一進入點，
在那裡取一次租戶屬性，其他地方都不必各自查。
這也讓「忘記判斷 is_sandbox」這種錯誤更難發生。

LINE 之後接上時同樣處理：訊息開頭加「【沙箱模擬】」，
推播對象改成測試者，原對象寫在訊息內。

### 階段 -1：前置改動（約 2 天，必須先做）

這三項不做，階段 2 會做到一半才發現卡住。

| # | 項目 | 為什麼是前置 |
|---|------|-------------|
| 1 | **預覽 API 支援真實 data**（§4.3）| 不做的話模擬畫面的條件顯示欄位全部判錯 |
| 2 | **表單版本鎖定**（§7.1）| 沙箱會大量改表單定義，進行中實例會抓到新版 |
| 3 | **WF-E012 路徑存在性驗證** | AI 產生的條件式引用錯路徑會靜默跳過簽核。見 [02_AI產生表單與流程交接](02_AI產生表單與流程交接.md) §4.1 |

第 2 項的說明見下方 §7.1。

### 階段 0：流程監控（約 3 天）

功能 A。純唯讀，不碰沙箱。

**驗收**：選單有「流程監控」，看得到所有執行中流程的清單與詳情，
權限正確（一般使用者看不到別人的單），欄位遮蔽正確。

這階段獨立有價值——目前系統缺這個畫面。

### 階段 1：開發模式基礎（約 3 天）

1. `tenant` 表三個欄位 + `sandbox_session` 表
2. `tenant_tx()` 帶上租戶屬性（§5.4）
3. 建立／重置／銷毀開發租戶的 API
4. 主檔複製（**不含 user**）
5. 前端開發模式標示
6. **通知標題前綴與收件人改寫**（§5）

**驗收**：建一個開發租戶，在裡面改表單存檔，確認正式租戶完全不受影響。
觸發一次通知，收到的信標題以「【沙箱模擬】」開頭且寄到測試者信箱。

### 階段 2：模擬簽核（約 1 週）

功能 C。本次核心。

1. 真實 resolver 解析 + 解析失敗的明確錯誤
2. **簽核 API 的授權開洞**（§4.5）—— 安全邊界，先做這項
3. 扮演切換 + 權限過濾畫面（呼叫擴充後的預覽 API）
4. `acting_as` 稽核（要新建，見 §4.4）
5. 平行分支的模擬畫面

**驗收**：一個測試者從頭走完含平行分支的報價單流程，
每關看到的欄位與該角色實際會看到的一致。
**正式租戶的非 assignee 仍然被擋**（回歸測試）。

### 階段 3：時間快轉

§4.7。逾時與提醒的模擬。

### 階段 4：與 AI 產生器整合

AI 產生的 DSL 寫進開發租戶，立刻可模擬。

**AI 產生器的 API 只接受開發租戶 id，傳正式租戶 id 回 400。**
這條要寫進 API 設計，不靠呼叫端自律。

### 7.1 表單版本鎖定（階段 -1 的第 2 項）

流程實例已經鎖定流程版本：

```sql
-- server/migrations/0005_workflow_instance.sql:21
workflow_version_id uuid not null
    references workflow_definition_version(id) on delete restrict,
```

**表單沒有對應的欄位。**

後果：流程跑到一半改表單定義，進行中的實例會用到新版。
欄位被刪掉、必填變選填、權限改了——都會直接影響還沒簽完的單。

這在人工編輯時已經是問題（`02_工作現況` §4.4 列為低優先）。
**在沙箱與 AI 產生的脈絡下它不低**——這兩者都會大量改表單定義。

而且需求 03 §3.5 宣稱「進行中的實例不受還原影響」，
這個宣稱目前**不成立**，因為沒有東西把實例綁在某個表單版本上。

要做的：

```sql
alter table workflow_instance
  add column form_version_id uuid
      references form_definition_version(id) on delete restrict;
```

與 `workflow_version_id` 同樣用 `on delete restrict`——
理由一致：進行中的單所依賴的定義不該被刪除。

## 8. 測試要求

沿用專案標準（見 [工作規劃交接](01_工作規劃交接.md) §7.1）。

| 層 | 測什麼 |
|----|--------|
| 單元 | 權限過濾三態、resolver 解析失敗處理、主檔複製範圍 |
| **隔離測試** | **最重要**。開發租戶的單據不出現在正式租戶的任何查詢 |
| 整合 | 建立→設計→模擬→重置→銷毀完整生命週期 |
| E2E | 流程監控唯讀、進入開發模式、模擬簽核走完流程，**附截圖** |

隔離測試要覆蓋（比照既有九項 RLS 測試）：

```
待辦列表  單據列表  報表統計  稽核查詢
Temporal 實例查詢   通知收件人解析   流程監控清單
```

**雙向都要測**——單向會漏掉「開發租戶看得到正式單據」這種情況。

特別要測的：

- **正式租戶的非 assignee 必定被擋**（§4.5，任何角色組合都不例外）
- 沙箱租戶的非建立者被擋
- 模擬簽核產生的稽核同時含 `actor_id` 與 `acting_as`
- 條件顯示的欄位在模擬畫面判定正確（§4.3，要有真實 data）
- 開發租戶寄出的信，標題以「【沙箱模擬】」開頭
- **開發租戶的信一律寄給測試者**，原收件人在內文（§5.3）
- **每一個呼叫 `send_notification` 的路徑都有前綴與收件人改寫**
  （human_task 建立、提醒、逾時、ESCALATE、流程結束）——
  這是 §5.2 最容易漏的地方
- 原收件人 email 無效時，內文照樣顯示它（測試者才看得出打錯）
- 扮演不同角色時欄位可見性正確切換
- resolver 解析不到人時顯示錯誤而非跳過

## 9. 已知風險

| 風險 | 說明 | 緩解 |
|------|------|------|
| **沙箱信被當成真待辦** | 收件人看到信就去簽核 | §5.3，一律改寄測試者；§5.2 標題加「【沙箱模擬】」前綴 |
| 前綴或收件人改寫漏做 | 某個呼叫點忘了處理 | §5.2、§5.4，都在**寄送端**做，不靠呼叫端 |
| 主檔複製不完整 | resolver 找不到人 → FAILED | 複製後跑冒煙測試；解析失敗要明確報錯 |
| 權限判定兩份 | 模擬畫面重寫一套判定，與正式漂移 | 複用 `domain::permission::resolve_form()`（§4.3）|
| **模擬畫面條件顯示判錯** | 預覽 API 傳空 `data`，`eval_bool` 求值不到 | §4.3，擴充 API 支援 `instance_id` |
| **正式環境冒名簽核** | 授權開洞條件設計成可配置的權限 | §4.5，綁死 `is_sandbox`，加回歸測試 |
| 進行中實例抓到新版表單 | 表單沒有版本鎖定 | §7.1 |
| 租戶數量膨脹 | 已有 574 個測試租戶的前例 | `expires_at` + 定期回收 |
| 使用者誤判 | 在開發模式核准以為正式也核准了 | 不可關閉的全域標示 |
| 監控成為權限後門 | 「管理功能」顯示所有欄位 | §2.3，監控一樣吃 `readable_roles` |

清理時注意 `audit_event` 外鍵是 `RESTRICT` 不是 `CASCADE`，
刪租戶會被擋。這是刻意設計。**開發租戶的稽核可以刪**（非真實業務行為），
但 `sandbox_session` 要保留「某人在某時建過開發模式」這件事。

## 10. 要避免的方向

| 不要做 | 理由 |
|--------|------|
| 模擬做成「簡化版預覽」 | 使用者無法驗證流程真的會怎麼跑 |
| 讓測試者換身分登入扮演 | 使用者要的是點選扮演，不是登入五次 |
| 用假資料解析簽核人 | §4.2，這個功能的價值就在真實解析 |
| 模擬畫面重寫權限判定 | 複用 `domain::permission::resolve_form()`，兩份會漂移 |
| 把授權開洞做成可配置的角色 | §4.5，正式租戶誤給就開放冒名簽核 |
| 模擬畫面直接用現有預覽 API | §4.3，它傳空 `data`，條件顯示會判錯 |
| 稽核只記 `acting_as` | §4.4，會變成「張文華核准了他不知道的事」 |
| 同租戶加 `is_sandbox` 過濾 | §3.2，漏一個查詢就靜默洩漏 |
| 沙箱信不寄只攔截 | §5.1，驗證不到信真的送得到 |
| 前綴靠呼叫端傳 | §5.2，多處呼叫遲早漏一個 |
| 沙箱信照常寄給解析出的同事 | §5.3，對方可能當真去簽 |
| 在 Python Activity 改收件人 | §5.4，Activity 不該知道沙箱概念 |
| 流程監控提供修改入口 | 唯讀是硬性要求，修改一律走開發模式 |
| AI 產生器直接寫正式租戶 | 在 API 層擋，不靠自律 |
