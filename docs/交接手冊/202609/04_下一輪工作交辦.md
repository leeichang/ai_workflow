### 2.3 實機驗證抓到兩處猜測錯誤

單元測試不會抓到——MSW 不驗 schema：

1. **`fields` 有 `minItems: 1`**，零欄位的表單被擋
   （`/fields：[] has less than 1 item`）
2. **欄位結構是 `{ key, section, ui: { component, label }, data }`**，
   `component` 與 `label` 在 `ui` 底下不是頂層

第 1 點反而對使用者有利：新表單帶一個起始欄位，
進設計器就看得到實際欄位長什麼樣。

### 2.4 與業務物件定義的對齊

起始欄位的路徑用 `{object}.number` 而非 `business_key`。

`business_key` 是 `workflow_instance` 的識別碼，不是業務資料。
`schemas/business-objects/*.json` 收錄的是 `quotation.number` 這類
業務欄位——指向 `business_key` 會建立一條永遠不在正式定義裡的路徑。

測試已釘住這個決定（`expect(...data.path).toBe('employee.number')`）。

### 2.5 業務物件定義（2026-09-18 新增 `leave_request`）

`schemas/business-objects/*.json` 是 WF-E012 的合法路徑來源。
**目前三個**：

| 檔案 | 業務物件 | 欄位數 | 用途 |
|------|---------|--------|------|
| `quotation.json` | 報價單 | 13 | 主要業務場景、操作手冊 05 |
| `purchase_request.json` | 採購申請 | 12 | 第二個業務物件，驗證通用性 |
| `leave_request.json` | 請假單 | 12 | **新增**。操作手冊 03 的流程示範 |

#### 新增業務物件的三個步驟

漏掉任何一步都會讓該業務物件**靜默失去 E012 保護**：

```
1. 建立 schemas/business-objects/{name}.json
2. 在 business_object.rs 加 include_str! 常數
3. 把常數加進 all() 的陣列
```

第 3 步最容易漏——檔案建了、常數也加了，但沒放進 `all()`，
`paths_for()` 就回空集合，而**空集合在 E012 代表「不檢查」**。

`embedded_definitions_parse` 測試用精確數字（`assert_eq!(defs.len(), 3)`）
而非 `>=`，就是為了強迫這三步同步。新增第四個定義時那個測試會失敗，
提醒你更新。

#### `leave_request` 的三個設計決定

寫在該檔的 `notes` 裡，避免日後被「順手改掉」：

| 決定 | 理由 |
|------|------|
| `days` 用小數（0.5 = 半天），另有 `hours` | 兩者由表單的計算欄位維持一致 |
| **假別的可選值不在定義裡列舉** | 同一家公司的假別會隨制度調整，寫死會讓每次調整都要改程式。那屬於表單的下拉選單 |
| **`agent_id`（職務代理人）不是簽核人** | 代理人接手工作，簽核人決定准不准。流程的 resolver 不該指向它 |

第三項容易混淆——兩者都是「請假時相關的人」，但語意完全不同。

#### 發布時檢查業務物件是否已定義（2026-09-18 完成）

`validate_draft` 與 `publish` 現在都會檢查 `is_known()`，
未定義時回報警告。**警告不擋下發布**——新業務物件尚未定義時仍應可用，
否則使用者要先請人幫他建 JSON 定義才能做事，與「使用者自己是 Owner」
的定位衝突。

回應多了 `warnings` 欄位，與 `errors` 分開：

```jsonc
// 驗證
{ "valid": true, "warnings": ["業務物件「expense_claim」尚未定義，…"] }

// 發布（成功，但帶警告）
{ "id": "...", "version": 3, "warnings": ["…"] }
```

畫面用琥珀色 banner 顯示（`warning-banner`），與紅色的錯誤區分——
紅色代表「不能發布」，琥珀色代表「可以發布但你該知道」。

**警告也記進稽核**，事後查得到哪些流程是在沒有 E012 保護的狀態下
發布的。

**表單也有同樣的檢查**，但理由不同。表單不會引用路徑，沒有靜默跳過
簽核的風險；它的問題是**欄位的 `data.path` 決定日後流程能引用什麼**。
路徑寫成 `quotation.total_amount`（舊名稱）時表單本身能用，
但流程的條件式 `quotation.total > x` 會取不到值——而這要等流程跑起來
才會發現。所以表單回報兩種警告：

| 警告 | 時機 |
|------|------|
| 業務物件未定義 | 日後建流程時路徑不會被檢查 |
| 欄位路徑不在正式定義 | 流程的條件式可能引用不到 |

第二種只檢查屬於該業務物件的路徑（`quotation.*`）。表單引用其他物件
的資料（例如 `customer.name`）是正常的，不該警告。

這解決了[待處理問題清單 §5](../../實踐規劃/總結/202609/02_待處理問題清單.md)
記錄的項目。

## 5. 環境注意事項

### 5.1 `rtk` hook 會無聲弄壞 `cargo`

全域 `rtk` hook 把 `cargo` 改寫成 `rtk cargo`，但佔住程序卻不 spawn
真正的 cargo：輸出 0 bytes、沒有 `target/`、在
`~/.cargo/.package-cache` 留下 stale lock 讓後續 build deadlock。

最難查的是 `ps aux | grep cargo` 也被過濾成空的，看起來像「沒在跑」。

**繞法**：用絕對路徑 `~/.cargo/bin/cargo`。
卡住時用 `lsof ~/.cargo/.package-cache` 找持鎖的 PID。

同一個 hook 也吃掉 vitest/playwright 的輸出，
改讀 `web/.vitest/json/output.json` 或
`~/Library/Application Support/rtk/tee/*.log`。

### 5.2 interop 測試需要 Python Worker

`cargo test --workspace` 的 `temporal-client` interop 測試
需要 Worker 推進流程。只起 Temporal 不夠，
要 `./start_service.sh` 全部起來。

本文 §1 的「Rust 178 無法複驗」就是這個原因。

### 5.3 其他

| 項目 | 手冊寫的 | 實際 |
|---|---|---|
| PostgreSQL | 17 | **16.13**（migration 與 RLS 九項全過）|
| seed 順序 | seed → 啟動 | **相反** |
| seed 內容 | 含流程定義 | **不含**，見 §3.1 |

### 先前「04 卡住」的原因（已釐清）

從**畫面**建單時，主管簽核的待辦落在 `designer` 而非 `cfo`。
先前判斷是「組織結構 seed 沒設好」，**那是誤判**。

查證後：`sales` 的主管確實是 `designer`，組織結構是對的。

```
sales@demo.local     → 主管: designer@demo.local
designer@demo.local  → 主管: cfo@demo.local
```

resolver 是 `manager_of`（發起人的主管）。用 API 建單時發起人是
`designer`（主管是 cfo），從畫面建單時發起人是 `sales`（主管是
designer）——**是我的腳本假設錯了，不是資料錯了**。

這件事寫進操作手冊 05 當教學點：
「換別人送簽，第一關就會是別人的主管」。

## 8. 給接手者

前一輪的機器交出了一份高品質的總結，特別是抓到**兩份交接文件都沒涵蓋
的設計問題**（WF-E012 的路徑真相來源不能是表單定義）。
那個發現直接改變了實作方向。

值得沿用的兩個做法：

**不確定的事寫進待處理清單交給分派者，不順手修。**
`cargo fmt` 79 處與 clippy 86 處被刻意留著，理由是「混在功能改動裡
會讓 review 無法分辨，也讓 git blame 失真」——這個判斷正確。

**flake 不用加 timeout 掩蓋。** `auth-navigation` 間歇失敗
（57/1 → 58/0 → 單獨 22/22）被如實記錄並判定為既有競態，
沒有動手「修好」它。加長 timeout 只會把競態藏到 CI 上再爆。

另外：**看到「已宣告但沒人用」的欄位值得查一下**。
`ValidationContext.known_paths` 就是前人留了地基卻沒接線，
前一輪才接上。類似的可能還有。
