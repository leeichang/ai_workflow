## 2. 使用者要的是什麼

原話（2026-09-17）：

> 執行時可以直接由系統依據目前的系統角色設定解析出實際簽核的人員，
> 測試的人可以直接點選模擬這個人簽核，系統依據權限設定顯示每個
> 簽核人員的畫面，讓使用者模擬簽核！一一完成後最後整個流程完成！

拆開來是三件事：

| # | 要求 | 意思 |
|---|------|------|
| 1 | **真的解析簽核人** | 用當前的角色與組織設定跑 resolver，不是假資料 |
| 2 | **一人扮演所有角色** | 不換身分登入，點選就切換扮演對象 |
| 3 | **看到那個人會看到的畫面** | 欄位可見性依被扮演者的角色重算 |

第 2 點是關鍵轉變：**沙箱不是另一個環境，是一個附身模式**。
先前規劃過「複製使用者帳號、測試者換身分登入」，使用者的描述
否定了那個方向——不必複製 user 主檔，一人就能走完五關。

## 4. 各階段的重點

完整設計在 [03_沙箱架構交接](03_沙箱架構交接.md)，這裡只列容易做錯的。

### 4.1 P3 表單版本鎖定（1 天）

`workflow_instance` 已鎖定流程版本，表單沒有：

```sql
alter table workflow_instance
  add column form_version_id uuid
      references form_definition_version(id) on delete restrict;
```

用 `on delete restrict` 與 `workflow_version_id` 一致——
進行中的單所依賴的定義不該被刪除。

規劃見[前置改動實踐規劃](../../實踐規劃/規劃/202609/01_前置改動實踐規劃.md)。

### 4.2 S0 流程監控（5 天）

選單新增「流程監控」。**唯讀是硬性要求**——不提供任何修改定義的入口，
只有一個「進入編輯開發模式」的按鈕。

要注意的：

| 項目 | 說明 |
|------|------|
| API 可能不足 | `GET /instances` 現有回傳未必含節點歷程與待簽人，要確認 |
| 權限分級 | 一般使用者只看自己的、主管看部門、admin 看全部 |
| **監控不是權限後門** | 表單資料一樣要吃 `readable_roles`。薪資、成本在監控畫面同樣要遮蔽 |

### 4.3 S1 開發模式基礎（4 天）

影子租戶。**現有系統已經幫你做好大部分隔離**：

| 機制 | 沙箱要改嗎 |
|------|-----------|
| RLS（九項隔離測試通過）| **不用** |
| `tenant_tx()` 單一進入點 | **不用** |
| `workflow_id::build` 已含 tenant 前綴 | **不用** |
| `workflow_id::belongs_to` 歸屬檢查 | **不用** |

建一個沙箱租戶，資料隔離就自動成立。**不需要在任何查詢加
`where is_sandbox = false`。**

要新增的：

```sql
alter table tenant
  add column parent_tenant_id uuid references tenant(id),
  add column is_sandbox boolean not null default false,
  add column expires_at timestamptz;
```

加上 `sandbox_session` 表。**主檔複製不含 user**——測試者不換身分。

`is_sandbox` 的取得方式：**由 `tenant_tx()` 回傳時帶上**，
不要各處自己查 `tenant` 表。那也讓「忘記判斷 is_sandbox」更難發生。

### 4.4 S2 模擬簽核（1.5 週）

本批的核心。四個容易做錯的地方：

#### ⚠️ 簽核 API 的授權要開洞，但條件必須寫死

`server/crates/http-public/src/tasks.rs:134`：

```rust
let is_assignee = task.assignee_user_id == Some(actor.user_id);
```

模擬時測試者不是 assignee，會被擋。必須開洞，而**開洞的地方正是
安全邊界**：

```rust
// 條件嚴格且寫死：
//   1. 必須是沙箱租戶
//   2. 操作者必須是該沙箱的建立者本人
//
// 不做成「有某個角色就能扮演」——那會變成正式環境的提權路徑。
// 沙箱身分不是一種權限，是一種環境狀態。
let is_simulation = tenant.is_sandbox
    && sandbox_session.created_by == actor.user_id;
```

**要有回歸測試**：正式租戶的非 assignee 必定被擋，任何角色組合都不例外。
防止日後有人為了方便把條件放寬。

#### ⚠️ 權限判定要複用後端，且要帶真實 data

判定邏輯在 `domain::permission::resolve_form()`
（`server/crates/domain/src/permission.rs:68`），**不是前端**。
前端的 `usePermissionPreview.ts` 只有 97 行，是 API 呼叫殼。

P2 已經讓預覽 API 支援 `instance_id`（帶入真實單據資料），
模擬要用那個能力——不帶的話 `visibility.when` 依賴欄位值的欄位
全部判錯，而沙箱的整個價值就是「看到的畫面與那個人會看到的一樣」。

#### ⚠️ 稽核要同時記兩個身分

```jsonc
{
  "actor_id": "測試者的 uuid",     // 真正按下按鈕的人
  "acting_as": "張文華的 uuid",    // 扮演的對象
  "is_simulation": true
}
```

只記 `acting_as` 的話，稽核會顯示張文華核准了某張單，而他根本不知道。
沙箱裡雖無害，但**兩套稽核語意會讓程式碼分岔**。

`acting_as` 目前**不存在**（`grep acting_as server/crates/` 零命中），
要新建。`AuditEvent::actor()` 現在收 `(id, name)` 兩個參數。

#### ⚠️ 通知照常寄出，但改寄測試者

使用者的決定（D-07d）：

```
收件人：李一昌 <測試者的信箱>        ← 不是原收件人
標題：【沙箱模擬】【待辦提醒】報價單 QT-... 待簽核

──────────────────────────────
這是沙箱模擬的通知，不是真實待辦。
原收件人：張文華 <cfo@demo.local>
解析依據：resolver role = cfo
──────────────────────────────
```

**照常寄出而非攔截**，理由是驗證得到「信真的送達」——
攔截只驗證到「系統決定要寄給誰」，收件人 email 打錯不會發現。

實作位置：`internal.rs:408`（`resolve_recipients` 之後、
`subject_of` 之前）。**在寄送端做，不在呼叫端**——
`send_notification` 有五個呼叫點，靠每處記得處理遲早漏一個。

## 6. 測試要求

沿用專案標準。特別要測的：

| 層 | 內容 |
|----|------|
| **隔離測試** | **最重要**。沙箱單據不出現在正式租戶的任何查詢，**雙向都要測** |
| 授權 | 正式租戶的非 assignee 必定被擋（任何角色組合）|
| 稽核 | 同時含 `actor_id` 與 `acting_as` |
| 權限 | 扮演不同角色時欄位可見性正確切換 |
| 通知 | 標題有前綴、寄到測試者、原收件人在內文 |
| E2E | 完整模擬流程，**附截圖** |

隔離測試要覆蓋的查詢面（比照既有九項 RLS 測試）：

```
待辦列表  單據列表  報表統計  稽核查詢
Temporal 實例查詢   通知收件人解析   流程監控清單
```

**雙向都要測**——單向會漏掉「開發租戶看得到正式單據」。

### E2E 的 teardown

本輪剛解決 E2E 自我毒化（見
[03_流程0到1與E2E健康度總結](../../實踐規劃/總結/202609/03_流程0到1與E2E健康度總結.md)）。

**模擬的 E2E 會建立沙箱租戶，那也要收。** `support/instances.ts`
的模式可以延伸——但沙箱租戶的清理比實例複雜，
`audit_event` 外鍵是 `RESTRICT` 不是 `CASCADE`。

建議：沙箱租戶的稽核可以刪（非真實業務行為），
但 `sandbox_session` 要保留「某人在某時建過沙箱」這件事。

## 7. 要避免的方向

| 不要做 | 理由 |
|--------|------|
| 模擬做成「簡化版預覽」 | 使用者無法驗證流程真的會怎麼跑，功能失去價值 |
| 讓測試者換身分登入扮演 | 使用者要的是點選扮演，不是登入五次 |
| 用假資料解析簽核人 | 這個功能的價值就在真實解析 |
| 模擬畫面重寫權限判定 | 複用 `domain::permission::resolve_form()` |
| 把授權開洞做成可配置的角色 | 正式租戶誤給就開放冒名簽核 |
| 稽核只記 `acting_as` | 會變成「張文華核准了他不知道的事」 |
| 同租戶加 `is_sandbox` 過濾 | 漏一個查詢就靜默洩漏 |
| 沙箱信不寄只攔截 | 驗證不到信真的送得到 |

## 9. 一件本輪發現、你可能會遇到的事

### 登入耗時的量測結果不一致

前一輪在他們機器上量到 `/auth/login` 穩定 2.0～2.5 秒，
據此把登入斷言放寬到 15 秒（commit `f028bb2`，後被 merge 捨棄）。

**本機重新量測是 543ms**（5 次樣本：591、548、485、545、544）。
差了四倍。

可能是機器效能差異、當時有負載累積（那次量測在 teardown 之前）、
或 argon2 參數在不同環境的表現不同。

**建議**：接手後自己量一次再決定要不要放寬。
`loginAndWait()` 的設計思路是對的——只放寬登入那一段，
不調高全域 `expect` timeout（後者會讓真正的失敗慢 3 倍才回報）。
但 15 秒這個數字要依你的實測調整。

commit `f028bb2` 還在歷史裡，需要時可以取回實作。
