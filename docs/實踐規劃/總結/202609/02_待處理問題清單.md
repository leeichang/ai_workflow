### 1.2 `cargo clippy`（86 處）

```bash
cd server && cargo clippy --all-targets
```

| 位置 | 處數 | 類型 | 建議 |
|---|---|---|---|
| `crates/temporal-client/.../api.rs` | 80 | doc list 縮排 | **不要修**。這是 protobuf 產生的檔案，改了下次重產又回來。應加 `#![allow(clippy::doc_lazy_continuation)]` 或在 build script 抑制 |
| `crates/domain/src/permission.rs:11` | 1 | doc list 縮排 | 修 |

| 其餘 | 3 | doc 相關 | 修 |

`cargo clippy --fix` 可自動處理多數項目，但**產生檔案那 80 處要用
allow 而非修改**，否則每次重產 protobuf 都會復發。

### 為何本批不修

跑 `cargo fmt` 會一次改 18 個檔案、79 處，**其中絕大多數與本批改動無關**。
那會讓 review 無法分辨「哪些是功能改動、哪些是排版」，
也會讓 `git blame` 失真。

已確認**本批新增的程式碼本身是 rustfmt-clean 與 clippy-clean 的**：

- rustfmt：新增區段在 `workflow_validator.rs` 的 68、676、714、766 行
  與 1343 行之後，而回報的 15 處全落在 150～1312 之間，無一重疊
- clippy：回報的位置全在 `temporal-client` 的產生檔、
  `domain/src/permission.rs`（本批未改動）與既有測試檔

### 建議做法

**單獨一個 commit**，訊息寫明「僅排版，無行為變更」，
且**不與任何功能改動混在一起**。做完之後建議加上
PostToolUse hook 或 CI 檢查，避免再度累積。

## 2. `auth-navigation` E2E 間歇性失敗

測試：**「切換帳號後顯示對應的人與角色」**
（`web/e2e/auth-navigation.spec.ts:275`）

```
expect(locator).toHaveText(expected) failed
Locator: getByTestId('user-name')
Expected: "陳雅婷"
Error: element(s) not found
```

### 觀察到的行為

| 執行方式 | 結果 |
|---|---|
| 全量 E2E 第一次 | 57 通過 / **1 失敗** |
| 全量 E2E 第二次 | **58 通過 / 0 失敗** |
| 單獨執行該檔 | 22 通過 / 0 失敗 |

同樣的程式碼，結果不同——是競態，不是功能壞掉。

### 已排除的原因

- 本批改動全在後端 validator 與預覽 API，未觸及登入、路由守衛或 session
- Playwright 依檔名順序執行，`auth-navigation` 排在本批新增的
  `dsl-path-validation` **之前**，新測試不可能污染它

### 推測

交接手冊 §12 已記錄同類症狀：

> E2E 逾時在第二次登入 — 已登入時 guard 會把 `/login` 導回首頁。
> 換帳號前先清 session

該測試正是在換帳號。推測是登出與重新登入之間，
`user-name` 元素在畫面重繪的空檔查不到。

### ⚠️ 修的時候請注意

**不要用加長 timeout 解決。** 那只是把競態藏起來，
之後會在 CI 上以更難查的形式重現。

應該改成等一個明確的就緒訊號（等 `user-name` 出現而非等固定時間），
或在測試間顯式清除 session。

## 3. `seed` 不建立流程定義（高）

交接手冊 §7 說兩個 seed 腳本會建立「報價單表單與**簽核流程定義**」。
**實際上只建表單。**

後果：`web/e2e/task-approval.spec.ts` 的 **6 個測試全部回 404**
（`POST /instances` 找不到 `quotation_approval`），
訊息是「啟動流程失敗」，看起來像服務沒起來，但六個服務其實都正常。

### 修法

seed 之後從 fixture 註冊並發布：

1. `POST /workflows`，body 取自
   `schemas/fixtures/quotation_approval_v1.json`，組成
   `{workflow_key, business_object, name, description, content: <整份 fixture>}`
2. `POST /workflows/quotation_approval/draft/publish`

兩步都需要 `designer` 角色。**建議直接寫進 `seed-demo.sh`**，
否則每次重建環境都會踩到。

### 附帶：seed 的執行順序也與手冊相反

兩個 seed 腳本都會 `curl` 打 `/auth/login` 與 `/forms`，
所以**必須先 `./start_service.sh` 再 seed**，
與手冊 §7 → §8 的順序相反。手冊需更正。

## 4. 業務物件欄位命名不一致（高，需決策）

同一個 `business_object = quotation` 的兩張表單，**13 條路徑只有 3 條重疊**：

| 概念 | `server/seed.sh` 的表單 | `schemas/fixtures/quotation_form_v1.json` |
|---|---|---|
| 總計 | `quotation.total_amount` | `quotation.total` |
| 內部備註 | `quotation.internal_notes`（複數）| `quotation.internal_note`（單數）|
| 毛利率 | `quotation.gross_margin` | `quotation.margin_rate` |
| 客戶 | `customer.name` / `customer.tax_id` | `quotation.customer_party_id` |

### 為什麼這是問題

條件式 `quotation.total > x` 在不同表單建立的單據上**行為不一致**——
一邊取得到值，一邊取到 null 被當成 false。
這與 WF-E012 要擋的靜默失敗是同一類問題，只是發生在資料層而非定義層。

### 本批的處理與未決事項

`schemas/business-objects/quotation.json` 已**採用 fixture 的命名**
（`total`、`internal_note`、`margin_rate`）作為正式名稱，
並在檔案的 `notes` 欄位記錄舊名稱與不收錄的理由。

**但 `server/seed.sh` 內嵌的表單尚未同步。** 需要決定：

1. 確認正式名稱是否就是 fixture 那套（本批的假設）
2. 決定 `seed.sh` 的表單要改名、還是標記為「示範用的簡化表單」
3. 若已有正式環境資料使用舊名稱，需要資料遷移計畫

**這項需要業務決策，不能由開發端單方面決定。**

## 5. 業務物件漏登記會靜默失去 WF-E012 保護（中）

`known_paths` 為空集合代表「不檢查」
（沿用 `known_roles` / `known_actions` 的既有慣例）。

目前只有 `quotation` 與 `purchase_request` 有定義。
**新增業務物件時若忘記登記，該業務物件的所有流程就沒有 E012 保護，
且沒有任何警告。**

這正是 E012 本身要擋的那類靜默失敗，只是換了一層。

### 修法

`server/crates/domain/src/business_object.rs` 已提供 `is_known()`，
但發布路徑（`workflows.rs` 的 `publish` / `validate_draft`）尚未使用它。

建議：發布時若 `business_object` 沒有定義，**明確回報警告**
（不一定要擋下發布，但要讓使用者看見）。

## 6. E2E 自我毒化：每跑一次環境就更慢（高）

> **2026-09-18 更新**：原本記為「測試資料只增不減（中）」。
> F2 那批實測後升級為**高**——它不只是佔空間，而是讓測試套件
> 逐漸失去可信度。

### 實測證據

同一份程式碼、同一台機器，連續三次全量 E2E：

| 次序 | 耗時 | 結果 |
|---|---|---|
| 第一次 | 403 秒 | 60 / 3 |
| 第二次 | 437 秒 | 62 / 1 |
| 第三次 | **1348 秒** | 61 / 2 |

**6.7 分鐘 → 22 分鐘，超過 3 倍**，且每次失敗的是不同的測試。

### 原因

測試會啟動流程但**不會跑完**。流程停在人工節點後，
那個 Temporal workflow 永遠活著並持續輪詢。

```
COMPLETED:  6
RUNNING:   73     ← 永遠不會結束
```

每跑一次全量 E2E 就永久增加約 10 個。Worker 要服務的執行數只增不減。

### 這解釋了先前被當成「flake」的現象

- 測試報告 12 §4.4 的「切換帳號」間歇失敗
- F2 那批 `task-approval` 第一次 211 秒失敗、稍後 76 秒全過

**不是多個獨立的競態，是同一個負載問題。**

### 修法

測試加 teardown，結束時取消自己啟動的流程
（`POST /instances/{id}/cancel` 已存在），或套件結束時統一清理。

**不要用加長 timeout 解決**——那只會讓 22 分鐘變 30 分鐘。

清理既有殘留時注意兩件事：

1. Temporal 端要一起處理，只刪 DB 列會製造孤兒
   （已發生過：34 個執行中只有 6 個有 DB 列）
2. `audit_event` 外鍵是 `RESTRICT` 不是 `CASCADE`，刪租戶會被擋。
   這是刻意設計，清理時要顯式決定稽核留不留

### 原本記錄的部分（仍然成立）

交接手冊 §4 階段 B-2 已記錄：574 個測試租戶、634 筆稽核事件、992 個使用者。

本批的整合測試同樣每跑一次就新建一個租戶，會持續累積。

### 難點

`audit_event` 的外鍵是 `RESTRICT` 不是 `CASCADE`，刪租戶會被擋。
**這是刻意設計**（稽核軌跡不該因上層刪除而消失），
清理時要顯式決定稽核留不留。

### 建議

整合測試加 teardown，或寫一支以租戶名稱白名單為界的清理腳本
（測試租戶的 code 有 `perm-` 等前綴可辨識）。

## 8. `rtk` hook 弄壞 `cargo`（高，環境問題）

**這不是專案程式碼的問題，但會嚴重拖慢開發。**

全域 `rtk` hook 把 `cargo` 改寫成 `rtk cargo`，但 rtk 佔住程序卻
**從未 spawn 真正的 cargo 子程序**：

- 輸出檔 0 bytes，沒有 `target/` 目錄
- 在 `~/.cargo/.package-cache` 留下 stale lock，讓後續 build 互相 deadlock
- `ps aux | grep cargo` 也被 rtk 過濾成空的，看起來像「沒在跑」

最後一點最難查——要用 `lsof ~/.cargo/.package-cache` 才看得到程序確實存在。

### 繞法

```bash
/Users/leeichang/.cargo/bin/cargo build --bin api
```

絕對路徑可繞過 hook 的比對。若已卡住，用
`lsof ~/.cargo/.package-cache` 找出持鎖的 PID（`ps -p <pid>` 才看得到），
全部 kill 後再重跑。

### 同一個 hook 也影響測試輸出

`vitest` 與 `playwright` 的輸出會被吃掉（顯示
`vitest parser: All parsing tiers failed`）。
改讀 JSON report（`web/.vitest/json/output.json`）
或 rtk 自己的 tee 日誌（`~/Library/Application Support/rtk/tee/*.log`）。

### 建議

請調整 hook 設定，或把 `cargo` 從 rtk 的攔截清單移除。
這個失敗模式是無聲的，新接手的人會浪費大量時間才找到原因。

### 9.2 PUBLISHED 版本需要 `published_at`

`wf_published_has_version` 約束（`migrations/0004:51`）要求
`status = 'PUBLISHED'` 時 `version` 與 `published_at` 都不可為 NULL。

測試輔助函式漏了 `published_at` 會在插入時才爆，
錯誤訊息只有約束名稱，不看 migration 不知道缺什麼。
本批已在測試註解標明。
