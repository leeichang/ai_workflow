## 2. 本輪最有價值的產出：E2E 不再自我毒化

這不在交辦清單裡，是追查「測試到底有沒有過」時挖出來的。

### 現象

同一份程式碼、同一台機器，連續三次全量 E2E：

| 次序 | 耗時 | 結果 |
|---|---|---|
| 第一次 | 403 秒 | 60 / 3 |
| 第二次 | 437 秒 | 62 / 1 |
| 第三次 | **1348 秒** | 61 / 2 |

**6.7 分鐘變成 22 分鐘**，而且每次紅的是不同測試。

### 原因

測試會啟動流程，但**不會把它跑完**——停在人工節點之後沒有人去簽，
那個 Temporal workflow 就永遠活著並持續輪詢。
每跑一次全量永久增加約 7 個。

### 修法與驗證

`web/e2e/support/instances.ts`：追蹤測試啟動的實例，
`afterAll` 用 `POST /instances/{id}/cancel` 收掉。

**用 cancel 而非直接刪資料庫是關鍵。** 那支端點會送取消請求給 Temporal，
由 workflow 自己清理待辦與稽核後回報最終狀態。
直接刪 DB 列會留下 Temporal 孤兒——驗證 seed 時就製造過 28 個。

清理失敗刻意不影響測試結果：清理是衛生工作不是被測行為，
一個清理失敗蓋掉真正的測試結果會更難查。

連續兩次全量驗證：

```
Temporal 執行中    28 → 28     ← 沒有增加
demo 租戶 RUNNING   0 →  0     ← 沒有增加
```

同時清掉既有積壓 34 個，Temporal 執行數 62 → 28。

**最終：1348 秒 → 210 秒，63 全過。**

### 補漏：`manual-04-endtoend` 也在漏

merge 之後跑全量，發現 demo 租戶又多了 2 個 RUNNING，
單號是 `QT-<時間戳>`——不是 `task-approval` 的命名。

追出來是遠端補進來的 `manual-04-endtoend.spec.ts`。
它**從畫面建單**，所以拿不到 instance id，只知道自己填的單號。

因此在 `support/instances.ts` 加了 `cancelByBusinessKey()`：
列出實例再比對單號。用 list 而非查詢參數，
是因為 `GET /instances` 目前沒有依 `business_key` 過濾的能力。

驗證：執行前 demo RUNNING 0 → 執行後 0，Temporal 維持 28。

**教訓**：teardown 要涵蓋**每一個會建實例的 spec**，
新增 spec 時容易漏掉。判斷方式是跑完看一眼
demo 租戶的 RUNNING 有沒有回到 0。

## 3. 三個更正

本輪推翻了三個先前文件裡的判斷。記錄下來避免再繞一次。

### 3.1 交辦 §6 說組織結構要修，其實不用

交辦寫「主管簽核的待辦落在 `designer` 而非 `cfo`……
組織結構 seed 需要確認」。

查證後組織結構是**正確**的：`sales → designer → cfo`。
節點的 resolver 是 `manager_of(initiator)`，解析的是**發起人的主管**：

| 建單者 | 解析出的簽核人 | 對不對 |
|---|---|---|
| `designer`（API 測試）| `cfo` | ✅ |
| `sales`（畫面操作）| `designer` | ✅ |

**兩者都對。** 要修的是 `manual-04` 腳本的預期，不是 seed。
本輪未改 seed。

### 3.2 「E2E 58」的基線不成立

F1 把選單從 `/designer/forms/quotation_form` 改成清單頁，
但沒有更新 `auth-navigation.spec.ts` 的三條斷言。

```
git diff 6eccf90^ 6eccf90 -- web/src/components/AppShell.vue
  → 確認 F1 改了 path，且該 commit 未觸及 auth-navigation.spec.ts
```

**其中兩條在本輪之前就已經是紅的。** 交辦 §1 的「E2E 58」
是 F1 之前的數字，F1 之後沒有重跑全量。

### 3.3 登入的間歇失敗——這一條我原本也判斷錯了

> **2026-09-18 更正。** 本節原本主張「根因是 argon2 讓登入穩定要
> 2.0～2.5 秒，5 秒的 expect 餘裕不足」。**那個測量值是錯的。**

原本的量測：

```
2.002s  2.483s  2.306s  2.070s  2.463s
```

**但那是在 load 24.6、Temporal 積壓 62 個 workflow 的環境下量的**——
也就是 §2 那個還沒修的自我毒化問題。**量測本身被要修的問題污染了。**

teardown 修完、積壓清掉之後（load 8.45）重測：

```
1.011s（冷啟）0.463  0.477  0.780  0.472  0.465  0.483  0.475
中位數約 475ms
```

另一台機器獨立量到平均 543ms，與此一致。**差了四倍。**

#### 更正後的結論

登入的間歇失敗**不是** argon2 慢，**就是 §2 的負載問題**，
不是獨立的第二個原因。

所以 `loginAndWait()` 其實是多餘的——merge 捨棄它之後
另一台機器 74/74 全過，正是因為那台機器沒有積壓，本來就沒有餘裕問題。

它的**設計思路仍然成立**（只放寬登入那段、不調全域 `expect` timeout），
若日後真的遇到餘裕不足可以取回（commit `f028bb2`），
但 **15 秒這個數字是從污染的量測來的，要依當下實測重訂**。

#### 教訓

**在退化的環境裡量效能，量到的是退化本身。**
先確認環境健康（見 §8 的檢查指令）再量，否則會像這次一樣
把一個原因說成兩個，還附上四倍失真的數字。

## 4. 量測時踩到的 RLS 陷阱

追查過程中一度把數字報錯，值得記下來。

`psql -d workflow` 用的是作業系統帳號（**superuser**），
而 superuser 完全繞過 RLS——即使下了 `set app.tenant_id` 也沒有作用，
查到的是**所有租戶**的資料。

```
不過濾（實為全部 210 個租戶）   流程定義 300、RUNNING 40
明確 where tenant_id = demo    流程定義 254、RUNNING  0
```

**查租戶資料要顯式寫 `where tenant_id = ...`**，
不能依賴 `set app.tenant_id`——那只對 `workflow_app` 角色有效。
這正是 migration 刻意讓應用程式用非 superuser 連線的理由。

要解需先決定產品行為：

- 使用者能不能刪流程定義？
- 已被實例引用的定義怎麼辦？（FK 是 `restrict`，刪不掉）
- 軟刪還是硬刪？稽核怎麼留？

**這需要業務決策。**

## 8. 給下一棒

**先補 P3，再進 S0。** P3 會改 `workflow_instance` 的 schema
與建立實例的寫入點，而 S0 流程監控要顯示「當時那版表單」，兩者相接。

**跑 E2E 之前先看一眼積壓。** teardown 已經接上，正常情況不會再累積。
但若發現全量執行明顯變慢，先查：

```bash
docker exec temporal-temporal-1 temporal workflow count \
  --address temporal:7233 --query "ExecutionStatus='Running'"
```

健康值約 28（都是孤兒）。明顯超過就是有地方沒收乾淨。

**別用加 timeout 解決慢。** 本輪整批「慢」與「間歇失敗」
最後都收斂到**同一個原因**：負載累積。

我一度以為有第二個原因（argon2 讓登入要 2.5 秒），
那是在退化環境下量錯的——見 §3.3。收掉垃圾之後登入只要 475ms。

**量效能之前先確認環境健康**，否則會把一個原因說成兩個。
而無差別加長全域 timeout 一個都解決不了，只會讓真正的失敗
更慢才被發現。
