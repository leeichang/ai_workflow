## 3. 第二階段的起點：兩個洞

09-17 下午開始分兩條線。當時的系統雖然跑得完整條流程，
但有兩件事要等到上線才會知道。

### 3.1 A 線要解的：它不知道「人」是誰

`app_user` 只有 email、姓名、密碼、部門、主管五個欄位。
這帶來三個具體問題：

1. **產線作業員進不來**。他們不用電腦、不需要帳號，但可能是
   別人的主管、可能要被指派待辦。`password_hash` 是 `not null`，
   沒有密碼就建不了這個人
2. **沒有員工編號**。客戶的人事系統用工號當主鍵，平台沒有對應的
   欄位，兩邊的資料永遠接不起來
3. **組織錯了沒人知道**。某個人沒有主管，流程會卡在「找不到簽核人」——
   但那要等到他第一次送單才會發現，而那通常是上線日

第三點是 A 線最大的主題。

### 3.2 B 線要解的：流程設計對不對，上線前驗證不了

要驗證一條含三關簽核、兩天逾時的流程，得真的找三個人、真的等兩天。
所以設計錯誤都拖到正式上線才發現——與 §3.1 的第三點是同一種病。

#### 階段一：資料模型（migration 0009）

| 改動 | 為什麼 |
|---|---|
| `password_hash` 轉 nullable + `can_login` | 產線作業員要存在但不登入 |
| `employee_no`、`job_title`、`hired_at`、`left_at` 等 | 對得上客戶的人事系統 |
| `platform_managed_fields` | **這是整個同步機制的地基**，見 §5.2 |
| `sync_status` | 來源查不到的人標記而非刪除 |
| `employee` view | 對外用 EIG 的詞彙，實體仍是 `app_user`，Resolver 零改動 |

安全處理：登入流程**顯式檢查 `can_login`**，不依賴「有 hash 就能登入」
的隱含假設。資料庫有約束擋住不一致狀態，但約束是最後防線不是唯一防線。
不可登入時回「帳號或密碼錯誤」而非「此帳號不可登入」——後者會洩漏
email 是否存在。

#### 階段二：組織健康檢查（A14）

回答一個問題：**哪些人現在送單會卡住？**

八項檢查，每一項都對應到 `participant.rs` 裡某個 resolver 的失敗路徑。
**不是照需求文件抄的**——先讀 resolver 的 SQL，得到三個與文件不同的結論：

- **多一項**：`department_manager_of` 有 `m.id <> u.id`（避免自己簽自己），
  後果是**部門主管本人送單時解析回空**。文件沒列這項，而實機資料證實
  它是 demo 租戶最多的一種問題（5 次）
- **一項性質不同**：`manager_of` 的 join 完全不看主管狀態，
  主管離職不是「解析失敗」而是「解析出一個收不到信的人」——
  流程照走、通知照寄到停用信箱，永遠沒人處理
- **少一項**：文件列的「email 重複」是死碼。`app_user` 有
  `unique (tenant_id, email)`，重複在資料庫層就進不來

實機驗證抓到 demo 租戶 **11 個 HIGH**。

#### 階段三：組織管理 UI（A15）

部門樹、員工清單與編輯，並把健康檢查串起來——報表每一筆都有
「前往修正」，點了直接開那個人的編輯。

核心是**欄位級 ownership**（§5.2）。

#### 階段四：CSV 匯入與同步（A16、A17）

完整的管線：Parse → Map → Validate → Upsert，含完整性閘與計數契約。

三個縮減都在 UI 與 API 明講，不靜默失敗：

- 只做 CSV 不做 xlsx（上傳說明寫「Excel 請另存為 CSV UTF-8」）
- 只做員工不做部門（API 回「目前只支援員工資料的同步」）
- 不建 Raw Layer（P1 的原始檔案本身就是 raw layer）

排程同步**刻意不做**：FILE connection 的資料來源是「管理員上傳的
檔案」，沒有檔案時排程無事可做。等 REST connection 才有意義。

#### 為什麼需要這個

客戶導入時要驗證流程設計對不對，得真的找五個人、真的等兩天逾時。
那不可行，所以流程設計的錯誤都拖到正式上線才發現。

#### 核心設計：沙箱不是另一個環境，是附身模式

測試者**不換身分登入**，點一下就以某個人的身分簽核。

| 元件 | 做法 |
|---|---|
| 沙箱租戶 | `tenant.is_sandbox`，複製主檔資料進去 |
| 授權 | 寫死兩個條件：必須是沙箱租戶、操作者必須是建立者本人 |
| 稽核 | 同時記 `actor_id`（真正按按鈕的人）與 `acting_as`（被扮演的人） |
| 通知 | 收件人改寫成測試者，標題加【沙箱模擬】前綴 |

授權條件**刻意不做成角色**：

> 不做成「有某個角色就能扮演」——那會變成正式環境的提權路徑。
> 沙箱身分不是一種權限，是一種環境狀態。

稽核記兩個身分也是同樣的謹慎：只記 `acting_as` 的話，
稽核會顯示張文華核准了某張單，而他根本不知道有這回事。

#### 實機走查：一人走完兩關

```
以 designer@demo.local 全程操作，不換身分登入

待簽：主管簽核 → 張文華（真實 resolver 解析，不是假資料）
以張文華簽核 APPROVE
  ↓ discount_gate 判定 0.2 > 0.15，走財務加簽分支
待簽：財務簽核 → 李淑芬
以李淑芬簽核 APPROVE
  ↓
待簽：客戶簽核 → c@example.com
```

#### 四項收尾（B15）

| 項目 | 關鍵決定 |
|---|---|
| **權限過濾畫面** | 角色取**被扮演者**的，不是測試者的。取錯的話流程照樣會動、測試照樣全綠，但模擬出來的畫面與那個人真正簽核時看到的不同，功能就失去意義 |
| **平行分支模擬** | 種子裡沒有 parallel 節點，先補了一條會簽流程。分支資訊從 DSL 推導而非另存狀態——「兩份狀態就有兩份要對帳」 |
| **時間快轉** | 走**真正的逾時策略**，不假造決策。假造 APPROVE 會讓模擬顯示「通過了」，而正式環境設的 `AUTO_REJECT` 其實是退回——那比不給快轉更糟，使用者會帶著錯誤的結論上線 |
| **流程監控** | 原本 `GET /instances` 只靠 RLS，而 **RLS 隔離的是租戶**，同租戶的人看得見彼此每一張單。加了 `visible_to` 過濾 |

時間快轉的授權擋**兩層**：HTTP 與 Workflow Signal。
Signal 是能繞過 HTTP 的介面，而快轉會讓單據在沒人簽的情況下前進。
`is_sandbox` 預設 `False` 代表既有的執行中實例也一併受保護。

流程監控的 `visible_to` 刻意做成 `Option` 而非 `bool + user_id`：
呼叫端必須明確表態「不設限」，**漏傳會變成看得到全部**，
那正是要避免的方向。單筆查詢回 **404 而非 403**——
403 等於告訴對方「這張單存在」。

#### 那一台修掉的四個設計錯誤

四個都是**只有實機操作才會發現**的，單元測試全綠時它們都在：

| # | 問題 | 為什麼單元測試看不出來 |
|---|---|---|
| 1 | 主檔複製靜默失敗 | 沒設 `app.tenant_id` 時 RLS 讓來源 SELECT 回 0 筆，`INSERT ... SELECT` 插入 0 列**且沒有錯誤**。沙箱看起來建好了，裡面卻沒有人 |
| 2 | id 沿用來源值會撞鍵 | `app_user.id` 是全域主鍵 |
| 3 | 授權模型一開始就錯 | 測試直接呼叫函式沒經過登入。畫面上才看到「只有建立者可以模擬簽核」——**建立者反而進不了自己的沙箱** |
| 4 | 少了在沙箱啟動測試單的入口 | `POST /instances` 用 `actor.tenant_id`，測試者得登入沙箱才能啟動流程，又與「不換身分」矛盾 |

第 1 個是本專案最討厭的那類失敗——**沒有錯誤訊息的失敗**。

#### 那一台誠實記下的兩個「沒驗證到」

## 5. A 線：三個值得記住的設計決定

### 5.1 健康檢查對齊 resolver，不對齊文件

檢查邏輯與 `participant.rs` 的 SQL 一一對應。兩邊不一致的話，
**報表會說一切正常而流程照卡**——那比沒有報表更糟。

這個原則讓我們抓到需求文件漏掉的第八項檢查。

### 5.2 欄位級 ownership 是同步機制的地基

需求 D-14 說「ERP 優先、平台補缺」。要讓這句話成立，
同步時必須知道**哪些欄位不准碰**。

典型情境：ERP 的 `manager_id` 有 300 人沒維護，管理員在平台補上。
沒有 `platform_managed_fields` 的話，下一次同步會把這 300 筆沖掉。

實作上這變成一個 API 設計決定：PATCH 帶**明確的欄位清單**
而非「有值就改」。

```json
{ "fields": ["manager_id"], "manager_id": null }
```

兩個理由：`Option<T>` 無法表達「把主管清成空」（送 null 與不送
反序列化後都是 None）；而 `fields` 同時就是要鎖定的欄位清單，
兩件事合一不必推導。

### 5.3 完整性閘是整個同步最危險的判斷

需求的原話：

> 來源 1000 人，API 只回 823 人，若直接刪 177 人，
> 其中只要有一個是主管，**全公司相關流程立刻卡死**

三個判斷：

- 用**通過驗證的筆數**比較，不是讀到的筆數。一份格式全壞的檔案
  讀得到 1000 列卻一筆都寫不進去，那跟「來源只回 100 筆」一樣危險
- 首次匯入不比較（`NULL` 與 `0` 是不同的意思）
- 中止時什麼都不寫，**包含不更新比較基準**

後來定案 Q-02 時改成「比例**且**絕對值」雙條件——只看比例的話，
50 人的公司走掉 6 人就誤觸發，而管理員被擋下之後只能調高門檻，
**調高之後保護就變弱了**。

## 6. B 線：兩個值得記住的設計決定

### 6.1 授權條件寫死成「環境狀態」而非角色

模擬簽核必須在 `tasks.rs` 的 assignee 檢查上開一個洞——
測試者不是 assignee。而開洞的地方正是安全邊界。

條件寫死成兩個，**都不是角色**：必須是沙箱租戶、
操作者必須是該沙箱的建立者本人。

> 不做成「有某個角色就能扮演」——那會變成正式環境的提權路徑。

那幾條授權測試**刻意複寫一份條件**而非呼叫實作——
條件被偷改時測試與實作會分歧而爆出來。

其中 `production_tenant_never_allows_simulation` 是最重要的一條：
正式租戶不論操作者是誰、任何角色組合都被擋。

### 6.2 快轉要走真正的策略，不假造決策

`skip_time` Signal 把等待視為已到期，讓**真正的逾時處理**執行，
與真的等到逾時走同一條路。

假造一個 APPROVE 會讓模擬顯示「通過了」，
而正式環境設的 `AUTO_REJECT` 其實是退回——
**那比不給快轉更糟**，使用者會帶著錯誤的結論上線。

Python 測試直接釘住這件事：`test_AUTO_REJECT_快轉後是退回而非通過`。
快轉若假造決策，這條會變成通過。

這個設計還有個副作用——它第一次上工就抓到 `sales_director` 掛 0 人
（見 §7 的 #6）。**模擬在驗證 resolver 設定對不對，而那個設定是錯的。**

## 7. 第二階段抓到的真 bug（六個）

這些都不是測試沒過才發現的，是實機驗證或寫測試時發現的。

| # | 問題 | 怎麼發現的 | 後果 |
|---|---|---|---|
| 1 | 欄位對應把「部門名稱」對成員工的 `name` | 寫了臨時 probe 去驗，發現先前測試通過是巧合 | 整份人員名單的姓名欄被寫成部門名，而同步回報成功 |
| 2 | `miss_count` 永遠停在 1 | 測試抓到 | 需求 §7 規則 3 的「連續 N 次」完全失效 |
| 3 | 消失的人回來後卡在 `MISSING_IN_SOURCE` | 修 #2 時想到 | 永遠留在待停用清單，管理員最後真的會把他停用 |
| 4 | 匯入精靈每次都建新 source | 寫 E2E 時撞唯一約束 | 新 source 沒有比較基準，**完整性閘永遠不生效**——最糟的失效方式，因為它安靜 |
| 5 | seed 的表單定義從來沒套用過 | 查 N4 時發現資料庫欄位名與 seed.sh 不同 | **表單定義的任何修改都不會套用到既有環境** |
| 6 | `sales_director` 掛 0 人 | 另一台的模擬功能第一次上工就抓到 | 逾時加簽靜默不發生，Worker 只留一行 WARNING |

第 5 個最值得說：N4 回報的是「種子表單沒有 `readable_roles`」，
但實際上 `seed.sh` 裡**一直都有**。沒生效是因為 seed 只用
`POST /forms` 建立，表單已存在就撞唯一約束、印 `CONFLICT` 跳過，
接著把舊草稿發布出去。`readable_roles` 只是第一個被發現的受害者。

第 6 個修法不只是補 seed——補 seed 只解決 demo 租戶。
真正的問題是**這類錯誤沒有人會發現**，所以加了
`ROLE_HAS_NO_MEMBERS` 健康檢查，掃所有已發布流程的角色引用。

這六個裡有四個屬於同一類：**沒有錯誤訊息的失敗**。
主檔複製插入 0 列、完整性閘永遠不生效、表單定義從來沒套用、
逾時加簽靜默不發生——共同點是系統回報成功，而事情沒有發生。

本專案反覆遇到這類問題，所以這週兩條線都在同一個方向上加東西：
A 線加健康檢查讓設定錯誤上線前看得到，
B 線加模擬讓流程設計上線前跑得完。

9 人、6 部門、0 來源、0 待停用。
