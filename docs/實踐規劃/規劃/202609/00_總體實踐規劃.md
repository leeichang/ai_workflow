### 3.1 為什麼 P1 排最前

WF-E012 同時是 AI 線（[02 §4.1](../../../交接手冊/202609/02_AI產生表單與流程交接.md)
標為「阻斷性」）與沙箱線（[03 §7 階段 -1](../../../交接手冊/202609/03_沙箱架構交接.md)）
的前置。

它擋住的風險是**靜默的**：條件式路徑打錯 → 求值取不到 → 當成 false →
少走一段簽核 → 高折扣報價單不經財務就發給客戶，且無任何錯誤訊息。

人工編輯時使用者至少會看 JSON；AI 產生時不會。**沙箱也救不了它**——
模擬簽核走的是同一條求值路徑，錯誤的條件式在沙箱裡一樣靜默跳過，
測試者只會看到「流程跑完了」。

所以 P1 不能靠 S2 兜底，必須先做。

### 3.2 為什麼 P2 擋住 S2 而非 S0

流程監控（S0）顯示表單資料時有真實單據，但它是**唯讀且以當前使用者
身分**檢視，走既有路徑即可。

模擬簽核（S2）要以**被扮演者的角色**重算可見性，且有真實單據。
預覽 API 目前傳空 `data`，`permission.rs:193` 的 `eval_bool`
求值不到 `visibility.when` 依賴的欄位值，凡是條件顯示的欄位全部判錯。

沙箱的整個價值是「看到的畫面與那個人會看到的一樣」，這一判錯
價值歸零。所以 P2 是 S2 的硬前置。

### 3.3 為什麼 P3 排在沙箱之前

`workflow_instance` 已鎖定流程版本（`workflow_version_id`，
`on delete restrict`），**表單沒有對應欄位**。

沙箱與 AI 都會大量改表單定義。不先補上，進行中的實例會抓到新版表單——
欄位被刪、必填變選填、權限改動都會直接影響還沒簽完的單。

而且需求 03 §3.5 宣稱「進行中的實例不受還原影響」，
在沒有表單版本鎖定的前提下**那個宣稱目前不成立**。

## 5. 本批的執行原則

### 5.1 前置階段（P1～P3）先全部做完再進 S0

三項前置各自獨立、都不大，但**都會改到後續階段依賴的介面**：

- P1 改 validator 的規則集與 `GraphError` 的產生條件
- P2 改預覽 API 的簽章（加可選參數）
- P3 改 `workflow_instance` 的 schema 與建立實例的寫入點

先做完再往下，避免 S0/S1 寫到一半又回頭改介面。

### 5.2 安全邊界的改動要有回歸測試

兩處改動是安全邊界，**放寬容易、收回難**：

| 改動 | 風險 | 必要的回歸測試 |
|---|---|---|
| S2 簽核 API 授權開洞 | 正式租戶冒名簽核 | 正式租戶的非 assignee**任何角色組合**都被擋 |
| S1 沙箱通知改寫 | 沙箱信被當真待辦去簽 | 五個 `send_notification` 呼叫路徑**每一個**都有前綴與收件人改寫 |

這兩項的測試要在**實作之前**寫（RED），防止日後有人為了方便放寬條件。

### 5.3 不重複既有機制

交接文件反覆強調的一點，實作時逐條對照：

| 既有機制 | 不要做的事 |
|---|---|
| `domain::permission::resolve_form()` | 模擬畫面重算一份權限判定 |
| `workflow_validator.rs` | 為 AI 另寫一套 validator |
| `schemas/form.schema.json` | 為 AI 另訂一套 DSL |
| RLS + `tenant_tx()` | 用 `where is_sandbox = false` 過濾 |
| 既有 renderer / designer | 讓 AI 產生 Vue 程式碼或座標 |

### 5.4 實機驗證的權重高於加測試

專案已有 754 個測試，但 SMTP 欄位漏傳、`N_OF_M` 預設值、
截圖搶跑全是實機操作才發現的。

本批特別容易出現「測試綠但功能錯」的兩處：

- **LLM 功能的 mock**：mock 回傳的永遠是你寫的那個完美 JSON，
  測不到真實模型的畸形輸出
- **沙箱通知**：mock 驗到「有呼叫 `send_notification`」就算過，
  但前綴與收件人改寫是否生效只有真的寄一封信才知道

每階段驗收都要有實機步驟，不只跑測試。
