### P1.1 現況查證

交接文件把這項描述成「要新增一條規則」。實際查證後，**地基已經鋪好但從未接線**：

| 項目 | 現況 | 位置 |
|---|---|---|

| `known_paths` 的使用處 | **零**。宣告後全專案未被讀取 | — |
| `with_paths()` builder | 不存在（只有 `with_roles` / `with_actions`）| `workflow_validator.rs:49` |

`known_paths` 欄位直接使用，不需新增資料結構。

### P1.2 ⚠️ 未解決的設計問題：路徑的真相來源

**這是本階段唯一需要決策的事，且會影響工作量級距。**

資料庫**沒有**業務物件結構定義表（查 `\dt` 無 business/object/schema 相關表）。
路徑目前只在表單欄位的 `data.path` 宣告。

**但表單不能當真相來源**，因為同一個 `business_object` 可以有多張表單，
而實測顯示**它們的路徑詞彙互不相容**。

`business_object = quotation` 目前有兩張表單，實測比對：

```
只在 seed.sh 的表單          只在 fixture 的表單
  customer.name                quotation.number
  customer.payment_terms       quotation.valid_until
  customer.tax_id              quotation.customer_party_id
  quotation.total_amount   ←→  quotation.total
  quotation.internal_notes ←→  quotation.internal_note
  quotation.gross_margin   ←→  quotation.margin_rate
                               quotation.customer_contact_ids
                               quotation.subtotal
                               quotation.payment_terms
                               quotation.attachments

兩者都有（僅 3 條）
  quotation.currency   quotation.discount_rate   quotation.lines
```

同一個業務物件的「總金額」在一張表單叫 `total_amount`、另一張叫 `total`；
「內部備註」一張是 `internal_notes`（複數）、另一張是 `internal_note`（單數）。

**後果**：若 `known_paths` 取自表單，
則「取哪一張」會改變驗證結果——取 seed 的表單，
fixture 流程的 `quotation.customer_contact_ids` 驗不過；
取 fixture 的表單，則 seed 那張表單自己的欄位驗不過。
取聯集則等於不檢查拼錯字（`internal_note` 與 `internal_notes` 都合法）。

這決定性地說明：**路徑的真相來源必須獨立於任何一張表單。**

#### 三個選項

| 選項 | 做法 | 工作量 | 風險 |
|---|---|---|---|
| **A. 新增業務物件結構定義** | 建 `business_object_schema` 表或 JSON，明確宣告每個業務物件的所有欄位 | 大（migration + 維護介面 + 既有資料補登）| 正確但拖慢前置階段 |
| **B. 表單路徑取聯集** | 同 business_object 的所有表單路徑取聯集 | 小 | **不可行**。上面的實測顯示聯集會讓 `internal_note` 與 `internal_notes` 都合法，等於不檢查拼錯字——而拼錯字正是 E012 要擋的東西 |
| **C. 分級：表單有的報 error，其餘報 warning** | 找不到就標為 warning 不擋發布 | 小 | **等於沒解決**——靜默問題變成沒人看的警告 |

#### 建議：A，但拆成兩步

**理由有兩層**。

其一，B 與 C 都被上面的實測否決：B 的聯集讓拼錯字合法，C 等於不解決。

其二，選項 A 是 AI 產生器**本來就需要**的東西。
[02 AI 交接 §4.2](../../../交接手冊/202609/02_AI產生表單與流程交接.md) 要求
「產生的 DSL 只能引用該租戶已存在的 `business_object`、`role`、`form_key`」——
沒有業務物件的結構定義，AI 無從知道 `quotation` 有哪些欄位可用。
若讓 AI 從表單反推，它會同時看到 `total` 與 `total_amount` 而不知道該用哪個，
正是上面實測顯示的問題。

**拆法**：

- **P1a（本階段）**：建立業務物件結構定義，
  先以 `schemas/business-objects/*.json` 檔案形式存在，不進資料庫。
  E012 讀它。
- **P1b（A4 之前）**：需要多租戶自訂時再搬進資料庫。

檔案形式足以擋住 E012 要擋的錯誤，且不阻塞前置階段。
P1a 的結構定義本身即是 P1b 的資料來源，先做不會白費。

**副產物**：建立 `quotation` 的結構定義會迫使我們決定
`total` 與 `total_amount` 到底哪個是正式名稱。
這個歧義目前散落在兩張表單裡沒人發現，
而它會讓條件式 `quotation.total > x` 在不同表單的單據上行為不一致。

> **待使用者確認**：若偏好直接進資料庫（跳過 P1a 的檔案階段），
> 工作量由 1 天增為 3 天，且需設計維護介面。本規劃先按 P1a 進行。

### P1.3 實作

**規則定義**

| 碼 | 檢查 | 觸發條件 |
|---|---|---|
| WF-E012 | 條件式與 resolver 引用的資料路徑存在於業務物件結構定義 | `known_paths` 非空時才檢查（沿用既有慣例，空集合代表不檢查）|

**要收集的路徑有兩類**，`collect_expressions` 只涵蓋第一類：

| 類別 | 來源 | 現有函式是否涵蓋 |
|---|---|---|
| 表達式內的路徑 | `condition.expression`、resolver `cel` / `when`、`timeout.to` | ✅ `collect_expressions` |
| resolver 的 `path` 欄位 | `external_contacts` 等 resolver 的 `path` | ❌ **要新寫 `collect_data_paths`** |

第二類是 `quotation.customer_contact_ids` 那種，取不到值會讓流程
`NoParticipants` → FAILED。雖然是明確失敗（比靜默跳過安全），
但在發布前擋下來仍優於上線後第一張單卡住。

**從表達式抽路徑**

表達式是 CEL 片段（如 `quotation.discount_rate > 0.15`）。
`expression_parses()` 的註解已載明「完整 CEL 解析排在任務 2.2」，
目前只做括號與單等號的粗略檢查。

E012 同樣**不做完整 CEL 解析**，只用正規表示式抽出
`識別字(.識別字)+` 形態的 token，再排除 CEL 內建函式與字面值。
理由與 `expression_parses` 一致：**看不懂的一律放行**，
避免誤擋合法但複雜的表達式。誤擋會讓使用者無法發布正確的流程，
比漏擋更快失去信任。

**檔案改動**

| 檔案 | 改動 |
|---|---|
| `crates/domain/src/workflow_validator.rs` | 加 `with_paths()` builder；加 `collect_data_paths()`；加 E012 規則區塊 |
| `crates/persistence/src/workflow.rs` | `load_validation_data()` 回傳值加第三個元素 `paths` |
| `crates/http-public/src/workflows.rs` | `publish` 的 `ValidationContext` 串上 `.with_paths()` |
| `schemas/business-objects/quotation.json` | 新增。業務物件結構定義 |

### P1.4 測試（先寫，確認 RED）

| 層 | 測試 |
|---|---|
| 單元 | `known_paths` 為空 → 不檢查（回歸，保護既有行為）|
| 單元 | 條件式引用不存在的路徑 → 回 WF-E012 |
| 單元 | 條件式引用存在的路徑 → 通過 |
| 單元 | resolver `path` 引用不存在的路徑 → 回 WF-E012 |
| 單元 | 打錯字的近似路徑（`discount_rat`）→ 回 WF-E012 |
| 單元 | CEL 內建函式（`has()`、`size()`）不被誤判為路徑 |
| 單元 | 字面值與數字不被誤判為路徑 |
| 整合 | 發布含錯誤路徑的流程 → API 回 400 並含 WF-E012 |
| 整合 | **現有 `quotation_approval_v1.json` 補登後通過驗證**（回歸）|

最後一項特別重要：這份 fixture 是 E2E 的基礎，
若 E012 讓它驗不過，51 個 E2E 會連鎖失敗。

### P1.5 驗收

- 條件式引用不存在的路徑時，發布 API 回 400 並指出是哪個節點的哪條路徑
- 既有的 51 個 E2E 全數仍通過
- `cargo test` 全綠

## P2　權限預覽 API 支援真實 data

### P2.1 現況查證

`crates/http-public/src/permissions.rs:187`：

```rust
let empty = Value::Object(Default::default());
let ctx = Context {
    node_id: q.node_id.as_deref(),
    roles: &roles,
    participant_kind: &q.participant_kind,
    data: &empty,        // ← 寫死
};
```

設計器預覽時沒有實際單據，空物件合理。
但 `domain/src/permission.rs:193` 的 `eval_bool` 會用 `data` 求值
`visibility.when` 的條件式——模擬簽核有真實單據，傳空的會全部判錯。

### P2.2 實作（選項 A：擴充既有 API）

採 [D-07 前置條件 2](../../../需求規劃/202609/02_決議紀錄.md) 的建議，
**不另開端點**，理由是兩條路徑要維持一致的成本高於加一個可選參數。

```
GET /forms/{form_key}/permissions/preview
    ?roles=...&node_id=...&participant_kind=...
    &instance_id=<uuid>        ← 新增，可選
```

行為：

| `instance_id` | `data` 來源 |
|---|---|
| 未傳（設計器）| 空物件，**行為與現在完全相同** |
| 有傳（模擬簽核）| 該實例的業務資料 |

**授權**：`instance_id` 指向的實例必須屬於當前租戶。
RLS 已保證這點（查詢走 `tenant_tx`），但仍要顯式處理「查無此實例」
回 404 而非默默退回空物件——**默默退回空物件會讓模擬畫面判錯而無人察覺**，
正是本專案一再踩到的靜默失敗類型。

### P2.3 測試

| 層 | 測試 |
|---|---|
| 單元 | 不傳 `instance_id` → `data` 為空物件（回歸）|
| 整合 | 傳 `instance_id` → `visibility.when` 依賴欄位值的欄位判定正確 |
| 整合 | 傳不存在的 `instance_id` → 404，**不是**空物件 |
| 整合 | 傳他租戶的 `instance_id` → 404（RLS 擋下）|

### P2.4 驗收

- 設計器預覽行為不變（既有測試全綠）
- 帶 `instance_id` 時，條件顯示欄位的判定與真實簽核畫面一致

## P3　表單版本鎖定

### P3.1 現況查證

`workflow_instance` 已鎖定流程版本：

```sql
-- migrations/0005_workflow_instance.sql:21
workflow_version_id uuid not null
    references workflow_definition_version(id) on delete restrict,
```

**表單沒有對應欄位。** 查證方式與結果：

```
grep form_version_id migrations/*.sql
  → 唯一命中是 0002:91 的錯誤訊息字串，不是欄位

psql \d workflow_instance
  → 有 workflow_version_id，無 form_version_id
```

確認交接文件的描述正確。

### P3.2 實作

```sql
-- migrations/0006_form_version_lock.sql
alter table workflow_instance
  add column form_version_id uuid
      references form_definition_version(id) on delete restrict;

comment on column workflow_instance.form_version_id is
  '實例建立當下的表單版本。與 workflow_version_id 同樣用 restrict——
   進行中的單所依賴的定義不該被刪除';
```

**可為 NULL**，理由：既有實例沒有這個值，設 `not null` 會讓 migration
無法套用到既有資料。新建的實例一律填入。

**寫入點**：建立實例時解析 `business_object` 對應的當前發布表單版本。
一個業務物件可能有多張表單（實測 `quotation` 有 39 張，多數是測試殘留），
需要決定綁哪一張——建議由流程 DSL 的 `trigger` 指定 `form_key`，
若未指定則不填（維持現狀，不擋流程啟動）。

**讀取點**：渲染實例的表單資料時改用 `form_version_id` 指向的版本，
而非當前發布版本。

### P3.3 ⚠️ 影響範圍比「加個欄位」大

讀取點分散在 Rust 與 Python 兩端，且模擬簽核與流程監控都會用到。
本階段**只做 schema 與寫入**，讀取點改用鎖定版本排在 S0，
理由是 S0 的流程監控是第一個真正需要「看到當時那版表單」的功能。

### P3.4 測試

| 層 | 測試 |
|---|---|
| 單元 | 建立實例時填入當前發布的表單版本 |
| 單元 | 流程 DSL 未指定 `form_key` → `form_version_id` 為 NULL，流程照常啟動 |
| 整合 | 已被實例引用的表單版本無法刪除（`restrict` 生效）|
| 整合 | 既有實例（`form_version_id` 為 NULL）不受影響 |

### P3.5 驗收

- migration 可套用到含既有資料的資料庫
- 新建實例有 `form_version_id`
- 刪除被引用的表單版本被資料庫擋下
