## 1. 現況查證

### 1.1 API 回傳不足以支撐詳情頁

交接手冊 §2.1 說「要確認回傳內容是否足夠，不足就補」。**查證結果：不足。**

`InstanceDetail`（`http-public/src/instances.rs:43`）只有攤平的
`WorkflowInstance` 加一個 `live_status`。而 `WorkflowInstance` 的欄位是：

```
id  workflow_version_id  business_object  business_key
temporal_workflow_id  temporal_run_id  status
input  output  error  started_by  started_at  ended_at
```

詳情頁需要而**目前沒有**的：目前節點、已完成節點、待簽核人、各節點耗時。

這是 S0 的實質工作量所在，也是本文把交接估計的 3 天調整為 5 天的理由。

### 1.2 好消息：節點歷程可從 `human_task` 組出

`human_task` 表已含詳情頁所需的全部欄位：

```
instance_id  node_id  node_label
assignee_user_id  assignee_role  participant_kind
status  decision  comment
due_at  created_at  decided_at  decided_by
```

且已有 `human_task_instance_idx (instance_id, node_id)` 索引，
查某實例的所有節點不需新增索引。

### 1.3 ⚠️ 限制：非人工節點沒有執行記錄

`human_task` 只記人工節點。`condition`、`action`、`notification`、
`parallel`、`join` 的實際走向**不在任何資料表**。

後果：流程圖要標示「已走過的路徑」時，人工節點標得出來，
分支條件實際走了哪一邊標不出來。

#### 三個選項

| 選項 | 做法 | 代價 |
|---|---|---|
| **A. 查 Temporal Event History** | 由 Temporal 取得完整執行軌跡 | 需擴充 `temporal-client`；受 retention 限制（預設 30 天）|
| **B. 新增 `instance_node_log` 表** | Worker 走過每個節點時寫一筆 | 多一次寫入；但不受 retention 限制，且可查詢可統計 |
| **C. 第一版只標人工節點** | 分支走向以「下游有無 human_task」推斷 | 推斷不出沒有人工節點的分支 |

**建議 C 先上、B 補完**：

- C 足以支撐第一版的驗收（使用者要看的主要是「卡在誰那裡」）
- B 是正解但會改到 Python Worker 的每個節點處理路徑，
  與 S1/S2 的改動重疊，放在一起做較省
- A 受 retention 限制，而 `temporal/README.md` 已註明
  「長流程（報價往返可能數週）需確認 retention 大於最長流程週期」——
  拿它當監控畫面的唯一資料來源會在長流程上失效

> **待使用者確認**：第一版接受「分支走向只標人工節點」嗎？
> 若要求完整軌跡，S0 增加 2 天並需改動 Python Worker。

## 2. 要做的

### 2.1 API 擴充

```
GET /instances                     既有，擴充回傳欄位
GET /instances/{id}                既有，擴充回傳欄位
GET /instances/{id}/nodes          新增，節點歷程
```

**清單回傳新增**（由 `human_task` 聚合）：

| 欄位 | 來源 |
|---|---|
| `current_node` | `human_task` 中 status=PENDING 的 node_label |
| `current_assignees` | 同上的 assignee 解析後姓名 |
| `elapsed` | `now() - started_at`（由前端格式化）|
| `is_overdue` | 存在 `due_at < now()` 的 PENDING 待辦 |

**避免 N+1**：清單頁一次查 N 筆實例時，
`human_task` 用單一 `where instance_id = any($1)` 批次取回，
不要每筆實例各查一次。這是本專案 code-review 標準列的項目。

**節點歷程回傳**：

```jsonc
{
  "nodes": [
    { "node_id": "manager_approval", "node_label": "主管簽核",
      "status": "COMPLETED", "decision": "APPROVE",
      "assignee": { "id": "...", "name": "張文華" },
      "comment": "同意", "created_at": "...", "decided_at": "...",
      "duration_seconds": 3600 }
  ],
  "join_progress": [
    { "node_id": "join_1", "policy": "N_OF_M", "n": 2,
      "completed": 1, "total": 3 }
  ]
}
```

### 2.2 前端

選單新增「流程監控」。

**清單**：業務物件／單號、流程定義＋版本、目前節點、待簽核人、
狀態、已耗時、發起人／發起時間。
篩選：狀態、流程定義、日期區間、是否逾時。

**詳情**：

- 流程圖，標出已走過的節點與目前位置（受 §1.3 限制）
- 每個節點的簽核記錄（誰、何時、核准／退回、意見）
- 目前待辦的對象與到期時間
- 平行分支各 branch 狀態與 join 進度
- 表單資料（唯讀，依當前使用者權限顯示）
- **唯一的出口**：「進入編輯開發模式」按鈕

流程圖複用既有的 `WorkflowDesigner` 佈局邏輯，
但以唯讀模式渲染——**不要另寫一套繪圖**。

### 2.3 表單資料用鎖定版本渲染

P3 已加上 `form_version_id`。監控詳情頁是第一個真正需要
「看到當時那版表單」的功能，讀取點改用鎖定版本在此階段完成。

`form_version_id` 為 NULL 的既有實例退回當前發布版本，並在畫面標註。

## 3. 權限（硬性要求）

### 3.1 可見範圍三級

| 角色 | 看得到 |
|---|---|
| 一般使用者 | 自己發起的、自己簽過的 |
| 主管 | 部門內的 |
| admin | 全部 |

### 3.2 監控不是權限後門

表單資料的欄位顯示要吃既有的 `readable_roles`。
**不能因為是「管理功能」就顯示所有欄位**——薪資、成本、毛利率
在監控畫面一樣要遮蔽。

判定一律複用 `domain::permission::resolve_form()`，
不在監控端重算。理由與
`usePermissionPreview.ts` 檔頭註解相同：判定邏輯只該有一份，
兩份必然漂移，而漂移的症狀是「畫面說看得到、實際查詢被擋」。

## 4. 測試

| 層 | 測試 |
|---|---|
| 單元 | 節點歷程聚合：多節點、含平行分支、含退回重跑 |
| 單元 | 耗時計算：未結束的實例、已結束的實例 |
| 契約 | 清單批次查 `human_task` 不產生 N+1 |
| 整合 | 一般使用者看不到別人發起的實例 |
| 整合 | 主管看得到部門內、看不到部門外 |
| 整合 | admin 看得到全部 |
| **整合** | **`readable_roles` 遮蔽的欄位在監控畫面同樣不出現** |
| 整合 | `form_version_id` 有值時用該版本渲染；NULL 時退回當前版本 |
| E2E | 清單篩選、進詳情、看節點歷程，**附截圖** |
| E2E | 詳情頁**沒有**任何修改定義的入口（唯讀回歸）|

倒數第二項是安全測試，倒數第一項是防止日後有人「順手」加編輯功能。

## 5. 驗收

- 選單有「流程監控」，看得到所有執行中流程的清單與詳情
- 一般使用者看不到別人的單
- `readable_roles` 遮蔽正確
- 詳情頁除「進入編輯開發模式」外無任何修改入口
- 實機：建一張報價單走到財務簽核，監控畫面顯示「卡在李淑芬」

跑到哪一關」的地方。
