## S1　開發模式基礎

### S1.1 資料隔離：影子租戶，不加過濾條件

採 [D-07b](../../../需求規劃/202609/02_決議紀錄.md) 選項 A。

現有機制已提供隔離，**不需要改**：

| 機制 | 現況（已查證）|
|---|---|
| RLS（`workflow_app` 非 superuser）| 已啟用，九項隔離測試通過 |
| `tenant_tx()` 單一進入點 | `persistence/src/lib.rs:70`，確認所有 DB 存取都經過 |
| `workflow_id::build` | 已含 tenant 前綴 |
| `workflow_id::belongs_to` | 已實作歸屬檢查 |

建一個開發租戶，隔離自動成立。**不需要在任何查詢加
`where is_sandbox = false`**——每處查詢都要記得過濾，漏一個就靜默洩漏，
與「條件式路徑打錯靜默跳過簽核」同一類問題。

### S1.2 Schema

```sql
-- migrations/0007_sandbox.sql
alter table tenant
  add column parent_tenant_id uuid references tenant(id),
  add column is_sandbox boolean not null default false,
  add column expires_at timestamptz;

create table sandbox_session (
    id                uuid primary key default uuid_generate_v4(),
    tenant_id         uuid not null references tenant(id),  -- 來源租戶
    sandbox_tenant_id uuid not null references tenant(id),  -- 開發租戶
    change_request_id uuid,
    created_by        uuid not null,                        -- 測試者
    status            text not null default 'ACTIVE'
                      check (status in ('ACTIVE','RESET','EXPIRED','DISCARDED')),
    created_at        timestamptz not null default now(),
    expires_at        timestamptz not null
);
```

### S1.3 `tenant_tx()` 帶上租戶屬性

採 [D-07d](../../../需求規劃/202609/02_決議紀錄.md) 選項 A。

現況：`tenant_tx(tenant_id) -> Result<TenantTx>`。
要讓 `TenantTx` 帶上 `is_sandbox` 等屬性，使呼叫端不必各自查 `tenant` 表。

**這是影響所有呼叫端的改動**，也是本階段估計由 3 天調為 4 天的理由。
但選這個做法的理由正是：在單一進入點取一次，
「忘記判斷 `is_sandbox`」這種錯誤就更難發生。

實作時保持 `TenantTx` 既有方法簽章不變，只新增欄位與 getter，
避免 15 個稽核呼叫點與所有查詢同時要改。

### S1.4 主檔複製（不含 user）

複製：`role`、`department`、業務物件定義、主檔（部門、客戶等）。
**不複製 `app_user`**——測試者不換身分（[D-07c](../../../需求規劃/202609/02_決議紀錄.md)）。

複製後跑冒煙測試：對每個流程節點跑一次 resolver，
解析不到人就在建立沙箱時就報錯，而不是等模擬到一半才 FAILED。

### S1.5 通知改寫（§5，最容易漏的地方）

兩件事，**都在寄送端做**，插入點 `internal.rs:408`
（`resolve_recipients` 之後、`subject_of` 之前）：

1. **標題加前綴** `【沙箱模擬】`
2. **收件人一律改成測試者**，原收件人寫進內文

```rust
// 沙箱的信一定要能一眼認出來，且不能真的寄給同事——
// 對方收到「【沙箱模擬】待簽核」很可能還是會點進去簽。
// 前綴與改寫都在寄送端做，不靠呼叫端記得傳：
// send_notification 有五個呼叫路徑（human_task 建立、提醒、
// 逾時、ESCALATE、流程結束），靠每處自律遲早漏一個。
const SANDBOX_SUBJECT_PREFIX: &str = "【沙箱模擬】";
```

**稽核記三層**：

```jsonc
{
  "to": ["<uuid>"],                      // 原始參與者 id
  "recipients": ["cfo@demo.local"],      // 解析後的真實收件人
  "actual_recipients": ["tester@..."],   // 沙箱改寫後實際寄達的
  "is_sandbox": true
}
```

只記最後一層就查不出「原本要寄給誰」，而那正是沙箱要驗證的。

**不在 Python Activity 改**：Activity 不該知道沙箱這個概念。

### S1.6 測試

| 層 | 測試 |
|---|---|
| **隔離** | **最重要**。開發租戶的單據不出現在正式租戶的任何查詢 |
| 隔離 | **雙向**：正式租戶的單據也不出現在開發租戶 |
| 隔離 | 覆蓋：待辦列表、單據列表、報表統計、稽核查詢、Temporal 實例查詢、通知收件人解析、流程監控清單 |
| 單元 | 主檔複製範圍（含 role/department，不含 user）|
| **契約** | **五個 `send_notification` 呼叫路徑每一個都有前綴與收件人改寫** |
| 整合 | 沙箱寄出的信標題以「【沙箱模擬】」開頭 |
| 整合 | 沙箱的信一律寄給測試者，原收件人在內文 |
| 整合 | 原收件人 email 無效時，內文照樣顯示它 |
| 整合 | 建立→設計→重置→銷毀完整生命週期 |

倒數第五項是 §5.2 最容易漏的地方，要逐一列舉五個路徑分別測。

### S1.7 驗收

- 建開發租戶，在裡面改表單存檔，正式租戶完全不受影響
- 觸發通知，收到的信標題以「【沙箱模擬】」開頭且**寄到測試者信箱**
- 實機寄一封真的信驗證（不只跑 mock）

## S2　模擬簽核（本批核心）

### S2.1 ⚠️ 安全邊界：簽核 API 授權開洞

**這是整批工作最需要謹慎的地方，且要先做。**

現況（已查證，`http-public/src/tasks.rs:134`）：

```rust
// 驗證這張待辦確實指派給當前使用者。
// RLS 只保證同租戶，不保證是本人——沒有這道檢查，
// 同租戶的任何人都能核准別人的單。
let is_assignee = task.assignee_user_id == Some(actor.user_id);
let has_role = task.assignee_role.as_deref()
    .is_some_and(|r| actor.roles.iter().any(|mine| mine == r));

if !is_assignee && !has_role {
```

模擬簽核時測試者不是 assignee，會被擋。必須開洞，
**但條件寫死，不可做成可配置的權限**：

```rust
// 條件嚴格且寫死：
//   1. 必須是沙箱租戶
//   2. 操作者必須是該沙箱的建立者本人
//
// 不做成「有某個角色就能扮演」——正式租戶誤給該角色
// 等同開放冒名簽核。沙箱身分不是一種權限，是一種環境狀態。
let is_simulation = tx.is_sandbox()
    && sandbox_session.created_by == actor.user_id;
```

**測試先寫（RED），且第一條是永久回歸測試**：

| 測試 | 目的 |
|---|---|
| 正式租戶的非 assignee，**任何角色組合**都被擋 | 防止日後為了方便放寬條件 |
| 沙箱租戶的非建立者被擋 | |
| 沙箱租戶的建立者可扮演任何解析出的簽核人 | |

### S2.2 解析簽核人要真的解析

呼叫既有的 `resolve_participants` activity，用開發租戶裡真實的角色與組織設定。
**不能用假資料**——這個功能最大的價值就是在驗證 resolver 設定對不對。

解析失敗要**明確報錯**，不可跳過或用預設人員頂替：

```
❌ 無法解析簽核人員
   節點：財務簽核
   resolver：role = finance_manager
   原因：此角色沒有指派任何使用者
```

已踩過的坑：`resolver.user_id` 需要 UUID 不是 email，寫錯會讓流程 FAILED。
模擬簽核讓這類錯誤在**上線前**浮現。

### S2.3 權限過濾畫面

切換扮演對象時，欄位依**那個人的角色**重算：

| DSL 欄位 | 效果 |
|---|---|
| `readable_roles` | 不在清單內 → 不顯示 |
| `editable_roles` | 不在清單內 → 唯讀 |
| `external_visible` | 外部客戶節點 → false 的欄位不顯示 |

三態語意（既有規則，不可改）：

```
key 不存在 → 不限制    []  → 全部拒絕    ["a"] → 只有角色 a
```

**呼叫 P2 擴充後的預覽 API 並傳 `instance_id`**，
不傳的話條件顯示欄位全部判錯（見 [前置規劃 P2](01_前置改動實踐規劃.md)）。

**不在模擬畫面重算權限**，複用 `domain::permission::resolve_form()`。

### S2.4 `acting_as` 稽核

已查證：`acting_as` 在 `server/crates/` **零命中**，要新建。
`AuditEvent::actor()` 現收兩個參數（`persistence/src/lib.rs:183`），
稽核呼叫點 **15 處**。

```jsonc
{
  "actor_id": "測試者的 uuid",     // 真正按下按鈕的人
  "acting_as": "張文華的 uuid",    // 扮演的對象
  "is_simulation": true,
  "sandbox_tenant_id": "..."
}
```

只記 `acting_as` 會變成「張文華核准了他不知道的事」。
沙箱裡雖無害，但**兩套稽核語意會讓程式碼分岔**——寧可一開始就一致。

實作方式：新增 `.acting_as()` builder 而非改 `actor()` 簽章，
避免 15 個呼叫點全部要改。

### S2.5 平行分支的模擬

```
並行簽核（join: N_OF_M, n=2）
  ├── 財務  李淑芬   ✅ 已核准
  ├── 法務  王大明   ⏳ 待簽      [ 以王大明簽核 ]
  └── 採購  陳小華   ⏳ 待簽      [ 以陳小華簽核 ]

  進度：1 / 2（再一人核准即通過）
```

這個畫面本身就是 join policy 設定是否正確的驗證工具。

### S2.6 測試

| 層 | 測試 |
|---|---|
| **安全** | §S2.1 的三條，第一條為永久回歸 |
| 單元 | 權限過濾三態 |
| 單元 | resolver 解析失敗 → 明確錯誤，非跳過 |
| 整合 | 稽核同時含 `actor_id` 與 `acting_as` |
| 整合 | 條件顯示欄位在模擬畫面判定正確（依賴 P2）|
| 整合 | 扮演不同角色時可見性正確切換 |
| E2E | 一人走完含平行分支的報價單流程，**附截圖** |

### S2.7 驗收

- 測試者一人從頭走完含平行分支的流程
- 每關看到的欄位與該角色實際會看到的一致
- **正式租戶的非 assignee 仍然被擋**（回歸）

估計 1.5 週。

## S3　時間快轉

含 `timeout` 與 `remind_at` 的流程無法等真實時間（P3D 要等三天）。

提供「快轉到下一個時間點」，觸發最近的提醒或逾時。

Temporal 的 `start_time_skipping()` 已在 Python 測試使用過可評估複用，
但要注意它與 `start_local()` 的行為差異——測試曾因此卡住
（本次環境建置也重現過：time-skipping 會讓等待中的流程瞬間衝到逾時）。

**不阻擋第一版**，估計 3 天。

## 風險對照

| 風險 | 緩解 |
|---|---|
| 沙箱信被當成真待辦 | S1.5 一律改寄測試者 + 標題前綴 |
| 前綴或收件人改寫漏做 | S1.5 都在寄送端做；S1.6 逐一列舉五個路徑測 |
| 主檔複製不完整 → resolver 找不到人 | S1.4 複製後跑冒煙測試 |
| 權限判定兩份而漂移 | S2.3 複用 `resolve_form()` |
| 模擬畫面條件顯示判錯 | 依賴 P2，傳 `instance_id` |
| **正式環境冒名簽核** | S2.1 綁死 `is_sandbox` + 永久回歸測試 |
| 進行中實例抓到新版表單 | 依賴 P3 |
| 租戶數量膨脹 | `expires_at` + 定期回收（已有 574 個測試租戶的前例）|
| 使用者誤判 | 不可關閉的全域開發模式標示 |

清理時注意 `audit_event` 外鍵是 `RESTRICT` 不是 `CASCADE`，刪租戶會被擋。
**開發租戶的稽核可以刪**（非真實業務行為），
但 `sandbox_session` 要保留「某人在某時建過開發模式」這件事。
