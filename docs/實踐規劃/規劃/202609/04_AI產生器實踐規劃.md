- 日期：2026-09-17
- 對應：[總體實踐規劃](00_總體實踐規劃.md) 的 A1～A4
- 依據：[02 AI 交接](../../../交接手冊/202609/02_AI產生表單與流程交接.md)

**唯一不可妥協的原則：AI 是 Compiler，不是 Frontend Developer。**

```
❌  Prompt → AI → Vue template / JavaScript
✅  Prompt → AI → DSL (JSON) → Validator → 既有 Renderer
```

## 2. 前置：WF-E012（阻斷性）

見 [前置改動實踐規劃 P1](01_前置改動實踐規劃.md)。

**不做這個就不要開始接 LLM。** 理由：條件式路徑打錯會靜默當成 false，
流程少走一段簽核而無任何錯誤訊息。人工編輯時使用者至少會看 JSON，
AI 產生時不會。

P1 規劃中發現的問題同樣影響本階段：**業務物件的實際欄位 ⊋ 表單宣告的欄位**
（`quotation.customer_contact_ids` 是執行期帶入、表單未宣告）。
AI 需要知道業務物件有哪些欄位可用，
所以 P1a 的業務物件結構定義檔是 AI 產生器的必要輸入，不只是 validator 的。

## 3. A1　LLM client 介面（1 天）

放在 Python 端（`python-ai/ai/`），理由：LLM SDK 的 Python 生態最成熟，
且 `python-ai` 已是既有的第二語言邊界，不需為此在 Rust 引入新相依。

```
python-ai/ai/
├── client.py        # LLM 呼叫，抽成 Protocol 方便測試
├── form_compiler.py # Prompt → Form DSL
├── flow_compiler.py # Prompt → Flow DSL
├── patcher.py       # 既有 DSL + Prompt → patch operations
└── prompts/         # system prompt 版本化管理
```

抽成 Protocol 的做法參考 `http-public/src/mailer.rs` 的 `Transport` trait——
之後換模型不會動到上層。

**先做一個假實作**供測試使用，真實模型另做實機測試。

### 3.1 模型選擇（未決）

| 選項 | 考量 |
|---|---|
| 雲端 LLM | structured output 成熟，但表單定義含業務資訊 |
| 地端模型 | 資料不出門，但 JSON 穩定度差、硬體成本轉嫁客戶 |
| 混合 | 敏感租戶走地端，複雜度高 |

**建議先用雲端把流程跑通**，介面抽好，之後要換不動上層。

> **待使用者確認**：模型與供應商。這項不擋 A1 的介面設計，
> 但擋 A2 的實機驗證。

## 4. A2　Form 產生（1 週）

### 4.1 做法

1. system prompt——**限制在既有欄位類型內**
2. structured output 直接接 `form.schema.json`，
   **不要讓模型輸出 markdown 再用正規表示式挖 JSON**（失敗模式的溫床）
3. validator repair loop
4. 全新產生（不含 patch）

### 4.2 Repair loop

```
LLM 產生 DSL → validator → valid?
                  │
                  否 → 把 GraphError 清單餵回 LLM 修正（上限 2 次）
                  │         └─ 仍失敗 → 降級成手動編輯，告訴使用者哪裡不合法
                  是 → 進入差異顯示
```

`GraphError` 已定義在 `workflow_validator.rs:22`，直接序列化給 LLM。

**重試上限 2 次**，否則成本失控。

### 4.3 驗收

輸入「建立員工基本資料表單，必填員工編號、姓名、部門、職稱、到職日，
部門用下拉選單」→ 產生合法 Form DSL → 既有 renderer 畫得出來。

## 5. A3　Flow 產生（1 週）

同 A2，接 `workflow-dsl.schema.json`。

**位置交給程式算。** Vue Flow 需要 `position: {x,y}`，
但**不要讓 LLM 產生座標**——它算不準會重疊。
DSL 只描述邏輯（node + edge），前端用 dagre 之類的自動佈局算位置。
這也符合既有設計：`workflow-dsl.schema.json` 本來就不含 position。

### 驗收

輸入「請假流程，員工申請後部門主管審核，核准再由 HR 審核，
任一關拒絕就結束，全部通過通知員工」→ 合法 Flow DSL →
既有 designer 畫得出來 → Temporal 跑得起來。

## 6. A4　Patch 修改（1 週）

第二次以後的修改**必須是 patch，不是全量重產**：

```jsonc
{ "operation": "add_field", "section": "customer",
  "field": { "key": "delivery_site", "component": "input",
             "label": "交貨地點",
             "data": { "path": "customer.delivery_site" } } }

{ "operation": "update_node", "node_id": "manager_approval",
  "changes": { "timeout": { "after": "P2D", "policy": "ESCALATE" } } }
```

理由：

- 全量重產會動到使用者沒改的部分，diff 無法閱讀
- 需求 03 §3.2 要求「用業務語言顯示改了什麼」，patch 天然對應
- 版本歷史要能還原到任一版，patch 讓歷史有意義

### 驗收

對 A2 的表單說「再增加生日和手機號碼」→ 產生 `add_field` patch，
其餘欄位不變。

## 7. 安全：Prompt 注入防範

使用者輸入會進到 prompt，**使用者輸入不受信任**。

最低要求：

- 使用者輸入以**資料**而非指令的形式傳入（分隔標記、明確界線）
- 輸出一律過 JSON Schema 驗證，**不接受 schema 外的欄位**
- 產生的 DSL 只能引用該租戶已存在的 `business_object`、`role`、`form_key`
- **AI 產生的內容永不直接上線**，一律進需求 03 的審核流程
- **AI 產生器的 API 只接受開發租戶 id，傳正式租戶 id 回 400**——
  寫進 API 設計，不靠呼叫端自律

## 8. 測試

| 層 | 測什麼 |
|---|---|
| 單元 | prompt 組裝、patch 套用、repair loop 的分支 |
| 契約 | LLM 畸形輸出：截斷的 JSON、多餘欄位、schema 外的類型 |
| 整合 | 產生的 DSL 存進 `form_definition_version` 後能被既有 API 讀回 |
| E2E | Prompt → 產生 → 預覽 → 存檔，**附截圖** |

**LLM 呼叫一律 mock**，測試不該依賴外部服務也不該花錢。

特別要測的失敗情境：

- LLM 回傳不合法 JSON
- LLM 產生 schema 外的欄位類型（如 `magic_dropdown`）
- LLM 產生引用不存在 role 的 resolver
- **LLM 產生引用不存在路徑的條件式** ← WF-E012 的核心
- repair loop 重試耗盡
- **LLM 回傳空 fields 陣列**——注意 falsy 陷阱，
  寫過 `participants or [DEFAULT]` 導致「沒有參與者」的測試
  實際測了「一個參與者」

### 8.1 mock 的侷限（必讀）

**mock 回傳的永遠是你寫的那個完美 JSON。**

專案已有前例：SMTP 的單元測試驗到「有呼叫 `send_notification`」就算過，
但 Activity 漏傳 `kind` 欄位，信寄出去標題是「【流程通知】」
而非「【待辦提醒】」。**那個錯誤只有真的寄一封信才會發現。**

LLM 功能更容易造成這種假象。**一定要有實機驗證並寫報告。**

## 9. 要避免的方向

| 不要做 | 理由 |
|---|---|
| 讓 AI 直接產生 Vue 程式碼 | §1 |
| 為 AI 新設一套 DSL | 既有的已被生產程式碼使用，兩份會漂移 |
| 換成 FormCreate 的 rule 格式 | 會丟失權限、外部可見性、明細表格、巢狀路徑能力 |
| 讓 AI 決定資料庫 schema | 可提案，但要過命名規則、安全規則、migration engine |
| 讓 AI 產生 Vue Flow 的 position | §5，程式算 |
| AI 產出直接上線 | 一律進審核流程 |
| 新增欄位類型 | 受限生成是輸出可預測的關鍵 |
| AI 產生器直接寫正式租戶 | §7，在 API 層擋 |

### 關於 `form-create-assistant`

**參考它的 AI 互動設計（JSON Patch 增量修改、多模型抽象、system prompt 寫法），
不參考它的資料格式。** 它的 rule JSON 是 FormCreate 專用，
本專案的 `form.schema.json` 已包含權限、外部可見性、明細表格、巢狀路徑——
那些是 ERP 場景必需，FormCreate 沒有。

## 10. 這件事的意義

專案定位是服務**沒有資訊單位的台灣製造業中小企業**，
要讓**使用者自己是 Owner**。

AI 產生 DSL 是這個定位的關鍵一塊——沒有它，使用者面對的還是一個
要懂 JSON 才能改的系統。

但也正因如此，**治理比生成更重要**。AI 產得出來只是開始，
能讓使用者看懂改了什麼、能先試跑（沙箱）、能送審、能還原，才是產品。

這也是本批工作把沙箱排在 AI 之前的理由。
