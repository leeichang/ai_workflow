## 2. Client 呼叫 Server API 單元測試（L3）

`web/tests/api/workflows.test.ts`，以 MSW 攔截 `fetch`，驗證請求格式、
回應解析、錯誤處理與認證標頭四件事。測試設定為
`onUnhandledRequest: 'error'`，任何未攔截的請求都會讓測試失敗，
可防止測試悄悄打到真實網路。

涵蓋的端點與重點：

| 端點 | 測試重點 |
|------|----------|
| `GET /workflows` | `#[serde(flatten)]` 攤平後的 summary 欄位、`Bearer` 標頭 |
| `GET /workflows/{key}` | 草稿與已發布並存、草稿 `version` 為 `null`、key 做 URL 編碼、404 |
| `POST /workflows` | 完整建立請求、缺 `designer` 角色時的 403 |
| `PUT /workflows/{key}/draft` | 包在 `content` 鍵下、斷開的流程也能存 |
| `DELETE /workflows/{key}/draft` | 容許 204 空回應 |
| `POST /.../draft/validate` | 通過時省略 `errors` 鍵、失敗仍回 200 且帶 `node_id` |
| `POST /.../draft/publish` | 回傳版本號、422 時錯誤進 `ApiError.validationErrors` |
| `GET /.../versions` | 版本清單 |

回應結構刻意與後端 `crates/http-public/src/workflows.rs` 及
`crates/persistence/src/workflow.rs` 對齊，後端改欄位時這裡會失敗。

其中兩個約定特別重要：

- **驗證失敗回 200 而非 4xx**。畫布需要完整的錯誤清單來標記節點，
  用錯誤狀態碼表達會讓 client 走到例外分支，處理變複雜。
- **`errors` 為空時整個鍵會消失**（後端 `skip_serializing_if`），
  前端型別必須容忍缺鍵。

## 4. 實機測試發現並修正的缺陷

單元測試全過、型別檢查也過的情況下，實機截圖仍抓到三個問題。
這三個都是「不會拋出例外、只有看畫面才發現」的類型。

### 4.1 工具列被頂部列蓋住

**現象**：工具列的 y 座標是 32，但固定頂部列高 56，工具列整排被蓋掉一半。

**原因**：`AppShell` 的 `main` 用 `p-space-xl` 加 `pt-[56px]` 避開頂部列，
設計器為了佔滿視窗用 `-m-space-xl` 抵銷 padding，卻連上方的 56px
一起抵銷掉了。

**修正**：只抵銷左右與下方。

```
- class="flex flex-col -m-space-xl h-[calc(100vh-56px)]"
+ class="flex flex-col -mx-space-xl -mb-space-xl h-[calc(100vh-56px)]"
```

修正後量測 `工具列 top = 56`、`頂部列 bottom = 56`，恰好貼齊。

### 4.2 condition 的兩個分支標記完全重疊

**現象**：「折扣 > 15%」與「折扣 <= 15%」兩個標記都在 `(996, 509)`，
畫面上只看得到一個。

**原因**：標記位置取自路徑字串的起點 `M x y`。condition 的兩條邊
從同一個節點分岔，起點自然相同。

**修正**：改取路徑的最後一個座標。

### 4.3 改取終點後，四條退回標記又疊在一起

**現象**：修正 4.2 後，四個「退回 / 失敗」標記全部落在 `(1008, 299)`。

**原因**：退回邊的方向與前進邊相反。四個節點都退回同一個
「業務修改報價」節點，終點自然相同。

**修正**：依邊的方向決定取哪一端。

```ts
const p = isReturn ? points[0] : points[points.length - 1]
```

並把這段邏輯抽到 `src/workflow/edgeLabel.ts`，補上 4 個迴歸測試，
包含「任兩個標記不重疊」與「標記不蓋住插入點」兩項幾何檢查。
修正後實測：重疊 0 組、遮蔽插入點 0 組。

**這三個缺陷的共同點**：畫面座標的正確性無法靠型別或既有單元測試守住。
第 4.2 與 4.3 是同一個規則的兩面，只修一邊就會壞另一邊，
因此測試直接斷言「不重疊」這個目的，而非斷言某個座標值。

## 5. 設計決策的落實

### 5.1 固定自動排版（D-03）

依決議不支援自由拖曳，節點位置一律由 `computeLayout()` 決定。
使用者的操作是「在連接線上選一個插入點，再從節點庫選型別」，
節點元件沒有綁定任何拖曳事件。

理由是中小企業的流程多為主幹加分支的受限結構，自由拖曳會讓
不同人畫出風格不一的圖，維護時反而難讀。

### 5.2 兩種控制流的區別

流程有兩種控制流，三處邏輯對它們的處理方式各不相同，
搞錯任何一處都不會報錯，只會讓畫面或驗證悄悄出錯：

| 邏輯 | 是否含 `goto` | 錯誤後果 |
|------|---------------|----------|
| 可達性分析（WF-E002） | **要含** | 只靠 goto 進入的「修改」節點被誤判為孤立 |
| 上游判斷（WF-E004） | **不可含** | 退回關係被當成前進路徑，形成迴圈 |
| 佈局層級計算 | 不含（另行處理） | 退回目標被排到流程最下方，end 不再是終點 |

前端的 `upstream.ts` 與後端的 `workflow_validator.rs` 都在註解中
標明這一點，並各自有測試釘住。`upstream.test.ts` 的
「goto 不算上游關係」一項即為此而設。

### 5.3 節點操作集中管理

節點與邊是兩份資料，任何節點操作都必須同時維護 `edges`。
所有變更集中在 `useWorkflowDesigner.ts`，畫面只呼叫語意化的動作
（`insertNode` / `removeNode` / `setRejectTarget`），不直接碰
`nodes` 與 `edges`。

三個容易出錯的細節，各有測試守住：

- **插入節點時，原邊的 `when` 必須留在前半段**。
  分支條件屬於「離開 condition 的那條邊」，跑到後半段就失效了。
- **刪除節點要接合前後**，否則圖斷成兩半；同時要避免產生重複邊。
- **刪除節點要清掉指向它的 `goto`**，否則發布時被 WF-E006 擋下，
  而使用者只是刪了一個節點，不會聯想到錯誤來源。

## 6. 已知限制

| 項目 | 現況 | 說明 |
|------|------|------|
| `parallel` / `join` 的分支編輯 | 節點可新增，但分支結構需手動接 | 插入點目前只處理單一前進邊 |
| `composite` 簽核人 | 可讀取顯示，不可在面板編輯 | 面板顯示「組合（N 項）」，需改 DSL 才能調整 |
| `input_mapping` | 未提供編輯介面 | 系統動作的參數對應待 Temporal 整合階段一併處理 |
| 版本比較 | 未實作 | `GET /versions` 已可呼叫，畫面尚未使用 |

這些都不影響報價單流程的既有結構編輯，留待後續階段補上。
