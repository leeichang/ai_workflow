## 2. 整合內容

這一階段要解決的問題是：表單設計器與權限系統原本各自為政。
設計器可以編輯 `editable_roles` 等欄位，但設計者看不到這些設定
實際會產生什麼結果；權限矩陣則因為後端缺一塊實作，
永遠只顯示「開始」一欄。

### 2.1 後端：權限矩陣接上真實流程節點

`load_workflow_nodes()` 原本是佔位實作：

```rust
// 流程定義表在任務 4.1 建立。目前先回初始節點，
let _ = (tx, workflow_key);
Ok(vec![NodeInfo::initial()])
```

流程定義表已於上一階段完成，因此改為實際查詢，
並只挑出 `human_approval` 與 `human_task`——
其他節點型別沒有使用者介面，列進矩陣只會讓設計者困惑
「這一欄要設定什麼」。

一律以草稿優先讀取。設計者調整流程後，權限矩陣要立刻反映新節點，
否則得先發布流程才能設定權限，順序上說不通。

實測結果，報價單流程的欄位從 1 欄變成 5 欄：

| 欄位 | 標籤 | participant_kind |
|------|------|------------------|
| `start` | 開始 | internal |
| `manager_approval` | 主管簽核 | internal |
| `finance_approval` | 財務簽核 | internal |
| `customer_review` | 客戶簽核 | **external** |
| `revise` | 業務修改報價 | internal |

`participant_kind` 必須正確帶出，否則客戶簽核那一欄會顯示成可編輯。
這一點有獨立測試守住。

### 2.2 前端：角色清單改為三態選擇

`editable_roles` 與 `readable_roles` 有三種語意不同的狀態：

| DSL 值 | 語意 |
|--------|------|
| 鍵不存在 | 不限制，任何角色皆可 |
| `[]` | 明確拒絕所有角色 |
| `["approver"]` | 僅該角色 |

原本的介面是單一逗號分隔輸入框。問題在於「拒絕所有角色」與
「不限制」都會是空字串，兩種相反的語意被壓成同一個輸入，
使用者根本無從表達前者。

改為明確的三態選擇器（`RoleListEditor.vue`），
並在選擇「全部拒絕」時顯示後果說明。

### 2.3 前端：權限預覽面板

欄位的實際權限由六條規則依序判定，設計者很難從四個獨立的
輸入框推出結果。新增的預覽面板直接問後端：
「某角色在某節點上，這張表單會長什麼樣？」

判定由後端計算而非前端重算。理由是判定邏輯只該有一份，
前端複製一份必然會與後端漂移，而漂移的症狀是
「畫面說可編輯、實際送出被擋」，極難追查。

面板同時列出判定順序，因為優先序會推翻個別設定，
設計者常誤以為規則沒生效：

1. 外部參與者遇到「客戶 Portal 不可見」的欄位 → 隱藏
2. 有計算連動公式 → 唯讀（管理員也不例外）
3. 角色不在可檢視清單 → 隱藏
4. 不符合顯示條件 → 隱藏
5. 管理員 → 可編輯（不受以下限制）
6. 外部參與者 → 唯讀
7. 角色不在可編輯清單，或符合唯讀條件 → 唯讀

## 3. 實作中發現並修正的缺陷

### 3.1 `mergeField` 讓「改為不限制」永遠沒有效果

**這是本次最嚴重的問題，且不會有任何錯誤訊息。**

`PropertyPanel` 的 `patchWorkflow()` 在值為 `undefined` 時
會從 patch 中刪掉該鍵，語意是「改為不限制」。
但 `useDesigner` 的合併邏輯是：

```ts
workflow: patch.workflow
  ? { ...base.workflow, ...patch.workflow }   // 刪掉的鍵從 base 補回來
  : base.workflow,
```

展開合併會把剛刪掉的鍵從 `base` 補回去，於是使用者把
「指定角色」改成「不限制」，畫面顯示已改變，存檔後卻原封不動。

**修正**：`workflow` 改為整組取代。

```ts
workflow: patch.workflow ?? base.workflow,
```

這一區塊的鍵「存在與否」本身帶有語意，不能用展開合併處理。
呼叫端本來就會送出完整的 workflow，取代不會遺失其他規則。

補上兩個迴歸測試：一個驗證刪掉的鍵不被補回，
一個驗證空陣列會被保留而非視同未設定。

### 3.2 權限矩陣沒有傳 `workflow_key`

後端修好之後矩陣仍只有一欄。追下去發現前端的 `load()`
從來沒有傳 `workflow_key`，後端的 `match` 於是永遠走
`None => vec![NodeInfo::initial()]` 這一支。

**修正**：以 `business_object` 找出對應流程後傳入。
表單與流程沒有直接外鍵，兩者透過 `business_object` 關聯。
找不到時回 `undefined`，矩陣退回單欄模式仍可使用。

### 3.3 工具列被頂部列蓋住（與流程設計器同一個缺陷）

表單設計器同樣用 `-m-space-xl` 抵銷 `AppShell` 的 padding，
連帶把避開固定頂部列的 56px 也抵銷掉。上一階段在流程設計器
修過一次，這次一併修正表單設計器。

修正後量測 `工具列 top = 56`、`頂部列 bottom = 56`，恰好貼齊。

### 3.4 角色清單在兩處各自維護

權限矩陣頁與表單設計器各有一份硬編碼的角色清單，
內容相同但沒有任何機制保證同步。抽出 `designer/roles.ts` 共用。

## 5. 三態語意的驗證重點

這組語意曾在先前階段出過缺陷：寫入端把空陣列的鍵整個移除，
讀取端把缺鍵視為「不限制」，於是「拒絕所有人」存檔後
變成「所有人都可以」，剛好相反。

因此本次測試把往返一致性當作最重要的一項，
四種值各自驗證「讀出再寫回不變」：

```ts
const cases = [undefined, [], ['approver'], ['a', 'b']]
// writeRoleList(readRoleList(value)) === value
```

另有一個容易忽略的互動細節：使用者把清單中最後一個角色取消時，
應轉為「全部拒絕」而非「不限制」。使用者剛剛明確地把所有角色
都取消了，意圖是拒絕；轉成不限制等於放行所有人，與操作意圖相反。

## 6. 已知限制

| 項目 | 現況 | 說明 |
|------|------|------|
| 角色清單 | 靜態五種 | 租戶自訂角色需要 `/roles` 端點，待權限管理畫面實作 |
| 表單與流程的關聯 | 以 `business_object` 比對 | 一個業務物件對多個流程時只取第一個 |
| 預覽的資料情境 | 空物件 | `visible_when` 這類依賴表單資料的條件無法真實求值 |
| 條件式規則編輯 | 純文字輸入 | 表達式沒有語法檢查與自動完成 |

第三項值得留意：預覽以空資料求值，因此
`visible_when: "form.amount > 100000"` 這類條件在預覽中
會走到「不符合顯示條件」。這是正確的求值結果，
但設計者可能誤以為規則寫錯了。後續可考慮讓預覽支援輸入測試資料。
