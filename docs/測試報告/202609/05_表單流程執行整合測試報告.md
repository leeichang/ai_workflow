## 3. 條件表達式不使用 eval()

DSL 的 condition 節點帶表達式，例如 `quotation.discount_rate > 0.15`。
表達式來自流程設計器，而設計者是**租戶的使用者**，不是平台管理員。

用 `eval()` 會讓任何能編輯流程的人在 Worker 上執行任意程式碼：
讀取其他租戶的資料、對內網發請求、讀環境變數裡的資料庫密碼。
這是租戶隔離的破口，不是效能或風格問題。

改以 `ast` 解析後走白名單直譯，只允許比較、布林運算、字面值與
資料路徑。九個已知的逃逸手法各有一個測試：

```python
"__import__('os').system('id')"
"open('/etc/passwd').read()"
"(1).__class__.__mro__[1].__subclasses__()"
"lambda: 1"
...
```

**測試抓到一個白名單擋不住的漏洞。** `quotation.__class__.__bases__`
是純粹的 Attribute 存取鏈，完全符合節點白名單。目前資料都是 dict
走 `.get()` 取不到，所以實際回傳 None——但這依賴「資料剛好都是 dict」
這個前提。只要有一個值是物件，`getattr` 就會沿 `__class__` 一路挖到
`__subclasses__`，那是經典的沙箱逃逸路徑。

修正是在解析階段就拒絕任何雙底線屬性與名稱，不依賴資料型別。

算術運算刻意不支援。需要算術時應在表單的 computed 欄位算好，
條件式只做判斷——支援算術會讓白名單持續膨脹。

## 4. 實作中發現並修正的缺陷

### 4.1 Temporal 檢查的順序讓權限檢查失效

**現象**：整合測試 `不是自己的待辦不可決策` 期望 403，實得 **503**。

**原因**：決策端點一開始就檢查 Temporal 是否連線：

```rust
let handle = state.temporal.as_ref().ok_or_else(|| {
    ApiError::ServiceUnavailable("流程引擎未連線".into())
})?;
// 之後才檢查「這張待辦是不是你的」
```

兩個後果：

1. 探測別人的待辦會得到 503 而非 403。回應碼本身洩漏了
   「這張待辦存在」。
2. **Temporal 斷線時，所有授權與狀態檢查都不會執行。**
   這才是嚴重的部分——基礎設施故障不該讓權限檢查整組跳過。

**修正**：把 Temporal 檢查移到授權與狀態檢查之後、送 Signal 之前。
此時的 503 確實只代表基礎設施問題。

這個缺陷單元測試測不到——要有一個「Temporal 未連線且使用者無權限」
的組合才會浮現。整合測試把 `temporal: None` 當成預設狀態，
剛好構成這個組合。

### 4.2 測試夾具的 `or` 讓測試永遠測不到目標情境

```python
STATE["participants"] = participants or [DEFAULT]
```

`reset_state(participants=[])` 的意圖是「沒有任何參與者」，
但空陣列是 falsy，於是落回預設的一個參與者。
`test_找不到參與者時明確失敗` 實際上測到的是「有一個參與者」，
流程正常建立待辦後永遠等下去，最後以 pytest 逾時失敗。

**修正**：改用 `is None` 判斷。這類 `or` 的誤用在空集合、`0`、
空字串上都會出現，而且症狀是「測試通過但沒測到東西」，
比失敗更難發現——這次是因為逾時才暴露。

### 4.3 測試環境選錯導致全數逾時

第一版測試用 `WorkflowEnvironment.start_time_skipping()`，14 個測試
全部逾時。原因是 time-skipping 會在 Workflow 等待時快轉虛擬時鐘，
而測試需要輪詢 Query 等節點就緒再送 Signal——快轉讓等待中的流程
瞬間衝到逾時。

改用 `start_local()`。另外把 fixture 改為 module 範圍共用同一個
Server：每個測試各起一個讓整批測試從 **3 分鐘降到 7 秒**。

## 5. 兩個系統的一致性

使用者按下「核准」後要發生兩件事：資料庫記錄決策、Temporal 收到
Signal 讓流程前進。兩者沒有分散式交易。

順序是**先寫資料庫（未提交）→ 送 Signal → 成功才提交**。

| 順序 | Signal 失敗時的狀態 |
|------|---------------------|
| 先寫後送，成功才提交 | 交易回滾，待辦維持 PENDING，使用者可重試 |
| 先提交再送 Signal | 待辦顯示「已核准」，流程卻停在原地等——而且沒有人會再送一次 |

後者是最糟的狀態：使用者以為做完了，流程實際上永遠卡住。
測試 `temporal_未連線時決策回_503_且不改狀態` 守住這一點。

流程結束時由 Interpreter 呼叫 `report_instance_finished` 回寫狀態。
Temporal 知道流程結束了，但收件匣與報表查的是 PostgreSQL，
不回報的話單據會永遠顯示「進行中」。回報失敗不改變流程結果——
流程確實跑完了，只是投影沒更新，可由對帳程序修正。

## 6. 端到端驗證

經真實 API、真實 PostgreSQL、真實 Temporal、真實 Python Worker。

### 6.1 低折扣路徑（跳過財務簽核）

| 步驟 | 結果 |
|------|------|
| `POST /instances` 啟動報價單流程 | 201，狀態 RUNNING |
| Worker 解析簽核人 | `manager_of(initiator)` → cfo@demo.local |
| `GET /tasks`（以 cfo 登入） | 1 筆「主管簽核 / QT-E2E-001」 |
| `POST /tasks/{id}/decision` APPROVE | signalled: true |
| 流程自動前進 | discount_gate 走 false 分支，跳過財務 |
| publish_to_customer 動作執行 | internal/actions/run 200 |
| 客戶簽核建立 | 指派給 cust@example.com（external） |
| 客戶核准後 | 流程 COMPLETED，ended_at 寫入 |

Temporal 記錄的最終路徑：

```
["start", "manager_approval", "discount_gate", "publish_to_customer",
 "customer_review", "create_order", "notify_done", "end"]
```

八個節點，財務簽核正確跳過。

### 6.2 高折扣路徑（退回、修改、再送審、加簽財務）

| 步驟 | 結果 |
|------|------|
| 啟動（discount_rate 0.2） | RUNNING |
| 主管 REJECT | 待辦 REJECTED，流程走到 revise |
| 業務完成修改 | revise APPROVED，流程回到 manager_approval |
| 主管第二次 APPROVE | 第二筆 manager_approval APPROVED |
| 條件判斷 | 0.2 > 0.15，這次走 true 分支 |
| 財務簽核建立 | 依 role 指派給 finance@demo.local |
| 財務 APPROVE | 流程前進至客戶簽核 |

待辦紀錄完整保留兩輪：

```
manager_approval | REJECTED | cfo@demo.local
revise           | APPROVED | designer@demo.local
manager_approval | APPROVED | cfo@demo.local
finance_approval | APPROVED | finance@demo.local
customer_review  | PENDING  | c2@example.com
```

同一個節點被走過兩次，`task_id` 也重複產生。Signal 帶 `node_id`
才能分辨決策屬於哪一輪——這是退回路徑最容易出錯的地方。

### 6.3 一個需要說明的觀察

端到端測試中，`customer_review` 一度顯示為 CANCELLED 而非 APPROVED。
追查後確認**不是缺陷**：當時我為了繞過「客戶不是 app_user 無法登入」
的限制，直接對 Temporal 送 Signal，資料庫從未收到那筆決策，
於是流程結束時 `cancel_by_instance` 把它當成殘留的 PENDING 取消了。

走正常 API 路徑時行為正確（見 6.2 的退回測試，REJECTED 被保留）。
已在程式碼加註說明，並補測試
`取消待辦不影響已決策的` 釘住這個界線。
