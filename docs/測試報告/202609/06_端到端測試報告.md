## 3. 測試中的觀察

### 3.1 客戶簽核的待辦顯示 CANCELLED

**不是缺陷，是測試方式的限制。**

外部客戶目前沒有登入管道（Portal 未實作），因此客戶核准是以
`temporal workflow signal` 直接送給 Temporal，繞過了 Rust API。
資料庫從未收到那筆決策，於是流程結束時
`cancel_by_instance` 把它當成殘留的 PENDING 取消了。

走正常 API 路徑時行為正確——主管與財務兩個節點都正確記錄為
`APPROVED` 並帶 `decision`。相關界線已有測試
`取消待辦不影響已決策的` 釘住。

這也說明了為何 Portal 是第一階段之後最優先的缺口：
沒有它，報價單流程無法真正端到端由客戶完成。

### 3.2 整合測試不清理自己的資料

清點資料庫時發現的，比預期嚴重，記錄下來。

整合測試每個案例都建立一個隨機 UUID 的租戶，跑完不刪。
累積數次 `cargo test` 之後：

| 租戶名稱 | 筆數 |
|----------|------|
| 整合測試租戶 | 192 |
| 權限測試租戶 | 156 |
| 權限寫入測試 | 156 |
| 待辦測試租戶 | 70 |
| **測試租戶合計** | **574** |
| 台製精工股份有限公司（正式） | 1 |
| RLS 測試 A／B（示範） | 2 |

連帶的 634 筆稽核事件、992 個使用者、432 份表單定義同樣留著。

**測試本身沒有錯**——每個案例用獨立租戶正是 RLS 測試該有的隔離方式，
不清理也讓失敗時能進資料庫追查。但沒有任何一層會回收，
資料量只增不減。

兩件事值得記下來：

1. **`audit_event` 的外鍵是 `RESTRICT`，不是 `CASCADE`。**
   刪租戶會被稽核事件擋住。這是刻意的設計——稽核軌跡不該因為
   上層資料被刪就跟著消失。清理時必須顯式決定稽核要不要留。

2. **用 `workflow_app` 角色查不到任何資料。**
   清點時第一次查詢回 0 筆，因為沒設 `app.tenant_id`，
   RLS policy 擋掉全部。要跨租戶清點得用 superuser。
   這反過來證實了 RLS 對非 superuser 確實生效。

後續應在測試框架加租戶回收（`Drop` 或 fixture teardown），
或提供一支以租戶名稱白名單為界的清理腳本。這不影響端到端結果，
但會讓資料庫持續膨脹。

## 5. 全期間修正的重要缺陷

以下是各階段實測抓到、單靠單元測試不會浮現的問題。

| # | 缺陷 | 症狀 | 為何單元測試測不到 |
|---|------|------|-------------------|
| 1 | `mergeField` 展開合併 | 「改為不限制」永遠無效，無錯誤訊息 | 需要「刪鍵後再合併」的組合才浮現 |
| 2 | Temporal 檢查順序 | 引擎斷線時**所有權限檢查被跳過** | 需要「未連線且無權限」的組合 |
| 3 | `keepLastRowsTogether` 從未執行 | 測試全綠但渲染路徑沒呼叫到 | 測的是純函數本身，不是渲染 |
| 4 | pdfme 座標語意 | 版面重疊、多出空白頁 | 座標正確性無法靠型別或邏輯測試守住 |
| 5 | 金額大寫跨節補零 | `100001` 讀成「十萬一千」 | 2000 組隨機值的不變量測試才抓到 |
| 6 | 分頁模擬與框架不一致 | 只在明細恰好 49 列時出錯 | 手挑案例測不到，需掃 1440 組 |
| 7 | 合計列欄數不符 | `raw.split()` 崩潰，訊息看不出原因 | 欄數是資料層面的約定 |

第 2 項最值得記錄：型別錯誤原本就在警告「這個切點不存在」，
被 `as unknown as` 壓掉之後，整段保護邏輯從未執行而測試依然全綠。
