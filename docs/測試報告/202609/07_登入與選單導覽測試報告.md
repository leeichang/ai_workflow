## 1. 起因

使用者回報兩件事：

1. 系統不能登入登出
2. 點左邊的選單沒有反應

兩者都確認屬實，且原因不同。

### 1.1 登入：被開發用的自動登入蓋掉了

`web/src/dev-auth.ts` 在應用啟動時自動以 `designer@demo.local` 登入，
token 寫進 `localStorage`。系統因此永遠處於登入狀態——
沒有登入頁，也沒有登出的入口。

檔案開頭的註解寫著「登入頁尚未實作，此模組在開發模式下自動登入，
正式版由登入頁取代」。它如實說明了自己是暫時的，但沒有人回來取代它。

右上角顯示的「林建志 協理／營運製造部」是設計稿的假資料，
與實際登入的陳雅婷無關。

**後端並沒有問題。** `POST /auth/login`、JWT 簽發與驗證、
Argon2 密碼雜湊、`Actor` extractor、`last_login_at`、稽核事件
全部都在。缺的是前端。

### 1.2 選單：七個項目只有一個有路由

`AppShell.vue` 的側邊欄有七個項目，`router.ts` 只註冊了四條路由，
全都在 `/designer/` 底下。`/`、`/tasks`、`/quotations`、
`/purchase-requests`、`/reports`、`/settings` 都沒有對應路由，
點擊後撞上 catch-all：

```ts
{ path: '/:pathMatch(.*)*', redirect: '/designer/forms/quotation_form' }
```

全部被彈回表單設計器。畫面看起來沒動，實際上是換了路由又被導回原地。

「設計器」看似有效是巧合：它同樣沒註冊，但被導回的目標剛好在
`/designer/` 底下，而 `isActive` 用 `startsWith('/designer')` 判斷，
所以那一項一直亮著。

### 1.3 四個設計器只有一個有入口

補完上述路由後使用者再次回報：選單裡只看得到表單設計器。

確認屬實。四個設計器的路由都註冊了，頁面也都實作完成：

| 路由 | 頁面 | 檔案大小 |
|------|------|----------|
| `/designer/forms/:formKey` | 表單設計器 | 16.1K |
| `/designer/workflows/:workflowKey` | 流程設計器 | 15.2K |
| `/designer/templates/:templateKey?` | 單據套版設計器 | 12.8K |
| `/designer/permissions` | 權限矩陣 | 18.2K |

但側邊欄的「設計器」是單一項目，`/designer` 直接
redirect 到 `/designer/forms/quotation_form`。
另外三個**沒有任何入口**——功能做完了，使用者卻無從得知它們存在。

改成可展開的子選單（見步驟 11）。

## 5. 設計決定

**token 存 localStorage 而非 sessionStorage。**
關掉分頁再開回來不該要求重新登入。代價是 XSS 時 token 會被讀走，
但那要靠 CSP 與輸入清理防範，換 sessionStorage 並不能解決。

**登出是純前端清除。**
JWT 無狀態，後端沒有 session 可作廢，token 會一直有效到 `exp`。
要做到立即失效需要黑名單或 refresh token，屬於後續工作。
這一點寫在 `useSession.logout()` 的註解裡。

**`redirect` 只接受 `/` 開頭的路徑。**
否則會變成開放重導向——攻擊者可以用一條看似正常的登入連結
把使用者導到釣魚站。

**前端 `hasRole` 讓 admin 通過所有檢查。**
與後端 `Actor::is_admin` 對齊。兩邊不一致的話，畫面會藏起
使用者其實有權限做的操作。

**未實作的功能做說明頁，不藏選單也不做假畫面。**
藏起來的話，使用者不知道這個功能未來會有；做假畫面的話，
填著假數字的報表會被當成真的。說明頁寫「缺什麼」而非「開發中」——
後者等於沒說。

**待辦徽章查不到時不顯示，而非顯示 0。**
0 會讓使用者以為真的沒有待辦，而實際上是沒查到。

## 6. 過程中發現並修正的缺陷

### 6.1 `ApiError` 沒有 `body` 屬性

登入頁原本寫 `error.body.message`，但 `ApiError` 把訊息放在
`message`（建構時 `super(body.message)`）。讀 `undefined.message`
拋出 TypeError，整個 catch 區塊中斷——錯誤訊息沒顯示，密碼也沒清。

四個 401／403 測試因此失敗，而網路錯誤的測試反而通過，
因為它走 else 分支不碰 `.body`。這個對比正好指出問題在哪。

### 6.2 409 之後錯誤訊息被清掉

待辦頁收到 409（別人已處理）時會重新載入列表，
而 `load()` 成功時把 `errorMessage` 清成空字串，
蓋掉剛設好的「待辦已被處理」。

使用者會看到自己按的那一筆憑空消失，沒有任何說明。

修正：`load()` 不主動清除錯誤，另開 `refresh()` 給使用者
主動觸發的重新整理用。清除的時機由呼叫端決定。

### 6.3 截圖搶在導航完成前拍攝

`05-登入後回原頁.png` 第一次只有 21.8K，內容是停在「登入中…」
的登入頁，而非預期的權限矩陣。

`toHaveURL` 會重試到通過為止，`page.screenshot()` 卻是立即執行——
URL 已經變了，畫面還沒換完。

修正：截圖前 `waitForLoadState('networkidle')`，
並在該測試補上元素可見的斷言。修正後 123.2K，內容正確。

**這個問題值得記錄**：測試全部通過，截圖卻是錯的。
斷言與截圖看的是不同時間點，前者通過不代表後者拍對。

## 9. 實機驗證中發現的問題

### 9.1 測試資料欄位放錯層級

第一次執行時流程狀態為 `FAILED`，錯誤是
「NoParticipants: 節點 customer_review 找不到任何參與者」。

原因是我寫的測試資料把欄位放在頂層：

```jsonc
// 錯誤
{ "discount_rate": 0.2, "external_contacts": ["cust@example.com"] }
```

而流程定義讀的是 `quotation` 底下：

```jsonc
"expression": "quotation.discount_rate > 0.15"
"resolver": { "type": "external_contacts", "path": "quotation.customer_contact_ids" }
```

兩個後果不同：

- **條件式取不到值 → 當成 false**，靜默跳過財務簽核。
  流程照跑，只是少了一個節點，不會有任何錯誤。
- **resolver 取不到 → NoParticipants**，整個流程 FAILED。

第二點的失敗是明確的，第一點是靜默的。**表達式取不到值時當成
false 而非報錯，是值得檢討的設計**——寫錯路徑的流程會安靜地
少走一段簽核，而沒有人會發現。

這次是測試資料寫錯，但正式環境若有人打錯 `quotation.discount_rate`，
後果是「高折扣的報價單不經財務就發出去」。建議後續在 DSL 驗證時
檢查條件式引用的路徑是否存在於業務物件結構中。

### 9.2 Temporal 以 workflow_id 去重，重複單號靜默失敗

用先前用過的單號 `QT-E2E-001` 啟動時，API 回 201 並建立了新的
資料庫紀錄，但 Temporal 沒有新的執行——`temporal workflow describe`
顯示的是一天前的舊執行。

Temporal 以 workflow_id 去重是正常行為，問題是 **Rust API 沒把
這個情況往上報**，呼叫端拿到 201 會以為啟動成功。

實務上單號本來就不該重複，但「重複時靜默失敗」比「明確報錯」
難查得多。E2E 因此改用帶時間戳的單號。

### 9.3 換帳號時測試卡住

第二次 `login()` 逾時，卡在找不到登入表單。

原因是 guard 的正確行為：已登入時 `/login` 會被導回首頁，
登入表單根本不會渲染。測試直接 `goto('/login')` 換帳號因此卡住。

這不是缺陷——guard 就該這樣。修正的是測試：換帳號前先清 session。

### 9.4 E2E 測試不清理資料

七條測試各啟動一個流程，跑一次留下約 10 筆實例與對應待辦。
反覆執行後累積到 38 筆。

與報告 06 記錄的 574 個測試租戶是同一類問題：測試建立資料但不回收。

待辦徽章因此顯示 11（截圖 `01`），數字本身是正確的，
但其中多數是測試殘留。

後續應在 E2E 加 teardown，或提供以單號前綴為界的清理腳本。
