- 日期：2026-09-17
- 範圍：WF-E012 資料路徑存在性驗證、權限預覽 API 支援 `instance_id`
- 環境：本機 PostgreSQL **16.13**、Temporal 1.25.2、Rust API `:3001`、前端 `:3040`
- 規劃：[前置改動實踐規劃](../../實踐規劃/規劃/202609/01_前置改動實踐規劃.md)
- 相關決議：[D-07 前置條件 1、2](../../需求規劃/202609/02_決議紀錄.md)

## 1. 這批改動要解決什麼

兩項都是「編輯開發模式（沙箱）」與「AI 產生表單與流程」的**阻斷性前置條件**。

### 1.1 WF-E012：擋住會靜默跳過簽核的流程

改動前，流程定義寫成這樣是可以正常發布的：

```jsonc
"expression": "quotation.discount_rat > 0.15"    // 少一個 e
```

求值時取不到 `discount_rat` 的值，**被當成 false**，流程照跑，
只是少走一段簽核。沒有任何錯誤訊息。

實際後果：高折扣的報價單不經財務核准就發給客戶，而沒有人會發現。

人工編輯時使用者至少會看 JSON；**AI 產生時不會**。
這是 [02 AI 交接](../../交接手冊/202609/02_AI產生表單與流程交接.md) 把它
標為「不做這個就不要開始接 LLM」的理由。

### 1.2 權限預覽帶真實單據：讓模擬畫面與真實簽核一致

改動前 `permissions.rs:187` 把 `data` 寫死成空物件。
設計器預覽沒有實際單據，空的合理；但模擬簽核有真實單據，
而 `permission.rs:193` 的 `eval_bool` 會用 `data` 求值條件式。

不改的話，凡是 `visible_when` 依賴欄位值的欄位在模擬時**全部判錯**——
而沙箱的整個價值就是「看到的畫面與那個人會看到的一樣」。

## 2. 規劃階段發現的設計問題

**這是本次最重要的發現，兩份交接文件都沒有涵蓋。**

WF-E012 需要一份「合法路徑」名單。直覺做法是從表單定義的 `data.path` 推導，
但實測發現**同一個 `business_object` 的多張表單，路徑詞彙互不相容**。

`business_object = quotation` 目前有兩張表單，實測比對結果：

| | `server/seed.sh` 的表單 | `schemas/fixtures/quotation_form_v1.json` |
|---|---|---|
| 總計 | `quotation.total_amount` | `quotation.total` |
| 內部備註 | `quotation.internal_notes`（複數）| `quotation.internal_note`（單數）|
| 毛利率 | `quotation.gross_margin` | `quotation.margin_rate` |
| 客戶 | `customer.name` / `customer.tax_id` | `quotation.customer_party_id` |

**13 條路徑中只有 3 條重疊**（`currency`、`discount_rate`、`lines`）。

### 後果

若 `known_paths` 取自表單，會有三種都不能接受的結果：

| 取法 | 後果 |
|---|---|
| 取 seed 的表單 | fixture 流程的 `quotation.customer_contact_ids` 驗不過 |
| 取 fixture 的表單 | seed 那張表單自己的欄位驗不過 |
| 取聯集 | `internal_note` 與 `internal_notes` **都合法**——等於不檢查拼錯字，而拼錯字正是 E012 要擋的東西 |

### 決定

**路徑的真相來源必須獨立於任何一張表單。**

新增 `schemas/business-objects/*.json` 作為業務物件的正式欄位定義，
先以編譯期內嵌的檔案形式存在，需要多租戶自訂時再搬進資料庫
（規劃中的 P1a → P1b）。

定義中**刻意不收錄舊名稱**，並在檔案的 `notes` 欄位記錄原因：
收錄的話 E012 就擋不住拼錯字。

> **副產物**：建立定義的過程迫使我們決定 `total` 與 `total_amount`
> 哪個是正式名稱。這個歧義原本散落在兩張表單裡沒人發現，
> 而它會讓條件式 `quotation.total > x` 在不同表單的單據上行為不一致。

## 3. 實作

### 3.1 查證：地基已鋪好但從未接線

實作前逐項查證交接文件的技術宣稱：

| 宣稱 | 查證結果 |
|---|---|
| 要新增 `known_paths` 資料結構 | ❌ **已存在**（`workflow_validator.rs:46`），註解寫「空集合代表不檢查」，但宣告後全專案零使用 |
| 要新增表達式收集 | ❌ **已存在** `collect_expressions()`（`:637`），E006 已用同樣模式迭代 |
| `acting_as` 不存在 | ✅ 確認，全 `crates/` 零命中 |
| `form_version_id` 缺少 | ✅ 確認，migration 唯一命中是錯誤訊息字串 |

改動因此比交接文件預期的小：E012 沿用 E006 的迭代模式即可。

### 3.2 改動清單

| 檔案 | 改動 |
|---|---|
| `schemas/business-objects/quotation.json` | 新增，13 個欄位 |
| `schemas/business-objects/purchase_request.json` | 新增，12 個欄位 |
| `domain/src/business_object.rs` | 新增，編譯期內嵌定義並提供 `paths_for()` |
| `domain/src/workflow_validator.rs` | 加 `with_paths()`、`collect_data_paths()`、`extract_paths_from_expression()`、`strip_string_literals()`、E012 規則 |
| `http-public/src/workflows.rs` | `validate_draft` 與 `publish` 兩處串上 `.with_paths()` |
| `http-public/src/permissions.rs` | `PreviewQuery` 加 `instance_id`，有值時帶入實例的 `input` |

### 3.3 刻意不做完整 CEL 解析

`extract_paths_from_expression()` 只用字元掃描抽出
「識別字.識別字」形態的 token，並排除函式呼叫、數字與字串字面值。

理由與既有的 `expression_parses()` 一致（其註解已載明
「完整 CEL 解析排在任務 2.2」）：**看不懂的一律放行**。

誤擋會讓使用者無法發布正確的流程，比漏擋更快失去信任。

`web/e2e/dsl-path-validation.spec.ts`

|---|---|

### 4.4 一個既有 E2E 間歇性失敗

全量執行時 `auth-navigation.spec.ts` 的
**「切換帳號後顯示對應的人與角色」**有時失敗：

```
expect(locator).toHaveText(expected) failed
Locator: getByTestId('user-name')
Expected: "陳雅婷"
Error: element(s) not found
```

#### 判定：間歇性失敗，非本批改動造成

三次執行的結果：

| 執行 | 結果 |
|---|---|
| 全量第一次 | 57 通過 / **1 失敗** |
| 全量第二次 | **58 通過 / 0 失敗** |
| `auth-navigation.spec.ts` 單獨執行 | 22 通過 / 0 失敗 |

判定依據：

1. 本批改動全在後端 validator 與預覽 API，**未觸及登入、路由守衛或 session**
2. Playwright 依檔名順序執行，`auth-navigation` 排在
   `dsl-path-validation`（本批新增）**之前**，新測試不可能污染它
3. 同樣的程式碼第二次全量執行完全通過

#### 可能原因

交接手冊 §12 已記錄同類症狀：

> E2E 逾時在第二次登入 — 已登入時 guard 會把 `/login` 導回首頁。
> 換帳號前先清 session

這個測試正是在換帳號。推測是登出與重新登入之間的競態——
`user-name` 元素在畫面重繪的空檔查不到。

#### 建議

**不建議用加長 timeout 解決**，那只是把競態藏起來。
應該在換帳號後等待一個明確的就緒訊號
（例如等 `user-name` 出現而非等固定時間），
或在測試間顯式清除 session。

本批未修正，因為它不在範圍內，且修錯地方會掩蓋真正的競態。
已列入下一棒的建議。

## 5. 實機驗證

**為什麼單元測試不夠**：單元測試只驗到 `validate_graph` 回傳錯誤碼，
驗不到 API 是否真的擋下發布。本專案已有前例——SMTP 的單元測試驗到
「有呼叫 `send_notification`」就算過，但實際欄位漏傳，信寄出去標題是錯的。

重啟 Rust API 後（改完要重啟才生效），以 `designer@demo.local` 實際操作：

```
建立流程定義（條件式路徑改成 quotation.discount_rat）
  POST /workflows                          → HTTP 201

發布
  POST /workflows/{key}/draft/publish      → HTTP 422
```

回應內容：

```json
{
  "code": "VALIDATION_FAILED",
  "message": "[WF-E012] 資料路徑不存在於業務物件定義：quotation.discount_rat",
  "details": {
    "errors": ["[WF-E012] 資料路徑不存在於業務物件定義：quotation.discount_rat"]
  }
}
```

訊息明確指出是哪一條路徑，使用者不需要讀 JSON 就知道哪裡錯。

驗證後已清除測試產生的流程定義，`demo` 租戶未留下殘留資料。

## 6. 過程中發現的問題

### 6.1 `rtk` hook 會無聲弄壞 `cargo`

全域 `rtk` hook 把 `cargo` 改寫成 `rtk cargo`，但 rtk 佔住程序卻從未
spawn 真正的 cargo 子程序——零輸出、沒有 `target/` 目錄，
還在 `~/.cargo/.package-cache` 留下 stale lock 讓後續 build 互相 deadlock。

更難查的是 `ps aux | grep cargo` 也被 rtk 過濾成空的，看起來像「沒在跑」，
但 `lsof ~/.cargo/.package-cache` 顯示程序確實存在。

**繞法**：絕對路徑 `~/.cargo/bin/cargo`。
同一個 hook 也會吃掉 vitest/playwright 的輸出，
要改讀 JSON report 或 `~/Library/Application Support/rtk/tee/*.log`。

### 6.2 測試用的 PUBLISHED 版本需要 `published_at`

`wf_published_has_version` 約束（`0004:51`）要求
`status = 'PUBLISHED'` 時 `version` 與 `published_at` 都不可為 NULL。

測試輔助函式漏了 `published_at` 會在插入時才爆，錯誤訊息是約束名稱，
不看 migration 不知道缺什麼。已在測試註解標明。

### 6.3 環境與手冊的差異

本機是 **PostgreSQL 16.13**，不是手冊寫的 17。
六份 migration 全部正常執行，`verify_rls.sh` 九項檢查全過。

另外手冊 §7／§8 的順序有誤：兩個 seed 腳本都會 `curl` 打
`/auth/login` 與 `/forms`，**必須先啟動服務再 seed**。

### 6.4 `seed` 不建立流程定義

手冊 §7 說 seed 會建立「報價單表單與簽核流程定義」，
實際上只建表單。`quotation_approval` 需另外從
`schemas/fixtures/quotation_approval_v1.json` 註冊並發布，
否則 `task-approval.spec.ts` 的 6 個測試全部回 404。

## 7. 已知限制

| 限制 | 說明 |
|---|---|
| 業務物件定義是編譯期內嵌 | 新增業務物件需重新編譯。多租戶自訂時要搬進資料庫（規劃 P1b）|
| 路徑抽取不做完整 CEL 解析 | 複雜表達式中的路徑可能漏檢。刻意選擇，見 §3.3 |
| 陣列元素路徑未檢查 | `quotation.lines[].qty` 這類只檢查到 `quotation.lines` |
| 只有兩個業務物件有定義 | `quotation`、`purchase_request`。其他業務物件的 `known_paths` 為空集合，等於不檢查 |

最後一項要特別注意：**漏登記業務物件會靜默失去保護**。
`business_object.rs` 已提供 `is_known()` 供呼叫端做明確性檢查，
但目前發布路徑尚未使用它。建議在 S0 或 AI 產生器階段補上
「未定義的業務物件要明確警告」。
