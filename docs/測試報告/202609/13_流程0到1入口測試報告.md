## 1. 這批改動要解決什麼

### 1.1 F2：使用者無法從零建立流程

| 元件 | 狀態 |
|---|---|

使用者看到的是「這個系統只能編輯報價單簽核流程」——
與產品定位「讓使用者自己是 Owner」直接衝突。

看起來像服務沒起來，但六個服務其實都正常。

## 2. 最關鍵的設計約束：起始骨架必須可發布

**流程與表單在這裡有本質差別。**

表單只要有一個欄位就合法（`minItems: 1`）。
流程則要通過 **WF-E001～E012** 的圖結構驗證才能發布：

| 規則 | 對起始骨架的要求 |
|---|---|
| WF-E001 | 要有 trigger 節點與 end 節點 |
| WF-E003 | 每個節點都要被邊碰到，不能有孤兒 |
| WF-E005 | 引用的角色要存在 |
| WF-E012 | 引用的資料路徑要在業務物件定義中 |

**產生一個「建得出來卻發布不了」的流程，比不給建還糟**——
使用者會以為是自己設計錯了，而錯誤訊息講的是他沒寫過的節點。

### 2.1 起始骨架的設計

```
送出申請（trigger）→ 主管簽核（human_approval）→ 完成（end）
```

三個決定與其理由：

**中間放一關簽核而非只有 start→end。** 與表單起始欄位同一個理由：
使用者進設計器時看得到一個實際的節點，知道節點長什麼樣、
屬性面板怎麼用，而不是對著兩個框不知從何下手。

**resolver 用 `manager_of` + `initiator`。** 這是唯一不需要任何前置
設定就能跑的 resolver——`role` 要角色存在（WF-E005）、
`external_contacts` 要資料路徑存在（WF-E012），
新建的業務物件多半兩者都還沒有。

**不引用任何資料路徑。** 新流程的業務物件通常還沒有
`schemas/business-objects/*.json` 定義檔，引用任何路徑
都會讓 WF-E012 擋下發布。已用測試釘住這點。

## 5. 過程中發現的問題

### 5.1 ⚠️ 交辦文件對「主管簽核落在 designer」的診斷是錯的

[04_下一輪工作交辦](../../交接手冊/202609/04_下一輪工作交辦.md) §6 寫：

> 從畫面建單時，主管簽核的待辦落在 `designer` 而非 `cfo`。
> ……這不是腳本的錯，是**組織結構 seed 需要確認**——
> `sales@demo.local` 的主管是誰？現況似乎沒有正確設定。

**查證結果：組織結構是正確的，不需要修。**

```
使用者                主管
sales@demo.local  →  designer@demo.local（陳雅婷）
designer@...      →  cfo@demo.local（張文華）
finance@...       →  cfo@demo.local
```

`manager_approval` 節點的 resolver 是
`{"type": "manager_of", "of": "initiator"}`——解析的是**發起人的主管**：

| 建單者 | 解析出的簽核人 | 是否正確 |
|---|---|---|
| `designer`（API 測試）| `cfo` | ✅ |
| `sales`（畫面操作）| `designer` | ✅ |

**兩者都對。** 差異來自發起人不同，不是 seed 錯誤。
`manual-04` 腳本卡住的原因是它預期了 API 測試的簽核人，
而它自己是用 `sales` 建單的——**要修的是腳本的預期，不是 seed**。

### 5.2 測試資料累積已經影響畫面

流程清單的截圖（`01-流程清單.png`）顯示 **111 個流程定義**，
其中絕大多數是 `rm_1789657405837`、`par_e2e_1789657377850`
這類測試殘留。

這讓截圖幾乎無法當作操作手冊的素材，也顯示一個真實的 UX 問題：
開發環境的清單會被測試資料淹沒。

這是[待處理問題清單 §6](../../實踐規劃/總結/202609/02_待處理問題清單.md)
已記錄的「測試資料只增不減」，現在具體浮現了。
本批未清理——那是獨立的工作項，且刪資料要先決定稽核留不留
（`audit_event` 外鍵是 `RESTRICT` 不是 `CASCADE`）。

### 5.3 F1 遺留了三條釘住舊路徑的 E2E 斷言

`auth-navigation.spec.ts` 有三條斷言期待帶結尾斜線的路徑：

```
['nav-designer-forms',     '/designer/forms/'],      ← 期待直接開某一張表單
['nav-designer-workflows', '/designer/workflows/'],  ← 期待直接開某一個流程
```

F1 把選單從 `/designer/forms/quotation_form` 改成 `/designer/forms`
（清單頁），但**沒有更新這三條 E2E**。

查證方式：

```
git diff 6eccf90^ 6eccf90 -- web/src/components/AppShell.vue
  → 確認 F1 改了 path，且該 commit 未觸及 auth-navigation.spec.ts
```

**所以其中兩條在本批之前就已經是紅的**——
交辦文件 §1 的「E2E 58」是 P1/P2 那輪的數字，F1 之後沒有重跑全量。
本批的 F2 以同樣的方式讓第三條變紅。

三條的根因相同，已一併修正為指向清單頁，
並加上「清單頁的建立按鈕可見」的斷言——
只驗 URL 不驗畫面內容的話，路由改壞但頁面空白時測試仍會通過。

### 5.4 mock 少寫 `code` 會讓測試測錯東西

「代碼重複時顯示後端訊息」這條第一次是紅的：

```
expected '伺服器回應異常（HTTP 409）' to contain '已存在'
```

原因是 mock 只回了 `{ message }`。`client.ts` 的 `normalizeError`
要求 **同時有 `code` 與 `message`** 才採用後端訊息，否則退回泛用訊息。

**實作是對的，測試的 mock 是錯的。** 真實後端回的是
`{code, message, details}`。

記錄這件事是因為它示範了 mock 與真實 API 形狀不一致的危害：
若當初把這條寫成「顯示任何錯誤即可」，就會漏掉
「使用者看不到是代碼重複，會一直重試同一個代碼」這個實際問題。

### 5.5 Temporal 孤兒流程

驗證 seed 時先刪了 `workflow_instance`，但 Temporal 端的執行還在跑。
結果是 34 個執行中的 workflow 只有 6 個有對應的 DB 列，
**28 個是孤兒**——它們持續重試找不到實例的 internal API 呼叫。

清理孤兒需要 `temporal workflow terminate` 權限，本批未執行。
建議清理測試資料時連 Temporal 端一起處理，
否則刪 DB 列只會製造更多孤兒。

### 5.6 ⚠️ E2E 套件會自我毒化，每跑一次環境就更慢

**這是本批最重要的發現，影響所有後續開發。**

#### 現象

同一份程式碼、同一台機器，連續三次全量 E2E：

| 次序 | 耗時 | 結果 | 失敗的是哪一條 |
|---|---|---|---|
| 第一次 | 403 秒 | 60 / 3 | 三條 F1 遺留的舊斷言（真缺陷，已修）|
| 第二次 | 437 秒 | 62 / 1 | 權限矩陣（登入逾時）|
| 第三次 | **1348 秒** | 61 / 2 | 登入逾時 + 待辦逾時 |

**耗時從 6.7 分鐘變成 22 分鐘，超過 3 倍。**
而且每次失敗的是**不同**的測試——這是負載的特徵，不是缺陷的特徵。

#### 原因

測試會啟動流程，但**不會把它跑完**。流程停在某個人工節點之後，
那個 Temporal workflow 就永遠活著，持續輪詢。

目前資料庫的狀態：

```
COMPLETED:  6
RUNNING:   73     ← 永遠不會結束
```

停在哪些節點：

```
approval           18
manager_approval   15
finance_approval   13
revise              4
```

累積速度（每小時新增的實例）：

```
11:00   5
10:00  16
09:00  12
昨 22:00  32
```

**每跑一次全量 E2E 就永久增加約 10 個不會結束的 workflow。**
Worker 要同時服務的執行數只增不減，到某個點就開始逾時。
系統負載實測 24.6。

#### 這解釋了先前記錄的多個「flake」

- 測試報告 12 §4.4 的「切換帳號」間歇失敗（57/1 → 58/0 → 單獨 22/22）
- 本批 `task-approval` 第一次 211 秒 4 個失敗、稍後 76 秒 7 個全過

**那些不是獨立的競態，是同一個負載問題的不同表現。**
先前判定為「既有競態，加長 timeout 只會掩蓋」——
方向對，但真正的根因在這裡。

#### 建議的解法

**測試要有 teardown。** 每個測試結束時把自己啟動的流程取消
（`POST /instances/{id}/cancel` 已存在），
或在套件結束時統一清理。

不做 teardown 的話，任何「E2E 全綠」的宣稱都有時效性——
它只在環境夠乾淨的時候成立，而環境會隨著每次執行變髒。

**這比加長 timeout 重要得多。** 加 timeout 只會讓 22 分鐘變成
30 分鐘，問題照樣在。

## 6. 已知限制

| 限制 | 說明 |
|---|---|
| 起始骨架固定 | 不能選「只要 start→end」或「兩關簽核」。等使用者回饋再決定要不要做範本選擇 |
| 業務物件不檢查是否存在 | 填一個沒有定義檔的業務物件可以建立，但之後用到資料路徑時 WF-E012 會擋。建立當下不擋是刻意的——強迫先建定義檔會讓 0→1 卡住 |
| 清單無分頁與搜尋 | 目前 111 個流程已經難以瀏覽（§5.2）。資料清理後再評估是否需要 |
