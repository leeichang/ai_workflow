## 2. 權限過濾畫面

使用者原話的第三件事：

> 系統依據權限設定顯示每個簽核人員的畫面

新增 `GET /sandboxes/{id}/tasks/{task_id}/form`。三個決定：

| 決定 | 為什麼 |
|---|---|
| 角色取**被扮演者**的 | 取測試者的會讓畫面是「測試者眼中的表單」。流程照樣會動、測試照樣全綠，但模擬出來的畫面與那個人真正簽核時看到的不同，功能就失去意義 |
| 資料用實例的 `input` | `visible_when` 依欄位值求值。不帶真實資料，條件式欄位全部判錯 |
| 表單版本用 P3 鎖定的 | 用當前發布版的話，簽核到一半改表單會讓模擬與實際不同 |

判定本身複用 `domain::permission::resolve_form()`，不重寫一份。

### 實機驗證

扮演張文華（`approver`、`cfo`）：

```
扮演: 張文華   角色: approver、cfo      ← 不是測試者的 designer
表單: quotation_form
  customer_name   唯讀    discount_rate  唯讀
  gross_margin    唯讀    internal_notes 可編輯
  ...共 9 欄
```

截圖 `simulation/06`。

### 一個要講清楚的限制

**HIDDEN 這條路徑沒有實機觀察到。** 種子的 `quotation_form`
沒有任何設 `readable_roles` 的欄位（唯一一個 `budget_note` 在
採購申請表單上），所以張文華的 9 欄全是唯讀或可編輯。

HIDDEN 的判定由 `domain` 的 `role_not_in_readable_list_gets_hidden`
與前端的四條測試蓋住，**但沒有在實機上看過一個人真的看不到某欄位**。
記下這個區別，是因為 14 號報告 §4.5 的教訓正是
「同一個條件成立」不等於「觀察到」。

## 3. 平行分支模擬

驗收標準（交辦 §5 S2）：**一個測試者從頭走完含平行分支的報價單流程**。

### 先補一條可走的流程

種子裡的 `quotation_approval` **沒有 parallel 節點**——
沒有平行流程可走，那條標準就無從驗證。

新增 `quotation_parallel_approval`（報價單會簽流程）：
主管簽核 → **財務與法務同時會簽（join ALL）** → 客戶簽核。
通過 DSL 驗證器並發布。

### 分支資訊從哪裡來

執行期**不存**會簽狀態——Temporal 自己持久化分支進度
（`interpreter.py:_run_parallel`：「不另外建 parallel_group 表：
兩份狀態就有兩份要對帳」）。

代價是「這張待辦屬於哪個會簽」在資料庫查不到。新增
`domain::parallel::branch_of()` 從 DSL 推導，**走訪規則刻意與
interpreter 一致**（分支起點＝parallel 的出邊；終點＝往下第一個 join）。
兩邊分歧會讓畫面說錯「還在等誰」，所以那 6 條單元測試
同時是對 interpreter 行為的一份說明。

### 實機走查：一人走完會簽

```
主管簽核 → 張文華            [無會簽]
  ↓ 以張文華簽核
會簽展開
  財務簽核 → 李淑芬          [財務與法務會簽 0/2 · ALL]
  法務簽核 → 張文華          [財務與法務會簽 0/2 · ALL]
  ↓ 以李淑芬簽財務
  法務簽核 → 張文華          [1/2 · 還在等法務]
  ↓ 以張文華簽法務
join 放行 → 客戶簽核
```

全程一個測試者、不換身分。截圖 `simulation/07`、`08`。

畫面把同一個會簽的待辦歸成一組並顯示進度——平鋪列出的話
使用者會以為流程分岔成兩條獨立的路，而實際上要兩邊都簽完才會往下走。

## 4. 時間快轉

`quotation_approval` 的 `manager_approval` 設 `P2D`、
`customer_review` 設 `P7D`。模擬時要真的等兩天、七天，等於無法驗證。

### 設計上的關鍵：不假造決策

新增 `skip_time` Signal，把等待視為已到期，讓**真正的逾時處理**執行
（`_handle_timeout_inline`，與真的等到逾時同一條路）。

假造一個 APPROVE 會讓模擬顯示「通過了」，而正式環境設的
`AUTO_REJECT` 其實是退回——**那比不給快轉更糟**，
因為使用者會帶著錯誤的結論上線。

Python 測試直接釘住這件事：

| 測試 | 驗證 |
|---|---|
| `test_AUTO_APPROVE_快轉後視為通過` | 走 AUTO_APPROVE → COMPLETED |
| `test_AUTO_REJECT_快轉後是退回而非通過` | **重點**。走 AUTO_REJECT → REJECTED。快轉若假造決策，這條會變成通過 |

### 授權擋兩層

```
HTTP  require_simulation_owner()    與模擬簽核同一條線
Workflow  InstanceInput.is_sandbox  預設 False
```

Signal 是能繞過 HTTP 的介面，而快轉會讓單據在沒人簽的情況下前進。
`is_sandbox` 預設 False 代表**既有的執行中實例也一併受保護**。
`test_正式租戶的實例拒絕快轉` 是永久回歸。

### 實機驗證，以及它抓到的東西

對 `manager_approval`（`P2D` / `ESCALATE`）快轉：

```
HTTP 200  {"policy": "ESCALATE", "after": "P2D"}

Worker log:
  WARNING 節點 manager_approval 逾時加簽，但解析不到新的參與者，改為繼續等待
```

逾時處理確實執行了。而它順手抓到一件真的事：

> **demo 租戶的 `sales_director` 角色掛了 0 個人。**
> 也就是說 `manager_approval` 設的 P2D 加簽在正式環境會靜默不發生。

```
demo 租戶角色人數：viewer 0 · sales_director 0 · designer 1 · admin 1
                  finance_manager 1 · cfo 1 · requester 3 · approver 3
```

**這正是模擬的價值**——它在驗證 resolver 設定對不對，
而這個設定是錯的。截圖 `simulation/09`、`10`。

按鈕寫明「快轉 2 天（加簽給上級）」而不只是「快轉」：
快轉跑的是真正的策略，使用者要先知道按下去會發生什麼。

## 5. 流程監控（S0）

交辦 §5 S0：「看得到所有執行中流程的清單與詳情。**權限正確
（一般使用者看不到別人的單）**」。

### 原本是全租戶可見

`GET /instances` 只靠 `tenant_tx()` 的 RLS——**RLS 隔離的是租戶**，
同租戶的人預設看得見彼此的每一張單。流程監控直接接上去
就變成全租戶的資料出口。

新增 `ListFilter.visible_to`：

```
看得到的條件（visible_to 為 None 時不設限）：
  1. 自己發起的
  2. 自己有（或曾有）待辦的
```

第二條不算新增洩漏——那張單本來就在你的收件匣裡。
少了它，簽核者在監控畫面看不到自己正在簽的單。

`visible_to` 刻意做成 `Option` 而非 `bool + user_id`：
呼叫端必須明確表態「不設限」，**漏傳會變成看得到全部**，
那正是要避免的方向。

單筆 `GET /instances/{id}` 同樣要濾——否則知道 id 就能繞過清單，
而 id 會出現在通知連結與稽核紀錄裡，不是秘密。
回 **404 而非 403**：403 等於告訴對方「這張單存在」。

### 實機驗證

```
admin@demo.local     roles=[admin]              107 筆（全部）
designer@demo.local  roles=[designer]           107 筆 ← 其中 101 筆自己發起、6 筆自己有待辦
sales@demo.local     roles=[requester]            6 筆（只有自己的）
```

逐筆查證：designer 看到的 6 筆非自己發起的單，**每一筆都確實有
designer 的待辦**。

```
sales 猜 designer 的單 id → 404
admin 讀同一筆           → 200
```

### 不設限的只有 admin

刻意**不**把 `approver`、`finance_manager` 一併放行：
那些角色是「會簽到某些單」，不是「該看到全部單」，
兩者混為一談會讓監控變成全租戶的資料出口。

> **這條需要確認。** 「誰該看得到全部」是政策決定不是技術決定。
> 目前寫死 admin，若營運上主管需要看團隊的單，要另外定義。

## 6. 過程中修掉的兩個自己的錯

### 6.1 不一致警告會叫錯（截圖才看得出來）

詳情頁比對「本地狀態」與「Temporal 回報」，不一致就跳警告。
第一版直接比字串。

截圖上看到：本地 `已取消`、引擎 `COMPLETED`、**跳了警告**。

原因：流程自己處理完取消後是**正常返回**的，Temporal 看到的是
「執行完成」，本地記的是業務結果「已取消」——兩者都對，
只是講的是不同層次的事。

這代表**每一筆取消的單都會跳警告**。
會叫錯的警告比沒有警告更糟：真的出問題時沒人會看。

改成只在「一邊說還在跑、另一邊說結束了」時才標。

### 6.2 載入失敗時同時顯示錯誤與「沒有單」

單元測試抓到的。載入失敗時 `items` 是空的，空狀態文案
「沒有你看得到的流程」照樣顯示——那會被讀成結論，而它是錯的。

### 6.3 E2E 自己的缺陷（全套執行才會紅）

`知道 id 也讀不到看不見的單` 原本直接拿 designer 清單的第一筆。
單跑會過，全套跑時因其他測試建立的資料而變成 sales 看得到的單，
回 200 而非 404。

**不是產品問題，是測試自己依賴了順序。**
改為先取 sales 的可見集合，再挑一筆確實不在裡面的。
