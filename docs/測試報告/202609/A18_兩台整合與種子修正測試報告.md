## 2. Migration 編號衝突（三組）

| 編號 | 這一台 | 另一台 |
|---|---|---|
| 0006 | `organization` | `form_version_lock` |
| 0007 | `integration` | `sandbox` |
| 0008 | `sync_thresholds` | `sandbox_creator_mapping` |

**這一次剛好沒出事**：同號的兩份動的是完全不同的表，互不依賴，
glob 排序下的執行順序恰好可行。

但那是運氣：

- 同號檔案的相對順序取決於檔名後半的字典序，沒有人會去檢查它
- 只要有一次真的交叉依賴（A 建表、B 改那張表），
  新環境從零跑就會失敗，而既有環境完全看不出問題

處理：這一台的三份往後移成 `0009` / `0010` / `0011`
（後合併的一方改自己的，不動已合併進來的）。
規則寫進 `server/migrations/README.md`。

改編號不影響已套用的環境——`psql -f` 不記錄檔名。

## 4. N4：問題比回報的更根本

N4 說「種子表單沒有任何 `readable_roles`」。

**實際上 `seed.sh` 裡的 `internal_note` 一直都有。**
沒生效的原因是 seed 只用 `POST /forms` 建立表單——
表單已存在時撞唯一約束、印出 `CONFLICT` 就跳過，
接著把**舊草稿**發布出去。

資料庫裡的欄位是 `internal_notes`、`gross_margin`，
而 `seed.sh` 寫的是 `internal_note`、`margin_rate`——
兩者從來沒對上過。

也就是說：**表單定義的任何修改都不會套用到既有環境。**
`readable_roles` 只是第一個被發現的受害者。

修法：seed 改成「建立失敗（409）就 `PUT /forms/{key}/draft` 更新草稿」。

### 4.1 實機驗證

```
requester  → internal_note: HIDDEN   （理由：角色不在可讀清單）
approver   → internal_note: EDITABLE
兩者       → margin_rate:   READONLY （理由：系統計算欄位）
```

HIDDEN 路徑第一次在實機上成立。

加了 `web/e2e/seed-permission-hidden.spec.ts`（3 條）守住它。
第二條刻意驗證 approver 看得到——只測 HIDDEN 的話，
一個所有人都看不到的欄位也會通過，但那是設定錯誤而非過濾正常。

## 5. N2：改成健康檢查抓，不只是補資料

N2 是 `sales_director` 掛 0 人，導致 `P2D` 逾時加簽靜默不發生。

補 seed 只解決 demo 租戶。**真正的問題是這類錯誤沒有人會發現**——
Worker 只留一行 WARNING，畫面與稽核都看不到。

所以在組織健康檢查加了 `ROLE_HAS_NO_MEMBERS`：
掃所有**已發布**流程的角色引用，兩種位置都看。

| 位置 | 失效方式 |
|---|---|
| `resolver.type = "role"` | 流程卡在該節點 |
| `timeout.to.type = "role"` | 升級**靜默不發生**，比卡住更難發現 |

草稿不檢查——還在改的流程引用一個還沒建人的角色是正常的設計過程。

找不到角色時也報（用 nil uuid），訊息不同：
「角色『X』在這個租戶裡不存在」。跳過等於讓一個更嚴重的問題
完全看不見。

### 5.1 雙向驗證

```
拿掉 sales_director 的指派 → 抓到：業務總監 | 角色代碼：sales_director | HIGH
跑 seed-demo 還原         → ROLE_HAS_NO_MEMBERS: 0
```

### 5.2 前端要處理第三種 subject

`ROLE_HAS_NO_MEMBERS` 的 subject 是角色，不是人或部門。
組織管理頁沒有「編輯角色成員」，指過去只會開一個不存在的
員工編輯然後靜默失敗——**那比沒有連結更糟**。

所以 role 類型不顯示「前往修正」。等角色管理 UI 做出來再接。
