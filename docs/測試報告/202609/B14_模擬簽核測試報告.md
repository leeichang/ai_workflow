## 1. 使用者要的是什麼

原話（2026-09-17）：

> 執行時可以直接由系統依據目前的系統角色設定解析出實際簽核的人員，
> 測試的人可以直接點選模擬這個人簽核，系統依據權限設定顯示每個
> 簽核人員的畫面，讓使用者模擬簽核！一一完成後最後整個流程完成！

三件事：**真的解析簽核人**、**一人扮演所有角色**、**看到那個人會看到的畫面**。

第二點是關鍵：**沙箱不是另一個環境，是一個附身模式**。
測試者不換身分登入，點一下就以某個人的身分簽核。

---

## 2. 實機驗證：一人走完兩關

從正式租戶身分（`designer@demo.local`）全程操作，**不換身分登入**：

```
建立開發模式                    → HTTP 201
在沙箱啟動報價單（折扣 0.2）    → HTTP 201
  ↓
待簽：主管簽核 → 張文華（真實 resolver 解析）
以張文華簽核 APPROVE            → HTTP 200
  ↓
discount_gate 判定 0.2 > 0.15，走財務加簽分支
  ↓
待簽：財務簽核 → 李淑芬
以李淑芬簽核 APPROVE            → HTTP 200
  ↓
待簽：客戶簽核 → c@example.com（外部，正式環境的已知缺口）
```

**簽核人由真實 resolver 從沙箱的角色與組織設定解析，不是假資料。**
這正是模擬最大的價值——它在驗證 resolver 設定對不對。

### 稽核同時記兩個身分

```
actor_id   31de0960-...  （真正按下按鈕的測試者）
acting_as  a3d0fc5a-...  （被扮演的張文華）
payload    is_simulation: true
```

只記 `acting_as` 的話，稽核會顯示張文華核准了某張單，
而他根本不知道有這回事。

### 3.1 授權邊界（永久回歸，6 條）

**這是整批最需謹慎的地方。** `tasks.rs:134` 的 assignee 檢查會擋下模擬
（測試者不是 assignee），必須開洞——而開洞的地方正是安全邊界。

條件寫死成兩個，**都不是角色**：

```rust
// 1. 必須是沙箱租戶（正式租戶的 is_sandbox 永遠是 false）
// 2. 操作者必須是該沙箱的建立者本人
//
// 不做成「有某個角色就能扮演」——那會變成正式環境的提權路徑。
// 沙箱身分不是一種權限，是一種環境狀態。
```

| 測試 | 驗證 |
|---|---|
| `production_tenant_never_allows_simulation` | **最重要**。正式租戶不論操作者是誰、任何角色組合都被擋 |
| `production_tenant_is_never_sandbox` | 正式租戶的 `is_sandbox` 恆為 false |
| `sandbox_creator_is_allowed` | 建立者本人可以 |
| `sandbox_non_creator_is_blocked` | 非建立者不可 |
| `retired_sandbox_blocks_simulation` | 退役後條件自動不成立 |
| E2E：正式租戶不可被當成開發模式 | 端到端回 403 |

那幾條**刻意複寫一份條件**而非呼叫實作——條件被偷改時
測試與實作會分歧而爆出來。

### 3.2 隔離（雙向）

```
sandbox_data_does_not_leak_into_parent              沙箱 → 正式
parent_data_does_not_leak_into_sandbox_after_creation  正式 → 沙箱
```

**雙向都測**——單向會漏掉「沙箱看得到正式的新資料」。
隔離本身沿用既有的 RLS + `tenant_tx()`，
不在任何查詢加 `where is_sandbox = false`：每處都要記得過濾的話，
漏一個就靜默洩漏。

## 4. 過程中修正的設計錯誤

四個都是**只有實機操作才會發現**的，單元測試全綠時它們都在。

### 4.1 主檔複製會靜默失敗

最初 `copy_master_data` 走原始連線池。應用程式角色是非 superuser，
**沒設 `app.tenant_id` 時 RLS 讓來源的 SELECT 回 0 筆**，
`INSERT ... SELECT` 於是插入 0 列，而且沒有任何錯誤。

沙箱看起來建好了，裡面卻沒有人——要到模擬簽核解析不到人才會發現。
正是本專案最討厭的那類失敗。

改為兩段 `tenant_tx` 讀寫，並在來源為空時當場失敗。

### 4.2 id 不能沿用來源的值

原本想讓「沙箱的張文華」與「正式的張文華」是同一個 uuid，
這樣 `acting_as` 能直接指回真人。但 `app_user.id` 與
`department.id` 都是**全域主鍵**，會撞鍵。

改為重新產生 + 對照表。要對回真人靠 email。

### 4.3 授權模型一開始就錯了（畫面才看得出來）

修完 4.2 之後，我把授權改成比對「沙箱內的 user id」。
單元測試全過——因為測試直接呼叫函式，沒有經過登入。

但畫面上出現一行紅字：**「只有開發模式的建立者可以模擬簽核」**。

原因：交辦寫明**測試者不換身分登入**，他一直以正式租戶的身分操作沙箱，
JWT 帶的是正式租戶的 id，與沙箱內的 id 不同，比對必定不成立——
**建立者反而進不了自己的沙箱**。

改為比對正式租戶的 id，並加上「沙箱必須屬於我的租戶」這條：
少了它，別的租戶只要知道沙箱 id 就能操作它。

### 4.4 少了在沙箱啟動測試單的入口

`POST /instances` 用 `actor.tenant_id`，測試者得登入沙箱才能啟動流程
——又與「不換身分」矛盾。

補上 `POST /sandboxes/{id}/instances`，閉環才成立。

---

### 4.5 通知改寫：收件人已驗證，標題前綴沒有

以沙箱身分呼叫 `POST /internal/notifications`，稽核記錄：

```
原收件人      ["cfo@demo.local"]        ← resolver 解析出的真實同事
實際寄達      ["designer@demo.local"]   ← 改寫成測試者本人
沙箱標記      true
狀態          sent
```

**收件人改寫確實生效**——信沒有寄給真實同事。三層收件人也都記下來了，
查得出「原本要寄給誰」。

**但標題前綴沒有直接驗證。** 它與收件人改寫是同一個條件
（`sandbox_tester.is_some()`），所以收件人改寫生效就代表前綴也加了——
**這是推論，不是觀察**。

記下這個區別是因為 SMTP 那次的教訓正是：
「有呼叫 `send_notification`」不等於「欄位是對的」。
要真正驗證得攔下寄出的信檢查標題，例如在測試用一個會記錄
`Mail` 的 transport。目前沒做。

## 5. 一個測試自己的缺陷

E2E 的模擬走查一度跑 **18 分鐘**後逾時。追查後不是產品問題：

```ts
page.getByRole('button', { name: /以張文華簽核/ })   // 找不到
```

模板是 `以 {{ t.assignee_name }} 簽核`，**Vue 會在插值前後留空白**，
實際文字是「以 張文華 簽核」。正規式沒有空白，比對不到，
點擊等滿 180 秒才逾時。

改用 `[data-testid^="act-as-"]` 之後，同一批測試 **14.8 秒**跑完。

**教訓**：靠渲染文字定位很容易因空白而失準，尤其有插值時。
有 testid 就用 testid。
