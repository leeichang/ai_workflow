### 1.1 職責邊界（不可互搶）

| 角色 | 負責 | 不負責 |
|---|---|---|
| Rust API | 身份、權限、業務資料、簽核人解析、稽核、對外 API | 執行流程、等待、重試 |
| Temporal | 流程存活、等待、Timer、Retry、取消、版本 | 業務資料、決策規則 |
| Python Worker | 流程語意解釋、Join 判斷、實際做事（PDF、ERP、通知、AI） | 身份驗證、權限判斷 |
| PostgreSQL | 業務真相、查詢用投影 | 流程執行狀態（在 Temporal） |
| AI | 回傳結構化結果 | 決定下一節點、直接寫入 ERP |

## 2. 核心模型

### 2.1 Business Object

每個場景以 Business Object 為根，下掛四份定義：

```text
business_object: quotation
 ├── data_contract      欄位、型別、來源綁定（JSON Schema）
 ├── form_definition    UI（單一物件，欄位內 ui / data / workflow 三 key，A-02）
 ├── workflow_definition DSL（版本化，發布即 immutable）
 └── permission         誰可建、可看、可改；欄位層級 Phase 2
```

### 2.2 Workflow DSL

DSL 是 Rust / Python / 前端三方共用契約，唯一真相是 `schemas/workflow-dsl.schema.json`。

```json
{
  "workflow_key": "quotation_approval",
  "version": 1,
  "business_object": "quotation",
  "trigger": { "type": "form_submit" },
  "nodes": [
    { "id": "start", "type": "trigger" },
    { "id": "manager_approval", "type": "human_approval",
      "participant": "internal",
      "resolver": { "type": "manager_of", "of": "initiator" },
      "on_reject": { "action": "goto", "node": "revise" } },
    { "id": "discount_gate", "type": "condition",
      "expression": "quotation.discount_rate > 0.15" },
    { "id": "finance_approval", "type": "human_approval",
      "participant": "internal",
      "resolver": { "type": "role", "value": "finance_manager" },
      "on_reject": { "action": "goto", "node": "revise" } },
    { "id": "publish_to_customer", "type": "action",
      "action": "quotation.publish",
      "idempotency_key": "{{instance.id}}:{{node.id}}:{{quotation.version}}" },
    { "id": "customer_review", "type": "human_approval",
      "participant": "external",
      "resolver": { "type": "external_contacts", "path": "quotation.customer_contacts" },
      "join": { "completion": "ALL", "result": "ALL_SUCCESS" },
      "timeout": { "after": "P7D", "policy": "ESCALATE", "to": "initiator" },
      "on_reject": { "action": "goto", "node": "revise" } },
    { "id": "revise", "type": "human_task",
      "participant": "internal",
      "assignee": { "type": "initiator" },
      "next": "manager_approval" },
    { "id": "create_order", "type": "action",
      "action": "odoo.create_sale_order",
      "idempotency_key": "{{instance.id}}:{{node.id}}" },
    { "id": "notify_done", "type": "notification",
      "channel": ["email"], "to": ["initiator", "quotation.customer_contacts"] },
    { "id": "end", "type": "end" }
  ],
  "edges": [
    ["start", "manager_approval"],
    ["manager_approval", "discount_gate"],
    ["discount_gate", "finance_approval", { "when": true }],
    ["discount_gate", "publish_to_customer", { "when": false }],
    ["finance_approval", "publish_to_customer"],
    ["publish_to_customer", "customer_review"],
    ["customer_review", "create_order"],
    ["create_order", "notify_done"],
    ["notify_done", "end"]
  ]
}
```

DSL 規則：
- Node 型別 MVP：`trigger` `condition` `human_approval` `human_task` `parallel` `join` `action` `notification` `end`。`ai_task` Phase 2。
- `human_approval` 內建多人與 Join Policy；`parallel` / `join` 只用於「不同節點並行」的情境。
- `on_reject.goto` 是唯一允許的回跳；Validator 檢查回跳目標必須在同一路徑上游，防止死迴圈以外的任意跳轉。
- 表達式語言：CEL 子集（比較、邏輯、算術、路徑存取），Rust 與 Python 各用一個 CEL 實作，以共用 fixture 驗證一致。
- DSL 不得含 Temporal 詞彙（activity / signal / timer）。DSL → Execution IR → Temporal 在 Python 內完成。

### 2.3 Approval Policy Engine（Python，純函數）

```text
輸入：task_results: list[{task_id, participant_id, decision: APPROVE|REJECT|PENDING, at}]
      policy: {completion: ALL|ANY|N_OF_M, n?: int, result: ALL_SUCCESS|ANY_REJECT|MAJORITY}
      now, deadline?
輸出：CONTINUE | WAIT | REJECT | TIMEOUT
```
- 決定性、無 IO、可在 Temporal Workflow 內直接呼叫。
- 表格式測試涵蓋 ALL / ANY / N_OF_M × ALL_SUCCESS / ANY_REJECT × Timeout 交錯。

### 2.4 Approver Resolver（Rust）

```text
POST /internal/resolver/resolve
{ tenant_id, resolver: {type, ...}, context: {initiator_id, business_object: {...}} }
→ { participants: [{id, kind: internal|external, display, contact}] }
```
支援型別 MVP：`user` `role` `department_manager` `manager_of` `external_contacts` `expression`（CEL 篩選）。SQL / API / AI resolver 後做。
每次呼叫即時解析，不快照人名（離職即自動換人）。

### 2.5 Human Task 生命週期

```text
Workflow → activity human_task.create(node, participants, deadline)
        → Rust 建 human_task rows（status=PENDING）→ 通知
        → 使用者 / 外部客戶提交 → Rust 驗證身份、權限、狀態
        → Rust Signal Temporal: task_completed{task_id, decision, comment}
        → Workflow 更新結果集合 → Policy Engine → CONTINUE / WAIT / REJECT
        → CONTINUE 時 activity human_task.cancel(剩餘 PENDING)
```

### 2.6 外部參與者

```text
external_party         客戶公司（tenant 內）
external_contact       聯絡人（email、姓名、職稱）
portal_access          per (instance, contact) 的 token；到期、可撤銷、單一用途 nonce
external_task          human_task 的子型，participant_kind=external
```
- Portal 只暴露：該 instance 的文件檢視、簽核、留言、版本歷史、PDF 下載。
- Token 存 hash，一次性 nonce 防重放；操作全部寫 audit（IP、UA、時間）。
- 不與內部 JWT 共用 session。

### 2.7 文件模板引擎

- 模板：Jinja2 HTML；租戶可覆寫 Logo、抬頭、條款；版本化存 DB。
- 渲染：WeasyPrint → PDF；CJK 字型內建（Noto Sans CJK）。
- 每個 quotation 版本渲染一次，PDF 存物件儲存，`document_version` 記 hash。
- 替代方案（若 WeasyPrint 版面不足）：Playwright Chromium 列印，成本較高，Phase 2 評估。

## 3. 資料層

### 3.1 表分類

| 類型 | 表 | 儲存方式 |
|---|---|---|
| 租戶與身份 | tenant, user, role, user_role, department, external_party, external_contact, portal_access | Relational |
| 定義 | business_object_def, data_contract_version, form_definition_version, workflow_definition_version, document_template_version | Relational 表頭 + JSONB 內容；發布後 immutable |
| 業務實例 | quotation, quotation_line, quotation_version, purchase_request … | Relational（每個 BO 自己的表，非 EAV） |
| 流程投影 | workflow_instance（id, tenant, bo_type, bo_id, definition_version_id, temporal_workflow_id, status, current_nodes[]） | Relational，由 Worker 事件更新，供列表查詢 |
| 任務 | human_task（id, instance_id, node_id, participant_kind, participant_id, status, decision, comment, deadline, decided_at） | Relational |
| 稽核 | audit_event（append-only, actor, action, target, payload JSONB, ip, ua, at） | Relational + JSONB |
| 整合 | erp_write_log（idempotency_key UNIQUE, target_system, external_id, status） | Relational |
| AI | ai_execution（Phase 2） | Relational + JSONB |

### 3.2 隔離
- 所有表帶 `tenant_id`，PostgreSQL Row Level Security 強制；連線層設定 `app.tenant_id`。
- Temporal 單一 Namespace，workflow_id 帶 tenant 前綴；Enterprise 需求再拆 Namespace。

### 3.3 版本
- 定義表發布後 immutable；修改即新版本。
- `workflow_instance.definition_version_id` 在啟動時鎖定；在途實例跑舊版到結束。
- 程式碼層演進用 Temporal patching；在途遷移工具 Phase 3。

## 4. 安全

- 內部：JWT（短效）+ refresh；RBAC 角色：admin / designer / approver / requester / viewer。
- 外部：magic link token（hash 存 DB，TTL 7 天，可撤銷），每次操作附一次性 nonce。
- 憑證：Odoo / SMTP / LINE 憑證加密存 `tenant_credential`（KMS 或 libsodium sealed box），Worker 執行時解密，不進日誌。
- ERP 寫入：`idempotency_key` 唯一約束；重試前先查 `erp_write_log`。
- AI（Phase 2）：Tool 白名單、輸出 Schema 驗證、外部文件內容標記為不可信、寫入一律經人審。
- 稽核：所有簽核、發布、下載、ERP 寫入寫 audit_event。

## 5. 部署

- 單一 `docker-compose.yml`：postgres、temporal、temporal-ui、api（Rust）、worker（Python）、web（Vue 靜態）、portal（Vue 靜態）、minio（物件儲存）。
- SaaS 與 On-premise 同一份 compose；差異只在環境變數與憑證。
- 觀測：Temporal Web UI 技術視角；業務 Monitor 讀 `workflow_instance` 與 `human_task` 投影。
