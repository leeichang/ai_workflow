# 功能規劃

- 日期：2026-09-14
- 範圍：MVP 功能（[02_功能清單.md](02_功能清單.md) 標 MVP 者）的行為規格與驗收條件。P2 以後只列方向。
- 格式：每模組含使用者故事、行為規則、API 面、驗收條件（Given / When / Then）。

## 1. 身份、租戶、權限

### 1.1 使用者故事
- 管理者建立租戶、匯入使用者與部門、設定主管鏈。
- 管理者指派角色；業務員（requester）建報價；主管（approver）簽核；設計者（designer）改流程。
- 業務員新增客戶公司與聯絡人，供報價單外部簽核。

### 1.2 行為規則
- 每個使用者屬一個租戶；`user.manager_id` 可空；部門有 `manager_user_id`。
- 角色不可自訂（MVP 固定五種）。
- 外部聯絡人不是 user，無密碼，只能透過 portal_access token 進入。
- RLS：連線設定 `SET app.tenant_id`，所有表 policy 檢查 `tenant_id = current_setting('app.tenant_id')`。

### 1.3 API（Rust）
```text
POST   /auth/login                      → JWT
GET    /me
GET    /users?department=
POST   /users  PATCH /users/{id}
GET    /departments  POST /departments
GET    /external-parties  POST /external-parties
POST   /external-parties/{id}/contacts
```

### 1.4 驗收
- Given 兩個租戶各有一筆 quotation，When 租戶 A 使用者查詢 `/quotations`，Then 只回租戶 A 的資料，且直接 SQL 以租戶 A 連線亦查不到 B。
- Given 使用者無 approver 角色，When 提交簽核，Then 403。

## 2. Business Object：quotation

### 2.1 資料結構
```text
quotation
  id, tenant_id, number（租戶內流水，QT-2026-0001）, status
  customer_party_id, customer_contact_ids[]（外部簽核人）
  initiator_user_id, currency, valid_until, payment_terms
  discount_rate（表頭折扣）, subtotal, tax, total, margin_rate（計算）
  current_version, created_at, updated_at
quotation_line
  id, quotation_id, seq, product_ref（Odoo product id）, name, qty, unit, unit_price, cost, line_discount, amount
quotation_version
  id, quotation_id, version, snapshot JSONB, pdf_object_key, pdf_sha256, published_at, published_by
quotation_attachment
  id, quotation_id, file_object_key, filename, uploaded_by
```

### 2.2 狀態機（業務狀態，與流程節點對應）
```text
DRAFT → SUBMITTED → IN_APPROVAL → PUBLISHED（送客戶）→ CUSTOMER_REVIEW
  → ACCEPTED → ORDERED
  → REVISING（任一階段退回）→ SUBMITTED（版本 +1）
  → CANCELLED
```
- 狀態由 Workflow 的 action / 節點進入事件更新，不由前端直接改。
- `margin_rate = (subtotal - Σcost) / subtotal`，後端計算，前端唯讀。

### 2.3 驗收
- Given 明細三行，When 更新 line_discount，Then subtotal / total / margin_rate 重新計算且與手算一致（測試給定數值）。
- Given 已 PUBLISHED，When 業務員直接 PATCH 明細，Then 409，必須經 REVISING。

## 3. 表單

### 3.1 Schema 格式（A-02，單一物件）
```json
{
  "form_key": "quotation_form",
  "version": 1,
  "fields": [
    {
      "key": "discount_rate",
      "ui":   { "component": "number", "label": "表頭折扣率", "precision": 4, "width": 6 },
      "data": { "path": "quotation.discount_rate", "type": "decimal", "min": 0, "max": 0.5 },
      "workflow": {
        "readonly_when": "node.id != 'start' && node.id != 'revise'",
        "required_when": "true"
      }
    },
    {
      "key": "lines",
      "ui":   { "component": "table", "label": "報價明細",
                "columns": ["product_ref", "name", "qty", "unit_price", "line_discount", "amount"] },
      "data": { "path": "quotation.lines", "type": "array", "item": "quotation_line" },
      "workflow": { "readonly_when": "node.id != 'start' && node.id != 'revise'" }
    }
  ]
}
```

### 3.2 渲染規則
- Runtime 合併：form schema + 當前 node + 使用者角色 + 業務資料 → 計算 readonly / visible / required → 轉成 @form-create rule 陣列。
- 表達式以 CEL 子集求值，前端與 Rust 各一實作，共用 fixture 測一致。
- 外部 Portal 用同一 schema 但強制 readonly，且只顯示 `ui.external_visible != false` 的欄位。

### 3.3 驗收
- Given node = manager_approval，When 主管開表單，Then 折扣率唯讀、明細唯讀、簽核意見欄可寫。
- Given node = revise，When 業務員開表單，Then 折扣率與明細可寫。

## 4. Workflow 定義與 Designer

### 4.1 使用者故事
- 設計者在 Designer 拖入節點（固定排版）、設定屬性、儲存草稿、驗證、發布。
- 發布產生新版本；在途實例不受影響。

### 4.2 Validator 規則（MVP）
| 規則 | 錯誤碼 |
|---|---|
| 恰一個 trigger、至少一個 end | WF-E001 |
| 所有節點可從 trigger 到達，且可到達某 end | WF-E002 |
| condition 有 true / false 兩條出邊 | WF-E003 |
| `on_reject.goto` 目標在該節點上游路徑 | WF-E004 |
| resolver.type 合法且 role / department 存在於租戶 | WF-E005 |
| 表達式可解析且引用路徑存在於 Data Contract | WF-E006 |
| action 名稱存在於 Action Registry | WF-E007 |
| `human_approval.participant=external` 的 resolver 必須是 external_contacts | WF-E008 |

### 4.3 Designer 行為
- 節點面板：trigger / condition / human_approval / human_task / parallel / join / action / notification / end。
- 佈局：dagre 由上往下；condition 與 parallel 子分支橫向；使用者不可拖移位置，只可拖入插入點。
- 屬性面板由 `node-property.schema.json` 驅動；每種節點一份屬性 Schema。
- 儲存即呼叫 Validator，錯誤標在節點上。

### 4.4 API
```text
GET    /workflows                          列表（含各版本狀態）
POST   /workflows                          建立草稿
PUT    /workflows/{key}/draft              儲存草稿 DSL
POST   /workflows/{key}/draft/validate     → {errors: [{code, node_id, message}]}
POST   /workflows/{key}/draft/publish      → {version}
GET    /workflows/{key}/versions/{v}
```

### 4.5 驗收
- Given DSL 有回跳到下游節點，When validate，Then 回 WF-E004 指向該節點。
- Given v1 有 3 個在途實例，When 發布 v2，Then 3 個實例 `definition_version_id` 仍為 v1，新建實例為 v2。

## 5. Runtime

### 5.1 Interpreter 行為
```text
run(dsl, instance_ctx):
  cursor = trigger.next
  loop:
    node = dsl.nodes[cursor]
    match node.type:
      condition     → eval CEL → cursor = true/false edge
      human_approval→ participants = activity resolver.resolve()
                      activity human_task.create(participants, deadline)
                      wait signals until policy(results) != WAIT or timer(deadline)
                      CONTINUE → activity human_task.cancel(pending); cursor = next
                      REJECT   → apply on_reject（goto: quotation.version += 1 via activity; cursor = target）
                      TIMEOUT  → policy ESCALATE: activity notify(to); 再等；或 AUTO_*：視同結果
      human_task    → 同上，單人、無 policy，完成即 CONTINUE
      parallel      → 各分支 child path 以 asyncio.gather 執行至 join
      join          → policy 判斷後合流
      action        → activity <action>(idempotency_key)；失敗依 retry policy；耗盡 → instance FAILED，通知 admin
      notification  → activity notify
      end           → instance COMPLETED
    activity instance.update_projection(cursor, status)
```
- Signal 名稱：`task_completed{task_id, decision, comment, actor}`、`cancel_instance{reason}`。
- Query：`current_state` → {current_nodes, pending_tasks}。

### 5.2 Policy Engine 測試矩陣（節錄）
| completion | result | 輸入 | 期望 |
|---|---|---|---|
| ALL | ALL_SUCCESS | 3 人 2 APPROVE 1 PENDING | WAIT |
| ALL | ALL_SUCCESS | 3 人 3 APPROVE | CONTINUE |
| ALL | ANY_REJECT | 3 人 1 REJECT 2 PENDING | REJECT（立即） |
| ANY | ALL_SUCCESS | 3 人 1 APPROVE | CONTINUE |
| N_OF_M n=2 | ALL_SUCCESS | 4 人 2 APPROVE | CONTINUE |
| 任一 | 任一 | now > deadline 且 WAIT | TIMEOUT |

### 5.3 Idempotency
- 每個 action 執行前：`SELECT status FROM erp_write_log WHERE idempotency_key = ?`；SUCCESS 直接回傳既有 external_id；PENDING 視為衝突等待；無紀錄才寫入 PENDING 後執行。

### 5.4 驗收
- Given Worker 在 customer_review 等待中被 kill，When 重啟，Then 實例狀態不變，客戶提交後流程繼續。
- Given Odoo 第一次呼叫 timeout 但實際建單成功，When Temporal 重試，Then 不建第二張單，`erp_write_log` 只有一筆 SUCCESS。

## 6. 簽核人解析

### 6.1 Resolver 型別與語意
| type | 參數 | 語意 |
|---|---|---|
| user | user_id | 固定人 |
| role | value | 租戶內該角色所有人（human_approval 時全部成為參與者） |
| department_manager | of: initiator \| department_id | 部門主管 |
| manager_of | of: initiator \| user_id | 該人的 manager_id |
| external_contacts | path | 業務資料路徑上的聯絡人 id 陣列 |
| expression | cel | 對候選集合篩選，例如 `user.role == 'finance_manager' && quotation.total > 1000000` |

### 6.2 規則
- 解析結果為空 → 節點錯誤 `RESOLVE_EMPTY`，實例進 FAILED_RESOLUTION，通知 admin 指定人後 Signal 續跑。
- 解析在 human_task.create 前即時進行，不快照。

## 7. Human Task 與收件匣

### 7.1 API
```text
GET    /tasks?status=pending|done&mine=true
GET    /tasks/{id}                          → task + form(rendered rules) + instance progress
POST   /tasks/{id}/decision  {decision: APPROVE|REJECT, comment}
```
### 7.2 規則
- 只有 participant 本人可提交；已 DECIDED 或 CANCELLED 回 409。
- 提交成功後同步 Signal Temporal；Signal 失敗則交易回滾，回 503 請重試。
- 逾期：deadline 過後標示 OVERDUE，通知由 Workflow Timer 觸發，不由收件匣輪詢。

## 8. 客戶 Portal

### 8.1 進入
- 發布時對每位 customer_contact 產生 token（32 bytes random，DB 存 SHA-256），寄 Email 含 `https://portal.{domain}/q/{token}`。
- 開啟：驗 token 未撤銷、未過期、對應 instance 在 CUSTOMER_REVIEW；成功後發短效 portal session（15 分鐘，cookie，SameSite=Strict）。

### 8.2 功能
```text
GET  /portal/session/{token}          → 建 session
GET  /portal/quotation                → 當前版本 HTML 檢視資料 + 版本列表
GET  /portal/quotation/versions/{v}/pdf
POST /portal/decision  {decision: APPROVE|REJECT, comment, nonce}
```
- 多聯絡人時各自一個 external_task；Policy ALL / ALL_SUCCESS。
- 退回：instance 進 REVISING；所有 token 撤銷；重新發布時重發新 token。
- 稽核：session 建立、PDF 下載、決定，各寫 audit_event（ip, ua）。

### 8.3 驗收
- Given token 已撤銷，When 開啟連結，Then 顯示「此報價已更新，請查看最新 Email」。
- Given 兩位聯絡人，When 一位 REJECT，Then 立即 REVISING，另一位開啟顯示已關閉。

## 10. Odoo 整合

### 10.1 讀
- `res.partner`：搜尋客戶（name / vat），建立 external_party 時可一鍵帶入。
- `product.product`：搜尋品項，帶 `list_price`、`standard_price`（成本）。
- 快取：15 分鐘，租戶層級。

### 10.2 寫（action `odoo.create_sale_order`）
```text
輸入：quotation snapshot（ACCEPTED 版本）
步驟：
  1. erp_write_log 檢查 idempotency_key
  2. partner_id = 對照表（external_party.odoo_partner_id），無則 create res.partner
  3. sale.order create {partner_id, date_order, validity_date, order_line: [(0,0,{product_id, product_uom_qty, price_unit, discount})], client_order_ref: quotation.number}
  4. action_confirm（可設定：僅建 quotation 不確認）
  5. 回寫 quotation.odoo_sale_order_id、erp_write_log SUCCESS
```
- 憑證：`tenant_credential(kind='odoo', url, db, uid, api_key)` 加密。

### 10.3 驗收
- Given 明細含折扣，When 建單，Then Odoo 該單 amount_total 與平台 total 差 < 0.01。

## 14. 採購簽核場景（MVP-P6，D-01b）

### 14.1 流程
```text
採購申請（人工填單）→ 動態並簽（金額門檻決定參與者）→ 全數核准 → Odoo 建 PO → 通知申請人
                                              └ 任一退回 → REVISING → 修改後重簽
```

### 14.2 資料結構
```text
purchase_request
  id, tenant_id, number（PR-2026-0001）, status
  requester_user_id, department_id, supplier_party_id（可空，未定供應商）
  need_by_date, reason, currency
  subtotal, tax, total, current_version, created_at, updated_at
purchase_request_line
  id, purchase_request_id, seq, product_ref（Odoo product id）, name, qty, unit, unit_price, amount, note
```

### 14.3 狀態機
```text
DRAFT → SUBMITTED → IN_APPROVAL → APPROVED → ORDERED
  → REVISING（任一關退回）→ SUBMITTED（版本 +1）
  → CANCELLED
```
與 quotation 差異：無 PUBLISHED / CUSTOMER_REVIEW / ACCEPTED（無外部參與者）。

### 14.4 DSL
```json
{
  "workflow_key": "purchase_approval",
  "version": 1,
  "business_object": "purchase_request",
  "trigger": { "type": "form_submit" },
  "nodes": [
    { "id": "start", "type": "trigger" },
    { "id": "approval", "type": "human_approval",
      "participant": "internal",
      "resolver": { "type": "composite", "of": [
        { "type": "manager_of", "of": "initiator" },
        { "type": "role", "value": "finance_manager" },
        { "type": "role", "value": "cfo",
          "when": "purchase_request.total > 1000000" }
      ]},
      "join": { "completion": "ALL", "result": "ALL_SUCCESS" },
      "timeout": { "after": "P3D", "policy": "ESCALATE", "to": "initiator" },
      "on_reject": { "action": "goto", "node": "revise" } },
    { "id": "create_po", "type": "action",
      "action": "odoo.create_purchase_order",
      "idempotency_key": "{{instance.id}}:{{node.id}}" },
    { "id": "revise", "type": "human_task",
      "participant": "internal",
      "assignee": { "type": "initiator" },
      "next": "approval" },
    { "id": "notify_done", "type": "notification",
      "channel": ["email", "line"], "to": ["initiator"] },
    { "id": "end", "type": "end" }
  ],
  "edges": [
    ["start", "approval"],
    ["approval", "create_po"],
    ["create_po", "notify_done"],
    ["notify_done", "end"]
  ]
}
```

新增能力：`resolver.type = composite`，子 resolver 可帶 `when` 條件式，條件為 false 時該子項不產生參與者。這是「金額門檻動態加簽 CFO」的實作方式，比在 DSL 畫多條 condition 分支簡潔，且 Designer 屬性面板可用表格呈現。

### 14.5 Odoo 建 PO（action `odoo.create_purchase_order`）
```text
輸入：purchase_request snapshot（APPROVED 版本）
步驟：
  1. erp_write_log 檢查 idempotency_key
  2. partner_id：supplier_party_id 對照 odoo_partner_id；未指定供應商則此步失敗，退回 REVISING 要求補
  3. purchase.order create {partner_id, date_planned: need_by_date,
       order_line: [(0,0,{product_id, product_qty, price_unit, date_planned})],
       partner_ref: purchase_request.number}
  4. button_confirm（可設定：僅建草稿不確認）
  5. 回寫 purchase_request.odoo_purchase_order_id、erp_write_log SUCCESS
```

### 14.6 表單
與 quotation 同一機制（單一 Schema 物件、明細表格元件複用 `LineTable.vue`）。差異欄位：`need_by_date`、`reason`、`supplier_party_id`（供應商 lookup，Odoo `res.partner` 篩 `supplier_rank > 0`）。無折扣率、無毛利率。

### 14.7 驗收
- Given total = 900,000，When 提交，Then 產生 2 個 task（主管、財務），無 CFO。
- Given total = 1,200,000，When 提交，Then 產生 3 個 task 含 CFO。
- Given 財務退回，When 申請人修改金額至 800,000 重新提交，Then 版本 +1 且只產生 2 個 task。
- Given 未指定供應商而流程走到 create_po，Then 進 REVISING 並通知申請人補供應商，不建立 Odoo 單。
- Given Odoo 建單 timeout 後重試，Then `erp_write_log` 僅一筆 SUCCESS，Odoo 僅一張 PO。
