# 報價單與採購簽核實作計畫

> 層級：系統規劃。每個 Phase 開工前，依 `superpowers:writing-plans` 展開為逐步 TDD 任務計畫（`docs/superpowers/plans/`）。本文件定義 Phase、任務、介面契約、驗收條件與風險。

**目標：**
1. 報價單（Phase 0～5，14 週）：業務員建立 → 內部審核鏈（主管，折扣門檻加簽財務）→ 送交客戶 Portal → 客戶端多人簽核與下載 PDF → 客戶接受 → Odoo 建立訂單 → 通知。
2. 採購簽核（Phase 6，+3～4 週，累計 18 週）：人工填單 → 金額門檻動態並簽 → Odoo 建立 PO → 通知。複用報價單全部引擎，增量僅 5 項功能。

**架構：** Rust (Axum) API 負責身份、權限、業務資料、簽核人解析與 Temporal gRPC 控制；Temporal Self-host 負責流程存活；Python Worker 解釋 DSL、判斷 Join Policy、執行 PDF / Odoo / 通知 Activity；Vue 3 內部應用與客戶 Portal。詳見 [01_系統架構.md](01_系統架構.md)。

**技術棧：** Rust 1.8x + Axum + sqlx + tonic；Python 3.12 + temporalio + httpx；Node 20 LTS + pdfme（單據 PDF 渲染服務）；Vue 3 + Vite + TypeScript + @form-create + Vue Flow + dagre + @pdfme/ui；PostgreSQL 16；Temporal Server（docker）；MinIO。

## 全域限制
- DSL 唯一真相：`schemas/workflow-dsl.schema.json`；Rust / Python / TS 型別皆由此產生；CI fixture 一致性測試必過。
- 所有表帶 `tenant_id` 且啟用 RLS；migration 內建 policy。
- 任何寫入外部系統的 Activity 必帶 `idempotency_key` 並經 `erp_write_log`。
- 外部 Portal 與內部 API 分開 router、分開 session 機制、分開 OpenAPI 檔。
- 每個 Phase 結束必須有可示範的端到端行為，不得只有元件。
- 不做：n8n、AI 節點、自由拖曳 Designer、Saga、Dataset Version（見 [02_功能清單.md](02_功能清單.md)）。
- 報表：不整合 CellReport（授權含商用加註、.NET 6 已 EOL、直連資料庫繞過 RLS，見 [05_報表模組評估.md](05_報表模組評估.md)）。MVP 只做固定報表與 CSV 匯出（任務 4.3b），自助分析列 P2 且須先通過 Univer spike。
- 任何新增的資料查詢一律經 Rust 連線中介層，確保 `app.tenant_id` 生效。不允許任何元件直連 PostgreSQL。
- **ERP 整合目標為 Odoo 16 社群版**（決議 D-04b）。Adapter 只用 XML-RPC / JSON-RPC 標準介面，不裝自訂 Odoo 模組。欄位差異集中於 `python-ai/adapters/odoo/v16.py`。不得依賴任何企業版模組。
- **測試強制要求**（見 [09_測試策略.md](09_測試策略.md)）：
  - 每個新增的 API 端點，必須有 client 呼叫的單元測試（Vitest + MSW，涵蓋請求格式、回應解析、錯誤處理、認證標頭四項），以及後端整合測試（含跨租戶 RLS 隔離）。
  - 每個新增的 UI 畫面，必須有 Playwright E2E 測試，至少涵蓋正常、錯誤、邊界三個情境。
  - 所有可測元素必須標 `data-testid`，禁止用 CSS class 或文字內容當選擇器。
  - MSW 需設 `onUnhandledRequest: 'error'`，未攔截的請求視為失敗。

### 任務 2.6a Node 渲染服務（pdfme）
- 依據：[06_單據套版設計器選型.md](06_單據套版設計器選型.md) 第 5 節。取代原訂 Jinja2 + WeasyPrint。
- 檔案：`render/package.json`、`render/src/server.ts`、`render/src/fonts.ts`、`render/Dockerfile`、`render/tests/render.test.ts`
- 介面：
  ```text
  POST /render   Content-Type: application/json
  { "template": {...}, "inputs": [{...}], "fonts": ["noto-sans-tc"] }
  → 200 application/pdf (bytes)
  → 400 {code: "INVALID_TEMPLATE"|"INVALID_INPUT", message}
  GET /health → 200 {status: "ok", pdfme_version}
  ```
  ```typescript
  // render/src/server.ts
  import { generate } from '@pdfme/generator';
  import { text, image, barcodes } from '@pdfme/schemas';
  import { tablePlus } from './plugins/table-plus';   // 任務 2.6d

  const plugins = { text, image, table: tablePlus, ...barcodes };

  app.post('/render', async (req, res) => {
    const { template, inputs, fonts } = RenderRequest.parse(req.body);
    const pdf = await generate({ template, inputs, plugins, options: { font: loadFonts(fonts) } });
    res.type('application/pdf').send(Buffer.from(pdf));
  });
  ```

  - 步驟：讀 template version → 組 pdfme inputs → POST 渲染服務 → 上傳 MinIO → 回 object_key 與 sha256。
  - 明細 2D 陣列組裝（[06 選型](06_單據套版設計器選型.md) 7.1）：明細行之後附加合計列，稅額為零時不附加該列。
    ```python
    rows = [[l.name, fmt_qty(l.qty), l.unit, fmt_money(l.unit_price), fmt_money(l.amount)]
            for l in snapshot.lines]
    rows.append(["", "", "", "小計", fmt_money(snapshot.subtotal)])
    if snapshot.tax > 0:
        rows.append(["", "", "", "稅額", fmt_money(snapshot.tax)])
    rows.append(["", "", "", "總計", fmt_money(snapshot.total)])
    ```
  - 金額格式化在 Python 端完成（千分位、幣別小數位），渲染服務不做業務格式化。
- 驗收：中文無缺字；同一 snapshot 兩次渲染 sha256 相同（模板決定性，日期由 snapshot 提供）；50 行明細產生多頁且每頁有表頭；合計三列不跨頁；不含稅報價只出現小計與總計兩列。

### 任務 6.5 採購 DSL 與流程模板
- 檔案：`schemas/fixtures/purchase_approval_v1.json`、`templates/workflow/purchase_approval.json`

### 任務 6.6 Odoo 建 PO Action

### 任務 6.7 端到端驗收

## 風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| Temporal gRPC 由 Rust 直呼，Payload 編碼與 Python 不相容 | Phase 1 卡關 | 任務 1.3 先做整合測試；不通則退回 Python Gateway（D-02 替代方案） |
| WeasyPrint 版面不符 pilot 報價單樣本 | PDF 重做 | Phase 0 取得樣本先試渲染；不行改 Playwright |
| pilot 客戶端不願用 Portal，只想回 Email | Portal 價值落空 | Portal 保留 Email 內「同意 / 退回」按鈕直達 decision 頁，一鍵完成 |
| Odoo 版本差異（14 / 16 / 17 欄位不同） | 建單失敗 | Adapter 以版本旗標分支；Phase 0 確認 pilot 版本 |
| 一人團隊三語言 | 進度 | Rust 範圍鎖死於 Phase 1 清單；新功能優先落 Python |
| 業務主管臨時要求 N_OF_M / 代理 | 範圍蔓延 | 列 P2；MVP 以 ALL + ANY_REJECT 回應 |
| 客戶資料不能出廠 | SaaS 不可用 | compose 即 On-premise 版，Phase 5 驗證 |
| Phase 6 發現引擎需改動才能支援採購 | 顯示 Phase 1～4 抽象錯誤 | 視為設計缺陷回頭修正，不在採購側特例；Phase 0 的 DSL 設計即以兩場景為輸入 |
| 採購 pilot 與報價 pilot 非同一家 | 兩套需求拉扯 | 優先服務報價 pilot；採購需求先記錄不實作，Phase 6 開工前一次評估 |
| 供應商未指定導致流程卡在建 PO | 使用者困惑 | 任務 6.6 明確走 on_failure → revise，不進 FAILED |
