# 報表模組評估

- 日期：2026-09-14
- 起因：使用者提議整合 [CellReport](https://gitee.com/NoneDay/CellReport)，讓使用者以現有表單欄位製作整合報表。
- 決議優先級：**P2**（報價單 pilot 上線後），四種情境全要。
- 結論：**不整合 CellReport**。改採自建輕量報表模組 + Univer 前端試算表元件。理由見下。

---

## 1. 需求確認

使用者確認四種情境全要：

| 情境 | 說明 | 現況 |
|---|---|---|
| R1 單據列印 | 報價單、採購單 PDF | **已在計畫內**（任務 2.6，Jinja2 + WeasyPrint） |
| R2 管理統計報表 | 各業務各月報價金額與成交率、各部門採購金額；中國式複雜表頭 | 缺 |
| R3 使用者自助分析 | 不寫 SQL，拖拉欄位產生報表與圖表 | 缺 |
| R4 流程營運儀表板 | 逐時、瓶頸、SLA | **已在計畫內**（MO-01、MO-04） |

實際缺口只有 R2 與 R3。R1 與 R4 已有規劃，不需要 CellReport。

---

## 2. CellReport 查核結果（2026-09-14）

| 項目 | 事實 |
|---|---|
| 定位 | 中國式複雜統計報表製作與執行工具，支援資料看板、大屏 |
| 後端 | .NET Core 6（C#） |
| 前端 | Vue + LuckySheet + Element UI + ECharts |
| 報表定義 | 類 Excel 介面，內建類 JS 語言的集合函數與儲存格公式 |
| 資料源 | SQL Server、MySQL、PostgreSQL、SQLite、Oracle、達夢、GaussDB、ODBC、Excel、REST API、既有報表 |
| 部署 | 獨立服務，port 5000，約 300MB 記憶體 |
| 認證 | 預設 admin/database!123，帳號存於 appsettings.json |
| 授權 | Apache 2.0 **加註**：`Copyright (c) 2022-present, NoneDay. 商业使用，请联系作者获取授权。` |
| 社群 | Gitee 1,206 stars / 358 forks |

### 2.1 授權問題（硬阻擋）

LICENSE 檔案在 Apache 2.0 全文外，額外加了一行要求商業使用需聯繫作者取得授權。

- Apache 2.0 第 2 條本身明確授予商業使用權，此加註與條款矛盾。
- 這類「寬鬆授權 + 商用加註」在中國開源專案常見，法律效力不明確，但意圖清楚：作者要對商業部署收費。
- 你的產品是收費 SaaS。整合後每個客戶部署都是商業使用。
- 風險不在於一定會被追究，而在於**這是一個未解的法律不確定性，會在募資、企業客戶法務審查、On-premise 交付時被翻出來**。

處置：若仍想用，必須先取得作者書面授權，且授權需涵蓋 SaaS 轉售與 On-premise 交付。這是商務動作，不是技術決定。

### 2.2 技術棧衝突

| 面向 | CellReport | 平台現況 | 衝突程度 |
|---|---|---|---|
| 執行環境 | .NET Core 6 | Rust + Python | 高。第三種執行環境 |
| 版本支援 | .NET 6 已於 2024-11 終止支援 | — | 高。需自行處理安全更新 |
| 資料存取 | 直連資料庫 | 經 Rust API + RLS | **極高。繞過租戶隔離** |
| 認證 | appsettings.json 靜態帳密 | JWT + RBAC + 多租戶 | 高。無法對接 |
| 部署 | 獨立服務 | compose 已 7 個服務 | 中。多一個 + Redis |

第三列是資安問題，不是架構潔癖。CellReport 直連資料庫取數的模式，意味著報表查詢不會經過 `app.tenant_id` 設定，RLS 形同虛設。要修正就得改它的資料存取層，等於 fork 一個 .NET 專案長期維護。

### 2.3 值得借鏡之處

CellReport 的核心設計思想是對的，這部分應該吸收：

- **集合函數取代預存程序**：不要求報表人員寫 SQL 或建臨時表，而是先定義多個資料集，再用集合函數在儲存格層組合。這對 SME 使用者友善。
- **多資料集並行取數後於記憶體運算**：避免複雜 JOIN。
- **類 Excel 設計介面**：SME 使用者的心智模型就是 Excel。

## 3. 替代方案

### 3.1 Univer（推薦作為前端試算表元件）

| 項目 | 事實 |
|---|---|
| 定位 | 全端 office SDK，試算表為最成熟產品線 |
| 授權 | Apache 2.0，**無商用加註**；Univer Pro 為選配商業版，OSS 版可獨立使用 |
| 技術 | TypeScript、Canvas 渲染、內建公式引擎、插件架構 |
| 執行 | 瀏覽器與 Node.js 皆可（isomorphic） |
| 框架 | React 為主，提供 framework adapters 支援 Vue |
| 社群 | GitHub 14.4k stars |

關鍵事實：**CellReport 前端用的 LuckySheet，作者已停止維護並轉做 Univer**。等於 CellReport 建立在已被作者放棄的前端元件上。直接用 Univer 是走在正確的技術路徑上。

注意事項：
- Univer 核心以 React 撰寫，在 Vue 3 專案中需透過 adapter 或 wrapper 掛載。這是可行但非零成本，需在 spike 中驗證。
- 圖表、匯入匯出、協同編輯屬 Univer Pro。OSS 版的圖表能力需確認，不足時前端另接 ECharts。

### 3.2 自建報表模組（推薦）

不引入完整報表平台，而是在現有架構內做一層薄的報表能力。

```text
Dataset 定義（Rust API）
  ├── 來源：平台 SQL（含 tenant_id，走 RLS）
  ├── 來源：Odoo Adapter 查詢
  └── 參數：日期區間、部門、狀態…（型別化）
        ↓
Report 定義（JSONB）
  ├── datasets: [dataset_key + 參數綁定]
  ├── layout: 儲存格公式（借鏡 CellReport 集合函數概念）
  └── charts: ECharts option 片段
        ↓
執行（Rust 取數並行 → 記憶體組合 → JSON）
        ↓
呈現（Univer 唯讀渲染 + ECharts）
        ↓
匯出（CSV / Excel / PDF）
```

優點：
- 資料存取一律經 Rust，`tenant_id` 與 RLS 天然生效。
- 不增加執行環境。
- 報表定義與 Workflow DSL、Form Schema 同一套版本化與稽核機制。

代價：
- 沒有現成的複雜表頭設計器。R2 的中國式表頭若真的需要多層合併儲存格，工作量會上升。
- 需自建公式求值。可複用已有的 CEL 實作（任務 2.2），不必再引入類 JS 引擎。

## 4. 方案比較

| 方案 | 授權風險 | 執行環境 | 租戶隔離 | 開發量 | 建議 |
|---|---|---|---|---|---|
| A. 整合 CellReport | **高**（商用加註未解） | +.NET 6（已 EOL）+Redis | **需改其資料層** | 整合 3～4 週 + 長期維護 fork | 不建議 |
| B. 自建 + Univer 渲染 | 無（Apache 2.0） | 無新增 | 天然正確 | 6～8 週 | **建議** |
| C. 只做固定報表 + CSV 匯出 | 無 | 無新增 | 天然正確 | 2 週 | MVP 過渡 |
| D. 接外部 BI（Metabase） | Metabase 為 AGPL，嵌入需商業版 | +Java | 需 sandbox 設定 | 2～3 週 | 備案 |

## 5. 建議路徑

### MVP（不變，不加報表模組）
- R1 單據 PDF：任務 2.6 已涵蓋。
- R4 營運儀表板：MO-01 已涵蓋。
- R2 過渡做法：提供 3～5 張**固定報表**（業務月報、部門採購統計、流程週期），後端寫死 SQL，前端表格 + ECharts，支援 CSV 匯出。開發約 2 週，排在 Phase 4 或 Phase 5 之間視進度。
- R3 自助分析：MVP 不做。

理由：pilot 尚未上線，此時猜使用者要什麼報表，猜錯的機率高。先給固定報表收集實際需求，再決定自助分析要拉到什麼程度。這與 [01_多AI意見彙整與最佳建議.md](../需求規劃/202609/01_多AI意見彙整與最佳建議.md) 5.4 節「抽象是觀察出來的」同一原則。

### P2（pilot 上線後）
- **先做 spike**：兩週驗證 Univer 在 Vue 3 中掛載、唯讀渲染、多層表頭合併儲存格、ECharts 併存。spike 不通過則退回方案 C 或 D。
- spike 通過後實作方案 B，約 6 週。

### 需商務決定
若你評估 CellReport 的複雜表頭設計器價值極高，值得走授權路線，那是**先聯繫作者談授權，取得書面許可後再談技術整合**。技術問題（.NET、租戶隔離）在有授權的前提下仍需解，但至少法律風險先排除。
