# 單據套版設計器選型

- 日期：2026-09-14
- 起因：使用者要求「第一步讓使用者做到一般表單報表設計」，即讓客戶自己設計報價單、採購單的列印版面，而非工程師改模板。
- 結論：**採用 pdfme**（MIT，WYSIWYG 設計器，動態表格自動分頁，CJK 字型可註冊）。
- 影響：取代任務 2.6 原訂的 Jinja2 + WeasyPrint 寫死模板方案。

---

## 1. 需求釐清

「表單報表設計」在此指**單據套版設計器**，不是統計報表。兩者區別：

| | 單據套版（本文件） | 統計報表（[05_報表模組評估.md](05_報表模組評估.md)） |
|---|---|---|
| 產出 | 一張報價單的 PDF | 一份跨單據的統計表 |
| 資料 | 單一筆 business object | 多筆聚合 |
| 設計對象 | 版面位置、字體、Logo、明細表格 | 欄位選擇、分組、小計、圖表 |
| 使用者 | 客戶自行調整成自家格式 | 管理者查數字 |
| 階段 | **MVP** | MVP 固定報表，P2 自助 |

本文件只處理前者。

## 2. 為何原方案不夠

任務 2.6 原訂 Jinja2 + WeasyPrint，模板是 HTML 檔案，租戶只能覆寫 Logo、抬頭、條款文字。實際狀況：

- 每家客戶的報價單格式都不同。欄位順序、要不要顯示成本、稅金呈現方式、頁尾條款位置都會差。
- 靠工程師改 HTML 等於每個客戶一次客製。這正是 [01_多AI意見彙整與最佳建議.md](../需求規劃/202609/01_多AI意見彙整與最佳建議.md) 中 Kimi 指出的盲點：「用 ERP 專案的腦袋做 SaaS，SaaS 必須 80% 標準化」。
- 給設計器，客戶自己調，是把客製工時轉成產品能力。

## 3. 候選比較

| 工具 | 授權 | 設計器 | 框架 | 動態表格 | CJK | 判定 |
|---|---|---|---|---|---|---|
| **pdfme** | MIT | WYSIWYG，純 JS bundle | 無關 | 自動分頁 | 註冊字型即可 | **採用** |
| vue-plugin-hiprint | 底層 hiprint 2.5.4 為 LGPL | WYSIWYG | Vue2/3，依賴 jQuery | 支援 | 支援 | 次選 |
| ReportBro | AGPLv3 或商業授權 | WYSIWYG | JS 設計器 + Python 產生 | 支援 | 支援 | 排除 |
| Stimulsoft Reports.JS | 商業 | WYSIWYG | Vue 有官方支援 | 支援 | 支援 | 排除 |
| json-pdf-designer | 未標示 | React 元件 | React | 支援 | 未確認 | 排除 |
| 維持 Jinja2 + WeasyPrint | 無 | 無，工程師改 HTML | — | 需自寫分頁 | 需內嵌字型 | 降為備援 |

排除理由：
- **ReportBro**：AGPLv3 要求衍生作品同樣開源，你的產品是閉源 SaaS，需買商業授權。
- **Stimulsoft**：商業產品，與開源策略不符，且授權成本會隨客戶數上升。
- **json-pdf-designer**：僅兩週歷史，授權未標示，React 綁定。不適合作為產品核心。

### 4.1 表格能力查核（明細列印，2026-09-14 深入查證）

pdfme 自 v4.5.0 起有 table schema，資料以 2D 陣列傳入，列數隨資料增減。JSON 結構：

```json
{
  "name": "lines",
  "type": "table",
  "position": { "x": 15, "y": 80 },
  "width": 180,
  "height": 57.5,
  "showHead": true,
  "head": ["品名", "數量", "單位", "單價", "金額"],
  "headWidthPercentages": [40, 12, 12, 18, 18],
  "tableStyles": {},
  "headStyles": {},
  "bodyStyles": {},
  "columnStyles": {}
}
```

樣式分四類：`tableStyles`（邊框、顏色）、`headStyles`、`bodyStyles`（含 `alternateBackgroundColor` 隔行變色）、`columnStyles`。每類可設 `borderWidth`、`borderColor`、`backgroundColor`、`fontColor`、`fontSize`、`alignment`、`verticalAlignment`、`padding`。

**四項報價單必要需求的實際支援狀況（2026-09-14 查證原始碼 `reference/pdfme` @ d71e544）：**

> 修正紀錄：本節初版依據 GitHub issues 與網路文件，判定四項全不支援。實際 clone 原始碼查證後發現其中兩項已實作，網路資料過時。以下為以原始碼為準的結論。

| 需求 | 實際狀況 | 證據 |
|---|---|---|
| 換頁後表頭重複 | **已支援**。`repeatHead?: boolean`，propPanel 有對應 UI | `tables/types.ts:29`、`propPanel.ts:27`、`dynamicTemplate.ts:35` |
| 逐欄對齊 | **已支援**。`columnStyles.alignment: { [colIndex]: ALIGNMENT }` | `tables/types.ts:36-38`、`tableHelper.ts:128` |
| 合計列獨立樣式 | **不支援**。`rowStyles` 僅內部隔行變色用，無法指定第 n 列 | `tableHelper.ts:130` 僅 alternateRowStyles |
| 最後 n 列不分頁 | **不支援**。有 `__isSplit` 內部旗標，但無 `keepTogether` 控制 | `dynamicTemplate.ts:115` |

[Issue #629](https://github.com/pdfme/pdfme/issues/629)（repeatHead）與 [PR #1055](https://github.com/pdfme/pdfme/pull/1055) 的逐欄對齊部分**應已合併**，issue 狀態未更新。

**實機驗證（2026-09-14，`poc/pdfme-font-test/test.mjs`）**

以 45 行明細加 3 列合計、A4 直式、Noto Sans CJK TC 實測：

| 驗證項 | 結果 |
|---|---|
| 中文嵌入 | 通過，`pdftotext` 可正確抽出中文，無豆腐字 |
| 自動分頁 | 通過，產生 2 頁 |
| `repeatHead: true` | **通過**，第 2 頁有完整表頭 |
| `columnStyles.alignment` | **通過**，逐欄設定生效 |
| Issue #332 跨頁重疊 | **未重現**，版面正常 |
| 輸出體積 | 128 KB（字型 subsetting 生效） |

這表示 spike 任務 0.2b 的第 5 項已提前完成，只剩第 6 項（自訂 plugin 補合計列樣式與最後 n 列不分頁）待驗證。

Issue #332 列出的缺陷：跨頁時 padding 造成內容重疊（#428）、第三頁以後分頁計算錯誤（#429）、Designer 拖拉欄寬時滑鼠與實際位置不符（#430）、多表格換頁後錯位（#433）、邊框在 Designer 與 PDF 呈現不一致且無 border-collapse（#431）。

維護者在 PR #1055 中說明：pdfme 支援以 Custom Schema Plugin 擴充，但不易「深度修改既有 schema」。這仍適用於尚未支援的兩項。

### 4.2 對策：自訂 table plugin（範圍已縮小）

決議（2026-09-14）：採 pdfme。官方 table 已涵蓋兩項需求，自訂 plugin 只補剩下兩項。

- 官方已支援，直接用：`repeatHead: true`、`columnStyles.alignment`。
- 需自行補齊：
  1. `rowStyles.byIndexFromEnd` — 指定倒數第 n 列的樣式（合計列粗體、上緣框線）。
  2. `keepLastRowsTogether: number` — 最後 n 列不得跨頁拆散。
- 作法：以 `reference/pdfme/packages/schemas/src/tables/` 的 11 個檔案為藍本複製，主要改動落在 `tableHelper.ts` 的樣式合併（第 130 行 rowStyles 處）與 `dynamicTemplate.ts` 的分頁計算（第 115 行 `__isSplit` 處）。
- 檔案落點：`pdfme/src/plugins/table-plus.ts`，Designer 與 Generator 共用同一份定義。
- 版本策略：`pdfme/src/plugins/PDFME_BASELINE.md` 記錄基準 commit `d71e544`；上游升級時以回歸渲染測試驗證後再升。
- **估時：約 2 天（原估一週，因兩項已由官方支援而縮減）。**
- 風險：上游 table schema 大改時需重新對齊。緩解方式是 plugin 只依賴公開型別，不 patch 內部實作。若上游日後支援指定列樣式，改回官方版。

被否決的替代方案：

| 方案 | 否決理由 |
|---|---|
| 明細改用多個 text schema 逐格擺放 | 失去自動分頁，明細行數受限，與需求「常超過一頁」衝突 |
| 接受限制先上線 | 金額欄無法靠右，pilot 客戶不會接受 |
| 改用 vue-plugin-hiprint | 表格四項原生支援，但渲染依賴 jQuery + DOM，伺服器端需 Puppeteer 無頭瀏覽器：容器約 1GB、首次呼叫 3 秒、需自行處理並發與記憶體洩漏。底層 hiprint 2019 後未更新 |
| 改用 Carbone（Word/Excel 模板） | 表格能力為 Word 原生，但需 LibreOffice 渲染，且設計方式是上傳 Word 檔而非網頁拖拉，不符需求 |

### 4.3 需注意的限制

**動態分頁與自訂底稿互斥。** `basePdf` 若設為 `{ width, height, padding }` 才支援自動分頁；若上傳既有 PDF 當底稿，版面固定，不套用動態分頁。

影響：客戶若要用自家印好的信紙 PDF 當底，明細行數就不能超過一頁。處置方式是提供兩種模式，設計時明確告知取捨：

| 模式 | basePdf | 動態分頁 | 適用 |
|---|---|---|---|
| 標準 | 尺寸 + 邊距 | 支援 | 明細行數不固定（預設） |
| 固定底稿 | 上傳 PDF | 不支援 | 已有印刷格式，明細行數固定 |

**CJK 字型需自行提供。** 預設 Roboto 不含中文。需在 Designer 與 Generator 兩處註冊同一份字型，否則設計時看得到、產生的 PDF 是豆腐字。字型檔約 10～20MB，需考慮載入策略（Designer 端延遲載入，Generator 端常駐）。

**Node.js 執行環境。** `@pdfme/generator` 是 Node 套件，但現有 Worker 是 Python。這是新增執行環境的決定，見下節。

## 5. 架構影響：新增 Node.js 渲染服務

pdfme 的 Generator 是 TypeScript/Node 套件，沒有 Python 版本。三個選項：

| 選項 | 做法 | 評價 |
|---|---|---|
| A | 新增輕量 Node 渲染服務，Python Activity 以 HTTP 呼叫 | **建議**。服務極薄，單一職責，容器約 200MB |
| B | 前端產生 PDF 後上傳 | 不可行。流程需在無瀏覽器的 Worker 中產生 PDF |
| C | 只用 pdfme Designer 產生模板 JSON，後端自行以 Python 實作渲染 | 不可行。等於重寫 pdfme 的渲染引擎 |

選 A。與 CellReport 的差別在於：

| | CellReport | pdfme 渲染服務 |
|---|---|---|
| 授權 | 商用加註未解 | MIT |
| 執行環境 | .NET 6（已 EOL） | Node 20 LTS |
| 資料存取 | **直連資料庫，繞過 RLS** | 不碰資料庫，只吃 Python 傳來的 JSON |
| 職責 | 完整報表平台 | 單一函式：模板 + 資料 → PDF bytes |
| 維護 | 需 fork 改資料層 | 無需改動，套件升級即可 |

關鍵差異是**不碰資料庫**。渲染服務是純函數式的無狀態服務，租戶隔離由呼叫端的 Python Activity 保證。

### 5.1 服務介面

```text
POST /render
{
  "template": { ...pdfme template JSON... },
  "inputs": [ { "field": "value", "lines": [[...], [...]] } ],
  "fonts": ["noto-sans-tc"]
}
→ 200 application/pdf (bytes)
→ 400 {code, message}   模板或資料不合法
```

- 無狀態、無認證（僅在 compose 內部網路暴露，不對外）。
- 字型檔隨映像檔打包，不從外部下載。
- 逾時 30 秒，由呼叫端 Temporal Activity 控制重試。

## 6. 對現有計畫的異動

### 6.1 任務 2.6 改寫

原任務 2.6「文件模板與 PDF Activity」以 Jinja2 + WeasyPrint 實作，改為：

- **2.6a** Node 渲染服務（`render/` 目錄，Dockerfile，`/render` 端點，CJK 字型打包）
- **2.6b** Python Activity 改呼叫渲染服務，介面簽名不變（`render_quotation_pdf(snapshot, template_version_id) -> {object_key, sha256, pages}`）
- **2.6c** 系統預設報價單模板（pdfme template JSON），取代 `templates/quotation/default.html`

介面簽名不變表示 Phase 3 的 publish Action（任務 3.1）不受影響。

### 6.2 新增任務：模板設計器前端

Phase 4 新增一個任務，讓客戶自己設計版面。放 Phase 4 的理由是與 Workflow Designer 同期，兩者都是「設計時」功能，UI 模式相近可共用外框。

### 6.3 資料模型調整

`document_template_version` 原設計存 `html` 與 `css` 兩欄，改為存 pdfme template JSON：

```sql
document_template_version (
  id, tenant_id, key, version,
  template   jsonb not null,     -- pdfme template
  base_mode  text not null,      -- 'sized' | 'fixed_pdf'
  base_pdf_object_key text,      -- base_mode = 'fixed_pdf' 時使用
  font_keys  text[] not null default '{noto-sans-tc}',
  created_by, created_at, published_at
)
```

### 6.4 風險

| 風險 | 對策 |
|---|---|
| Vue 3 掛載 pdfme Designer 不順 | Phase 0 花兩天做 spike，失敗則退回 vue-plugin-hiprint |
| CJK 字型檔過大影響 Designer 載入 | 字型延遲載入；必要時提供 subset 版本供設計預覽 |
| 客戶設計出破版模板 | 儲存時後端以樣本資料試渲染一次，失敗則拒絕發布 |
| pdfme 版本升級破壞既有模板 | 模板 JSON 記錄 `pdfme_version`；升級前以全部租戶模板跑回歸渲染 |
| 多一個 Node 服務增加維運 | 服務無狀態無資料庫，可隨時重啟；納入 compose 健康檢查 |

### 7.1 合計列設計細節

合計列（小計、稅額、總計）由 Python Activity 在組 inputs 時附加到明細 2D 陣列尾端，不是資料庫欄位，也不在 Designer 中手動擺放。

```python
# worker/activities/document.py 組資料時
rows = [[l.name, l.qty, l.unit, l.unit_price, l.amount] for l in snapshot.lines]
rows.append(["", "", "", "小計", fmt(snapshot.subtotal)])
rows.append(["", "", "", "稅額", fmt(snapshot.tax)])
rows.append(["", "", "", "總計", fmt(snapshot.total)])
```

樣式以「從尾端數」指定，因為明細筆數不固定：

```json
"rowStyles": {
  "byIndexFromEnd": {
    "0": { "fontName": "noto-sans-tc-bold", "borderTopWidth": 0.5 },
    "1": { "fontName": "noto-sans-tc-bold" },
    "2": { "fontName": "noto-sans-tc-bold" }
  }
}
```

三個必須處理的邊界情況，列入 spike 第 6 項與任務 2.6d 測試：

| 情況 | 預期行為 |
|---|---|
| 合計列正好落在換頁處 | 三列合計不得被拆散到兩頁。table-plus 需支援「最後 n 列不分頁」 |
| 明細恰好填滿一頁，合計被擠到次頁 | 次頁需重複表頭（`repeatHead` 已涵蓋），合計列正常呈現 |
| 稅額為零或不含稅報價 | 該列不附加，`byIndexFromEnd` 索引隨之位移，故樣式以「從尾端數」而非固定索引 |

第一項是原官方 table 沒有的能力（`keepLastRowsTogether`），需一併實作於 table-plus。這比原估工作量略增，但不改變一週估時。

## 8. 待你確認

1. **固定底稿模式要不要做？** 若 pilot 客戶已有印刷信紙，需要。若都用電子檔，MVP 可只做標準模式，省約 3 天。
2. **模板設計器開放給誰？** 建議只開放 admin 角色。若要開放一般使用者，需加模板權限模型。
3. **合計列的實作位置。** 目前規劃是把小計、稅額、總計當作表格的最後幾列（用 `rowStyles.last`）。另一種做法是表格外獨立擺 text schema。前者會跟著表格分頁走，後者位置固定但明細跨頁時可能與表格重疊。建議前者，但需在 spike 第 6 項一併驗證。
