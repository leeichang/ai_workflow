## 3. 風險與保險

### 3.1 已識別風險

| 風險 | 說明 | 保險 |
|---|---|---|
| Schema 被 UI 綁架 | 設計器先固化資料結構，接引擎時發現不合需回頭改 | **步驟 0：Schema 先定版** |
| 第 1～3 步無法端到端驗證 | 約 6～8 週看不到流程跑起來 | **假執行器**（步驟 1.5） |
| 權限設計過早 | 第 3 步做權限，但此時無真實流程情境 | 權限只做 RBAC 與欄位讀寫，ABAC 延後 |
| Temporal 風險延後暴露 | 第 4 步才接，若不可行前面白做 | Phase 0 的 Temporal PoC 仍**必須先做** |

### 3.2 兩個保險措施（使用者已確認採用）

**保險一：Schema 先定版**

DSL 與 Form Schema 的 JSON Schema 在步驟 1 之前寫死。設計器只是這些 Schema 的編輯器，不得反向決定 Schema 結構。多花約 3 天，換取第 4、5 步不推翻前面工作。

**保險二：假執行器**

步驟 1 完成後，插入一個不接 Temporal 的簡易直譯器（`poc/fake-runtime/`），讓表單能跑完一條假流程。步驟 2、3 都有東西可驗證，不必等到步驟 5。約 4 天，步驟 4 接上 Temporal 後丟棄。

假執行器的限制（刻意不做，避免變成第二套引擎）：
- 不持久化，程序重啟即失去狀態
- 不支援 Timer、Retry、長時間等待
- 不支援並簽的複雜 Join Policy，只做 ALL
- 單租戶，不檢查 RLS

## 6. 不變的原則

順序調整不改變 [01_系統架構.md](01_系統架構.md) 的架構與三條鐵律：

1. 任何元件不得直連 PostgreSQL。
2. AI 與外部工具只回傳結構化結果，流程決策由 Workflow Engine 負責。
3. 寫入外部系統的 Activity 必帶 `idempotency_key`。

Phase 0 的 Temporal PoC 仍必須在步驟 1 之前完成，因為它驗證的是整個架構的可行性，不是某個步驟的細節。
