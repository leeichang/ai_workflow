# 測試策略

- 日期：2026-09-14
- 適用：[04_報價單與採購簽核實作計畫.md](04_報價單流程實作計畫.md) 全部任務
- 原則：每個功能都必須有 client 呼叫 server API 的單元測試，以及 UI 功能的 E2E 測試。

---

## 1. 測試層級

五層，各有明確職責，不重疊。

| 層級 | 位置 | 工具 | 驗什麼 | 速度 |
|---|---|---|---|---|
| L1 單元 | 各語言就地 | Rust `cargo test`、Python `pytest`、Vitest | 純函數、計算、Policy Engine | 毫秒 |
| L2 契約 | `schemas/tools/`、CI | ajv、自製 graph-check | Schema 與 fixture 一致、三語言型別對齊 | 秒 |
| L3 Client API | `web/tests/api/`、`portal/tests/api/` | Vitest + **MSW** | 前端呼叫後端的請求格式、回應解析、錯誤處理 | 秒 |
| L4 整合 | `server/tests/`、`python-ai/tests/` | `cargo test` + testcontainers、pytest + Temporal test env | DB 交易、RLS、Temporal Workflow | 十秒級 |
| L5 E2E | `e2e/` | **Playwright** | 真實瀏覽器走完使用者流程 | 分鐘級 |

**L3 與 L5 是本次新增的強制要求。** 每個有 UI 的功能都要有這兩層。

## 2. L3：Client 呼叫 Server API 單元測試

### 2.1 為什麼用 MSW 而非手寫 mock

手寫 mock 會與真實 API 脫節。後端改了欄位，前端測試仍綠燈，直到 E2E 或正式環境才爆。

[MSW](https://mswjs.io/) 攔截真實的 `fetch`，回應由 OpenAPI 契約產生。契約改了，mock 自動失效，測試立刻紅燈。

### 2.2 檔案結構

```text
web/
├── src/api/                      API client（由 OpenAPI 產生 + 薄封裝）
│   ├── generated/                openapi-typescript 產出，不手改
│   ├── tasks.ts                  收件匣、簽核
│   ├── quotations.ts
│   ├── workflows.ts
│   └── forms.ts
└── tests/
    ├── msw/
    │   ├── server.ts             MSW node server 設定
    │   └── handlers/             依 OpenAPI 產生的 handler
    └── api/
        ├── tasks.test.ts
        ├── quotations.test.ts
        └── ...
```

### 2.3 每個 API 必測四件事

| 項目 | 說明 |
|---|---|
| 請求正確 | method、路徑、query、body 符合 OpenAPI |
| 回應解析 | 成功回應被正確轉成前端型別，日期、數字、null 處理正確 |
| 錯誤處理 | 4xx/5xx 各自產生預期的錯誤物件，不吞錯 |
| 認證標頭 | 內部 API 帶 JWT，Portal API 帶 session，不互相混用 |

### 2.4 範本

```typescript
// web/tests/api/tasks.test.ts
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';
import { beforeAll, afterEach, afterAll, describe, it, expect, vi } from 'vitest';
import { submitDecision, listMyTasks } from '@/api/tasks';

const server = setupServer();
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));  // 未攔截的請求直接失敗
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

describe('submitDecision', () => {
  it('送出正確的請求格式', async () => {
    let captured: { url: string; method: string; body: unknown; auth: string | null } | null = null;
    server.use(
      http.post('*/tasks/:id/decision', async ({ request, params }) => {
        captured = {
          url: String(params.id),
          method: request.method,
          body: await request.json(),
          auth: request.headers.get('authorization'),
        };
        return HttpResponse.json({ ok: true, instance_status: 'IN_APPROVAL' });
      }),
    );

    await submitDecision('task-123', { decision: 'APPROVE', comment: '同意' });

    expect(captured).toMatchObject({
      url: 'task-123',
      method: 'POST',
      body: { decision: 'APPROVE', comment: '同意' },
    });
    expect(captured!.auth).toMatch(/^Bearer /);
  });

  it('409 已簽核時拋出 TaskAlreadyDecided', async () => {
    server.use(
      http.post('*/tasks/:id/decision', () =>
        HttpResponse.json({ code: 'TASK_ALREADY_DECIDED' }, { status: 409 }),
      ),
    );
    await expect(submitDecision('task-1', { decision: 'APPROVE' }))
      .rejects.toThrowError(/TASK_ALREADY_DECIDED/);
  });

  it('503 Signal 失敗時可重試，不標記為已完成', async () => {
    server.use(
      http.post('*/tasks/:id/decision', () =>
        HttpResponse.json({ code: 'SIGNAL_FAILED', retryable: true }, { status: 503 }),
      ),
    );
    const err = await submitDecision('task-1', { decision: 'APPROVE' }).catch((e) => e);
    expect(err.retryable).toBe(true);
  });
});

describe('listMyTasks', () => {
  it('解析日期欄位為 Date 物件', async () => {
    server.use(
      http.get('*/tasks', () =>
        HttpResponse.json({
          items: [{ id: 't1', node_label: '主管簽核', deadline: '2026-09-20T10:00:00Z', status: 'PENDING' }],
          total: 1,
        }),
      ),
    );
    const res = await listMyTasks({ status: 'pending', mine: true });
    expect(res.items[0].deadline).toBeInstanceOf(Date);
  });
});
```

### 2.5 CI 門檻

- `onUnhandledRequest: 'error'` 必開。任何未被 handler 攔截的請求都算失敗，避免測試悄悄打到真實網路。
- 每個 `src/api/*.ts` 檔案都必須有對應的 `tests/api/*.test.ts`，CI 檢查檔案對應關係。

## 3. L5：UI 功能 E2E 測試

### 3.1 工具

[Playwright](https://playwright.dev/)。選它的理由：跨瀏覽器、trace viewer 可回放失敗、自動等待、內建處理檔案下載與多分頁（客戶 Portal 用得到）。

### 3.2 檔案結構

```text
e2e/
├── playwright.config.ts
├── fixtures/
│   ├── auth.ts                  各角色的登入 state，跨測試重用
│   └── seed.ts                  測試資料建立與清理
├── pages/                       Page Object，封裝選擇器
│   ├── FormDesignerPage.ts
│   ├── WorkflowDesignerPage.ts
│   ├── PermissionMatrixPage.ts
│   ├── TemplateDesignerPage.ts
│   ├── InboxPage.ts
│   └── PortalPage.ts
└── specs/
    ├── form-designer.spec.ts
    ├── workflow-designer.spec.ts
    ├── permission-matrix.spec.ts
    ├── template-designer.spec.ts
    ├── quotation-flow.spec.ts
    └── purchase-flow.spec.ts
```

### 3.3 選擇器規範

**一律用 `data-testid`，禁止用 CSS class 或文字內容當選擇器。**

class 會因樣式調整而變，文字會因 i18n 或文案修改而變。兩者都會造成測試假性失敗。

```vue
<!-- 元件內 -->
<button data-testid="form-designer-publish" @click="publish">發布</button>
<div data-testid="field-card" :data-field-key="field.key">...</div>
```

```typescript
// Page Object 內
readonly publishBtn = this.page.getByTestId('form-designer-publish');
fieldCard = (key: string) => this.page.locator(`[data-testid="field-card"][data-field-key="${key}"]`);
```

### 3.4 四個設計器各自的 E2E 重點

| 畫面 | 必測情境 |
|---|---|
| 表單設計器 | 拖入欄位、改屬性、設定唯讀條件、儲存草稿、重新載入後狀態一致、發布後版本加一 |
| 流程設計器 | 插入節點、設定簽核人、設定退回目標、驗證失敗時節點標紅、發布不影響在途實例 |
| 權限矩陣 | 儲存格三態循環、整欄批次設定、條件式權限、儲存後重載一致 |
| 單據套版 | 拖欄位進版面、調表格欄寬、開啟預覽、下載 PDF、發布前試渲染失敗被擋 |

### 3.5 範本

```typescript
// e2e/specs/form-designer.spec.ts
import { test, expect } from '@playwright/test';
import { FormDesignerPage } from '../pages/FormDesignerPage';

test.use({ storageState: 'e2e/.auth/designer.json' });

test.describe('表單設計器', () => {
  let page: FormDesignerPage;

  test.beforeEach(async ({ page: p }) => {
    page = new FormDesignerPage(p);
    await page.goto('quotation_form');
  });

  test('拖入數字欄位後可設定精度並儲存', async () => {
    await page.dragComponentToCanvas('number', { afterField: 'payment_terms' });
    await page.selectField('new_field_1');
    await page.propertyTab('基本').click();
    await page.labelInput.fill('運費');
    await page.propertyTab('資料').click();
    await page.dataPathInput.fill('quotation.shipping_fee');
    await page.precisionInput.fill('2');
    await page.saveDraft();

    await page.reload();
    await page.selectField('new_field_1');
    await expect(page.labelInput).toHaveValue('運費');
    await expect(page.dataPathInput).toHaveValue('quotation.shipping_fee');
  });

  test('設定唯讀條件後，該欄位在指定節點唯讀', async () => {
    await page.selectField('discount_rate');
    await page.propertyTab('規則').click();
    await page.readonlyRule.setSimple('當前節點', '不等於', ['開始', '修改']);
    await page.saveDraft();

    // 切到預覽模式，模擬在主管簽核節點
    await page.previewAs({ node: 'manager_approval' });
    await expect(page.previewField('discount_rate')).toBeDisabled();
  });

  test('資料路徑無效時顯示錯誤且無法發布', async () => {
    await page.selectField('discount_rate');
    await page.propertyTab('資料').click();
    await page.dataPathInput.fill('quotation.does_not_exist');
    await expect(page.dataPathError).toContainText('路徑不存在');
    await expect(page.publishBtn).toBeDisabled();
  });

  test('發布後版本號加一，草稿內容成為新版本', async () => {
    const before = await page.versionChip.textContent();
    await page.selectField('payment_terms');
    await page.labelInput.fill('付款方式');
    await page.publish();
    await expect(page.versionChip).not.toHaveText(before!);
    await expect(page.publishSuccessToast).toBeVisible();
  });
});
```

### 3.6 跨角色與跨視窗

報價單流程要驗證內部使用者與外部客戶的互動。Playwright 用多個 context 處理。

```typescript
// e2e/specs/quotation-flow.spec.ts
test('報價單完整流程：業務送出到客戶接受', async ({ browser }) => {
  const sales = await browser.newContext({ storageState: 'e2e/.auth/sales.json' });
  const manager = await browser.newContext({ storageState: 'e2e/.auth/manager.json' });
  const customer = await browser.newContext();   // 外部客戶無登入狀態

  // 業務建單送出
  const quotationNo = await createAndSubmitQuotation(sales);

  // 主管在收件匣看到並同意
  const inbox = new InboxPage(await manager.newPage());
  await inbox.goto();
  await expect(inbox.taskRow(quotationNo)).toBeVisible();
  await inbox.approve(quotationNo, '同意');

  // 攔截寄出的 Email 取得 magic link
  const link = await getLatestMagicLink(quotationNo);

  // 客戶開啟 Portal，下載 PDF，同意
  const portal = new PortalPage(await customer.newPage());
  await portal.open(link);
  const download = await portal.downloadPdf();
  expect(download.suggestedFilename()).toMatch(/\.pdf$/);
  await portal.approve('沒問題');

  // 驗證 Odoo 建單
  await expect.poll(() => findOdooOrder(quotationNo)).toBeTruthy();
});
```

### 3.7 環境

E2E 跑在 docker compose 起的完整環境，含 PostgreSQL、Temporal、渲染服務、Odoo 測試實例。

Email 用 [MailHog](https://github.com/mailhog/MailHog) 攔截，magic link 由其 API 取得，不真的寄出。

## 4. 每個任務的測試要求

實作計畫中每個任務，除原有的測試步驟外，額外要求：

| 任務類型 | 必補測試 |
|---|---|
| 新增 API 端點 | L3 四項（請求、回應、錯誤、認證）+ L4 整合（含 RLS 跨租戶隔離） |
| 新增 UI 畫面 | L3 該畫面用到的所有 API + L5 至少三個情境（正常、錯誤、邊界） |
| 新增 Activity | L4 Temporal test env 測試，含重試與 idempotency |
| 純函數 | L1，表格式參數化測試 |
| Schema 變更 | L2 正向與負向 fixture |

## 5. CI 門檻

```yaml
# 概念，實際在 .github/workflows/ci.yml
jobs:
  fast:       # 每次 push
    - L1 單元（三語言）
    - L2 契約
    - L3 Client API
    - lint、型別檢查
  full:       # PR 與 main
    - fast 全部
    - L4 整合（testcontainers）
    - L5 E2E（docker compose 完整環境）
```

規則：

- `fast` 必須在 3 分鐘內跑完，否則沒人會等。
- L5 失敗時必須附上 Playwright trace，可直接回放。
- 覆蓋率不設硬性數字門檻。改為檢查「每個 `src/api/*.ts` 有對應測試檔」「每個設計器有對應 spec」這類結構性規則，比數字有意義。

## 6. 測試報告

### 6.1 存放位置

```text
docs/測試報告/
└── YYYYMM/
    ├── NN_<主題>.md           報告本文
    └── screenshots/           E2E 截圖
        └── <spec>/<測試名>/
            ├── 01-<步驟>.png
            └── ...
```

每個月一個目錄。報告檔名以兩位數編號開頭，方便排序。

### 6.2 報告必含內容

| 區塊 | 內容 |
|---|---|
| 摘要 | 通過數、失敗數、執行時間、環境 |
| 驗證項目 | 每項對應的測試名稱與結果 |
| 失敗分析 | 失敗原因、是產品缺陷還是測試問題、如何修正 |
| 發現的問題 | 過程中發現但不影響結論的事項 |
| 結論 | 是否達成該階段目標，能否進入下一階段 |

失敗分析必須區分「產品缺陷」與「測試寫法問題」。兩者的處置完全不同，混在一起會誤導決策。

### 6.3 E2E 截圖規範

**每個 E2E 測試的關鍵步驟都必須截圖。** 這是驗收證據，也是設計走樣時的對照基準。

Playwright 設定：

```typescript
// e2e/playwright.config.ts
export default defineConfig({
  use: {
    screenshot: 'only-on-failure',      // 失敗自動截圖
    video: 'retain-on-failure',
    trace: 'retain-on-failure',
  },
  outputDir: '../docs/測試報告/當月/screenshots/_artifacts',
});
```

除了失敗自動截圖，關鍵步驟需主動截圖：

```typescript
// e2e/helpers/shot.ts
import type { Page } from '@playwright/test';

const MONTH = new Date().toISOString().slice(0, 7).replace('-', '');

export async function shot(page: Page, spec: string, testName: string, step: string) {
  const seq = String(++counters[`${spec}/${testName}`] ??= 1).padStart(2, '0');
  await page.screenshot({
    path: `docs/測試報告/${MONTH}/screenshots/${spec}/${testName}/${seq}-${step}.png`,
    fullPage: true,
  });
}
```

使用方式：

```typescript
test('拖入數字欄位後可設定精度並儲存', async () => {
  await shot(page.raw, 'form-designer', '新增數字欄位', '初始畫面');
  await page.dragComponentToCanvas('number', { afterField: 'payment_terms' });
  await shot(page.raw, 'form-designer', '新增數字欄位', '拖入後');
  await page.propertyTab('資料').click();
  await page.dataPathInput.fill('quotation.shipping_fee');
  await shot(page.raw, 'form-designer', '新增數字欄位', '設定資料路徑');
  await page.saveDraft();
  await shot(page.raw, 'form-designer', '新增數字欄位', '儲存成功');
});
```

規則：

- 檔名用兩位數序號開頭，確保依步驟排序。
- 截圖用 `fullPage: true`，避免捲動區域被裁掉。
- 四個設計器的 E2E 必須涵蓋：初始狀態、操作中、儲存後、錯誤狀態四類截圖。
- 截圖納入版控。它們是驗收證據，不是暫存檔。

### 6.4 報告產生時機

| 時機 | 報告 |
|---|---|
| 每個 Phase 結束 | 該 Phase 的完整測試報告 |
| PoC 完成 | PoC 驗證報告，含是否達成架構決策的驗證目標 |
| pilot UAT | UAT 執行報告，需 pilot 客戶簽署 |

## 7. 不做的事

| 不做 | 理由 |
|---|---|
| 視覺回歸測試（screenshot diff） | 設計期間畫面會頻繁改動，維護成本高於價值。pilot 上線後再評估 |
| 對 Odoo 正式環境跑 E2E | 只對測試實例。正式環境的驗證靠 UAT 腳本人工執行 |
| 效能測試 | MVP 階段使用者數少。[03_功能規劃.md](03_功能規劃.md) 13 節的目標值靠人工抽測 |
| 100% 覆蓋率 | 追數字會產生無意義的測試。改用結構性規則 |
