## 1. 三大爭議點：各 AI 立場對照

挑戰稿末尾指定的三個爭議點，是所有回答的主軸。

### 1.1 該不該自己做 Workflow Runtime？

| 來源 | 立場 | 關鍵理由 |
|---|---|---|
| S1 ChatGPT | 自己做（Token + Parallel Group + Join） | Token/Task/Gateway/Join 是引擎骨架；並簽列為 MVP 核心 |
| S2 ChatGPT | **改口：不要自己做，用 Temporal** | 自己做 Runtime 是「1～2 年打造另一套 Camunda」；Temporal 負責 Durable Execution，自己只做 DSL + Designer + Business Semantics |
| S3 Gemini | 不要，用 Temporal | Token/Saga/Versioning/Long-running 是分散式系統最深的水；自研會耗掉一整年 |
| S4 Claude | 不要，用 Temporal | 一人公司沒時間 debug 自寫 token model 在 Parallel Reject + Timeout 同時發生時的 race condition |
| S5 DeepSeek | 不要，用 Temporal + 自建 DSL/Compiler + 自建 Human Task Layer | 自研 TCO 只有在日均億級實例才划算；SME 沒有規模效應。並提出：若本質是人審批流程，Camunda 的 Human Task 原生更合適，但 Camunda 8 Self-Managed 生產非免費 |
| S6 Kimi | 不要，用 Temporal | 第十一～十三章擔心的所有問題正是 Temporal 存在的理由；並指出 **Temporal 沒有官方 Rust SDK** |
| S7 千問 | 強烈建議 Temporal，但也說 Rust 適合做 Runtime | 1～3 人團隊直接用 Temporal；自研至少一年才能生產級 |

**共識：7 份中 6 份明確反對自研 Runtime，S1 是在 Temporal 討論之前的早期立場，S2 已修正。Runtime 用 Temporal，自己做 DSL、Compiler、Human Task、Approval Policy。**

### 1.2 Data Contract + Data Adapter 是不是護城河？

| 來源 | 立場 |
|---|---|
| S1/S2 ChatGPT | 抽象合理，是核心架構骨架；護城河列為 Business Object + DSL + Approval Policy + Resolver + ERP/MES Adapter + AI Governance + Templates |
| S3 Gemini | 概念極佳，但 MVP 會拖垮；護城河在「開箱即用的業務場景」與你懂 KUNNR/VBELN 代表什麼，不在抽象層。MVP 先 hard-coded 或輕量 JSON Schema Adapter |
| S4 Claude | 抽象本身不是護城河，累積的 Mapping 知識才是；「先寫死 2～3 個 Adapter，做過 3 個客戶再抽象」，抽象是觀察出來的不是設計出來的 |
| S5 DeepSeek | 抽象正確且必要，但只是基礎設施；護城河是累積的 Data Adapter Templates 與 Business Data Contract Library（50 個客戶後 50 種 Pattern）。Data Catalog 需要、Dataset Version 先不需要；AI 產生 Mapping + 使用者確認；不要讓使用者直接編 JSON Schema |
| S6 Kimi | 好工程但不是護城河；做但克制：JSON Schema、AI 自動 Mapping 做，Data Catalog 與 Dataset Versioning 不做；Contract 掛在 Business Object 下 |
| S7 千問 | **極度合理且具極高壁壘**，是區別於 n8n 的核心；Dataset Version 是必須的（ERP 升級欄位變更時舊流程不能崩）；AI 自動 Mapping 是 MVP 亮點，能省 80% 接入時間 |

**共識：抽象方向正確、要做。分歧在「何時做」與「是不是護城河」。多數（S3/S4/S5/S6）認為護城河是「累積的垂直模板與領域知識」，抽象層只是載體；S7 認為抽象本身就是壁壘。**

### 1.3 通用 Workflow 還是 ERP/MES 周邊垂直切入？

| 來源 | 立場 |
|---|---|
| S2 ChatGPT | 定位「AI Business Process Automation for ERP-driven SMEs」，口號「不換 ERP，把 ERP 外面的人工流程自動化」；不做通用引擎 |
| S3 Gemini | 絕對不做通用（血海）；定位「ERP 增效器 / ERP Copilot & Automation Layer」 |
| S4 Claude | 垂直且要窄：「不用換 ERP，把 Excel/Email 簽核流程變成有 ERP 寫回、AI 輔助判斷的正式系統」 |
| S5 DeepSeek | 從 ERP/MES 周邊切入，但底層設計保持通用；引用台灣中小企業 AI 導入率 7.4% 的空白 |
| S6 Kimi | 垂直，一開始窄到只剩一個場景；台灣 SME 真正的競爭對手是 LINE 群組 + Excel + 紙本 |
| S7 千問 | 絕對不做完全通用平台；以 ERP/MES/財務/採購/製造為切入點 |

**共識：全票垂直切入。無一支持通用平台。**

## 2. 逐主題彙整（保留所有意見）

### 2.1 產品定位 A / B / C

- S7 千問：強烈建議 C（AI Business Operating System），這是 2026 年 Workspace Agents 從對話驅動走向任務閉環的趨勢。
- S4 Claude：想做 C，但先賣 B。C 是三年後的故事，B 是六個月能交付的產品。
- S5 DeepSeek：C 是對的願景，用 B 的姿態進入市場，用 A 的簡單性做 MVP。對外行銷語言是 B，對內架構是 C，使用者體驗像 A。
- S6 Kimi：C 是敘事不是產品；對外講故事，賣的是具體場景。
- S2 ChatGPT：不要叫「AI Workflow Platform」，會被拉去跟 n8n/Make/Zapier 正面競爭。
- S3 Gemini：SME 不買 Workflow Engine，買「自動化採購簽核模組」；賣場景不賣工具。

### 2.2 SME 真正願意付費的東西

- S3 Gemini：解決方案，例如「把 MES 生產異常用 AI 判斷嚴重度，自動發 LINE/Email 讓主管簽核」。
- S4 Claude：「這件事現在很痛、每天要人工做、出錯會被老闆罵」；只會為「少一個 FTE 在貼單據」付錢。
- S5 DeepSeek：痛感即時可量化、不需換系統、決策者自己會用、30 天內見效。
- S6 Kimi：決策者是老闆本人，賣的是「錢的控管」與「異常不漏接」，不是數位轉型。
- S7 千問：為結果與省時付費：消除重複勞動、降低對熟練員工依賴、合規可追溯。

### 2.3 競爭與差異化

- S3 Gemini：n8n/Zapier 是 Data-centric API 串接；Camunda 是 Process-centric；你的差異化是 Human-in-the-loop + AI Agent + Enterprise Data。
- S4 Claude：n8n 們全部做不好「企業內部並簽 + ERP 寫回 + 台灣 SME 真實簽核文化」。
- S5 DeepSeek：通用 SaaS 整合層已被佔據；「企業內部流程 + ERP 資料」層沒有。n8n/Zapier 不支援 SAP RFC、MES 資料格式、採購審批邏輯。
- S6 Kimi：台灣 SME 真實對手是 LINE + Excel + 紙本；只能靠「解決一個 LINE 解決不了的具體問題」。
- S7 千問：差異化在「Data Contract 驅動的 AI 業務流程」，結合 ERP 嚴謹數據模型與 AI 模糊推理。

### 2.4 Data Contract / Adapter / Mapping

- 使用 JSON Schema：S5、S6、S7 皆同意作為底層技術實現；S7 強調上層要包成 Data Contract（含業務描述、來源、更新頻率）；S5 強調不暴露 JSON Schema 給 SME 使用者。
- AI 自動 Mapping：S5、S6、S7 皆認為可行且應做（AI 產生 + 人工確認）。S3 認為 MVP 不要做全自動 Mapping。
- Data Catalog：S5 需要（讓使用者知道有哪些來源）；S6、S7 MVP 不需要重量級 Catalog。
- Dataset Version：S7 必須；S5 先用 immutable snapshot，10+ 客戶後再做；S6 不做。
- ERP Connector 定位：S1、S5、S7 一致同意降維成「預定義 Data Adapter Template」，核心只認 REST/SQL/SFTP 等標準協議。
- 先寫死再抽象：S3、S4 明確主張 MVP 先寫死 2～3 個具體 Adapter，S4 建議第 6 個月才重構成半抽象。

### 2.5 Form Engine

- S1 ChatGPT（最完整）：不 fork @form-create，在外面包 Enterprise Form Designer；Form-create 只管 UI Schema，自己維護 Workflow Metadata；儲存拆成 UI Schema / Data Schema / Workflow Schema 三份，Runtime 再與 Workflow Context + User Permission 合併後交給 form-create Renderer；同一張 Form 可被不同 Workflow 用不同規則使用；Property Panel 本身也 Schema-driven；每個欄位屬性分 Data / UI / Behavior / Workflow 四大類；MVP 可先在 form_definition 用三個 JSONB 欄位。
- S3 Gemini：三層分離絕對正確；不要自己做 Renderer，除非 @form-create 無法滿足 Master-Detail。
- S4 Claude：設計合理、不算過度設計、繼續做。
- S5 DeepSeek：五層 Schema（Business Form / UI / Data / Workflow / Permission）；@form-create 適合 MVP 但長期擴展性會成瓶頸，需要 Adapter Layer 以便未來換 Renderer。
- S6 Kimi（唯一反對）：三層分離是過度設計；MVP 一份 Schema 同時描述欄位、UI、顯示規則；**MVP 不做所見即所得 Designer**，AI 自然語言生成流程才是 Designer；One2Many 用子表單 + 陣列欄位；Signature 用 canvas 存圖。
- S7 千問：三層分離是企業級表單鐵律；One2Many / Reference / AI Field 做成 Custom Component + Data Binding，AI Field 本質是帶 async-fetch 的 Input。

### 2.6 Workflow Runtime Model（Token）

- S1 ChatGPT：Token + Task + Gateway + Join 是引擎骨架；Human Task 不直接控制 Workflow，必須經 Task Result → Parallel Group → Runtime 判斷 Join。
- S4 Claude：Execution/Instance 層交給 Temporal，不需要自己設計 workflow_token / workflow_execution 表。
- S5 DeepSeek：Token Model 合理（BPMN 標準），但用 Temporal 後不必自己維護 Token 表；需要一個從 Temporal History 投影出來的 Read Model 供 Monitor 查詢。
- S6 Kimi：概念對，但不需自己實作 Token 推進；Node Graph 只是「決定下一步呼叫哪個 Activity」的函數。
- S7 千問：Instance → Execution → Token → Task 是經典且正確的模型。

### 2.7 並簽 / Parallel / Join

- S1 ChatGPT：四種 Join 模式（ALL / ANY / N_OF_M / ALL_SUCCESS），再拆成 Completion Policy + Result Policy（ALL_SUCCESS / ANY_REJECT / MAJORITY / CUSTOM_EXPRESSION）+ Timeout Policy（WAIT / ESCALATE / AUTO_APPROVE / AUTO_REJECT）；Parallel Group 為 Runtime Entity（含 total/completed/approved/rejected 計數）；分支不固定人，走 Approver Resolver；Designer 的 Join 屬性面板包含 Join Type、N、Reject Policy、Timeout、Timeout Policy。
- S2 ChatGPT：並簽 = Multi-Instance Human Task + Parallel + Join Policy 三個基本能力；Approval Policy Engine 比 Workflow Designer 更有商業價值；CUSTOM 例如「至少一位財務主管 + 部門主管 + CFO 或 CEO 其中一位」。
- S3 Gemini：Temporal 中並簽只是多個非同步 Task 等結果；N_OF_M 收到 M 個訊號就繼續並取消剩餘。
- S4 Claude：ALL 與 ANY_REJECT 先做，N_OF_M 與 Custom Expression 等客戶要求再做。
- S5 DeepSeek：MVP 只做 ALL 與 ANY；Parallel Group 應是 Node 屬性不是 Runtime Entity；Human Task 生命週期（create → assign → claim → complete）由獨立 Human Task Service 管理。
- S6 Kimi：不建 Parallel Group 實體；Join 是帶完成策略的 Node，策略只是讀取已完成 Task 結果後求值的函數；離職 = Resolver 每次即時算不快照人名；Delegation 是 Task 層級代理規則；Reject 分支用 Human Task 兩條出線；Timeout 用 Temporal wait_condition + timer。
- S7 千問：Parallel Group 作為 Runtime Entity（parallel_group 表）；Reject 時立即觸發 Reject 分支並取消其他 Token；Human Task 必須有 SLA，超時 Escalation 或 Auto-Delegate。

### 2.8 Approver Resolver

- 全體認為必須做且是核心差異化（S3、S4、S6 明確）。
- S3：Expression Engine + Role-based 查詢，例如 SQL 查 department_managers。
- S4：Role-based + 動態金額門檻先做；SQL / API / AI resolver 留 v2。
- S5：Role / Department / Manager / Dynamic Expression 先做；SQL / API 作 fallback；AI resolver 只能「建議」，需人工確認。
- S6：MVP 只支援「角色 + 金額門檻」一種規則。
- S7：MVP 支援 Role-based 與 Department-based。

### 2.9 Node 類型

| 來源 | MVP Node 清單 |
|---|---|
| S2 ChatGPT | Trigger / Form / Condition / Human Task / Parallel / Join / Action / AI Task / Notification；四大類：Core、Human、Intelligence、Integration |
| S3 Gemini | 移除 Sub-workflow、Timer |
| S4 Claude | Trigger / Action / Condition / Human Approval / Parallel / Join / API；AI Task 併入 Action；Loop / Sub Workflow / Script / Event 全砍（Temporal Child Workflow 就是 Sub Workflow） |
| S5 DeepSeek | Trigger / Action / Condition / Human Approval 四種先做 Compiler；不做 N_OF_M、Sub Workflow、Loop / Wait / Timer |
| S6 Kimi | 6 種：Trigger（Webhook/Schedule/Manual）/ Action / Condition / Human Approval / AI Task / Join；Loop 不做成 Node |
| S7 千問 | Trigger / Condition / Human Approval / AI Task / API Action / Notification / Parallel-Join / Timer-Wait；Loop 與 Sub-workflow 後做 |

AI Task vs AI Agent：
- S6 Kimi：AI Task = 單次 LLM 呼叫、無狀態、可重試；AI Agent = 工具白名單 + 步數上限 + 預算上限 + 每次工具呼叫進 Audit。
- S7 千問：AI Agent 本質是「黑盒 Workflow」，內部循環呼叫 API 直到達成目標。
- S5 DeepSeek：AI Agent 可呼叫 Data Adapter 查詢，但不能直接呼叫寫入 API。
- S4 Claude：MVP 不要獨立出 AI Agent 概念。

### 2.10 AI 在 Workflow 的角色與治理

- 核心原則（S2、S3、S5、S6、S7 一致）：**AI 只回傳結構化結果，Workflow Engine 決定下一步；AI 不直接執行寫入**。S2 總結為「外部工具負責執行，Workflow Engine 負責決策與治理」。
- S3 Gemini：Agent Control Plane，AI 只輸出 Intent + Parameters，後端攔截檢查 RBAC / Tenant 後才呼叫 ERP API；AI 是無權限的大腦，系統是手腳。
- S5 DeepSeek 五層分級表：L1 Extraction（低風險可自動）、L2 Classification、L3 Decision（必須有 Human 確認或 override）、L4 Agent（寫操作必須 approval）、L5 Workflow Generator（Design-time 工具，人工 Review 才能 Publish）。AI Agent 要有獨立 Service Account，不用使用者 Token。
- S4 Claude：MVP 只做 Extraction；Agent 自主呼叫企業 API 在沒有客戶信任前不要做；Generator 是炫 demo 不是第一個客戶買單的東西。
- S6 Kimi：AI 可建議「核准」，寫回 ERP 前必須有人確認（或明確配置自動 + 事後稽核）；Generator 產生的 Workflow 必須過 Validator（有終點、無孤立節點、Join 分支數匹配、Resolver 角色存在）。
- S7 千問：AI 不能擁有超越發起人的權限；資金、刪除、對外發信只能建議。
- Prompt Injection（S5）：Input sanitization、Output schema validation、Tool call whitelist。

### 2.11 Business Object 作為核心

- S2 ChatGPT、S6 Kimi、S7 千問一致：不是線性 Contract → Form → Workflow，而是 Business Object 下掛 Data Contract / Form / Workflow / Permission。S6 補充：這對應客戶腦中的東西，也對應未來賣「採購套件」的方式。

### 2.12 Database

- JSONB：Workflow Definition、Form Schema、Data Contract、Mapping 規則、AI Prompt/Config、AI input/output、Audit payload（S3、S5、S6、S7 一致）。
- Relational：Tenant、User、Role、Permission、Workflow Instance 狀態（供列表查詢）、Task、Audit Log（S3、S5、S7）。
- Runtime State：交給 Temporal，PostgreSQL 只存 UI 展示與統計的 Metadata（S2、S3、S4、S6）。S2 明確：Temporal 不是 Business Database。
- Audit Log：append-only + JSONB payload（S6）。
- 已發布版本 immutable，改了就升版（S6）。

### 2.13 Versioning

- 全體一致：Instance 啟動時綁定 version_id（或快照定義），新版只影響新 Instance；在途 Instance 跑完舊版。
- S5 DeepSeek：提供「Migrate to V2」管理功能，選擇性遷移。
- S6 Kimi：程式碼層演進用 Temporal patching；「升級在途流程」一期可不做。
- S4 Claude：live-migration 先不處理，遇到讓使用者手動決定。
- S7 千問：禁止舊版 Worker 執行新版 Task（向前保護）。

### 2.14 錯誤 / Retry / Saga

- Retry / Timeout / Pause / Resume / Cancel 由 Temporal 提供（全體）。
- Idempotency 仍是自己的責任（S2）：Action 定義要有 idempotency_key，避免 ERP timeout 後重試建兩張 PO。
- Saga：S3、S4、S6、S7 一致 MVP 不做完整 Saga；S2 建議 DSL 預留 compensation 欄位；S7 建議「補償節點」由設計者手動畫；S3 建議失敗先停下人工介入。

### 2.15 Observability

- S5 DeepSeek：Temporal Workflow History → Read Model Projector → PostgreSQL materialized view → Vue3 Dashboard；指標分 Workflow / Instance / Task / AI / API 五層；Error Replay 需要 Node 執行 idempotent。
- S6 Kimi：Temporal Web UI 頂住技術視角；自己只做業務視角（進行中/逾時/卡關、平均週期、瓶頸節點）；每個 Node 完成寫一行 business event，餵未來 Process Mining。
- S3 Gemini：Month 5 串 Temporal API 顯示狀態與 Error Logs。

### 2.16 AI 成本模型

- Pre-computation + On-demand：S3、S5、S6、S7 全體肯定。S7：這是對 SME 銷售最大亮點（「別人家的 AI 越用越貴，我們的 AI 幫你省錢」）。S6：AI Token 成本包進套件月費。

### 2.17 技術棧

| 來源 | 建議 |
|---|---|
| S2 ChatGPT | 保留 Rust/Axum 做 Business API + Temporal Client；Python 做 AI Worker；「Rust + Temporal」不是「Rust vs Temporal」 |
| S3 Gemini | Vue3 + Python（Temporal Worker + AI/Data）+ Rust（API Gateway/Auth）+ PostgreSQL |
| S4 Claude | **不選 Rust**（學習曲線吃掉六個月）；Python FastAPI + Temporal Python SDK；Rust 留到效能瓶頸出現 |
| S5 DeepSeek | Rust 不適合（生態）；Workflow Compiler 與 Runtime Abstraction 用 **TypeScript**（與 Vue3 共用 type），AI Worker 用 Python |

分歧點：Rust 是否保留。S2/S3/S7 保留（範圍不同），S4/S5/S6 不保留。

### 2.18 n8n 的定位

- S2 ChatGPT（最完整）：n8n 不當 Workflow Engine，而是「External Workflow Provider」的一種 Integration Node；用 workflow_ref + version + input/output mapping + timeout + retry 引用，不存 n8n JSON；透過 Callback → Temporal Signal 非同步執行；n8n Flow 可帶 Input/Output Contract 自動註冊到 Automation Catalog；**大坑：不要讓 n8n 回傳 next_node 反過來控制主流程**。
- S3 Gemini：n8n 當底層 Data Connector，不做 Human Approval。
- S5 DeepSeek：不整合作 Runtime；特定場景當 Action Adapter。
- S6 Kimi：早期可當 connector executor（管 credential、現成節點），透過 webhook 觸發；寫回 ERP 的關鍵 Action 用自己的 Activity。

### 2.19 Temporal 授權與部署

- S2 ChatGPT：Temporal Server 為 MIT，可 Self-host 放進商業 SaaS 不付授權費；真正限制是運維（Backup / Upgrade / HA / TLS / Retention）；MVP 先單一 Namespace + workflow ID 帶 tenant_id，Enterprise 再 Namespace 隔離；建 THIRD_PARTY_LICENSES.md；On-premise 版適合台灣製造業（資料不能出廠）。

## 4. 可行的最佳建議（彙整版）

### 4.1 一句話定位

**給已經有 ERP 的台灣製造業 SME 的 AI 營運流程層：不換 ERP，把 Excel / Email / LINE 上的簽核與異常處理，變成有 ERP 寫回、AI 輔助判斷、可稽核的正式流程。**

對外賣「採購簽核套件」「負庫存追蹤套件」這種場景，不賣「Workflow Platform」。

### 4.2 架構 2.0

```text
[ 使用者端 Vue3 ]
  ├── Task Inbox（簽核收件匣，LINE / Email 通知進入）
  ├── 表單（@form-create Renderer + 自己的 Business Form Schema）
  ├── 極簡 Designer（Phase 2）／AI 自然語言生成（Phase 2）
  └── 業務視角 Monitor（進行中／逾時／卡關／瓶頸）

[ 控制層 Python FastAPI ]
  ├── Auth / Tenant（RLS）/ RBAC
  ├── Business Object Registry（Contract + Form + Workflow + Permission）
  ├── Workflow DSL Validator（靜態檢查 + 模擬）
  ├── Approver Resolver（角色 / 部門 / 金額門檻 表達式）
  ├── Approval Policy Engine（Completion / Result / Timeout Policy）
  ├── Human Task Service（create → assign → complete → 送 Signal）
  └── Temporal Client

[ 執行層 Temporal（Self-host, MIT）]
  ├── DSL Interpreter Workflow（讀 JSON DSL，逐 Node 呼叫 Activity）
  ├── Durable wait / Timer / Retry / Cancellation / Child Workflow
  └── Namespace 單一，workflow_id 帶 tenant_id

[ Worker（Python）]
  ├── Human Task Activity（建 Task、等 Signal）
  ├── AI Task Activity（Extraction / Classification / Decision，結構化輸出）
  ├── Data Adapter Activity（Excel / SQL 唯讀 View / Odoo / SAP，先寫死）
  ├── ERP Write Activity（idempotency_key 必填）
  ├── Notification Activity（LINE / Email）
  └── External Workflow Activity（n8n，Callback → Signal）

[ 資料層 PostgreSQL ]
  ├── Relational：tenant / user / role / business_object_instance / human_task / audit_log / workflow_instance_view
  ├── JSONB：workflow_definition_version / form_definition / data_contract / mapping / ai_config / ai_execution
  └── pgvector（Phase 2 RAG）
```

設計鐵律（來自各 AI 的共識）：
1. Definition 與 Runtime 徹底分離；發布即 immutable，Instance 綁定 version。
2. AI 與外部工具只回傳結構化結果；Workflow Engine 決策；寫入需人審或明確配置自動 + 事後稽核。
3. DSL 不是 Temporal API 的包裝；DSL → Execution IR → Temporal。
4. Human Task 不直接推進流程；經 Task Result → Policy → Runtime。
5. Idempotency 由 Business Activity 負責，不推給 Temporal。

## 5. 我的補充意見

以下是各 AI 未提或彼此矛盾處，我的判斷與補充。

### 5.1 語言選擇：單一語言 Python，Rust 暫不進場

- Temporal 的核心是 Rust 寫的，但對外正式 SDK 是 Go / Java / Python / TypeScript / .NET / PHP，Rust SDK 未正式釋出。S5 說 SDK 覆蓋 Rust、S7 說可用 Rust 寫 Temporal Worker，這兩點不可靠；S6 的說法正確。
- 一人公司多一種語言就多一份維護成本。AI Worker 必然 Python，控制層也用 Python FastAPI，型別用 Pydantic 統一 DSL Schema，前後端共用 JSON Schema 產生 TypeScript 型別。
- Rust 留給兩個明確場景：大批量 Excel/ERP 資料轉換 microservice、On-premise 版單一 binary 部署需求。都不是前六個月的事。

### 5.2 修正一個誤解：Temporal 長等待不佔資源

S5 提到「Task 等 3 天，Temporal Workflow 會一直佔用資源」。這不正確。Temporal Workflow 在等待 Signal 或 Timer 時不佔 Worker 執行緒，狀態持久化在 Event History，Worker 重啟後由 replay 恢復。人審批流程等數週、數月是 Temporal 的典型用途。不必因此考慮 Camunda。

### 5.3 Approval Policy Engine 應獨立成可測試的純函數模組

S2 點出「Approval Policy Engine 比 Designer 更有商業價值」，我同意並加一條：把它做成不依賴 Temporal、不依賴 DB 的純函數（輸入：Task 結果集合 + Policy；輸出：CONTINUE / WAIT / REJECT / ESCALATE），配一組表格式測試案例（ALL、ANY_REJECT、N_OF_M、Timeout 交錯）。這是整個平台最容易出 bug、又最容易單元測試的部分，也是未來 AI 生成流程的 Validator 可直接重用的核心。

### 5.4 Excel-first，ERP 唯讀 View 第二，寫回最後

台灣 SME 的現實：許多「ERP」是 SQL Server 上的舊系統或直接是 Excel。MVP 資料來源順序建議：
1. Excel/CSV 上傳（零整合成本，pilot 第一天就能跑）。
2. ERP 資料庫唯讀 View（請客戶 DBA 開一個 View，不碰 ERP API）。
3. ERP 寫回（最後才做，且一定要 idempotency_key + 人工確認）。

這樣 Data Adapter 的抽象會從三個真實來源自然長出來，符合 S4「抽象是觀察出來的」。

### 5.5 Dry-run 模擬器是低成本高價值的功能

各 AI 都提到 Validator，但只有 S2 提到 Simulation。建議在 Phase 2 做一個「用一筆樣本資料跑完整條流程、列出每個節點會找到誰簽、走哪條分支」的 dry-run。這對 pilot 導入時和客戶對規則、對未來 AI 生成流程的人工 Review，都是決定性的工具，且實作成本低（DSL Interpreter 換一個不呼叫真實 Activity 的 Runtime）。

### 5.6 AI Task 上線前先跑 Shadow Mode

AI Extraction / Decision 進入流程前，先以「影子模式」跑：AI 給結果但不影響流程，與人工結果比對，累積每家客戶的黃金資料集。準確率達門檻才切成「AI 建議 + 人確認」，再視客戶意願切成「自動 + 事後稽核」。這回答了各 AI 都在問的「哪些決策一定要 Human-in-the-loop」：不是固定清單，是由每個 AI Task 的實測準確率決定。

### 5.7 On-premise 版要早一點列入規劃，但不要早做

S2 指出製造業資料不能出廠。建議在 MVP 就遵守「所有服務都能用 docker compose 一鍵起」的紀律（Postgres + Temporal + API + Worker），不做任何綁定特定雲的設計。這樣 On-premise 版不是新產品，只是同一份 compose。

### 5.8 Grok 意見缺席

### 5.9 最需要警惕的一句話

七份回答裡最一致、也最不像技術建議的一點：**你低估了「賣」、高估了「做」。** 六個月裡真正的里程碑不是 Temporal 跑通，是第三家客戶付錢。所有架構決策都應以「能不能讓下一家客戶更快上線」為判準。
