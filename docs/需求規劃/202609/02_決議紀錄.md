## D-01 首個商業場景（2026-09-14 定案）

**選項**
- A. 採購簽核 + ERP 寫回（4 個 AI 首選）
- B. 負庫存 AI 分析追蹤（Gemini 首選）
- C. 企業報價單流程（使用者新增）

**決定：C 報價單當第一場景，A 採購當第二場景。**

**報價單流程定義**
```text
業務員建立報價單
  → 內部審核鏈（主管；折扣/毛利門檻動態加簽）
  → 送交外部客戶（客戶 Portal）
  → 客戶端簽核（可多人）、下載報價單 PDF
  → 客戶同意 → 回到內部流程 → 建立訂單（Odoo sale.order）
```

**子決議**
- 外部客戶簽核深度：**完整客戶 Portal**（非 Email + 一鍵連結最小版）。
- 報價單 PDF：**平台自己的模板引擎**（非 Odoo 報表）。

**理由**
- 碰營收、對外有展示效果、Odoo 寫回 API 現成。
- 採購流程結構相同（發起 → 動態簽核鏈 → 寫回），第二套件可重用引擎。

**已知風險與挑戰（已提出，使用者知情後仍選擇）**
- Odoo Sales 原生已有 quotation → 客戶 Portal 線上簽名 → 轉訂單。平台差異化必須落在：送出前內部審核鏈、AI 檢查（毛利/歷史價/信用）、客戶端多人會簽與版本往返、非 Odoo 客戶通用。
- 完整 Portal + 自有模板引擎，比多數 AI 建議的 MVP 範圍大。估計多 1.5～2.5 個月。

**新增的範圍項目（原 7 份 AI 意見未涵蓋）**

| 項目 | 說明 | 建議階段 |
|---|---|---|
| 外部身份體系 | 客戶 guest 帳號或 magic link；客戶方多人；與租戶使用者隔離 | MVP |
| 客戶 Portal | 檢視、簽核、留言、下載、版本歷史 | MVP |
| 電子簽核紀錄 | 簽核人、時間、IP、意見；是否需具法律效力的電子簽章待定 | MVP 基本紀錄；法律效力 Phase 2 |
| 模板引擎 | 報價單版面、多語、租戶 Logo、版本化；HTML → PDF | MVP |
| 版本往返 | 客戶退回 → 業務修改 → 重新審核 → 再送出；每版 PDF 存檔 | MVP |
| 對外通知 | Email 為主；LINE 視客戶 | MVP |
| Odoo 寫回 | quotation / sale.order 建立；idempotency_key | MVP |

**影響**
- Business Object 第一個實例：`quotation`（含 line items，即 One2Many 欄位需求提前）。
- Approver Resolver 首批規則：主管、折扣率門檻、毛利率門檻。
- Human Task 需區分 internal / external 兩種參與者。
- Workflow 需支援「回到前一節點」（客戶退回重審），即 loop-back edge，非 Loop Node。

### D-01b 採購簽核場景（第二場景，2026-09-14 定案）

**決定：併入同一份實作計畫，列為 Phase 6，不另開文件。**

**採購流程定義**
```text
採購申請（人工填寫表單，品項自 Odoo product 帶入）
  → 金額門檻動態並簽（部門主管 + 財務；超過門檻加 CFO）
  → 全數核准 → Odoo 建立 purchase.order
  → 通知申請人
```

**子決議**
- 範圍：純內部流程。不做供應商比價、不做供應商外部確認。
- 資料來源：人工填寫表單。不做負庫存 / 安全存量自動觸發。

**理由**
- 與報價單共用引擎、Resolver、Policy、Designer、Monitor、通知，增量僅 Business Object + 表單 + DSL + Odoo 寫入。
- 不含外部 Portal 與 PDF 模板，增量估 3～4 週。

**排除項（記錄以防日後誤以為遺漏）**
| 排除 | 原因 | 可能階段 |
|---|---|---|
| 供應商比價（至少 3 家報價） | 需新增 supplier_quote 物件與比價表 | P3 |
| 供應商外部確認交期 | 需複用 Portal，先驗證客戶端成效 | P3 |
| 負庫存 / 安全存量自動觸發 | 需 Schedule Trigger + 庫存讀取 | P2 |
| 收貨 / 驗收流程 | 屬 ERP 本身職責 | 不做 |

## D-02 後端語言組合（2026-09-14 定案）

**選項**
- A. Python 單一（Claude / Kimi）
- B. Rust API + Python Worker（ChatGPT / Gemini）
- C. TypeScript + Python Worker（DeepSeek）

**決定：B。Rust（API + Security）+ Temporal（Durable Execution）+ Python（Workflow + Activity + AI）。**

**硬限制**
Temporal 無正式 Rust SDK。Workflow 與 Activity 程式碼只能在 Python。Rust 只能啟動 / Signal / Query / Cancel Workflow，不能執行 Workflow。

**分工**

| 層 | 語言 | 職責 |
|---|---|---|
| API / Security | Rust (Axum) | Auth、Tenant、RBAC、Business API、Portal API、Audit、**Approver Resolver**（查 DB） |
| Durable Execution | Temporal Self-host | Workflow 狀態、Timer、Retry、Signal、Child Workflow |
| Workflow / Worker | Python | DSL Interpreter Workflow、**Approval Policy Engine**（純函數，跑在 Workflow 內）、所有 Activity、AI Task |

**子決議**
- Rust → Temporal 介接：**直接呼叫 Temporal gRPC**（tonic + WorkflowService proto），只用 StartWorkflow / SignalWorkflow / QueryWorkflow / RequestCancel 四個呼叫。不用 temporal-sdk-core crate，不加 Python Gateway。
- Approver Resolver 在 Rust：Python Activity 以 HTTP 呼叫 Rust API 取得簽核人清單。
- Approval Policy Engine 在 Python Workflow：純函數、決定性、表格式單元測試。

**共用契約**
- DSL JSON Schema 為單一真相來源；Rust 以 serde、Python 以 Pydantic 各自產生型別；CI 驗證兩邊對同一組 fixture 序列化結果一致。
- Rust 與 Python 之間的 HTTP 契約以 OpenAPI 定義。

**影響**
- 多兩種語言的維護成本，使用者知情接受。
- Temporal Workflow ID 格式：`{tenant_id}:{business_object}:{instance_id}`，Rust 產生，Python 遵守。

## D-03 視覺化 Designer（2026-09-14 定案）

**選項**
- A. 不進 MVP，手寫 JSON DSL（Kimi）
- B. 進 MVP，用開源工具加速（使用者）

**決定：B，進 MVP。**

**候選工具查核（2026-09-14）**

| 工具 | 授權 | 定位 | 結論 |
|---|---|---|---|
| Vue Flow v1.48 | MIT | 裸圖形庫（React Flow 移植），自訂節點/邊、Minimap、巢狀 | **採用為底層** |
| lowflow-design（tsai996） | MIT，220 stars | Vue3 + TS + Element Plus + UnoCSS + Pinia；節點：開始/審批/抄送/互斥閘道/條件/Timer/通知/服務/結束；會簽、或簽、通過比例；輸出 JSON + BPMN XML；Designer only | **參考來源**：節點 UI、屬性面板可複製 |
| VueWeave | 官網無授權/版本/GitHub 資訊 | 不明 | 排除 |

**子決議**
- 底層：Vue Flow + 自建節點庫。DSL 以自己的 JSON Schema 為唯一真相（承 D-02），Designer 只是 DSL 的檢視與編輯器，不反向決定 DSL。
- 版面：固定由上往下自動排版（dagre），不自由拖曳。並簽、條件分支橫向展開。釘釘風格，SME 熟悉，AI 生成後呈現穩定。
- 不 fork lowflow-design，不採用其 JSON 作 DSL，避免綁定其資料模型與 Element Plus。

**MVP Designer 範圍**
- 節點面板：Trigger、Condition、Human Approval（含 internal / external 類型）、Parallel、Join、Action、Notification。
- 屬性面板：節點屬性 Schema-driven（承 ChatGPT S1 建議，Property Panel 本身由 Schema 定義）。
- 不做：自由拖曳、Minimap、undo/redo（Phase 2）。

**影響**
- 前端多 2～3 週。
- 需要 `dsl → graph layout` 純函數，與 Rust/Python 無關，僅前端。

## D-04 首個 Data Adapter（2026-09-14 定案）

**決定：Odoo API（XML-RPC / JSON-RPC）。**

**理由**
- 使用者熟悉；API 完整；報價單場景對應 Odoo `sale.order`（state=draft 即 quotation）→ confirm 轉訂單。

**MVP 範圍**
- 讀：`res.partner`（客戶）、`product.product`（品項與價格）、`sale.order` 歷史（AI 歷史價比對，Phase 2）。
- 寫：`sale.order` + `sale.order.line` 建立；`action_confirm`。
- 每次寫入帶 idempotency_key（`workflow_instance_id:node_id`）存於 Odoo 自訂欄位或平台端對照表，重試前先查。

**第二 Adapter 順序（承彙整 5.4）**：Excel/CSV 上傳 → SQL 唯讀 View → 其他 ERP。

### D-04b Odoo 版本與版別（2026-09-14 定案）

**決定：Odoo 16 社群版（Community Edition）。**

**影響與限制**

社群版沒有的模組，規格中不得依賴：

| 模組 | 版別 | 對本專案影響 |
|---|---|---|
| `sale`（銷售、quotation、sale.order） | 社群版有 | 無影響，報價單寫回可行 |
| `purchase`（採購、purchase.order） | 社群版有 | 無影響，採購寫回可行 |
| `account`（會計基礎、發票） | 社群版有 | 無影響 |
| `sale_subscription`、`helpdesk`、`documents` | **僅企業版** | 不得依賴 |
| `account_accountant`（進階會計） | **僅企業版** | 不得依賴 |
| Studio、審批流程（`approvals`） | **僅企業版** | 正好是我們要取代的能力，不衝突 |

**這反而強化產品定位**：企業版的 Approvals 與 Studio 是付費功能，社群版使用者沒有。我們的平台等於為社群版補上簽核流程與表單設計能力，且不綁定 Odoo。

**技術約定**
- Adapter 只用 XML-RPC / JSON-RPC 標準介面，不裝自訂 Odoo 模組（降低導入阻力與升級風險）。
- 欄位差異集中於 `python-ai/adapters/odoo/v16.py`。
- 已查證的 model 檔案位置見 [README.md](../../../README.md)。

**Phase 0 待確認**：pilot 的 Odoo 16 小版本（16.0.x）、是否有第三方模組改動 `sale.order` 或 `purchase.order` 欄位。

## D-05 資料庫：是否支援 SQLite（2026-09-14 定案）

**提問**：測試與試用能否用 SQLite，正式環境才用 PostgreSQL？

**使用者提出的理由**（成立，已納入考量）
- 測試與試用只有一個客戶，不需要 Row Level Security。
- 試用版希望單檔攜帶，方便 demo。

**決定：不引入 SQLite。全環境統一 PostgreSQL 16。**

### 決定性理由：Temporal 不支援 SQLite

使用者同時要求「試用版要能跑真實流程，含簽核等待與逾期」。真實流程需要 Temporal，而 Temporal Server 的持久化層只支援 PostgreSQL、MySQL、Cassandra，**不支援 SQLite**。

因此「單檔攜帶」與「真實流程」兩者不可兼得。使用者選擇後者，SQLite 的主要動機自然消失。

### 其他差異（即使沒有 Temporal 因素仍存在）

| 功能 | PostgreSQL | SQLite | 本專案用途 |
|---|---|---|---|
| Row Level Security | 有 | 無 | 租戶隔離。單客戶時確實用不到，但測試就測不到此機制 |
| JSONB + GIN 索引 | 有 | 只有 JSON 文字 | Workflow DSL、表單定義、稽核 payload 全是 JSONB |
| decimal 型別 | 精確 | 動態型別，實際存 float | 報價金額。float 會產生精度誤差，算錯一元即失去客戶信任 |
| 並發寫入 | MVCC | 單寫入者鎖整庫 | 並簽多人同時提交 |
| pgvector | 有 | 無 | Phase 2 的 RAG |

decimal 這項單獨就足以否決。金額計算不能用浮點數。

### 雙資料庫的隱性成本

- SQL 語法、交易隔離、型別轉換三處差異，會造成「SQLite 綠燈、PostgreSQL 紅燈」。
- 每個 migration 要寫兩份並保持同步。
- 抽象層（例如 sqlx 的 Any driver）會迫使放棄 PostgreSQL 專屬功能，等於用 PostgreSQL 卻只享受 SQLite 的能力。

### 替代方案（已採用）

| 情境 | 做法 |
|---|---|
| 單元測試 | 純函數不碰資料庫。Policy Engine、CEL 求值、計算邏輯皆如此 |
| 整合測試 | **testcontainers 自動起 PostgreSQL**，測試前拉容器、測試後刪除。不需手動安裝，與正式環境完全一致 |
| 本機開發 | `docker compose up`，與 On-premise 交付同一份設定 |
| 試用版 | docker compose 打包。客戶裝 Docker Desktop 後一鍵啟動 |

### 試用版的攜帶性改善（不靠 SQLite）

若日後單檔攜帶仍是強需求，可行方向：
- 單一 Docker image 內含 PostgreSQL、Temporal、API、Worker，以 supervisor 管理。仍需 Docker，但只有一個 image。
- 雲端試用環境，客戶不裝任何東西，給一個網址。這對 SME demo 反而更順。

兩者都不需要第二套資料庫程式碼。

## D-06 是否需要獨立的 Job Service 處理逾時（2026-09-17 定案）

**提問**：能否做一個 job service 定期掃描逾時的流程並介入處理？

**決定：不做。Temporal 的 timer 已經處理逾時，再加一層是重複。**

### 理由：逾時已經是自動的

Interpreter 的 `_await_decisions` 用 `workflow.wait_condition(timeout=remaining)`
建立 Temporal timer。時間到時 Temporal 主動喚醒 Workflow，
依 policy 執行 WAIT／ESCALATE／AUTO_APPROVE／AUTO_REJECT。

決定當下的實況：

```
已逾期未處理    0
未到期         44
無期限         57
```

沒有任何待辦卡在「應該逾時但沒有」的狀態。

### 為什麼 Temporal timer 比輪詢好

| | Temporal timer | 輪詢 job |
|---|---|---|
| 精準度 | 到點即觸發 | 取決於掃描間隔 |
| 重複執行防護 | Workflow 決定性保證 | 要自己做分散式鎖 |
| 當機復原 | Temporal 重建 timer | 要自己記錄進度 |
| 狀態一致性 | 與流程狀態同一份 | 另一份，要對帳 |

輪詢會引入「兩個地方都可能推進流程」的競態：
job 判定逾時的同時，簽核人剛好按下核准。

### 修訂（2026-09-17 同日）

使用者指出我把兩件事混在一起了：

> 逾時前提醒就是剛剛講的 job service 要做的工作！
> 對帳的應該是 Temporal timer 要同步更新 postgresql

兩點都成立。修正如下：

| 缺口 | 原本的規劃 | 實際做法 |
|------|-----------|----------|
| 逾時**前**提醒 | 日後用 Temporal Schedule | **已實作**。不是逾時處理，是另一件事——多次觸發、可設定間隔。在同一個等待迴圈裡算出「下一個要醒來的時間點」，取提醒與到期的較早者 |
| 對帳 | 日後用定期任務修正 | **已實作**。不是事後補，而是寫入當下無限重試。先前重試 5 次就放棄，那筆資料永久不一致 |
| 測試資料回收 | 日後用 Temporal Schedule | 仍未做。這項確實適合定期任務，與流程執行無關 |

見測試報告 10。

**「不做獨立 job service」的結論不變**，但理由要更精確：
不是「這些需求不存在」，而是**它們都能在現有架構裡解決**——
提醒用 Workflow timer，對帳用 Activity 重試。

若日後要做測試資料回收，用 Temporal Schedule 而非獨立服務：
重試、防重複執行、執行歷史、監控都是現成的。
預定位置 `python-ai/schedules/`。

### 重新檢視的條件

若出現以下情況，這個決定應重新評估：

- 需要跨流程的批次處理（例如「所有逾期超過七天的單一次退回」）
- 需要在流程之外觸發的動作（例如每日從 ERP 拉資料）
- Temporal timer 的數量成為效能瓶頸（單一 Workflow 的 timer 數有上限）

## D-07 沙箱的形態與模擬簽核（2026-09-17 定案）

**提問**：需求 03 §3.3 規劃了沙箱但形態未定（三個技術選項），
且「模擬」的具體操作方式沒有描述。

**決定：沙箱是「編輯開發模式」，用影子租戶隔離資料，
測試者一人扮演所有簽核人走完流程。**

### D-07a 沙箱的定位：編輯開發模式

使用者的描述：

> 選單有一個目前執行的所有流程的清單與詳細內容顯示！但是都是唯讀！
> 如果要編輯！就要進入編輯開發模式！編輯開發模式就是一個沙箱！

這確立了三件事：

| # | 功能 | 性質 |
|---|------|------|
| A | **流程監控**：所有執行中流程的清單與詳情 | 唯讀，正式環境 |
| B | **編輯開發模式**：從監控進入，設計表單與流程 | 沙箱 |
| C | **模擬簽核**：一人扮演所有簽核人走完流程 | 沙箱 |

**唯讀是硬性要求**。流程監控不提供任何修改定義的入口，
只有「進入編輯開發模式」這一個出口。

### D-07b 隔離方式：影子租戶（選項 A）

需求 03 列的三個選項中選 A。

理由：**複用一個已經驗證過的隔離機制，而不是新增一個平行的。**

現有系統已提供、沙箱不需改動的部分：

| 機制 | 現況 |
|------|------|
| RLS（`workflow_app` 非超級使用者）| 已啟用，九項隔離測試通過 |
| `tenant_tx()` 單一進入點 | 所有 DB 存取都經過它 |
| `workflow_id::build` | 已含 tenant 前綴 |
| `workflow_id::belongs_to` | 已實作歸屬檢查 |

建一個開發租戶，資料隔離自動成立。不需要在任何查詢加
`where is_sandbox = false`。

**不選選項 B（同租戶加 `is_sandbox` 標記）的理由**：
每處查詢都要記得過濾，漏一個就洩漏，而且是**靜默失敗**——
與交接手冊記錄的「條件式路徑打錯靜默跳過簽核」同一類問題。
靜默的錯誤比會爆炸的錯誤危險。

**不選選項 C（獨立 schema）的理由**：migration 要維護兩份，
本專案已有 20+ 個 migration 檔，雙份遲早漂移。

### D-07c 模擬簽核：附身模式，不換身分

這一項修正了先前的規劃。

| 先前的設計 | 定案 |
|-----------|------|
| 複製使用者帳號到沙箱，測試者換身分登入 | **不複製 user，不換身分** |
| 操作體驗一致 = 用一樣的登入流程 | 操作體驗一致 = **看到的畫面與那個人會看到的一樣** |

使用者的描述：

> 執行時可以直接由系統依據目前的系統角色設定解析出實際簽核的人員，
> 測試的人可以直接點選模擬這個人簽核，系統依據權限設定顯示每個
> 簽核人員的畫面

務實得多：不必複製使用者主檔（先前列為最容易出錯的一步），
測試者一人就能走完五關，不必請五個同事配合。

**核心轉變：沙箱不是另一個環境，是一個附身模式。**

三個實作要點：

1. **解析簽核人要真的呼叫 resolver**，不能用假資料。
   這正是這個功能最大的價值——它在驗證 resolver 設定對不對。
   已踩過 `resolver.user_id` 需要 UUID 不是 email 導致流程 FAILED。
   解析失敗要明確報錯，不可跳過或用預設人員頂替。

2. **權限過濾複用 `domain::permission::resolve_form()`**（後端），
   不重寫。前端的 `usePermissionPreview.ts` 只是 API 呼叫殼，
   真正的判定在 `server/crates/domain/src/permission.rs:68`。

3. **稽核同時記 `actor_id` 與 `acting_as`**。
   只記 `acting_as` 會變成「張文華核准了他不知道的事」。
   沙箱裡雖無害，但兩套稽核語意會讓程式碼分岔。
   `acting_as` 目前不存在，要新建——跨所有稽核呼叫點。

4. **簽核 API 的授權開洞條件寫死，不可做成可配置的權限。**
   `tasks.rs:134` 的 `task.assignee_user_id == Some(actor.user_id)`
   會擋下模擬簽核，必須開洞。但條件只能是
   「`is_sandbox` 且操作者是沙箱建立者」——
   若做成「擁有某角色就能扮演」，正式租戶誤給該角色等同開放冒名簽核。
   **沙箱身分不是一種權限，是一種環境狀態。**

### D-07d 沙箱通知：照常寄出，標題加前綴，改寄測試者

**使用者的決策**：

> 沙箱不會寄出 mail 通知在 title 都會有『沙箱模擬』的開頭！

先前規劃是攔截不寄、畫面顯示「本來會寄給誰」。使用者的做法更好：

| 攔截不寄 | 照常寄出加前綴 |
|---------|--------------|
| 只驗證到「系統決定要寄給誰」 | 驗證到**信真的送達** |
| 收件人 email 打錯不會發現 | 退信就發現 |
| SMTP 設定問題上線才爆 | 沙箱就爆 |

與 D-07c 第 1 點同一個原則：
**沙箱的價值在於它真的跑，不是模擬它跑。**

前例支持這個判斷：SMTP 那次，單元測試驗到「有呼叫
`send_notification`」就算過，但 Activity 漏傳 `kind`，
信寄出去標題是「【流程通知】」而非「【待辦提醒】」。
**那個錯誤只有真的寄一封信才會發現。**

收件人範圍選 C（測試者確認）：

```
收件人：李一昌 <leeichang@gmail.com>       ← 測試者，非原對象
標題：【沙箱模擬】【待辦提醒】報價單 QT-2026-001 待簽核

──────────────────────────────
這是沙箱模擬的通知，不是真實待辦。

原收件人：張文華 <cfo@demo.local>
解析依據：resolver role = cfo
發起人：李一昌
──────────────────────────────
```

不寄給解析出的同事，因為對方可能當真去簽；
原收件人寫在內文，收件人解析與 resolver 設定照樣驗證得到。

**實作位置：寄送端 `internal.rs:408`（`resolve_recipients` 之後、
`subject_of` 之前），不是呼叫端。**

`send_notification` 的呼叫點有五處（human_task 建立、提醒、逾時、
ESCALATE、流程結束），靠每處記得處理遲早漏一個——
漏掉的那封信就會有人當成真待辦去簽核。

不在 Python Activity 改：Activity 不該知道沙箱這個概念，
它只負責「請寄這封信」。

稽核要記三層：`to`（參與者 id）、`recipients`（解析後的真實收件人）、
`actual_recipients`（沙箱改寫後實際寄達的）。
只記最後一層的話查不出「原本要寄給誰」，而那正是沙箱要驗證的。

`is_sandbox` 的取得方式：**由 `tenant_tx()` 回傳時帶上租戶屬性**，
不要各處自己查 `tenant` 表。`tenant_tx()` 已經是所有 DB 存取的單一
進入點，在那裡取一次，其他地方都不必重複——也讓「忘記判斷 is_sandbox」
這種錯誤更難發生。

LINE 之後接上時同樣處理。

### 對現有系統的影響

```sql
alter table tenant
  add column parent_tenant_id uuid references tenant(id),
  add column is_sandbox boolean not null default false,
  add column expires_at timestamptz;
```

新增 `sandbox_session` 表（需求 03 §4.2 已規劃）。

新增選單項目「流程監控」。現有 `/quotations` 是**單據**列表，
不是跨業務物件的流程實例列表，兩者不同。
API `GET /instances` 已存在可複用。

**版本狀態機的擴充仍未指派。** 需求 03 §4.1 規劃從
`DRAFT → PUBLISHED` 兩態擴充成四態（加 `SIMULATING`、
`PENDING_APPROVAL`）。D-07 沒有涵蓋這項，但沙箱需要它——
沒有 `SIMULATING` 態的話，沙箱裡的草稿與正式草稿在資料上分不開。

決定要不要納入本批工作時再處理。若不納入，
沙箱階段 1 至少要能用 `sandbox_session` 反查「這個草稿屬於哪個沙箱」。

### 前置條件

三項，都要在模擬簽核之前完成。

**1. DSL 驗證要加路徑存在性檢查**（WF-E012）

條件式引用不存在的路徑會靜默當成 false，流程少走一段簽核而無人察覺。
人工編輯時是「危險」，AI 生成時是「不可接受」——使用者不會去看 JSON。

這在需求 03 §4.3 已列為前置條件，D-07 同樣依賴它。

**2. 權限預覽 API 要支援真實 data**

`permissions.rs:187` 把 `data` 寫死成空物件。設計器預覽沒有實際單據，
空的合理；但模擬簽核有真實單據，而 `permission.rs:193` 的 `eval_bool`
會用 `data` 求值條件式。

不改的話，凡是 `visibility.when` 依賴欄位值的欄位在模擬時全部判錯——
使用者看到的畫面與真實簽核不同，而沙箱的整個價值就是兩者要一致。

做法：預覽 API 加可選的 `instance_id`，有值時帶入該實例的
`business_object`。設計器不傳就照舊。

**3. 表單要有版本鎖定**

`workflow_instance` 已有 `workflow_version_id`（`0005:21`），
**表單沒有對應欄位**。流程跑到一半改表單定義，
進行中的實例會用到新版。

沙箱與 AI 產生都會大量改表單定義，這個缺口會被放大。
而且需求 03 §3.5 宣稱「進行中的實例不受還原影響」，
在表單沒有版本鎖定的前提下，**那個宣稱目前不成立**。

```sql
alter table workflow_instance
  add column form_version_id uuid
      references form_definition_version(id) on delete restrict;
```

### 重新檢視的條件

- 開發租戶數量膨脹到影響效能（已有 574 個測試租戶的前例，
  靠 `expires_at` + 定期回收控制）
- 主檔複製的範圍不足以支撐模擬（resolver 找不到人）
- 使用者反映「一人扮演所有角色」不符合實際驗證需求
  （例如要多人同時在沙箱協作測試）
