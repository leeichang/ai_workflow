# 表單與流程異動治理需求

- 提出：2026-09-17
- 狀態：**需求記錄，尚未排入實作**
- 範圍：表單與流程的變更管理，含 AI 協助、沙箱模擬、審核上線

---

## 1. 為什麼要做

### 1.1 市場上的流程系統都預設有資訊單位

現有的 workflow 產品（包括本系統目前的樣子）都假設一件事：
**表單與流程的擁有者是資訊人員**。

使用者想改一個欄位，流程是這樣的：

```
使用者 → 提需求單 → 排隊 → 資訊人員理解需求 → 改設定 → 測試 → 上線
                     ↑
                 通常卡在這裡
```

問題不在工具，在於**中小企業根本沒有資訊單位**。

台灣製造業 SME 的實況：

- 沒有專職 MIS，或只有一位兼著做
- 業務流程變動頻繁（客戶要求、法規、季節性調整）
- 等不起排隊，結果是**繞過系統**——回到 Excel 與 LINE

繞過系統，這套工具就失去意義。

### 1.2 目標：讓使用者成為 Owner

**使用者應該能自己改自己的表單與流程，不需要經過資訊人員。**

但「自己改」不等於「隨便改」。沒有治理機制的自助等於災難：

- 改壞了進行中的單據
- 刪掉別人依賴的欄位
- 把該簽核的關卡拿掉

所以要的是三件事一起：

| | 解決什麼 |
|---|---|
| **AI 代工** | 使用者不必懂 JSON schema、不必學設計器的操作 |
| **沙箱模擬** | 改完先試，不影響正式資料 |
| **審核上線** | 有人把關，留下稽核軌跡 |
| **版本歷史與還原** | 改壞了救得回來 |

四者缺一不可。只有 AI 沒有審核 = 失控；只有審核沒有 AI = 還是要懂技術；
沒有沙箱 = 不敢改；沒有還原 = 改壞了只能求救。

**其中「還原」是心理門檻的關鍵。** 使用者不敢動系統設定，
多半不是因為不會操作，而是怕改壞了收不了場。
知道隨時能回到昨天的狀態，才敢真的把它當成自己的工具。

## 2. 目標流程

```
使用者用自然語言提出需求
        ↓
   AI 產生變更提案
        ↓
   顯示變更差異（改了什麼、影響誰）
        ↓
   沙箱模擬（試填、試跑，資料與正式隔離）
        ↓
   使用者確認沒問題 → 送審
        ↓
   審核者核准（走既有的流程引擎）
        ↓
      上線
```

每一步都可以退回前一步。

## 3. 各段的需求

### 3.1 AI 產生變更提案

**這次不實作，先記錄。**

使用者輸入自然語言，AI 產生對表單定義或流程定義的變更。

範例：

| 使用者說的 | AI 該產生的 |
|-----------|------------|
| 「客戶資訊加一個交貨地點的文字欄位」 | 表單新增 `delivery_site` 欄位，`data.path` 為 `customer.delivery_site` |
| 「報價金額超過一百萬要加一關董事長簽核」 | 流程新增 `condition` 節點與 `human_approval` 節點 |
| 「內部備註不要讓客戶看到」 | 該欄位的 `ui.external_visible` 改為 false |

需要考慮但尚未決定的：

- 用規則式（可解析的句型）還是真 LLM
- prompt 注入的防範（使用者輸入會進到 prompt）
- AI 輸出不合法時怎麼處理（重試？降級成手動？）
- 成本控制
- 模稜兩可的需求怎麼回問使用者

**已知的技術地雷**（來自現有系統的經驗）：

AI 產生的變更必須通過現有的驗證規則，尤其是
[交接手冊 5.1](../../交接手冊/02_工作現況與開發計劃.md) 記錄的那個：
**條件式引用的路徑打錯不會報錯，會靜默當成 false**。

如果 AI 產生一個引用了不存在路徑的條件式，流程會安靜地少走一段簽核，
而沒有人會發現。這在 AI 生成的情境下比人工編輯更危險——
使用者不會去檢查 JSON。

所以 DSL 驗證加上路徑存在性檢查，是這個功能的**前置條件**，不是附帶。

### 3.2 變更差異顯示

送審與模擬之前，使用者要看得懂「改了什麼」。

不能只顯示 JSON diff——使用者看不懂。要用業務語言：

```
新增欄位「交貨地點」到「客戶資訊」區塊
  類型：單行文字
  對應資料：customer.delivery_site

修改「內部簽核備註」
  外部客戶可見：是 → 否
```

還要顯示**影響範圍**：

- 有幾張進行中的單據使用舊版
- 刪除的欄位是否有既存資料
- 流程變更是否影響進行中的實例

### 3.3 沙箱模擬

**使用者的決策**：沙箱是一個與正式系統分開的環境，
操作體驗與正常系統完全一致，但資料與正式表單區隔。

要點：

| 項目 | 要求 |
|------|------|
| 操作體驗 | 與正式系統無差異，不是簡化版預覽 |
| 資料隔離 | 沙箱建立的單據不進正式資料，不出現在正式的待辦與列表 |
| 可試跑流程 | 能模擬各關核准／退回，看路徑走向 |
| 可重複 | 試錯後能重置，不留殘渣 |
| 明確標示 | 使用者要隨時知道自己在沙箱，不會誤以為在正式環境 |

技術選項（尚未決定）：

- **選項 A**：用租戶隔離。每個變更提案配一個 `sandbox_` 前綴的影子租戶。
  現有的 RLS 直接可用，資料天然隔離。代價是要複製主檔資料。
- **選項 B**：在同一租戶內加 `is_sandbox` 標記。
  改動小，但每一處查詢都要記得過濾，漏一個就洩漏。
- **選項 C**：獨立的 sandbox schema。隔離最乾淨，但 migration 要維護兩份。

初步傾向 A——本系統的 RLS 已經驗證過九項隔離測試，
複用它比新增一個平行的隔離機制安全。但要解決 Temporal 的
workflow_id 前綴（目前是 `{tenant_id}:{business_object}:{instance_id}`，
沙箱租戶天然會有不同前綴，這點有利）。

### 3.4 審核與上線

**使用者的決策**：沿用既有流程引擎跑審核。

#### form_change 是系統內建的表單，但用系統自己的機制建構

這一點要講清楚，它決定了實作方式。

`form_change` **不是**使用者自訂的表單，而是系統預設就存在的。
但它**不是**寫死在程式碼裡的特例——它就是一份表單定義 + 一份流程定義，
結構與 `quotation_form` 完全相同，差別只在於：

- 由 seed／migration 建立，每個租戶開通時自動具備
- 標記為系統內建（例如 `is_system: true`）
- 不能刪除

```
quotation_form   使用者建立的表單   ─┐
purchase_form    使用者建立的表單   ─┼─ 同一套資料結構
form_change      系統內建的表單     ─┘   同一套渲染引擎
                                          同一套流程引擎
```

這樣做的意義：

**系統吃自己的狗糧。** 變更治理流程本身就是用這套流程引擎跑的。
如果流程引擎有缺陷，第一個踩到的是我們自己，不是客戶。

**不需要為審核另寫一套 UI。** 審核者在「我的待辦」看到變更提案，
用的是同一個收件匣、同一個核准／退回介面。

**審核規則可以調整。** 因為它就是一份流程定義，可以用
WorkflowDesigner 打開來改——例如某個客戶想加一關、
某個客戶想讓小變更免審。

預設的審核流程：

```
start → 主管審核 → (影響範圍大?) → 資訊主管審核 → 上線
                 → (影響範圍小?) → 上線
```

#### 內建的審核流程可以改（2026-09-17 定案）

**決定：流程可以改，系統保留完整版本歷史，使用者可以還原到任何版本。**

理由：禁止修改不符合「使用者是 Owner」的定位。
不同客戶的治理需求本來就不同——有的要兩關、有的小變更想免審。
與其禁止，不如讓改壞了能救回來。

這個決定把風險從「不能改」轉成「改壞了能還原」，
而後者是可以用工程手段保證的。

表單欄位的部分仍傾向限制：變更內容、影響範圍、提案人這些
是系統邏輯依賴的，刪掉會壞掉。但這是「不可刪除」而非「不可修改」，
標籤、順序、額外欄位都可以調整。

#### 需要新增的

- `form_change` 業務物件的表單定義與流程定義（seed）
- 系統內建標記，避免被刪除
- 上線動作（把 `PENDING_APPROVAL` 版本轉成 `PUBLISHED`）
- 版本狀態機擴充（見 4.1）

### 3.5 版本歷史與還原（2026-09-17 定案）

**每一次變更都保留完整版本，使用者可以還原到任何一版。**

這是「可以改」的配套。有了它，改壞了不是災難，是按一個按鈕的事。

#### 好消息：資料結構已經支援

`form_definition_version` 與 `workflow_definition_version` 現在就是
**append-only** 設計：

- 每次發布產生新的 `version`（`coalesce(max(version), 0) + 1`）
- 舊版的列不會被刪除或覆寫
- `content` 存的是**完整快照**，不是 diff——還原不需要反向套用

`persistence` 層已經有 `list_versions()` 與 `get_version()`。

換句話說，**歷史已經在了**，缺的是：

| 缺什麼 | 說明 |
|--------|------|
| 還原操作 | 後端 API + 前端按鈕 |
| 版本歷史畫面 | 列出各版、誰發布的、何時、改了什麼 |
| 版本比較 | 任兩版之間的差異 |

#### 還原的語意：往前補一版，不改寫歷史

兩種做法：

| 做法 | 結果 | 問題 |
|------|------|------|
| 改寫歷史 | 把 v3 的內容蓋回 v5 | 稽核軌跡斷裂，「v5 曾經是什麼」消失 |
| **往前補一版** | 用 v3 的內容建立 v6 | 歷史完整，可以再還原回 v5 |

**採用後者。** 還原 = 以舊版內容建立新版本並發布。

```
v1 → v2 → v3 → v4 → v5
                     ↓ 使用者還原到 v3
                    v6（內容 = v3，來源標記為 v3）
```

好處：

- 稽核完整——每一版都是真實發生過的狀態
- 可以「還原的還原」——v6 不滿意可以再還原回 v5
- 不需要處理「還原後版本號怎麼算」的邊界情況

版本表要加一個欄位記錄來源：

```sql
restored_from_version integer  -- NULL 表示正常發布，有值表示由該版還原而來
```

#### 還原要不要經過審核？

**要。** 還原就是一次變更，走同一套 `form_change` 審核流程。

理由：還原也可能是錯的。使用者以為 v3 是對的，
但 v3 可能缺了 v4 才加上的合規欄位。

例外情況待議：緊急還原（線上出包）是否需要快速通道。

#### 進行中的實例不受還原影響

流程實例的 `workflow_version_id` 是綁定的，跑到一半的單據
繼續用它啟動時的那一版。還原只影響**之後**啟動的實例。

表單定義目前沒有這個綁定（見第 5 節第 6 項），
是還原功能落地前要一併解決的。

## 4. 對現有系統的影響

### 4.1 版本狀態機要擴充

現況只有兩態：

```
DRAFT → PUBLISHED
```

需要變成：

```
DRAFT → SIMULATING → PENDING_APPROVAL → PUBLISHED
  ↑          ↓              ↓
  └──────────┴──────────────┘  （退回都回到 DRAFT）
                              → REJECTED（審核不通過且不再修改）
```

影響 `form_definition_version` 與 `workflow_definition_version` 兩張表，
以及所有讀取「已發布版本」的地方——目前的查詢是
`status = 'PUBLISHED'`，加了中間態之後語意不變，但要確認
沒有地方寫成 `status != 'DRAFT'`。

### 4.2 新增資料表（初步）

| 表 | 用途 |
|----|------|
| `change_request` | 變更提案：誰提的、原始 prompt、產生的 patch、目標表單／流程、狀態 |
| `sandbox_session` | 沙箱工作階段：對應哪個提案、影子租戶 id、建立時間、到期時間 |

`change_request` 會與 `workflow_instance` 關聯——審核流程本身是一個實例，
`business_object = 'form_change'`，`business_key` 是提案編號。

現有的 `form_definition` 與 `workflow_definition` 要加一個系統內建標記
（避免 `form_change` 被刪除）。

版本表要加還原來源：

```sql
alter table form_definition_version
  add column restored_from_version integer;
alter table workflow_definition_version
  add column restored_from_version integer;
```

`NULL` 表示正常發布，有值表示由該版還原而來。

### 4.3 前置條件

**DSL 驗證必須先加上路徑存在性檢查**（見 3.1）。

這在交接手冊裡已列為高優先缺陷。在人工編輯的情境下它是「危險」，
在 AI 生成的情境下它是「不可接受」。

## 6. 分階段的建議

不建議一次做完。建議順序：

| 階段 | 內容 | 前置 | 規模 |
|------|------|------|------|
| 0 | DSL 路徑存在性驗證 | 無 | 小 |
| 1 | **版本歷史與還原** | 無 | 小 |
| 2 | 版本狀態機擴充 + 送審／審核／上線 | 0 | 中 |
| 3 | 變更差異顯示（業務語言 + 影響分析） | 2 | 中 |
| 4 | 沙箱模擬 | 2 | 大 |
| 5 | AI 產生變更提案 | 3、4 | 大 |

**階段 1 建議優先做，而且可以獨立出貨。**

資料結構已經是 append-only，歷史都在，缺的只是
「列出版本」「比較兩版」「還原」三個操作。投入小、
立即降低使用者改壞東西的恐懼——這是讓使用者敢當 Owner 的第一步。

階段 2～4 做完，使用者就能在設計器裡改、在沙箱試、送審上線，
只是還要自己操作設計器。階段 5 才是「用講的就能改」。

先做治理再做 AI 的理由：AI 改出來的東西沒地方試、沒人把關、
改壞了救不回來，那是負債不是資產。

## 7. 這個需求對產品定位的意義

目前的定位：

> 不換 ERP，把 Excel／Email／LINE 上的簽核變成有 ERP 寫回、可稽核的正式流程。

加上這個功能之後：

> **而且這些流程由使用者自己維護，不需要資訊人員。**

這是與現有 workflow 產品的真正差異點。市面上的產品都在比
「設計器多好用」，但那個前提是「有人會用設計器」。
中小企業缺的不是好用的設計器，是**會用設計器的人**。
