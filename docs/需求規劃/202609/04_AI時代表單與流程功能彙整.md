## 1. 傳統表單的基本功能（共識基礎）

在談 AI 之前，這些是任何 workflow 表單都必須有的。**結構先於智能**（X），
沒有這些，後面的模型沒東西可審。

### 1.1 資料輸入與格式

| 功能 | 說明 | 來源 |
|------|------|------|
| 多樣化欄位類型 | 單/複選、文字、數字、日期時間、下拉、附件上傳 | G |
| 明細列（子表格） | 一對多的資料列，讓單據可運算 | X, C |
| 動態邏輯（條件顯示） | 選「請假」才顯示假別；急件才出理由；達額才強迫比價 | G, X, C |
| 資料驗證與格式限制 | 必填、長度、Email/手機格式校驗 | G, K |
| 自動帶入與公式計算 | 登入者帶入姓名/部門/日期；自動算金額、天數、小計 | G |
| 分節與草稿 | 申請/明細/供應商/合規分區；送出後留下**不可變快照** | X |

### 1.2 審核與流程運作

| 功能 | 說明 | 來源 |
|------|------|------|

| 加簽 | 審核者臨時增加一位簽核人 | C |
| SLA / Timeout / Escalation | 逾時未簽的處理 | C |

### 1.3 權限與安全控制

| 功能 | 說明 | 來源 |
|------|------|------|
| 欄位級權限 | 各關卡分別設定「可編輯/唯讀/隱藏」 | G, C |

| 申請/初審/核准分離 | 三種角色不可同一人；高額會簽寫在政策不寫在人的記憶 | X |

### 1.4 紀錄與追蹤

| 功能 | 說明 | 來源 |
|------|------|------|

| 版本控制 | 表單改版後保留歷史版本，**舊單依原格式運作** | G, K |

### 1.5 通知與整合

| 功能 | 說明 | 來源 |
|------|------|------|

## 2. AI 時代要增加的表單功能

### 2.1 資料結構層：讓 AI 讀得懂

| 功能 | 說明 | 來源 |
|------|------|------|
| **Schema-aware 欄位** | 欄位定義本身可被 AI 讀取（JSON Schema / OpenAPI），讓 Agent 知道每個欄位的**語意、型別、驗證規則** | L, K, D |
| 欄位語意描述 | 不只是 label，要有 field description | K |
| 驗證規則宣告化 | regex、數值範圍、關聯邏輯（「請假 > 3 天需附證明」）寫成機器可讀規則，**不散落在程式碼裡** | K |
| 檔案附件可解析 | PDF、圖片、Excel — 痛點是「紙本/截圖→人工謄打」 | K |
| Agent 可呼叫的 Action Schema | 表單提交不只是存 DB，而是可觸發 Agent 執行的結構化指令 | L |

### 2.2 輸入層：多模態與對話式

| 功能 | 說明 | 來源 |
|------|------|------|
| **多模態輸入** | 上傳發票/合約 PDF、語音檔、拍照，AI 自動提取欄位（廠商、統編、金額、條款） | G, L, K |
| **對話式表單生成** | 使用者用自然語言描述需求，AI 互動中整理並填妥結構化表單 | G, L, D |
| 自然語言轉結構化 | 一段話 → 意圖辨識 + slot filling → 填入對應欄位 | L |
| 口述／文件進表 | 一句話填成欄位，人只核對統編與金額 | X |
| 對話式補件 | 資料缺漏時 AI 直接追問「出差地點是曼谷還是台北？」而非整張退回重填 | K |

### 2.3 驗證與輔助層：填表時就降錯

| 功能 | 說明 | 來源 |
|------|------|------|
| **語意邏輯檢查** | 不只格式：報銷寫「計程車費」但金額與收據不符、日期在休假期間 | G, L |
| **歷史比對與重複預警** | 「該供應商上週已提出相同金額的請款」「類似需求單兩天前已建立」 | G |
| 政策感知校驗 | 單價異常、類別不符、疑似重複 | X |
| 情境式預填 | 依操作習慣、專案脈絡、跨系統（ERP/CRM）資料預測並預填 | G, K |
| **信心分數（confidence score）** | AI 判斷欄位填寫的可信度，低信心觸發人工複核 | L, K, D |
| 送出前路由預覽 | 填的當下就知道會自動放行、補件、駁回還是人審 | X |

### 2.4 人機協作層：HITL 的落點

| 功能 | 說明 | 來源 |
|------|------|------|
| **置信度顯示欄位** | 每個欄位附 AI 解析的信心分數（如 OCR 金額 0.92），人工優先檢查低信心欄位 | K, D |
| **diff 檢視器** | 人類看的是「AI 提取結果 vs 原始文件」對照，不是只看最終值 | K, G |
| 一鍵覆寫（Override） | 人工改值要記錄，回流成 AI 的校正資料 | K, D, L |
| **來源標記** | AI 產生/修改的欄位要標記來源：人填 / AI 填 / AI 建議後人確認 | L |
| 差異高亮與摘要 | 標示「AI 核對一致」與「疑慮/差異欄位」 | G |

### 2.5 AI 字段（DeepSeek 特有觀點）

> 使用者可以像添加普通字段一樣，拖拽添加 **AI 文本摘要、AI 內容分析、
> AI 進度評估、AI 智能評分** 等能力，無需代碼開發。

意義：表單在填寫過程中就能自動提煉核心事由、識別風險點，審批人無需通讀長文。

### 2.6 動態表單

| 功能 | 說明 | 來源 |
|------|------|------|
| 依推論增減欄位 | conditional rendering **by inference**，而非單純規則樹 | L |
| 進度指示器 | 多步驟表單 1→2→3→4，已完成可跳回、未完成不可跳 | D |

## 3. AI 時代要增加的流程功能

### 3.1 AI Agent 自動執行與代理

| 功能 | 說明 | 來源 |

| API 自動處置 | 審核通過後 Agent 直接呼叫 API 完成後續設定（建 ERP 訂單、開 CRM 帳號） | G, C |

### 3.2 智慧動態路由

| 功能 | 說明 | 來源 |
|------|------|------|
| **基於意圖與風險的分流** | 不只靠「固定金額或部門」，由 AI 分析風險等級、緊急度、語意意圖，決定走快速通道或多層人工審查 | G, D |
| **最佳審核者推薦** | 依工作負載、歷史處理經驗、專業範疇動態指派 | G |

### 3.3 人機協同決策輔助（Decision Copilot）

| 功能 | 說明 | 來源 |
|------|------|------|
| 即時摘要與風險提示 | 審核者開啟關卡時，AI 提供「30 秒重點摘要」「異常風險提示」「歷史相似案例處理建議」 | G |
| 一鍵生成決策意見 | 審核者輸入簡單指示，AI 擴充為規範的簽核意見或退回說明 | G |

### 3.4 並簽 / Parallel + Join（ChatGPT 的核心貢獻）

**這一段是 ChatGPT 最有價值的部分，也是本系統目前明確缺少的能力。**

#### Parallel Group 模型

不要在引擎裡寫死「等待 A、等待 B、等待 C」，而要建立通用的
**Parallel Group / Execution Token**：

```
parallel_group_id = PG-001

tasks
├── T001 部門主管
├── T002 財務
├── T003 資材
└── T004 品保
```

Join Node 只需判斷 `完成數 / 總任務數`。

#### 四種 Join 完成模式

| 模式 | 規則 | 例子 |
|------|------|------|
| **ALL** | `completed == total` | 全部簽完才繼續 |
| **ANY** | `completed >= 1` | 三個主管任一核准即可，其餘 CANCELLED |
| **N_OF_M** | `approved >= N` | 5 位委員至少 3 位同意 |
| **ALL_SUCCESS** | 全部完成 AND 全部核准 | 任一 REJECT 就走 Reject |

#### Join 的三層 Policy

```
Join
 ├── Completion Policy    ALL / ANY / N_OF_M
 ├── Result Policy        ALL_SUCCESS / ANY_REJECT / MAJORITY / CUSTOM_EXPRESSION
 └── Timeout Policy       WAIT / ESCALATE / AUTO_APPROVE / AUTO_REJECT
```

#### Token 模型

```
                    Token-001
                       ↓
                    AND Split
                  /     |      \
             Token-A  Token-B  Token-C
                ↓        ↓        ↓
             Task-A    Task-B    Task-C
                 \       |       /
                   AND Join
                       ↓
                    Token-002
                       ↓
                   下一節點
```

有了 Token，引擎自然支援 Parallel、Conditional Branch、Loop、
Sub Workflow、Retry、Wait、Human Task、AI Task。

#### Human Task 必須與 Runtime 解耦

**不要**：使用者按核准 → 直接跳下一節點

**要**：

```
User → Human Task → Task Result → Parallel Group
     → Workflow Runtime → 判斷 Join → 建立下一個 Token
```

#### 資料表建議

```
workflow_parallel_group
  id, workflow_instance_id, join_node_id
  join_mode, required_count
  total_count, completed_count, approved_count, rejected_count
  status, created_at, completed_at
```

### 3.5 Approver Resolver

不要在設計時指定「王小明」，而是指定角色，Runtime 再解析。
支援的解析方式（C）：

- Role-based
- User-based
- Department-based
- Manager-based
- Dynamic expression
- SQL query
- API query
- AI resolver

待解問題（C 提出）：

- 某一分支 Reject 怎麼辦
- Timeout 怎麼辦
- 其中一人離職怎麼辦
- Delegation / Substitute
- 動態產生簽核人員
- 「部門主管 + 財務主管 + 金額超過 100 萬再加 CFO」這種動態並簽

### 3.6 系統與營運層級

| 功能 | 說明 | 來源 |
|------|------|------|
| **自我優化與瓶頸診斷** | AI 監控流程數據，指出「某環節平均卡關 3 天」「某欄位常被退回」，給出優化建議 | G, C |
| **自然語言流程建構（Text-to-Workflow）** | 「客戶退貨申請金額超過 5 萬先通知品保再送主管」→ AI 自動產生表單欄位與流程關卡 | G, C |
| Process Mining | 從執行歷史分析實際流程 vs 設計流程 | C |

## 4. AI Agent 自動初審關卡（HITL）架構

五個來源的架構高度一致，但各有獨到之處。

### 4.1 Gemini：三層架構

```
[ 表單提交 / 觸發事件 ]
         ↓
┌─────────────────────────────────────┐
│ 1. 資料預處理與檢索層 (Data & RAG)   │
│  - 多模態解析 (OCR / 語音 / PDF)     │
│  - 內部知識庫與歷史資料檢索 (RAG)     │
└──────────────────┬──────────────────┘
                   ↓
┌─────────────────────────────────────┐
│ 2. AI Agent 評估引擎                 │
│  - 語意合規性檢查                    │
│  - 異常偵測與風險計分                │
│  - 信心度評定                        │
└──────────────────┬──────────────────┘
                   ↓
┌─────────────────────────────────────┐
│ 3. 路由控制與決策層                  │
│  - 自動通過 / 人工覆核 / 直接退回     │
└─────────────────────────────────────┘
```

評估引擎執行三大檢核：

1. **規則硬指標**（Rule-based Guardrails）：金額上限、必填、格式
2. **語意與邏輯指標**（LLM Assessment）：條款風險、異常描述識別
3. **風險與信心度評分**：S_conf ∈ [0, 100] 與風險等級

分流門檻：

| 信心度 | 處置 |
|--------|------|
| S ≥ 85 | 自動簽核通過，寫 Audit Log，觸發下一關卡 |
| 50 ≤ S < 85 | 派發人工審核，附上 AI 檢驗報告與建議 |
| S < 50 | 自動退回申請人並提示修正，或轉高階合規主管 |

### 4.2 Kimi：雙閾值 + 管線式

```
[表單提交]
    ↓
┌─────────────────┐
│ 1. 結構檢查關    │ 完整性、格式、必填 ──(失敗)──► 直接退件/補件
└────────┬────────┘
         ↓
┌─────────────────┐
│ 2. AI 初審 Agent │ 語意理解 + 規則引擎 + 風險評分
└────────┬────────┘
         │ 輸出: { decision, confidence, reasons[], extracted_data }
         ↓
   ≥ 0.9  ──► 自動通過
   0.5~0.9 ──► 人工複核（只複核有 warn 的檢查項）
   < 0.5   ──► 強制人工全審
```

**關鍵原則（K）：AI 與規則引擎分工**

> 硬規則（金額上限、黑名單、日期邏輯）用 deterministic 規則引擎，
> 語意判斷（文件真偽、內容合理性、異常偵測）交給 LLM。
> **不要用 LLM 做它可以幻覺的精確計算。**

**複核介面要「對症下藥」（K）**

> 人工不該重看整張單，而是只看到 AI 標出的低信心欄位 + 原始文件對照。
> 這能把人工處理時間從 10 分鐘降到 1 分鐘，自動化率才撐得起來。

### 4.3 DeepSeek：置信度 × 風險雙維路由

```python
if confidence > 0.9 and risk_score < 0.3:
    return ai_engine.execute(input_data)
elif 0.7 < confidence <= 0.9:
    return hybrid_executor.run(input_data)
else:
    return human_workflow.create_ticket(input_data, priority=risk_score * 10)
```

| 置信度 | 風險 | 路由 |
|--------|------|------|
| > 0.9 | < 0.3 | 全自動執行 |
| 0.7 ~ 0.9 | 中等 | 人機協同：Agent 給建議，人工確認後執行 |
| < 0.7 | 高 | 建人工工單，優先級 = 風險分數 × 10 |

**Agent 的「只讀初審」邊界（D）**

以 Hugging Face Transformers 的 AI 評審 Agent 為例：

> Agent 僅具備**只讀工具**（read_file、list_dir、grep、fetch_url），
> 沒有任何寫入能力，也不能執行 shell 命令。
> 定位是「攔截人類評審必然會抓出的問題」，而非替代人類決策。
> 這一邊界防止 LLM 編造「我跑過測試」這類虛假證據。

**人工介入的上下文保持（D）**

> 平台應將暫停記錄為 **first-class request**，通知指定人員，
> 人工回應後將答案折疊回 Agent 的上下文，Agent 可繼續執行甚至再次暫停。

### 4.4 Claude：Rubric-based + 審查執行分離

**明確的審查準則（Rubric-based prompting）**

> 審查邏輯不能是黑箱指令，要拆成可稽核的規則清單（類似 checklist），
> Agent 逐項判斷並輸出理由，而非只給 pass/fail。

**結構化輸出（Structured Decision Object）**

```json
{
  "decision": "approve | flag | reject",
  "confidence": 0.0-1.0,
  "reasons": ["觸發規則A", "缺少欄位B"],
  "evidence": "引用原文片段",
  "recommended_action": "..."
}
```

**審查與執行分離**

> 審查 Agent 只產出「建議決策」，實際狀態變更由獨立的 workflow engine 執行，
> 避免 Agent 越權直接改動業務資料。

### 4.5 Grok：硬閘先於模型，四路出口

**五步管道，AI 不能跳關：**

```
收件正規化 → 硬性政策閘 → AI 初審代理人 → 合流與熔斷 → 四路出口
```

**硬閘在模型之前。** 黑名單、禁止項、比價、會簽、關係人、招待上限先跑。
這些閘的駁回／補件／升級，**AI 不能改成通過**。

**代理人只輸出四種結果：**

| 出口 | 條件 |
|------|------|
| 自動通過 | 無硬閘、低額、高信心、低風險；人可抽查 |
| 自動駁回 | 禁止交易或高信心明確違規；**不可用急件覆寫** |
| 退回補件 | 缺報價、缺理由；補齊後**整條閘重跑，不跳關** |
| 升級人審 | 高額、關係人、低信心、模型故障 |

**合流層只降級、不放行：**

> 傾向通過但信心不足 → 人審；
> 傾向駁回但信心不足 → **也改人審**，避免誤殺。
> API 失敗時標記熔斷，**沒有「模型沉默就當通過」**。

## 5. 例外處理機制（彙整）

五個來源的例外清單合併去重：

| 例外情境 | 處置機制 | 來源 |
|----------|----------|------|
| **API 逾時 / 服務中斷** | 硬性降級：繞過 AI 關卡轉入標準人工初審佇列，標記「AI 服務暫停」。佇列重試（exponential backoff）+ 死信佇列（DLQ） | G, K, L |
| **幻覺 / 結構化輸出失敗** | 重試最多 2～N 次（Retry with Schema Enforcement）；仍失敗則封裝原始資料與錯誤 Log 轉人工，標記「AI 異常」。**絕不能讓爛 JSON 流進下游** | G, K, D |
| **邊界值與模糊情境** | 系統標記高風險欄位，強制加簽人工主管 | G |
| **提示詞注入** | 輸入層護欄：LLM 處理前通過 Prompt Injection 檢測；**附件內容視為「資料」而非「指令」**；關鍵指令用結構化欄位傳遞，不信任文件內嵌文字 | G, K, L |
| **AI 與規則引擎結論衝突** | **一律以規則引擎為準**，記錄衝突事件供分析（這是發現 AI 漂移的重要訊號） | K, L |
| **Agent 信心過低** | 強制轉人工，並記錄「**為什麼判斷不了**」 | L |
| **低信心但量太大，人工處理不完** | 動態調整閾值（auto-escalation），或抽樣複核（audit sampling） | K |
| **人工覆寫 AI 決策** | 記錄覆寫原因（**必填**），定期回放分析 false positive / negative，迭代 prompt 與閾值 | K, D, L |
| **使用者對 AI 決策不服** | 提供申訴通道，申訴**一律強制轉人工**，附上原始 AI 判斷全文 | L |
| **連續多次同類駁回** | 觸發規則異常告警 — **可能是規則本身有問題而非使用者問題** | L |
| **Agent 超時 / API 失敗** | Circuit breaker：預設走人工審查，**不可讓流程卡死或靜默放行** | L, X |
| **責任與合規** | 法規要求人工簽署的環節（金融 KYC、醫療），AI 只能做「預審」，不可產生最終法律效力，**UI 上要明確標示「本單由 AI 預審」** | K, D |
| **業務錯誤（資料不匹配、欄位缺失）** | 建立例外工單，推送完整上下文給審閱者，**不猜測、不強行繼續** | D |

### 5.1 反饋閉環（DeepSeek）

- **短期反饋環**：人工決策中可規則化的邏輯**即時注入規則引擎**
- **長期反饋環**：人工標註資料清洗後進入訓練隊列，驅動模型週級迭代

### 5.2 分級審閱與爆炸半徑（DeepSeek）

> 多智能體先做初審，人類只挑選**影響範圍大**的項目深度審查。
> 審閱結論分級 CRITICAL / HIGH / MEDIUM / LOW，
> 對應 APPROVE / WARNING / BLOCK，並設 **Pre-Report Gate** 四問門檻過濾誤報。

## 6. 共識與分歧

### 6.1 高度共識（五個來源都提到）

1. **結構化輸出，不要只回 yes/no** — decision + confidence + reasons + evidence
2. **信心度分流，不是單一門檻** — 至少雙閾值，高自動、中人審、低退回
3. **硬規則歸規則引擎，語意判斷歸 LLM** — 不用 LLM 做精確計算
4. **AI 不可有最終決策權** — 審查與執行分離，AI 只產出建議
5. **降級要「往人工走」不是「往放行走」** — 模型沉默 ≠ 通過
6. **全程留痕** — AI 判斷、人工覆寫、覆寫原因都要記錄
7. **人工覆寫回流成訓練資料** — 形成反饋迴路

### 6.2 分歧點

| 議題 | 立場 A | 立場 B | 判斷 |
|------|--------|--------|------|
| **門檻數值** | Gemini：85 / 50（百分制）| Kimi：0.9 / 0.5；DeepSeek：0.9 / 0.7 | 數值應可設定，不寫死。不同流程的風險容忍度不同 |
| **是否加入風險維度** | Gemini、Kimi：只用信心度 | DeepSeek：信心度 × 風險分數雙維 | 雙維較完整。高信心但高風險（如大額）仍應人審 |
| **低信心的處置** | Gemini：可自動退回申請人 | Grok：低信心一律人審，**不自動駁回** | 傾向 Grok。低信心代表「AI 不確定」，不確定就不該由 AI 做終局決定 |
| **硬閘與 AI 的順序** | Gemini、Kimi：AI 內含規則檢核 | Grok：硬閘**在模型之前**獨立執行 | 傾向 Grok。硬閘結果 AI 不能推翻，順序上分離比較清楚 |
| **Agent 的工具權限** | Gemini：Agent 可呼叫 API 自動處置 | DeepSeek：初審 Agent **只讀**，無寫入權 | 初審階段應只讀。執行階段的寫入由獨立節點負責 |

### 9.3 ChatGPT：Form Engine 三層 Schema

```
Form Definition
├── UI Schema        怎麼顯示？
├── Data Schema      資料是什麼？
└── Workflow Schema  什麼情況可以看 / 改 / 送出？
```

**關鍵洞察：**

> Form 是資料與 UI 定義；Workflow 決定執行時的行為。

因此同一張 Form 可以被不同 Workflow 使用，且各自有不同規則：

```
普通採購：amount → editable
緊急採購：amount → readonly
```

**四大屬性分類：**

| 類別 | 內容 |
|------|------|
| Data | Binding / Data Type / Default / Data Source / Transformation |
| UI | Label / Component / Width / Placeholder / Format |
| Behavior | Visible / Readonly / Required / Validation |
| Workflow | Permission / Approval / AI / Action / Condition |

**Property Editor 本身也可以 Schema-driven：**

```json
{
  "property_group": "workflow",
  "properties": [
    { "name": "binding", "component": "expression" },
    { "name": "visible_when", "component": "condition_builder" },
    { "name": "readonly_when", "component": "condition_builder" },
    { "name": "required_when", "component": "condition_builder" },
    { "name": "roles", "component": "role_selector" }
  ]
}
```

只需增加 Property Definition。
