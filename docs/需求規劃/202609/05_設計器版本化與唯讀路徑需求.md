## 1. 使用者的需求原文

> 我想要的程式路徑是！表單設計器、程式設計器等等！
> List 只要顯示每個表單或流程當前使用的版本！
> 點選某個表單或流程後跟目前一樣顯示編輯畫面，但是為唯讀！
> 上半部增加一個開發的按鈕！點選開發按鈕後顯示一個清單！
> 顯示當前表單或流程的所有版本！點選後才能編輯表單與流程！
> 編輯後的儲存按鈕分兩個！一個是儲存！一個是另存新版。
> 但是完全新增一個表單或流程的版本就是直接打開編輯！
> 編輯頁面也要包含現在委托另外一台開發的模擬功能！

### 1.1 後續修正（同日）

> 不用每次儲存都進版本！要發布上線才進版本！
> 如果當前最新版本是 4，開啟版本 3 修改！儲存後還是版本 3，
> 但是如果發布上線就是版本 5。

> 可以限制一個表單只能有一個編輯中的草稿！

**這修正了原文的「另存新版」。** 版本只在發布時遞增，
所以兩個按鈕變成「儲存」（寫草稿）與「發布上線」（產生新版本），
不需要獨立的「另存新版」。詳見 §3.4。

## 2. 為什麼要改

### 2.1 現況的問題

目前點進設計器就是可編輯狀態。這有兩個問題：

**看與改沒有分界。** 使用者想確認「這張表單現在長什麼樣」時，
一進去就處於隨時可能誤改的狀態。手滑動到某個欄位，
按了存檔就改變了定義。

**版本不可見。** 資料結構是 append-only、所有歷史版本都在，
但畫面上看不到——使用者不知道有版本這件事，
也無從得知「上個月的版本是什麼樣」。

### 2.2 改動後的路徑

```
清單（只顯示當前版本）
   │
   ▼  點選
唯讀檢視（與編輯畫面相同，但不能改）
   │
   ▼  按「開發」
版本清單（該表單／流程的所有版本）
   │
   ▼  選一個版本
編輯模式（可改、可模擬、可存檔）
```

新增表單／流程時**跳過唯讀與版本清單，直接進編輯**——
新的東西沒有歷史可看。

### 2.3 這個設計的意義

**預設安全。** 誤改的成本高於多按一次的成本。
「要編輯就明確表示」比「隨時都能改」適合把 Owner 交給使用者的產品。

「開發」這個詞是使用者選的，與 [D-07](02_決議紀錄.md) 的
「編輯開發模式」一致——兩者指的是同一件事的兩個面向：
D-07 講的是資料隔離（沙箱），本文講的是進入路徑。

## 3. 各段的需求

### 3.1 清單：只顯示當前版本

**現況**：清單已顯示 `published_version` 與 `has_draft`
（`FormList.vue`、`WorkflowList.vue`，2026-09-18 完成）。

**要調整的**：

| 項目 | 現況 | 需求 |
|------|------|------|
| 顯示內容 | `v3`、`v2 · 有草稿`、`尚未發布` | 保持，語意已符合 |
| 點選行為 | 進入**可編輯**的設計器 | 進入**唯讀檢視** |

只有點選行為要改。

### 3.2 唯讀檢視

**與編輯畫面相同的版面**，但：

| 元素 | 唯讀時的行為 |
|------|-------------|
| 畫布 | 可以點選欄位／節點查看屬性 |
| 屬性面板 | 顯示所有設定，全部不可修改 |
| 元件庫／節點庫 | 隱藏或停用（不能加東西）|
| 儲存／發布按鈕 | 隱藏 |
| 驗證按鈕 | **保留**——檢視時確認合法性沒有壞處 |
| 權限預覽 | **保留**——那是唯讀操作 |
| **開發按鈕** | 新增。唯一的編輯入口 |

**要明確標示處於唯讀。** 使用者要看得出為什麼改不動，
而不是以為系統壞了。

技術上：`FormDesigner.vue` 與 `WorkflowDesigner.vue` 要支援
`readonly` 模式。這是既有元件的擴充，不是新頁面——
兩份版面必然漂移。

### 3.3 版本清單

按「開發」後顯示。

**要顯示的**：

| 欄位 | 說明 |
|------|------|
| 版本號 | v1、v2、v3… |
| 狀態 | 草稿／已發布／已封存 |
| 建立者、建立時間 | 誰在什麼時候改的 |
| 發布者、發布時間 | 已發布的版本才有 |
| 摘要 | 與前一版的差異（見 §5.2，可延後）|

**操作**：

- 點選版本 → 進入編輯模式
- 當前發布版本要有明顯標示

**後端已完備**：

```
GET /forms/{form_key}/versions
GET /forms/{form_key}/versions/{version}
GET /workflows/{key}/versions
GET /workflows/{key}/versions/{version}
```

**前端缺一半**：`web/src/api/forms.ts` 有 `listVersions` 與
`getVersion`，但 `web/src/api/workflows.ts` **沒有**——要補上。

### 3.4 儲存與發布的版本語意（2026-09-18 定案）

**版本號只在發布時遞增。儲存不進版本。**

| 按鈕 | 行為 |
|------|------|
| **儲存** | 寫入草稿。不產生版本號 |
| **發布上線** | 草稿轉為正式版本，版本號 = 目前最大版本 + 1 |

使用者的原話：

> 不用每次儲存都進版本！要發布上線才進版本！
> 如果當前最新版本是 4，開啟版本 3 修改！儲存後還是版本 3，
> 但是如果發布上線就是版本 5。

#### 實際行為

```
當前狀態：v1 v2 v3 v4（v4 為線上版本）

開啟 v3 → 修改 → 按「儲存」
   → 內容存進草稿，草稿記錄 based_on = 3
   → v3 本身不動，線上仍是 v4

繼續修改 → 再按「儲存」
   → 覆寫同一份草稿，仍不產生版本號

按「發布上線」
   → 草稿成為 v5（不是 v3 也不是 v4+1 的特例，就是 max+1）
   → 線上版本變成 v5
```

**為什麼「儲存後還是版本 3」不能真的覆寫 v3**

`migrations/0002_form_definition.sql:83` 有一個 trigger：

```sql
-- 已發布版本不得修改內容。這是資料層的最後防線，
-- 應用層也會擋，但雙重保險可防止遷移腳本或手動操作出錯。
create trigger form_version_immutable ...
```

已依據 v3 送出的單據，其表單定義若在事後被改，
那些單據的欄位、必填規則、權限都會跟著變——
使用者會看到「當初送的單」與「現在顯示的單」不一樣。

**定案（使用者確認）**：改的內容**存進草稿並標明來源版本**，
v3 保持不動。畫面上顯示「草稿（基於 v3）」讓使用者知道自己在改什麼。

#### 需要的資料結構

草稿要能記錄它從哪一版來：

```sql
alter table form_definition_version
  add column based_on_version integer;

comment on column form_definition_version.based_on_version is
  '草稿的來源版本。NULL 表示從當前線上版本開始編輯；
   有值表示使用者選了某個舊版本作為起點';
```

流程表比照。

這與需求 03 §4.2 規劃的 `restored_from_version` 是相關但不同的欄位——
那個記的是「這一版是由哪一版還原而來」（已發布的事實），
`based_on_version` 記的是「草稿以哪一版為起點」（編輯中的狀態）。
實作時要確認兩者不會混淆，或評估能否合併。

#### 一個表單只能有一份編輯中的草稿（2026-09-18 定案）

**維持現有約束，不放寬**（使用者確認）：

```sql
-- migrations/0002_form_definition.sql:62
create unique index form_version_single_draft
    on form_definition_version (form_id)
    where status = 'DRAFT';
```

這個限制是刻意的。允許多份草稿的話會產生「哪一份才是接下來要
發布的」這種問題，而使用者要自己記得——那正是治理要避免的狀況。

代價是：已經有草稿（例如基於 v4）時，使用者又開 v3 來改會撞到約束。

**處理方式（使用者確認）**：**提示使用者，要他選擇**。

```
⚠️ 已有一份未發布的草稿（基於 v4，最後修改於 09/18 14:30）

  開啟 v3 編輯會放棄那份草稿。

  [ 放棄草稿，改用 v3 ]  [ 回到現有草稿 ]  [ 取消 ]
```

不預設覆蓋——先前的修改可能是別人做的，或是自己忘了還沒發布的。
靜默消失比多按一次糟糕得多。

#### 「草稿基於舊版，期間有人發布新版」不會發生

先前曾把它列為待決的邊界，那是誤判。

單一草稿 + 編輯鎖定（§3.5）之後：

```
草稿存在 → 只有持鎖者能改 → 要發布也是他發布
         → 期間沒有第二個人能發布新版本
```

發布的前提是有草稿，而草稿只有一份且被鎖著。
所以不存在「草稿基於 v3，期間跑出一個 v5」的情況。

**這是單一草稿約束帶來的好處**——它同時消除了分支合併的問題。

### 3.5 編輯鎖定（2026-09-18 定案）

**使用者的決定**：

> 編輯時請直接將表單鎖定！只能一人編輯！

#### 為什麼需要

沒有鎖的話兩個人可以同時開同一份草稿編輯，後存的會覆蓋前一份，
而前一個人不會知道自己的修改消失了。

草稿只有一份，這個競態一定會發生。

#### 鎖的行為

| 情境 | 行為 |
|------|------|
| 進入編輯模式 | 取得鎖。已被別人鎖住則不能進入 |
| 編輯中 | **每分鐘自動續鎖** |
| 按「離開」或「發布」 | 釋放鎖 |
| **關掉瀏覽器** | 停止續鎖，**5 分鐘後自動失效** |
| 管理員介入 | **admin 可強制解鎖**，記稽核 |

被鎖住時的畫面：

```
🔒 這份表單正在被編輯

   編輯者：陳雅婷
   開始時間：09/18 14:30
   最後活動：09/18 14:52（2 分鐘前）

   [ 檢視唯讀版本 ]        ← 一般使用者
   [ 強制解鎖 ]            ← 僅 admin
```

#### 為什麼用「續鎖 + 逾時」而非固定期限

使用者關掉瀏覽器不會通知伺服器，鎖必須能自己失效。

| 做法 | 問題 |
|------|------|
| 只能手動解鎖 | 忘了解鎖或電腦壞掉就要管理員介入 |
| 固定期限（例如 30 分鐘）| 認真編輯超過期限會被別人拿走 |
| **續鎖 + 逾時**（採用）| 編輯中一直有效，離開後最多 5 分鐘自動釋放 |

續鎖間隔 1 分鐘、逾時 5 分鐘是初步值。太短會讓網路短暫斷線就掉鎖，
太長會讓誤關瀏覽器的人等太久。

#### 資料結構

```sql
alter table form_definition
  add column locked_by uuid references app_user(id),
  add column locked_at timestamptz,
  add column lock_heartbeat_at timestamptz;

comment on column form_definition.lock_heartbeat_at is
  '最後一次續鎖的時間。超過 5 分鐘未續鎖視為編輯者已離開，
   鎖自動失效——使用者關掉瀏覽器不會通知伺服器';
```

鎖放在 `form_definition` 而非版本表：鎖的是「這個表單的編輯權」，
不是某一份草稿。流程表比照。

#### 需要的 API

```
POST   /forms/{key}/lock        取得鎖
POST   /forms/{key}/lock/renew  續鎖（前端每分鐘打一次）
DELETE /forms/{key}/lock        釋放鎖
DELETE /forms/{key}/lock/force  強制解鎖（僅 admin，記稽核）
```

#### 實作要注意

**判定鎖是否有效要看 `lock_heartbeat_at`，不是 `locked_at`。**
用 `locked_at` 的話，編輯兩小時的人會被判定成逾時。

**強制解鎖一定要記稽核。** 那是拿走別人的編輯權，
事後要查得到是誰在什麼時候做的。

**取鎖要在交易內做並檢查現有鎖**，否則兩個人同時按「開發」
會都拿到鎖。

### 3.6 新增時直接進編輯

**現況已符合**：`FormList.vue` 與 `WorkflowList.vue` 建立成功後
直接 `router.push` 到設計器。

只要確認新增後進的是**編輯模式**而非唯讀模式即可。
實作時若用網址參數區分模式（例如 `?mode=edit`），
新增後要帶上那個參數。

### 3.7 編輯頁面整合模擬功能

**這部分等另一台機器完成 S2 模擬簽核後再整合。**

依 [總體實踐規劃](../../實踐規劃/規劃/202609/00_總體實踐規劃.md)，
模擬簽核依賴 P3 → S0 → S1 → S2，估計還有約 3 週。

整合時要決定的：

| 項目 | 說明 |
|------|------|
| 入口位置 | 編輯畫面的哪裡放「模擬」按鈕 |
| 模擬的對象 | 當前編輯中的草稿，還是要先存檔 |
| 未存檔的改動 | 模擬前強制存檔，或允許模擬記憶體中的版本 |
| 回到編輯 | 模擬完成後如何回來繼續改 |

**建議：模擬前強制存檔。** 模擬會建立沙箱租戶並跑真實流程，
拿一份記憶體中的草稿去跑，出問題時無從追溯用的是哪個版本。

## 4. 對現有程式的影響

### 4.1 要改的檔案

| 檔案 | 改動 |
|------|------|
| `web/src/router.ts` | 設計器路由要能區分唯讀／編輯／版本清單 |
| `web/src/pages/FormDesigner.vue` | 支援 `readonly` 模式 |
| `web/src/pages/WorkflowDesigner.vue` | 同上 |
| `web/src/pages/FormList.vue` | 點選改為進唯讀 |
| `web/src/pages/WorkflowList.vue` | 同上 |
| `web/src/api/workflows.ts` | **補 `listVersions` 與 `getVersion`** |
| 新增版本清單畫面 | 表單與流程共用一個元件 |
| **新增鎖定 API** | `server/crates/http-public/src/forms.rs` 與 `workflows.rs` |
| **新增續鎖機制** | 前端每分鐘打一次，離開時釋放 |

### 4.2 路由設計（初步）

```
/designer/forms                          清單
/designer/forms/:formKey                 唯讀檢視
/designer/forms/:formKey/versions        版本清單
/designer/forms/:formKey/edit            編輯當前草稿
/designer/forms/:formKey/edit/:version   編輯指定版本
```

流程比照。

**注意**：`/designer/forms/:formKey` 目前直接是編輯畫面，
改成唯讀是**破壞性變更**——`auth-navigation.spec.ts` 與
截圖腳本都會失敗。那是預期的，測試釘住的是舊行為。

### 4.3 不影響的部分

- 版本端點不用改（已存在）
- **草稿唯一性約束不用改**（維持一個表單一份草稿）
- 已發布版本不可修改的 trigger 不用改
- 權限判定不用改

**要加的欄位**：`based_on_version`（§3.4）與鎖定三欄（§3.5）。

**建議不要在本需求實作**，等治理流程那邊做好再複用。
先顯示版本號、狀態、建立者、時間就夠。

## 6. 與既有規劃的關係

```
本需求（設計器路徑）
   │
   ├── 依賴：無（後端 API 已完備）
   │
   ├── 交會：D-07 的「編輯開發模式」
   │         兩者都叫「開發」，指同一件事的不同面向：
   │         D-07 = 資料隔離（沙箱租戶）
   │         本文 = 進入路徑（唯讀 → 版本 → 編輯）
   │
   └── 等待：S2 模擬簽核（§3.7，約 3 週後整合）
```

**不衝突，但要協調命名。** 實作時「開發模式」這個詞
在兩處出現，要確認指的是同一個狀態——
使用者按「開發」進入的編輯模式，是否就自動在沙箱裡？

**傾向：是。** 那樣「開發」這個詞才只有一個意思，
使用者也不需要理解兩層概念。但這會讓本需求依賴 S1 沙箱基礎，
不能獨立完成。

需要決定的是：

| 選項 | 說明 |
|------|------|
| **獨立實作** | 先做唯讀／版本／編輯路徑，編輯仍直接改正式租戶。等 S1 完成再接沙箱 |
| **等 S1** | 一次做完，「開發」從一開始就是沙箱 |

**傾向獨立實作。** 唯讀路徑本身就有價值（防誤改、版本可見），
不該被 3 週後的東西擋住。接沙箱是之後的增量改動。

## 7. 建議的實作順序

假設選擇獨立實作（§6）：

| 階段 | 內容 | 估計 |
|------|------|------|
| 1 | `based_on_version` 欄位（migration + 寫入點）| 0.5 天 |
| 2 | **編輯鎖定**（migration + 四個 API + 前端續鎖）| 1.5 天 |
| 3 | 補 `workflows.ts` 的版本 API | 0.5 天 |
| 4 | 設計器支援 `readonly` 模式 | 1.5 天 |
| 5 | 路由調整 + 清單點選改為唯讀 | 0.5 天 |
| 6 | 版本清單畫面（表單與流程共用）| 1 天 |
| 7 | 草稿衝突提示 | 0.5 天 |
| 8 | 更新測試與截圖腳本 | 0.5 天 |
| **合計** | | **約 6.5 天** |

階段 8 不可省略：路由改動會讓 `auth-navigation.spec.ts` 與
四支截圖腳本失敗，手冊的 76 張截圖也要重產。

階段 2 的鎖定要特別測：同時取鎖、逾時釋放、強制解鎖的稽核。
這類競態問題單元測試抓不到，要寫整合測試模擬兩個使用者。

## 8. 要避免的方向

| 不要做 | 理由 |
|--------|------|
| 另開一個唯讀專用頁面 | 兩份版面必然漂移。擴充既有設計器 |
| 唯讀時隱藏驗證與權限預覽 | 那些是唯讀操作，檢視時很有用 |
| **每次儲存就產生新版本** | 版本只在發布時遞增。儲存進草稿 |
| **編輯舊版本時覆寫該版** | 資料庫 trigger 會擋。已依據它送出的單據會被改變定義 |
| **放寬草稿唯一性約束** | 會產生「哪一份才要發布」的問題，正是治理要避免的 |
| 草稿衝突時靜默覆蓋 | 先前的修改可能是別人做的。要提示讓使用者選 |
| **用 `locked_at` 判定逾時** | 要看 `lock_heartbeat_at`，否則編輯兩小時的人會被判逾時 |
| **鎖只能手動釋放** | 關掉瀏覽器不會通知伺服器，表單會永遠鎖著 |
| **強制解鎖不記稽核** | 那是拿走別人的編輯權，事後要查得到 |
| 等 S2 模擬完成才做 | 唯讀路徑本身有價值，不該被擋 3 週 |
| 唯讀時不標示狀態 | 使用者會以為系統壞了 |
