## 0. 已定案決策

| 編號 | 決策 | 內容 |
|---|---|---|
| **D-11** | 權威來源 | **混合**：`employee` / `department` / 主管鏈由客戶 ERP 同步進來且平台唯讀；簽核專屬資料（簽核角色、代理人、金額門檻、通知管道）由平台自己維護。兩者用 canonical id 綁定 |
| **D-12** | 接入方式 | MVP **四種全做**：REST API（Odoo 等）、Excel / CSV 匯入 + AI 欄位對應、資料庫直連唯讀、平台手動維護 |
| **D-13** | 組織層級 | **公司 + 部門樹**。單一法人、部門可多層。多公司 / 廠區 / 成本中心留到後續 |
| **D-14** | 主管鏈 | **ERP 優先、平台補缺**。ERP 沒維護或斷鏈的部分在平台後台補上並標記為「平台維護」，下次同步不覆蓋 |

D-11 與 D-14 共同推導出本文最核心的機制：**欄位級 ownership**（§3）。沒有它，「平台補缺」會在下一次同步被沖掉。

## 1. 現況盤點：已經有什麼，缺什麼

`0001_tenant_identity.sql` 已經建好了組織資料的骨架，**本案是擴充，不是重建**。

| 既有物件 | 現況 | 本案是否異動 |
|---|---|---|
| `tenant` | code / name / timezone / currency / locale / status | 不動。**依 D-13，tenant 即「公司」**，不另建 company 表 |
| `department` | tenant_id / code / name / parent_id / manager_user_id，自參照樹 | **擴充**：外部來源鍵、ownership、狀態、排序 |
| `app_user` | tenant_id / email / name / password_hash / department_id / manager_id / status | **擴充**：員工編號、職稱、到離職日、外部來源鍵、ownership、同步狀態 |
| `role` / `user_role` | MVP 固定五種角色，不開放自訂 | 不動。屬平台自有資料，不同步 |
| RLS | 每張帶 `tenant_id` 的表 `FORCE ROW LEVEL SECURITY`，fail-closed | **同步寫入必須走 `TenantTx`**，不可用 superuser 繞過 |
| `participant.rs` | `manager_of` 查 `app_user.manager_id`；`department_manager_of` 查 `department.manager_user_id` | **不動**。同步只要把資料填對，Resolver 零改動就能用 |
| DSL `resolver` | `user` / `role` / `department_manager` / `manager_of` / `initiator` / `external_contacts` / `expression` / `composite` | 不動 |

完全缺席的：

- 員工編號、職稱、到職 / 離職日、分機
- **代理人（簽核授權）** —— ERP 不會有，平台必須自建
- 外部系統對應鍵（`source_system` + `external_id`）
- 整組同步機制（connection / source / mapping / sync run / 資料品質）

> **關鍵認知**：`participant.rs` 的 `manager_of` 已經是可用的，它缺的不是程式碼，是**資料**。本案的價值就是把客戶 ERP 的組織資料可靠地灌進 `app_user.manager_id` 與 `department.manager_user_id`。

## 2. 核心設計一：人員與登入帳號的關係

**問題**：`app_user.password_hash` 是 `not null`。從客戶 ERP 同步進來的人，多數不會登入平台（產線作業員、不用電腦的主管），但他們**必須存在**，因為：

- 他們可能是別人的 `manager_id`
- 他們可能是 `department.manager_user_id`
- 他們可能需要被指派 Human Task（用紙本或代簽）

| 方案 | 內容 | 評估 |
|---|---|---|
| **A. 擴充 `app_user`（推薦）** | `password_hash` 改 nullable，新增 `can_login boolean`。`app_user` 即 EIG 的 canonical `employee` | Approver Resolver、`user_role`、Human Task、通知、RLS **全部零改動**。SME 場景下「組織人員」與「系統使用者」高度重疊，差別只在能不能登入 |
| B. 新增 `employee` 表，`app_user` 參照它 | 語意最乾淨，符合 EIG canonical dataset 命名 | `participant.rs` 四個查詢全要改寫、Human Task 的 assignee 指向誰要重新定義、DSL resolver 回傳 user_id 的語意要改。**MVP 階段成本遠大於收益** |

**採 A。** 對外（EIG canonical schema、WDC Connection、未來 MCP tool）一律用 `employee` 這個名字，資料庫實體是 `app_user`，中間用一個 view 對齊：

```sql
create view employee as
select id as employee_id, employee_no, name, email, department_id,
       manager_id, job_title, status
from app_user;
```

安全性：`password_hash` 轉 nullable 後，登入流程必須顯式檢查 `can_login = true and password_hash is not null`，不可依賴「有 hash 就能登入」的隱含假設。這條要有測試。

## 3. 核心設計二：欄位級 ownership（D-11 + D-14 的實作機制）

「ERP 優先、平台補缺」要能成立，同步時必須知道**哪些欄位不准碰**。

```sql
alter table app_user   add column platform_managed_fields text[] not null default '{}';
alter table department add column platform_managed_fields text[] not null default '{}';
```

規則：

1. 同步寫入時，`platform_managed_fields` 裡列出的欄位**一律跳過**
2. 管理員在後台編輯某欄位 → 該欄位名自動加入 `platform_managed_fields`
3. UI 在該欄位旁顯示「平台維護，不隨同步更新」，並提供**一鍵「改回跟隨 ERP」**（從陣列移除，下次同步即覆蓋）
4. 同步報表要列出「因平台維護而跳過的欄位數」，讓管理員知道兩邊差異有多大

典型情境：ERP 的 `manager_id` 有 300 人沒維護。管理員在平台補上 → 這 300 筆的 `manager_id` 進入 `platform_managed_fields`。日後 ERP 補齊了，管理員可批次「改回跟隨 ERP」。

> 這是本案唯一一個「非做不可、且沒有別的做法」的機制。沒有它，D-14 是空話。

## 4. 組織基本資料：完整欄位規劃

### 4.1 `department` 擴充

| 欄位 | 型別 | 來源 | 說明 |
|---|---|---|---|
| `external_id` | text | 同步 | 來源系統主鍵，**匹配用的第一順位** |
| `source_system` | text | 同步 | `ODOO` / `SQL` / `FILE` / `MANUAL` |
| `status` | text | 同步 | `ACTIVE` / `INACTIVE`。**不硬刪，見 §7** |
| `sort_order` | int | 平台 | 後台顯示排序 |
| `platform_managed_fields` | text[] | 平台 | §3 |
| `last_synced_at` | timestamptz | 同步 | — |

`unique (tenant_id, source_system, external_id)`，`code` 維持既有的 `unique (tenant_id, code)`。

### 4.2 `app_user` 擴充

| 欄位 | 型別 | 來源 | 說明 |
|---|---|---|---|
| `employee_no` | text | 同步 | 員工編號。**匹配用的第二順位**，`unique (tenant_id, employee_no)` |
| `job_title` | text | 同步 | 職稱 |
| `hired_at` / `left_at` | date | 同步 | 到職 / 離職日。`left_at` 決定簽核可用性 |
| `phone` / `extension` | text | 同步 | 通知管道備援 |
| `external_id` / `source_system` | text | 同步 | 同上 |
| `can_login` | boolean | 平台 | §2 |
| `password_hash` | text **nullable** | 平台 | §2 |
| `platform_managed_fields` | text[] | 平台 | §3 |
| `sync_status` | text | 同步 | `SYNCED` / `PLATFORM_ONLY` / `MISSING_IN_SOURCE` |
| `last_synced_at` | timestamptz | 同步 | — |

### 4.3 新增：代理人 `approval_delegation`（平台自有，不同步）

ERP 沒有這個概念，但 SME 簽核剛需（請假、出差時的代簽）。

```sql
create table approval_delegation (
    id            uuid primary key default uuid_generate_v4(),
    tenant_id     uuid not null references tenant(id) on delete cascade,
    delegator_id  uuid not null references app_user(id) on delete cascade,
    delegate_id   uuid not null references app_user(id) on delete cascade,
    scope         text not null default 'ALL',   -- ALL 或指定 business_object
    starts_at     timestamptz not null,
    ends_at       timestamptz not null,
    reason        text,
    created_by    uuid references app_user(id),
    created_at    timestamptz not null default now(),
    check (delegator_id <> delegate_id),
    check (ends_at > starts_at)
);
```

Approver Resolver 的銜接：解析出參與者後，**再過一層代理人展開**。`delegator` 與 `delegate` 誰收到任務、是取代還是併存，見 Q-05。

## 5. 客戶公司系統資料同步：統一模型

四種接入方式（D-12）**共用同一條管線**，差別只在最前面的 Extractor。這是 EIG §3 與 §21 的主張，本案採用。

```
Connection ──→ Source ──→ Extract ──→ Parse ──→ Map ──→ Validate ──→ Upsert
（怎麼連）    （抓什麼）   （原始列）  （結構化） （canonical）（品質閘）  （寫入）
                              │                                │
                              ↓                                ↓
                      integration_raw_record          integration_sync_run
                        （Raw Layer 留存）              （完整計數）
```

### 5.1 四種 Connection Type 的差異

| Type | Extractor | 憑證 | 增量策略 | 備註 |
|---|---|---|---|---|
| `REST` | HTTP client，分頁走 cursor / offset | OAuth2 / API Key / Basic，**存 credential_ref 不存明文**（WDC §8） | `WHERE write_date > :last_sync_time`（Odoo 慣例） | 平台目前**尚無 Odoo adapter**，需新建 |
| `SQL` | 唯讀連線執行**預先定義好的具名查詢** | DB 帳密存 vault | `WHERE modified_at > :last_sync_time` | **絕不接受使用者輸入的任意 SQL**（WDC §4）。查詢由 Connection Owner 建立、參數化綁定 |
| `FILE` | 上傳 Excel / CSV，或 SFTP 取檔 | 無 / SFTP key | 每次全量，靠 §7 的完整性閘保護 | 搭配 §8 AI 欄位對應 |
| `MANUAL` | 無。後台直接維護 | 無 | 不適用 | 所有欄位視同 `platform_managed_fields` |

### 5.2 匹配鍵（決定同步認不認得同一個人）

依序嘗試，**先命中先用**：

1. `(source_system, external_id)` —— 最穩定，來源系統主鍵
2. `employee_no` —— 次穩定，人事編號通常不變
3. `email` —— **僅限首次匯入時的輔助比對**，不可當長期主鍵（email 會改）

匹配不到 → 視為新進人員，建立。匹配到多筆 → 標為 `AMBIGUOUS` 丟進待處理清單，**不猜**。

### 5.3 寫入順序（實作陷阱）

`department.parent_id`、`department.manager_user_id`、`app_user.manager_id` 三個都是自參照 / 循環參照，一次 upsert 會踩到還不存在的 id。必須兩階段：

```
Phase 1  upsert department（不含 manager_user_id）
Phase 2  upsert app_user（含 department_id，不含 manager_id）
Phase 3  回填 department.manager_user_id
Phase 4  回填 app_user.manager_id
Phase 5  跑組織健康檢查（§9）
```

## 6. 同步觸發方式

EIG §10 列了四種，本案的取捨：

| 觸發 | 是否做 | 說明 |
|---|---|---|
| **Schedule** | ✅ MVP | 組織資料變動頻率低，**預設每日 02:00 全量**。不做 15 分鐘高頻——跑全量成本高、收益低 |
| **Manual（Sync Now）** | ✅ MVP | 新人到職當天要能簽核，管理員按一下即可。**MVP 最重要的一個按鈕** |
| **Webhook** | ⬜ 後續 | 客戶 ERP 要能推，SME 多半做不到 |
| **On-demand（cache miss 觸發）** | ❌ 不做 | 組織資料是 master data，不是 cache。流程執行中臨時觸發同步會讓簽核延遲不可預測 |

同步作業本身**跑在 Temporal**，不是 cron script：需要重試、逾時、可取消、可查詢進度，這正是既有架構已經有的能力。

## 7. 刪除策略與完整性閘（最危險的部分）

EIG §16 點出的問題在本案是**最高風險**：來源 1000 人，API 只回 823 人，若直接刪 177 人，其中只要有一個是主管，**全公司相關流程立刻卡死**。

規則，由嚴到寬：

1. **永不硬刪。** 來源消失的人 → `sync_status = 'MISSING_IN_SOURCE'`，`status` 維持不變
2. **完整性閘**：本次讀取筆數 < 上次成功同步筆數 × `completeness_threshold`（預設 0.9）→ **整批中止**，不寫入任何 destructive 變更，標記 `sync_run.status = 'ABORTED_INCOMPLETE'` 並告警
3. **停用需人工確認**：`MISSING_IN_SOURCE` 連續 N 次（預設 3 次）仍消失 → 進入「待停用清單」，由管理員確認後才改 `status = 'INACTIVE'`
4. **停用前置檢查**：該員工若是他人的 `manager_id`、或任何 `department.manager_user_id`、或有未完成 Human Task → **擋下停用**，先要求轉派
5. 離職（`left_at` 有值且已過）與「來源消失」是**兩件事**，分開處理。前者是 ERP 明示，可直接停用；後者是資料缺漏，不可推論

## 8. AI 欄位對應（WDC §35 / EIG §9）

給 `FILE` 與 `SQL` 兩種 Connection 用，這是 D-12 選 Excel 匯入後降低導入門檻的關鍵。

```
上傳 Excel
   ↓
讀表頭 + 前 20 列樣本
   ↓
AI 推測 → { "PERNR": "employee_no", "ENAME": "name", "ORGEH": "department_code", "MAIL": "email" }
   ↓
UI 顯示「AI 建議，請確認」，逐欄可改
   ↓
管理員按 Accept
   ↓
存成 integration_source.mapping_definition（此後固定，不再每次問 AI）
```

**安全邊界（不可協商）**：

- AI 只產生 **mapping 建議**，不直接寫任何一筆資料
- 送給 AI 的樣本列必須**遮蔽 PII**（姓名、email、身分證、電話），只留欄位名與型態特徵
- mapping 一經確認即固化，後續同步不再呼叫 AI —— 避免 AI 每次給出不同結果造成資料漂移

## 9. 組織健康檢查（本案對簽核最大的價值）

EIG §15 的 Data Quality 落到本專案的具體用途。每次同步結束後執行，產出「簽核可用性報表」：

| 檢查項 | 後果 | 嚴重度 |
|---|---|---|
| 員工無 `manager_id` | `manager_of` 解析回空 → 流程卡住 | **HIGH** |
| 部門無 `manager_user_id` | `department_manager_of` 解析回空 → 流程卡住 | **HIGH** |
| `manager_id` 指向已停用 / 已離職者 | 任務指派給收不到信的人 | **HIGH** |
| 主管鏈成環（A→B→A） | 若日後做 N 階簽核會無限迴圈 | **HIGH** |
| 員工無 `department_id` | 依部門解析的 resolver 失效 | MEDIUM |
| 員工 email 空白或重複 | 通知寄不出 | MEDIUM |
| 部門 `parent_id` 指向不存在的部門 | 組織樹斷裂 | MEDIUM |

報表直接對應到「哪些流程定義會因此無法執行」，讓導入期的問題在**上線前**就浮出來，而不是使用者送單後才卡住。

> 這一節建議做成獨立可重跑的檢查，不只在同步後跑 —— 平台手動維護（`MANUAL` connection）的租戶同樣需要。

## 10. 資料表清單

依 EIG §29 與 WDC §29，但**刪掉 MVP 用不到的**（YAGNI）：

### 10.1 本案要建的

```
integration_connection          連線定義（type / config / credential_ref / enabled）
integration_credential_ref      憑證參照，指向 Secret Manager，不存明文
integration_source              connection × dataset，含 query_definition 與 mapping_definition
integration_raw_record          Raw Layer，保留原始列供比對與重跑
integration_sync_run            同步批次與完整計數（§11）
integration_sync_issue          單筆層級的問題明細（AMBIGUOUS / VALIDATION_FAILED / SKIPPED_BY_OWNERSHIP）
approval_delegation             代理人（§4.3）
```

### 10.2 刻意不建（MVP）

| 表 | 不建的理由 |
|---|---|
| `integration_dataset` | MVP 只有 `employee` 與 `department` 兩個 dataset，寫死在程式碼即可。等第三個 dataset 出現再抽表 |
| `integration_schema` / `_version` | Canonical schema 由 `schemas/` 下的 JSON Schema 管，與既有做法一致，不進 DB |
| `integration_connection_version` | Connection 版本化等有客戶真的換 ERP 版本再說 |
| `integration_mapping`（獨立表） | 併入 `integration_source.mapping_definition` jsonb |
| `integration_dataset` 的 INLINE/REFERENCE/STREAM | 組織資料量級是千～萬筆，全部 INLINE。STREAM 是交易資料的問題 |

### 10.3 `integration_sync_run` 的計數契約

EIG §14 明確要求同步不能只回「success」。本案採用其計數，**每一個都要有**：

```
source_count      來源宣稱的總筆數（若來源能回報）
received_count    實際讀到幾筆
parsed_count      成功解析幾筆
mapped_count      成功映射到 canonical schema 幾筆
validated_count   通過驗證幾筆
inserted_count / updated_count / unchanged_count
skipped_by_ownership_count    因 platform_managed_fields 跳過的欄位數
rejected_count    被驗證擋下幾筆
missing_in_source_count       來源消失幾筆
status            SUCCESS | PARTIAL_SUCCESS | ABORTED_INCOMPLETE | FAILED
```

**日誌不得寫入**：API password / token、身分證號、完整 email 清單（WDC §30）。只存 `input_hash` / `output_hash` 供比對。

## 11. 執行中流程遇到人事異動

現況 `0001_tenant_identity.sql` 的註解寫得很清楚：

> `manager_id` — 直屬主管。Approver Resolver 的 `manager_of` 型別依此解析，**執行時即時查詢不快照**

同步會讓人事異動變頻繁，這個「不快照」的設計要補上邊界：

| 情境 | 處理 |
|---|---|
| 節點**尚未進入** | 即時解析。維持現況，同步後的新主管會生效 |
| Human Task **已建立、未完成** | **assignee 凍結**。已經寄出通知、對方可能正在看，不可因同步而換人 |
| 已凍結的 assignee 在同步後**離職 / 停用** | 進入「孤兒任務」清單，由管理員或原流程發起人轉派。**不自動改派**——自動改派等於平台替客戶做了人事決定 |
| 流程**已結束** | 不受影響。稽核紀錄保留當時的人 |

## 12. API 與 UI

### 12.1 REST API（Rust / Axum，與既有 API 同層）

```
組織
GET    /api/org/departments            部門樹
POST   /api/org/departments            建立（MANUAL）
PATCH  /api/org/departments/{id}       編輯（自動寫入 platform_managed_fields）
GET    /api/org/employees              查詢 / 搜尋（給表單 Reference 元件用，WDC §19）
PATCH  /api/org/employees/{id}
POST   /api/org/employees/{id}/unlock-field   改回跟隨 ERP
GET    /api/org/health                 組織健康檢查報表（§9）

代理人
GET    /api/org/delegations
POST   /api/org/delegations

同步
GET    /api/integration/connections
POST   /api/integration/connections
POST   /api/integration/connections/{id}/test          測試連線（WDC §34）
POST   /api/integration/sources/{id}/preview           試跑不寫入，回傳映射後前 20 筆
POST   /api/integration/sources/{id}/sync              Sync Now
POST   /api/integration/sources/{id}/suggest-mapping   AI 欄位對應建議（§8）
GET    /api/integration/sync-runs                      同步歷史與計數
GET    /api/integration/sync-runs/{id}/issues          問題明細
```

**`preview` 是必備**，不是加分項。沒有試跑，管理員第一次同步就是盲賭。

### 12.2 UI

- **組織管理**：部門樹 + 員工清單。平台維護的欄位有明顯標記與解鎖按鈕
- **同步中心**：連線清單、上次同步時間與結果、Sync Now、同步歷史（含 §10.3 的完整計數）
- **組織健康檢查**：一張報表列出所有 HIGH / MEDIUM 問題，每項可直接跳到對應的員工 / 部門去修
- **Excel 匯入精靈**：上傳 → AI 建議欄位對應 → 人工確認 → preview → 正式匯入

## 13. 落地順序

| 階段 | 內容 | 產出的能力 |
|---|---|---|
| **P0** | `app_user` / `department` 欄位擴充、`platform_managed_fields` 機制、`can_login` + nullable password、組織管理 UI、**組織健康檢查** | 客戶可以**手動**把組織建起來，且立刻知道哪些流程會卡。Demo / POC 可用 |
| **P1** | `FILE` connection：Excel / CSV 匯入 + AI 欄位對應 + preview + 完整性閘 + `sync_run` 計數 | 導入門檻降到最低。**這是台灣製造業 SME 最可能的第一條路徑** |
| **P2** | `REST` connection：Odoo adapter、排程同步（Temporal）、增量同步、待停用確認流程 | 真正的自動同步。`approval_delegation` 一併補上 |
| **P3** | `SQL` connection：唯讀直連 + 具名查詢定義；webhook 觸發 | 覆蓋沒有 API 的老 ERP |

P1 排在 P2 前面的理由：Excel 匯入不需要客戶 IT 配合、不需要開防火牆、不需要申請 API 帳號。**能不能拿到資料**在 SME 是比**同步得多即時**更前面的問題。

## 14. 安全檢查項

- [ ] 憑證一律 `credential_ref` 指向 Secret Manager，**不進 `integration_connection.config`**（WDC §8）
- [ ] `SQL` connection 只執行預先定義的具名查詢，參數化綁定，**不接受使用者輸入 SQL**（WDC §4）
- [ ] 同步寫入走 `TenantTx`，受 RLS 約束，不得用 superuser 連線
- [ ] 送 AI 做欄位對應的樣本必須遮蔽 PII
- [ ] `integration_execution_log` 不得寫入 token / 密碼 / 完整 PII（WDC §30）
- [ ] `password_hash` 轉 nullable 後，登入流程顯式檢查 `can_login`，需有測試覆蓋
- [ ] 上傳檔案：型別白名單、大小上限、病毒掃描、暫存檔到期刪除
- [ ] `REST` connection 的 URL 需防 SSRF（禁內網網段，除非明確允許）
